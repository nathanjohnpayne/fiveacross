One platform, three identities, every surface labeled. Five Across (fiveacross.app, general register, minimal camp, share mark ✳️) is the platform; Gay Cruise Bingo (gaycruisebingo.com, cruise register, full camp, 🚢) and Vacay Bingo (vacaybingo.com, trip register, moderate camp, 🧳) are Editions of it. Every frame opens with a brand chip naming the identity it renders and carries a stable anchor of the form #fx-<surface>-<brand>; pre-rename ids from earlier revisions of this doc still resolve as aliases. Wording follows the signed-off Edition lexicon (#608)—registers, wordmarks, share marks and per-surface tables are binding. Five Across ships its own theme trio—✨ Marquee / 🎊 Confetti Hour / 🌙 Afterglow (#617), Marquee the Edition default—and fiveacross-slate is a proposed alternative.

Canvas: iPhone 15 Pro—393×852 pt (19.5:9), Safari baseline, with Dynamic Island and home indicator. Installed-PWA frames run standalone (no browser chrome); the install-nudge frame shows Safari’s bottom bar, since that’s the only moment players see it. Every frame is painted with the actual theme tokens from src/theme/themes.css (fiveacross-slate alone uses a palette proposed in the specs; the tutorial themes and the Bodega day themes all ship). Marked squares use the app’s real linear-gradient(--primary, --secondary) fill with --on-gradient text. The header always shows today’s port and theme on two lines; the board area retints to the viewed Day.

Authoring rule, learned the hard way. When a caption cites a shipped component, the frame's copy must be lifted from that component in the same edit—never add the citation on its own. A frame carrying no reference is read skeptically; a frame captioned TomorrowsCardInvite.tsx is read as settled and gets implemented. So a half-applied citation does not half-fix the frame, it converts a guess a reviewer would have questioned into one they will not. Three findings on #867 were exactly this, all introduced in rounds that were adding rigor. Two corollaries: cite the derivation rule alongside any quoted string (ceremonialDayIndexSet outlives the wording “except the wrap-up”, and the rule stays true when the copy is rewritten), and re-check quoted strings against source immediately before pushing—main moves fast enough that a verbatim quote can go stale inside one branch. A frame that depends on seeded or provisioned state says so on the frame, never in the caption alone.

The list below is what is known, not a closed set—each round of review against the code has turned up another, so treat it as open and re-check before scheduling this. (1) Sign-in is not wildcard-capable. A hostname must be registered individually in Firebase Auth's authorized domains and as https://<host>/__/auth/handler on the Google OAuth web client—neither accepts a pattern—so a freshly claimed slug lands on an origin where isSignInReachableOnHost is false and the app renders auth-unconfigured. Writing routing documents in a transaction does not change that; only ADR 0010's centralised auth origin makes it wildcard-safe (today's handoff covers exactly one host). Until then, provisioning includes exact-host registration plus a redeploy, which is developer work. (2) There is no admission boundary. Current rules give path scoping, not membership isolation, so any signed-in account reaching the hostname can enter. A wizard whose final step hands out a QR would create ostensibly group-scoped Events that are not scoped at all. (3) Share and install identity are baked per bundle, not per host. index.html stamps og:title / og:image from the build-time Edition and the PWA manifest takes brand.appName the same way, so until the per-host edge work covers them a new Event's link unfurls with another Event's name and artwork, and a cross-Edition install inherits the wrong app name. Crawlers run no JavaScript, so runtime repair cannot reach the unfurl—this one outlives fixing auth and admission. (4) Nothing serves a new hostname yet. Today's Five Across deployment is a set of exact Firebase Hosting custom domains, one Event each; the shared multi-Event wildcard-router build is still future work (#545, see docs/app/deploy-targets.md). Writing the two Firestore hostname documents maps an address to an Event—it does not make that address route, terminate TLS, or serve the bundle. Pool is a three-way choice, not two: main, easy, and closing, and the closing pool belongs to a final Day. finaleTimes returns null when no Day carries that pool, so a wizard offering only easy/exploratory leaves the farewell Day either undealable or quietly assigned a main pool—no finale beats, no podium, no Most-Loved, and no standings freeze either. That last one runs through a second mechanism worth keeping straight: the finale beats are pool-anchored (finaleTimes finds the first closing Day), while the freeze is Scoring-Policy-anchored (standingsFreezeAtFor). The draft deliberately authors no scoring yet (ADR 0011's fields are deferred to #531), so a wizard-built Event resolves its policy through the legacy pool fallback—which is precisely why the closing-pool assignment still carries both today, and why it stops being sufficient the moment the draft learns to state scoring. Hence the explicit Days & pools assignment and the seeded closing Prompts. And a Day is not a calendar date: Bodega's Sunday is two Days—a competitive main-pool Day at 06:00 and a closing wrap-up at 11:00—so collapsing the last date into one closing Day would delete Sunday's competitive card and freeze standings at the wrong boundary. The rows are per Day, and two may share a date. And tutorial is its own required field, not a consequence of pool—the "counts ✓ / warm-up" chip. Bodega's easy-pool Friday is tutorial: false and only the closing wrap-up is true, so a provisioner that inferred tutorial status from easy/closing membership would wrongly exclude Friday's wins from Event-wide First-to-BINGO. Pool decides what a Day deals; tutorial decides whether its wins count. spicy is independent of pool, not a synonym for exploratory: it tracks sexual explicitness specifically, and the Event's 18+ posture is derived server-side from whether any active Prompt carries it. A custom Prompt added here therefore needs its own spicy control—defaulted off, as addItem does—because an organizer who picked "All ages" in Basics and then adds an explicit inside joke must still raise the public acknowledgement. But the control is main-pool only, and the row says so: adminAddItem forces spicy: false outside the main pool and the posture derivation ignores non-main pools, so a spicy toggle offered on an easy or closing Prompt would let an explicit square reach a card with no 18+ gate raised—the toggle would look honoured and be silently dropped. And the minimum is per pool, not per Event: a closing Day snapshots only its closing pool, and dealBoard rejects an unstratified pool below MIN_POOL (24), so a pack with 62 total but 4 closing yields a farewell card that cannot deal while every total-based check reports success. Each assigned pool is counted and gated on its own. Three more facts the built contract has since pinned down (specs/event-setup-wizard.md). Closing is exclusive to the finale: every finale consumer—client and server—resolves the farewell as the first closing Day, so a closing Day mid-schedule would freeze standings and post the podium days before the intended finale while a final-Day-only check still passed; the gate reports both Days by name. Prompt text is bounded 1–80 characters as persisted: firestore.rules applies text.size() to the stored value and the count gates never read text, so a pack padded with blank or over-long Prompts satisfies the 24-minimum and then fails at provisioning—text gets its own launch gate rather than riding the count. And the pack is a worked example, not a shipped asset: content ownership is open (#786 Decision 2), so every starterPackId in the occasion matrix is null until a pack is authored—the Coastal weekend pack here is a reference for shape and counts, not a promise that those 86 squares exist.

The wizard's reviewed default is 06:00, not the old 08:00 default, which is exactly the kind of cadence an Event would otherwise launch wrong while the intro promises every default is changeable before launch. The 12h offset assumes a closing Day on its own calendar date; the fallback is what keeps a same-day wrap-up like this one from silently losing the beat. The frame prints what the scheduler actually computes, because a wireframe that quietly displayed a plausible-but-wrong time would hide a future regression from whoever implements this. Step 5 · Launch—checklist, then the QR is the confettiEvery row is a verified gate (mirroring the POC launch-gate discipline) with an Edit escape hatch; Create is a trusted server-side provisioner, not a client transaction, and that is a rules fact rather than a preference: firestore.rules gates Event creation on isAdmin(eventId), which reads the Event document that does not exist yet, so a client cannot bootstrap its own first Admin grant; and hostnames/{host} denies create/update to every client including admins, because routing is global state no per-Event admin has authority over. A callable with platform-level authorization claims the canonical slug—and the Edition alternate, when the Edition owns one—atomically via the Admin SDK, seeds the Event, grants the creator Admin, and returns the invite QR + link + share. The checklist itself is now a real vocabulary, not a drawing: validateEventDraft (src/data/draftValidation.ts) returns issues rather than a boolean precisely so this screen can render each failure as its own row with its own Edit link—one organizer mistake, one row—and the settings the wizard draws no dedicated step control for—the photo-proof source, EXIF strip and vision gate behind this row's Edit, plus the spicy ratio and report-hide threshold—arrive committed from the occasion defaults, because the draft's settings block is Required: every value stated, nothing left to a call-site fallback. The creator is granted Admin on the new Event—that grant, not the Host field, is what authorizes every setup write; hostedBy stays player-facing display metadata (CONTEXT: “a Host is a social identity, not a permission”). The organizer lands in the familiar Admin hub afterward—setup ends where operations begin. Two rows are deliberately not what they were: there is no photo-enabled boolean in the Event contract—capture is always available, and the real knobs are photoProofSource, stripPhotoExif and visionGate—so the row names those rather than inviting a parallel setting no proof consumer reads. And the last-call row is the point even though it now passes (#784 gave `finaleTimes` a same-date fallback and a non-empty-window guard): it exists so "valid" is backed by an actual computed instant, not a rubber stamp—a schedule shape where the fallback still failed to land before the close would show up here, not slip through as an Event whose last call can never fire. Two rows are honesty, not decoration. The first-unlock row is a hard gate, not a nicety: every Prompt seeded at creation gets a createdAt, and activeSnapshotIds excludes Prompts created after a Day's cutoff—so launching after Friday's 06:00 has already passed permanently stamps an empty arrival snapshot. (The Bodega seed dodges exactly this with an unlockAt: 0 sentinel and a pre-stamped snapshot—but that pairing is Admin-SDK seed territory: no client can write the snapshot, so from the wizard the sentinel is refused under its own issue code as a provisioner capability request, not offered as an organizer choice. firstUnlockIssues says exactly that.) Launch from this flow therefore requires a first unlock still in the future, full stop. The 18+ row is derived server-side from the pool's spicy Prompts and is authoritative over the Step 2 audience choice, so it can contradict what the organizer picked—shown here rather than silently overriding. And the dashed warning carries the two real blockers, because a QR is worth nothing if either holds. Sign-in is per-exact-host, not wildcard: a hostname must be registered in Firebase Auth's authorized domains and as /__/auth/handler on the Google OAuth client, so a freshly claimed slug fails isSignInReachableOnHost and the app renders auth-unconfigured—an Event nobody can sign in to. Claiming the routing documents in a transaction does not help; ADR 0010's centralised origin is what makes this wildcard-safe, and today's handoff covers exactly one host. And there is no admission boundary: current rules give path scoping, not membership isolation, so any signed-in account that reaches the hostname is in whether invited or not. This flow stays blocked until both land—the frame draws the dependencies instead of pretending them away.
