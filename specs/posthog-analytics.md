# Spec: client-side PostHog product analytics (#96)

Adds PostHog product analytics to the React app **alongside GA4** (both fire; PostHog does not replace GA4). Set up initially via `@posthog/wizard` on branch `posthog-setup`; the wizard's server-side (`posthog-node`) output was reverted in favour of this client integration, because 2 of its 3 instrumented surfaces (the `share` Cloud Function and the Cloud Run OG renderer) are removed by ADR 0005 / #39, and the PRD's analytics goal is client events.

## Behaviour

- **Single dispatch path.** `track(name, params)` in `src/analytics.ts` is the only analytics call site in the app; it now fires each event to **both** GA4 (`logEvent`) and PostHog (`phCapture`). Each sink is independently guarded and never throws, so one failing or being unconfigured never blocks the other. The event catalog is `GA4_EVENTS`—the 12 PRD events plus the operational `login_failed` added later by #163; every catalogued event dispatches to both sinks. `login_failed` carries only `{ method, code }`, where `code` is an allowlisted Firebase Auth code or `auth/unknown`; raw provider messages never enter analytics, so PostHog's privacy posture below is unchanged.
- **Init.** `initPostHog()` (in `src/posthog.ts`) runs once from `main.tsx`. It is a **no-op without `VITE_POSTHOG_KEY`**, mirroring the GA4 guard—dev/test/CI without env vars stay silent. Ingestion walks a priority-ordered failover chain (#344, reordered by #612): the Brand-level proxy `https://d.fiveacross.app` (primary—ingestion is Brand-level, not Edition-selected, #578/#579, on the canonical domain of the #599 pivot), then the personal-domain proxy `https://d.nathanpayne.com` (same PostHog-managed proxy infrastructure, on a registered domain the #342 shipboard SNI filter does not block), then the first-party proxy `https://d.gaycruisebingo.com`, then direct PostHog Cloud at `https://us.i.posthog.com` (last resort, never probed). Boot probes all three proxies concurrently with short `no-cors` / `no-store` transport checks (one probe budget total) and initializes against the first host in chain order that answered, so events are delivered instead of silently queueing forever—a dead or unresolvable chain head costs only its own failed probe. The ordering lives in the code chain (`POSTHOG_INGEST_HOSTS`), never in `VITE_POSTHOG_HOST`, which stays UNSET in every build env (#612; `.env.example` ships it blank): a non-blank `VITE_POSTHOG_HOST` outside the proxy trio—including an explicit `https://us.i.posthog.com`—is the diagnostic bypass and skips the probes, silently disabling the failover (the #540/#578 launch-handoff trap); an override that merely restates one of the three proxies does not bypass. This app is US-region-bound: `ui_host` remains `https://us.posthog.com`, so toolbar and “view in PostHog” links target the US app rather than the proxy. The proxy forwards ingestion plus PostHog's `/static/*` and `/array/*` asset/config routes. The `phc_` project key is client-safe/public.
- **Identify.** On sign-in the User is identified by **uid only** (no PII person properties); identity is reset on sign-out. Wired from `main.tsx`/`ThemedApp` (not `AuthContext`) to keep analytics out of the protected `src/auth/**` path. Production init waits for Firebase's first resolved auth state before starting the SDK (see § Dimensions "Guaranteed ordering" below). A returning User whose persisted PostHog `$user_id` matches Firebase is identified in place, preserving the existing session/replay; an anonymous visitor is stitched normally; only a signed-out state or a DIFFERENT persisted User resets first. Later identify and reset calls that arrive while the proxy probe is pending are queued IN ORDER and replayed FIFO once the SDK is live (#613, Phase 4b P1): a sign-out during that window still lands after the identify it followed, so the identity is never resurrected past sign-out, and an account switch replays as reset-then-identify so the new uid is never merged onto the prior account's persisted identity. Every cross-user/sign-out transition closes the send gate until its reset (and any following identify) succeeds; failure drops later telemetry and leaves the Firebase state retryable rather than merging Users or continuing under the old one. A durable Board-transition capture is not acknowledged during the narrow reset→identify handshake or a failed identity transition: it stays in the listener-owned outbox and that subscription is notified once the identity is stable again, so `before_send` cannot silently discard the immutable transition.
- **Durable retry (#764, Event-scoped by #807).** `subscribeDirectMarkAnalytics` (`src/data/directMarkAnalytics.ts`) keeps its delivered-id set, cursor, and per-transition outbox under `(Event, uid)` storage keys. The listener and every retry closure retain that captured scope: an Event-A row can finish delivery for A, but a retired A callback or timer can neither dispatch as B nor advance B's acknowledgements. The outbox wakes—via the same `flushOutbox` entrypoint—on every one of: a new Firestore snapshot, `analyticsInitializationSettled` resolving, PostHog first becoming ready, and a bounded exponential-backoff timer (5s initial delay, doubling, capped at 2 minutes) that keeps retrying on its own if a sink transiently throws after both one-shot readiness signals have already fired and no later Board transition arrives to wake the listener. The timer resets to its initial delay on a full drain and is cancelled in the subscription's teardown closure, so it never spins once the outbox empties or outlives the subscription. (Tests: `src/data/directMarkAnalytics.test.ts`—Event-A/Event-B paths and storage keys remain separate; "drains a stranded outbox entry on a timed retry after both one-shot readiness signals have already fired (#764)"; "cancels the retry timer on unsubscribe so a stranded entry is never retried after teardown (#764)".)
- **Pageviews.** Autocaptured by posthog-js via `capture_pageview: 'history_change'` (initial load + SPA route changes) plus `capture_pageleave: true`. URLs are reduced to **path-only** by the `before_send` hook `sanitizeUrls` (query string and hash stripped), so URL-embedded credentials never reach analytics—preserving the app's original path-only pageview stance even though content is otherwise unmasked.
- **Local dev.** `initPostHog()` is skipped on localhost / loopback / `*.local` hosts (`isLocalDevHost`, #194) and for the uptime synthetic (#142), so dev sessions and Vite HMR errors never pollute production analytics or replays.

## Capture posture (noindex, 18+, single-viewer, UX debugging)

Full capture is **enabled** by owner decision (#193 reverses the original #96 lockdown). The owner is the sole PostHog viewer and uses session replay to find UX issues, so user content is recorded **unmasked**:

- `autocapture: true`
- `disable_session_recording: false`, with `session_recording.maskAllInputs: false` (PostHog masks inputs by default, so this opts out explicitly)
- `capture_pageview: 'history_change'` and `capture_pageleave: true`
- `person_profiles: 'identified_only'`

The one exception is **URL hygiene**: `before_send: sanitizeUrls` strips query/hash from the URL-bearing fields it can reach—event `properties`, the `$set` / `$set_once` person-property bags, and the rrweb Meta (type 4) / Custom-event (type 5) hrefs inside `$snapshot` replay data—so query-string secrets (e.g. Firebase auth-handler OAuth params or invite codes) do not surface in those URLs, on events or in the session-replay timeline. This scrub is scoped to URLs only; the rest of the replay payload (DOM content, typed inputs) is recorded unmasked per the owner decision above. These options are exported as `POSTHOG_INIT_OPTIONS` so the policy is unit-tested. `ConsentNotice.tsx` discloses to users that analytics—including session replay—is used; its dismissal key is versioned so the updated disclosure re-shows once to prior visitors. It is a notice, not a gate (GA4 and PostHog both fire without an opt-in), consistent with the existing analytics model.

## Dimensions: brand, edition, Event, Slug, Day (#556, part of #532)

One PostHog project carries every Edition and every Event across both Firebase projects—cross-Event comparison is the question the platform exists to answer, so splitting by Edition or Event would make it unanswerable (ADR 0008). GA4 is per Firebase project instead: one GA4 property each (gaycruisebingo and fiveacross), each with one web stream, so a cross-project question is a PostHog question, never a GA4 one. Five dimensions identify WHICH Edition/Event an event belongs to, and they are **registered once**, not threaded through every `track()` call site, mirroring `track()`'s own "one dispatch path" posture:

- `brand_id`—Five Across's single Brand identity (CONTEXT.md § Brand). A constant (`BRAND_ID` in `src/analytics.ts`); there is exactly one value.
- `edition_id`—the resolved Edition (`activeEdition()`, `src/editions.ts`).
- `event_id`—the resolved Event id (`EVENT_ID` / `Resolution.eventId`).
- `event_slug`—the Event's Slug (CONTEXT.md § Slug) when a `hostnames/{host}` document was read, else the Event id (a single-Event build never reads that document, so it has no separate Slug to report).
- `day_index`—"today's Day" (`todaysDayIndex`, `src/theme/autoTheme.ts`), the same Day-schedule resolution `todaysDayTheme` already uses for the Auto theme.

`page_location` is NOT one of the five registered dimensions, and deliberately does not live in `ga4Dims` (Phase 4b P1 on PR #584, superseding an earlier round's static-default attempt): this app is a `BrowserRouter` SPA, so a value frozen at whatever pathname was current when dimensions were first registered would leave every LATER tracked event attributed to the boot route. `track()`'s `currentPageLocation()` (`src/analytics.ts`) computes it fresh, from the CURRENT `window.location.pathname`, on every single call instead—and it is ALWAYS explicit, never omitted (#613, Phase 4b P1): when no canonical host is resolved (a single-Event build, or the bootstrap failure branch) it falls back to the page's own origin + pathname rather than sending the event without a `page_location`, because GA4 would then derive one from the browser's FULL current URL—query string and hash included—reintroducing exactly the query-string leakage the path-only policy exists to prevent. PostHog's `$current_url` was never subject to this staleness in the first place—it is fixed at the `sanitizeUrls`/`before_send` layer (posthog.ts), which runs per capture.

**Guaranteed ordering, independent of SDK internals (Phase 4b P1 on PR #584).** `initPostHog()` is called from `bootstrapEventResolution().then()`/`.catch()` in `main.tsx`—never at module scope—so PostHog cannot start until AFTER dimension registration has run. Production calls it with `waitForAuth: true`: `ThemedApp` supplies Firebase's first resolved state through `phSetAuthState`, while fallback screens that deliberately do not mount auth supply signed-out explicitly. The SDK therefore does not initialize until both Event resolution and authoritative auth resolution have completed. As defense in depth, `sanitizeUrls`/`before_send` applies the already-registered dimensions directly to every outgoing event's `properties`—the single point every captured event, autocaptured or explicit, passes through right before it leaves the SDK—so the guarantee does not depend on exactly when `posthog.register()` applied. The five `CONTROLLED_DIMENSION_KEYS` always come from CURRENT `registeredDims`; an unavailable one (typically `day_index`) is DELETED rather than inherited (#611), stripping stale super-properties that PostHog persisted from a prior Event. The same hook fails closed while the required auth baseline is not established, so even a reset/identify exception cannot let the SDK's already-scheduled first pageview escape under a stale User.

After `posthog.init()` restores SDK persistence, the auth baseline runs synchronously. Signed out resets; a different persisted `$user_id` resets then identifies; an anonymous or matching User identifies without reset, preserving valid returning-user session/replay continuity. The gate opens narrowly before `identify()` so PostHog's synchronous `$identify`/`$anon_distinct_id` handshake is admitted; it closes again if identify throws. Captures persisted by a PRIOR recovery load replay only AFTER this fresh baseline: identity operations deliberately do not persist, so the restored PostHog identity is not authoritative for a surviving capture (a signed-out reset may have died with the old page). Current-load operations still use ONE `pendingOps` queue and replay in ARRIVAL ORDER (#611 → #613, Phase 4b rounds 1–3): identify(A), capture, reset, identify(B) keeps the capture under A; a uid change with no sign-out inserts the implied reset; identical identifies coalesce. A failed reset/identify stops replay with the gate closed, so later captures cannot escape under the wrong User. Posthog-js schedules its automatic first `$pageview` one macrotask after init (`setTimeout(…, 1)` in the loaded step; verified in 1.409.5 and re-verified in the installed 1.434.0 on #632), while the auth baseline and queue replay are synchronous, so the pageview cannot outrun them even on the direct-host bypass.

`registerAnalyticsDimensions` (`src/analytics.ts`) installs the first four once `bootstrapEventResolution` resolves a `kind: 'event'` Resolution—called from `main.tsx`, skipped for the uptime synthetic (#142). `registerDayIndexDimension` installs `day_index` separately, from a `useEffect` in `main.tsx`'s `ThemedApp` keyed on the resolved index, because it is not known at startup and changes mid-session as a Day unlocks. Both call GA4's `setDefaultEventParameters` (merged into every subsequent `logEvent`, automatic events included) and PostHog's `phRegister` (`posthog.register`, merged into every subsequent `capture`)—the GA4/PostHog equivalents of `track()`'s own dispatch, applied once instead of per event. `phRegister` queues-and-merges before PostHog's async init settles, mirroring `phIdentify`'s own replay, so a dimension registered during the ~1.5 s ingest-host probe is never dropped, and it re-applies its full merged set after `posthog.reset()` (sign-out) so a second Player on the same tab still gets dimensioned captures (Codex P2, #556). GA4's own default-params slot does not merge across pre-init calls (`@firebase/analytics` keeps exactly one pending value), so `src/analytics.ts` keeps its own merged copy and resends the full set on every registration (Codex P2, #556).

**Canonical hostname—the analytics dimension, NOT the share origin (#556 as amended by #607).** Analytics report the Event's resolved canonical hostname (CONTEXT.md § Canonical hostname), never a raw `window.location` that could reflect a validated Alias before its edge redirect—one canonical host per Event, so cross-host traffic aggregates. `bootstrapEventResolution` installs it via `applyResolvedCanonicalHost` (`src/canonicalHost.ts`, deliberately its own dependency-free module so the dozens of tests that `vi.mock('../firebase', ...)` with a narrow stand-in never need to change); consumers read `resolvedCanonicalHost()` and supply their own `window.location` fallback for a build where resolution has not run, or a single-Event build with no separate Alias concept. Share links are the deliberate exception (#607, following the amended multi-domain policy in #599): every serving host stays live and brands dynamically, so the four Web Share API call sites (`Leaderboard.tsx`, `FarewellPodium.tsx`, `Celebration.tsx`, and the post-freeze `ArchivedLeaderboard.tsx`, #1152) source their share `url` from `shareOrigin()` (`src/canonicalHost.ts`)—the ENTRY-POINT origin the sharer is standing on—never the canonical host, or the shared link would unfurl and land recipients under another Edition's brand. (`canonicalOrigin()`, the origin-rewrite primitive those call sites consumed pre-#607, is removed; `src/canonicalHost.test.ts` pins the removal.) Alias-collapse is unaffected: a true redirect Alias never serves the app, so no share can originate from one. `track()`'s `currentPageLocation()` (`src/analytics.ts`, see below) still canonicalizes GA4's `page_location`—the analytics side of the split—computed fresh per event rather than as a static default. PostHog's equivalent is fixed at the `sanitizeUrls`/`before_send` layer instead—`canonicalizeOrigin` (`src/posthog.ts`) swaps the origin of `$current_url` / `$pathname` / `$initial_current_url` / `$session_entry_url` / `$session_entry_pathname` (#632) / the `$snapshot` replay hrefs to the resolved canonical host, but deliberately never touches `$referrer` / `$initial_referrer` / `$session_entry_referrer`, which are frequently a genuinely external origin (a search engine, a shared link elsewhere) that must not be overwritten with our own hostname.

**GA4's first `page_view`, dimensioned (#611, retro Phase 4b P1 on PR #584—gap closed).** PR #584 round 2 rebutted this as unfixable: GA4's automatic `page_view` fires deterministically, inside `@firebase/analytics`'s own `_initializeAnalytics`, BEFORE any pending `setDefaultEventParameters` could apply—confirmed via the SDK's own source, not a race any app-level ordering fix could win. The retro Phase-4b review re-flagged it with a path that sidesteps the ordering argument entirely instead of trying to win it: `src/firebase.ts` now initializes with `send_page_view: false` (`initializeAnalytics(app, { config: { send_page_view: false } })`, not `getAnalytics`), which removes the automatic event completely, and `emitInitialPageView()` (`src/analytics.ts`) fires ONE explicit `page_view` once BOTH `analyticsReady` (the same file) AND Event resolution have settled—the identical "wait for resolution, then start" pattern `startPostHogAfterResolution` already uses for PostHog. "ONE" is enforced by a module-level once-guard, consumed on first entry (#613, Phase 4b round-2 P2): `main.tsx`'s bootstrap `.catch()` also receives an exception thrown by the `.then()` success callback AFTER it already emitted, so without idempotence that path double-logged the `page_view`. By the time both have settled, dimension registration has already run too—and because Event resolution and the `isSupported()` chain settle independently, `emitInitialPageView()` additionally RE-APPLIES the merged `ga4Dims` cache via `setDefaultEventParameters` after readiness and before logging (#613, Phase 4b P1), so the "this `page_view` is dimensioned" guarantee is locally provable rather than resting on `@firebase/analytics`'s internal pre-init default-params slot; once gtag is live the resend is a harmless merge no-op. The event carries a fresh, canonicalized `page_location` via the same `currentPageLocation()` `track()` uses—always explicit, with the scrubbed origin + pathname fallback when no canonical host resolved (#613, see § Dimensions above), plus, as the one deliberate exception to path-only, the landing URL's allowlisted `utm_*` set (#632, § Campaign attribution below). This app still does not otherwise rely on GA4 for pageview TRACKING across SPA navigations—PostHog's `capture_pageview: 'history_change'` autocapture (see § Pageviews above) remains this app's actual mechanism for that; `emitInitialPageView()` only replaces the one automatic load-time event GA4 itself used to fire unprompted.

**Payload hygiene.** No invitation secrets, Prompt text, or private media are added by this instrumentation—the five dimensions are identifiers only. Sensitive URL parameters are already excluded by `sanitizeUrls` (PostHog) and the path-only pageview stance (both sinks); registering dimensions does not touch either. The one query-string carve-out is the allowlisted `utm_*` set on GA4's initial `page_view` (§ Campaign attribution), which carries only the three keys the app's own emails set, and only when the set is exactly what those emails produce for the resolved Event, so no other parameter, free text or PII can ride along. PostHog's own parsed campaign properties pass the same gate in `sanitizeUrls` on every captured event (§ Campaign attribution), and the SDK makes no `/flags` feature-flag request at all (`advanced_disable_feature_flags: true`, #1297), so its persisted raw initial props never leave the browser that way. The raw landing URL still sits in the SDK's own cookie and localStorage and reaches heatmap and web-vitals payloads; that residual is accepted (§ Campaign attribution).

## Campaign attribution (#632)

Every app deep link an email carries is tagged, so an email-driven session is attributable in both sinks instead of landing as direct traffic. The taxonomy lives in `functions/src/emailCampaign.ts`: `utm_medium=email` always; `utm_source` is `daily-email` or `podium-email`; `utm_campaign` is `<eventId>-day-<index>` (the 0-based Day index, the same value as the `day_index` dimension) for the daily email and `<eventId>-podium` for the podium email. The unsubscribe and preferences links, and the RFC 8058 `List-Unsubscribe` header, are never tagged: they reach the `emailUnsubscribe` function, not the app, so analytics never loads on them (`specs/daily-engagement-email.md` item 6). The admin alert digest's queue link is operational mail to Admins, not a Player campaign, and stays untagged.

**PostHog parses the tags itself, before the scrub.** posthog-js (1.434) runs `update_campaign_params()` inside `capture()`: it parses `utm_*` off `document.URL`, registers them as bare `utm_source` / `utm_medium` / `utm_campaign` / `utm_content` / `utm_term` super-properties, and records `$initial_utm_*` (person, via `set_initial_person_info`) and `$session_entry_utm_*` properties, all before `before_send` runs. The path-only URL scrub reaches only the URL-bearing keys (`$current_url`, `$pathname`, `$initial_current_url`, `$referrer`, `$initial_referrer`, and the session-entry fields the SDK adds to every event: `$session_entry_url` and `$session_entry_pathname`, the session's landing URL and path, and `$session_entry_referrer`, the referrer captured at session start, which may be an external URL and so keeps its origin like `$referrer`), so it never sees these values; `sanitizeUrls` therefore applies the same `matchEmailCampaign()` gate (`src/emailCampaignMatch.ts`) GA4's `campaignQuery()` uses, per prefix and in `properties`, `$set` and `$set_once` alike. This Event's own email campaign keeps its three keys while the query it came from is stripped; any other set (free text, an email address, another Event, a mismatched pair, an out-of-range Day, or no registered `event_id`) loses every campaign key, and `utm_content` / `utm_term` are always dropped. The SDK's other campaign parameters (ad-click ids such as `gclid` / `fbclid` / `msclkid`, and `gad_source` / `mc_cid`) are dropped under every prefix too, along with the `$fbc` value the SDK derives from `fbclid`: the app runs no ad or third-party mail campaign, so none of them is ours. At the source, `mask_personal_data_properties: true` makes the SDK mask those click ids as it parses the landing URL, so nothing it derives before `before_send` (the `$fbc` cookie value, feature-flag person properties) carries the raw value either. Because the matched keys are registered, they ride on every later event of the session, so an SPA navigation away from `/feed?utm_...` does not lose them. **No `/flags` request (#1297).** `before_send` gates captured events only, and the SDK's `/flags` feature-flag request carries `persistence.get_initial_props()`, which holds the raw parsed values (`$initial_utm_*`) and `$initial_current_url`, the full landing URL, outside it. The SDK sends that request on four triggers: `identify()`, every signed-out `reset()`, the first remote-config load, and the refresh every 5 minutes. Decision (owner, 2026-09-25, recorded on #1297): `POSTHOG_INIT_OPTIONS` sets `advanced_disable_feature_flags: true`, so `reloadFeatureFlags()` returns early and no trigger sends a `/flags` request. The app calls no feature-flag, survey or `setPersonProperties` API, so nothing depends on flags. `advanced_disable_flags` and `advanced_disable_decide` are deliberately not used: they also skip remote config, which would stop the session-replay settings from loading. `save_campaign_params: false` alone would not have closed the path either: `$initial_person_info` is still stored while `save_referrer` is on, and the session props manager runs regardless. Accepted residual, as decided: the raw landing URL still sits in the SDK's own cookie and localStorage (`$initial_person_info`), and it appears in heatmap payloads (`$heatmap_data`, keyed by `href`) and web-vitals payloads (`$current_url`, `navigationURL`), which `sanitizeUrls` does not reach. Masking `utm_*` through `custom_personal_data_properties` was declined because it would also hide real email-campaign attribution. A real-browser network capture confirming no `/flags` request, and that session-replay remote config still loads, is a post-release operator check, not a unit test.

**The query must still be on the URL when PostHog starts.** PostHog init waits for Event resolution and the first auth state (§ Dimensions, "Guaranteed ordering"), so the landing query has to survive that window, and today it does. The auth handoff clears only its own fragment (`clearUrlFragmentAndConfirm` rewrites `pathname + search`), a signed-out Player's sign-in return path keeps `search` (`SignIn.tsx`), and the Firebase-auth-host redirect keeps `search` (`canonical-redirect.ts`). `/feed` is a real route, so the catch-all `<Navigate>` never fires on it. A future change that rewrites the landing URL before PostHog init would silently drop PostHog attribution for that visit.

**GA4 needs the tags carried explicitly.** GA4 attributes a session from the campaign parameters on its first hit's page location, and #613 made every `page_location` explicit and path-only, so a plain `page_view` would report every email click as direct traffic. `emitInitialPageView()` therefore appends `campaignQuery()` of the landing URL's query, read once at module load (before the Router mounts), to its `page_location`. `campaignQuery` keeps only `utm_source`, `utm_medium` and `utm_campaign`, in that order, and only when they are exactly what the email taxonomy above produces for the resolved Event: `utm_medium=email`, plus either `daily-email` with `<eventId>-day-<index>` or `podium-email` with `<eventId>-podium`, where `<eventId>` is the registered `event_id` dimension. A partial set, a mismatched source/suffix pair, another Event's id, identifier-shaped free text (`alice-smith-podium`), `utm_content` / `utm_term`, and every other key (invite codes, auth params) forward nothing, and with no resolved Event id nothing is forwarded, so a hand-crafted link cannot push free text or PII into GA4. This is the only exception to the path-only rule: `track()` events keep the path-only `page_location`. Residual: a `track()` event that reaches GA4 before the initial `page_view` would become the session's first hit without the tags. That window is narrow because the app mounts from the same bootstrap callback that emits the `page_view`, and the gap is accepted.

Startup coverage pins the production auth gate: SDK init waits for Firebase; signed out resets before the deferred first pageview; the same returning User does NOT reset; a different persisted User resets before identify; the `$identify` stitch is admitted; a recovery-reload capture replays only after fresh auth; and a failed mandatory reset drops the deferred pageview. FIFO coverage keeps captures in place across later identity transitions, inserts implied A→B resets, coalesces identical identities, proves ready-path plus queued reset failures close the gate without identifying or capturing under the wrong User, and proves a same-uid retry reopens the `$identify` handshake after an identify exception.
