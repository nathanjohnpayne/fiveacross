# Google sign-in & AuthContext deal-error hardening (w1-auth-google)

Feature: Google is the only login (PRD non-goal: no non-Google login), and the client-driven honor-system deal (ADR 0001) that runs on sign-in no longer fails silently. When `joinAndDeal` throws—chiefly the ADR-0003/0004 `dealBoard` guard that rejects a Board when the active non-free Prompt pool is below the 24 a card needs—the Player sees a Player-worded retry surface instead of the blank Board the old `App.tsx` `.catch(() => {})` left behind.

## Contract

- `src/auth/AuthContext.tsx` owns the post-sign-in deal. It runs `joinAndDeal` when the User becomes known, fires `track('join_event')` on success, and exposes `dealError: string | null`, `dealing: boolean`, and `retryDeal(): void`. Every production endpoint uses an immutable first-party auth handler: `gaycruisebingo.vercel.app`, `gaycruisebingo.com`, and `gaycruisebingo.firebaseapp.com` pin `authDomain` to their own hostname at Firebase initialization. The stable Vercel preview alias pins the same way so a preview deploy exercises the real same-origin handler rather than a cross-origin fallback—it is the one non-production hostname on that list, and per-deployment preview hosts are deliberately excluded (`docs/adr/0007-preview-auth-stable-vercel-alias.md`). `fiveacross.vercel.app` pins the same way and is production, but belongs to the **other** Firebase project: it is the Five Across backup host, and its `/__/auth/*` helper is proxied to `fiveacross.firebaseapp.com` by a host-conditional rewrite rather than to the Gay Cruise Bingo one, so nothing on this page's Gay Cruise Bingo flows changes (#585, `specs/vercel-auth-proxy.md`, `docs/app/preview-deploys.md`). A signed-out `gaycruisebingo.web.app` visitor is history-replaced once to the same-project `firebaseapp.com` app before authentication; that stable callback is already authorized and does not depend on the blocked custom domain. The handoff fires on every signed-out settle—first load and a mid-session sign-out alike—and every navigation path to it (the auth-settled branch, the bounded settle timer, and the sign-in tap fallback) routes through one deduplicated chokepoint, so at most one cross-origin `location.replace` fires per document and no auth transaction ever starts on `web.app`. The chokepoint computes its target from the live location at navigation time, so a mid-session sign-out lands on the route, query, and hash the Player was actually on—never a stale mount-time snapshot. While an app-owned redirect sign-in return is completing on the current origin (the same-origin pending marker was present at mount and `getRedirectResult` has not settled), the handoff is suppressed and the settle timer re-arms once the return settles, so the navigation can never interrupt a returning sign-in mid-completion. Mobile browser tabs and installed desktop PWAs use one top-level `signInWithRedirect` transaction at a same-origin auth handler: mobile tabs avoid popup tabs that lose Firebase's initial session state or close without returning to the app, while standalone desktop Chrome/Edge app windows avoid popup UI that can be blocked or hidden with no address bar. "Mobile" includes iPadOS Safari's desktop-UA masquerade, detected as `platform === 'MacIntel'` with `maxTouchPoints > 1`—an accepted tradeoff under which a future touch-enabled Mac would also get redirect sign-in (benign: redirect is fully supported on desktop), revisited when a real capability signal distinguishes the two. Installed mobile PWAs, desktop browser tabs, and the emulator keep `signInWithPopup`; installed mobile PWAs report both mobile UA and standalone mode, so they stay on the popup path because the standalone app window supplies the stable opener that the browser-tab failure lacks. The provider coalesces concurrent sign-in calls into one Firebase transaction, finishes a redirect result once after reload, and preserves the 18+ acknowledgement that gated the original tap. Redirect completion does not depend on the same-origin pending marker: `getRedirectResult` is consulted on every mount, and a non-null result—which only an actual redirect return can produce—restores the `login` event even when the marker was lost mid-redirect; the marker scopes failure reporting, so a redirect rejection emits `login_failed` only when the marker proves an app-owned redirect was in flight, and an ordinary mount can emit neither `login` nor `login_failed`. The checked 18+ attestation is a stricter case (Phase 4b P1 round 3 on #836, narrowing an earlier version of this contract): it additionally requires the session-storage marker to still be present AND to carry the SAME per-attempt token as the acknowledgement record — see below — so losing the marker costs the attestation specifically, on either completion signal, even though `login` itself still lands. A second, durable `localStorage` signal (`gcb.signin.redirectPending`, TTL-bounded like the acknowledgement record) closes the remaining gap: when Safari drops both the same-origin marker and whatever helper state `getRedirectResult` itself depends on, so `getRedirectResult` also resolves `null` on the return, the redirect-return effect still completes once `onAuthStateChanged` publishes the restored User while that durable record is live. One completion latch shared by both signals keeps `login` to exactly once and the attestation write to at most once, whichever signal wins or whether both fire; neither the session marker nor the durable records are consumed by unverified signal (b), so a reload can still reach a later Firebase-verified result with the same tab proof intact. They are cleared only on an actual terminal outcome for the transaction they track—a completed redirect, or a `getRedirectResult` rejection CONFIRMED by the same-origin marker as belonging to this app's own attempt—never merely because a mount read them. A `getRedirectResult` rejection without the marker is inconclusive rather than confirmed—Firebase's own helper throwing does not prove the session it may still be restoring failed to land—so it does not clear the durable record either; the record is left standing to expire on its own TTL, preserving the same reload-survival guarantee for the marker-loss case the record exists to cover in the first place. Both the pending record and the acknowledgement record additionally reject a corrupted or future-dated stored timestamp (a backward wall-clock adjustment, or a tampered value) as expired rather than treating it as freshly live. Durable state is ORIGIN-WIDE `localStorage`, so on its own it proves only that some same-origin tab started a redirect, not that a given `onAuthStateChanged` publication is that same attempt returning—Firebase Auth persistence is shared across every open tab on the origin, so an unrelated tab's own sign-in also publishes through this tab's listener. The durable-record signal only ever fires on the mount's own FIRST-EVER auth-state settle, closing the far more likely shape of the collision: a stale record surviving into an already-running, already-settled tab's later, unrelated event. That alone does not make the durable record trustworthy for WHICH account a publication belongs to, though: the session-storage marker being present proves only that this tab once STARTED a redirect, never that a later `onAuthStateChanged` publication was CAUSED by that specific attempt, so it cannot promote the durable-record signal into a per-attempt correlation either. The attestation write is therefore gated on a stricter, unconditional rule: only a completion whose acknowledgement record can be PROVEN to belong to THIS attempt may ever persist it. The pending and acknowledgement records are stored at redirect start under keys addressed by the same random per-attempt token carried by the session marker; if signal (b) later logs `login`, its dedup record uses that same token-addressed namespace. `verifiedByFirebase` (whether `getRedirectResult` itself resolved non-null for this Auth instance) proves WHO signed in, but the acknowledgement still belongs to a separate origin-wide record, so even a Firebase-verified completion additionally requires a live pending record and acknowledgement record under the session token before persisting. If the session-storage token was lost (#346) there is nothing to verify against either way, so the attestation is withheld regardless of which signal completed the return; only `login` still fires. The durable-record signal (signal b) never persists an attestation itself, marker present or not — it still fires `login` (low-stakes, matches the existing marker-less-rejection precedent) but clears nothing. Only a Firebase-verified completion (signal a) removes its exact token-addressed in-flight keys; a different, newer attempt lives under different keys, so no read-compare-remove window can delete it. A TTL-bounded per-token terminal marker suppresses any read-only legacy singleton left by an in-flight upgrade without reopening that shared-key deletion race. A durable, per-token `login`-logged marker additionally keeps the login event to exactly once across mounts, not merely within one: an unverified completion deliberately leaves the pending record and session marker standing so a later verified result can still consume them, and without a durable log a second reload within the TTL would otherwise find that same live record and log `login` again. Success fires `track('login', { method: 'google' })`; failures fire `track('login_failed', { method: 'google', code })` with an allowlisted Firebase code and no raw provider message. Google remains the only provider.
- Redirect ownership is captured synchronously from the tab-scoped marker during the provider's initial render, before effects or asynchronous Firebase continuations can run. Every later completion, rejection, cleanup, and attestation decision uses only that mount-owned snapshot; a same-tab redirect started while an older `getRedirectResult` is pending may replace the live marker, but the older continuation can neither adopt nor clear the newer attempt or use its acknowledgement to attest the older User.
- Each deal attempt is tied to the latest launch. A late result from a superseded attempt—the initial deal is still in flight when the Player signs out and a different Google account signs in—is dropped, not applied, so it can never clobber the current User's board or error surface; auth changes also clear any stale `dealError`/`dealing` so the incoming User never flashes the previous account's surface.
- A raw deal failure is translated to Player-facing copy: the pool-below-24 guard yields a "prompt pool is below the 24 a card needs" message; known transient network/timeout failures yield a connection-worded fallback, and permanent or unclassified Firestore/Firebase failures keep the same retry surface without becoming cached-card fallback eligible. The same classifier also sets a TYPED `dealErrorReason` (`'pool-shortfall' | 'connection' | 'permanent' | null`) in lockstep with the message, so the pool-recovery auto-retry can arm on the cause rather than the copy (see `specs/w1-deal-auto-retry.md`). Both retryable surfaces are recoverable via `retryDeal`, which re-invokes `joinAndDeal` for the current User with no full reload. The prior error stays visible while the retry is in flight (the surface is never unmounted mid-retry, so the Player is never dropped onto a blank Board); `dealError` is replaced only when the new attempt settles—cleared on success, updated on a fresh failure.
- `src/App.tsx` no longer swallows the deal error. Once a User is signed in, a non-null `dealError` renders `<DealError>` as the Card tab's route content—the failure is never hidden behind a blank Board—while the app shell, Nav, and every other route stay mounted. In particular the `/items` Prompts tab remains reachable, because adding Prompts there is exactly how the pool-below-24 shortage is recovered; a full-screen takeover would lock the admin/player out of the fix.
- `src/components/SignIn.tsx` exports `DealError`, the retry surface: it shows the message with `role="alert"` and a Retry button that calls `onRetry`, disabled and relabeled while `retrying`. It owns the MANUAL retry; the AUTOMATIC pool-recovery retry lives at the app shell (`src/components/PoolRecoveryWatcher.tsx`, mounted in `AuthProvider`), not on this panel, so it survives the navigation to `/items` that unmounts the panel—see `specs/w1-deal-auto-retry.md`.

## Acceptance criteria

- Given the active Prompt pool has fewer than 24 non-free Prompts, when a User signs in and `joinAndDeal` throws, then the Player sees a retry surface on the Card tab explaining the deal failed (not a blank Board).
- Given a deal failure is showing, when the Player uses the still-mounted Nav, then the other tabs—the `/items` Prompts tab in particular—remain reachable so Prompts can be added to recover, and returning to Card still shows the retry surface.
- Given a signed-in User whose deal failed, when the Player taps Retry, then `joinAndDeal` is re-invoked without a full reload, the retry surface stays mounted (disabled `Dealing…` button) while the retry is in flight, and the surface clears once a deal succeeds.
- Given a deal is in flight when the Player signs out and a different Google account signs in and deals, when the original deal settles late, then its result is ignored and the new account's board / error surface is untouched.
- Given a deal failure that is not the pool guard, when it is surfaced, then the Player sees the connection-worded fallback copy.
- Given a signed-out Player opens `gaycruisebingo.web.app`, when Firebase settles the empty session, then the app history-replaces to the same path on `gaycruisebingo.firebaseapp.com` before rendering SignIn, so the Player sees one acknowledgement and starts no auth transaction on `web.app`. If Firebase stalls while the browser remains online, the same handoff fires after a bounded 3-second persistence-settle window; an offline transition cancels the timer, and a restored current User suppresses it, preserving cached sessions.
- Given a signed-in `web.app` session, when the Player signs out mid-session, then the same handoff fires—the signed-out settle lands on the canonical origin rather than a `web.app` SignIn whose tap would hand off anyway—and a sign-in tap racing the started handoff neither navigates a second time nor starts an auth transaction on `web.app`.
- Given an app-owned redirect sign-in return is completing on the current origin, when the settle window elapses first, then the handoff is deferred rather than interrupting the return, and it re-arms once the redirect result settles signed-out.
- Given a Player completes a mobile redirect sign-in but the same-origin pending marker was lost mid-redirect, when the app mounts with the returned redirect result, then `track('login', { method: 'google' })` fires, but the checked 18+ acknowledgement is NOT persisted (Phase 4b P1 round 3 on #836 — the lost marker means the acknowledgement record cannot be proven to belong to this attempt rather than a different same-origin tab's), and the existing re-prompt collects it instead; an ordinary mount (null redirect result, no marker) emits neither `login` nor `login_failed`.
- Given a Player completes a redirect sign-in but `getRedirectResult` resolves `null` on this mount, when `onAuthStateChanged` next publishes the restored signed-in User while a durable pending record is still live and this is the mount's own first-ever auth-state settle, then `track('login', { method: 'google' })` fires exactly once, even if both completion signals fire for the same return; the checked 18+ acknowledgement is NOT persisted by this signal. If the same-origin marker survived, signal (b) leaves it intact across an unmount/reload so a later Firebase-verified result can still consume the marker, prove the matching token-addressed pending and acknowledgement records, persist the acknowledgement, and remove only that attempt's in-flight keys. If the marker was lost, no signal may persist an attestation without it, so the existing re-prompt collects it instead. An expired or absent pending record, or a later auth-state event on an already-settled mount—including an ordinary cached-session restore where no redirect was ever started—emits neither `login` nor an attestation. A second reload within the pending record's TTL, with the same account already restored, does not log `login` a second time; and a terminal completion never clears a different attempt's records because each attempt has distinct token-addressed keys.
- Given mount-owned attempt A is still awaiting `getRedirectResult` when the same tab starts attempt B, when A later verifies or rejects, then B's session marker and token-addressed pending/acknowledgement records remain intact; A uses only its initial-render snapshot, and therefore cannot persist an attestation from B's acknowledgement.
- Given token-addressed redirect records have expired, when a later redirect starts, then their exact stale keys are pruned without touching any still-live attempt or the shared legacy migration keys.
- Given a Player is on a mobile browser at a first-party auth origin, when they tap sign in, then exactly one top-level redirect starts and no popup window opens or closes.
- Given a Player is in an installed desktop PWA at a first-party auth origin, when they tap sign in, then exactly one top-level redirect starts and no popup window opens or closes.
- Given a Player is in an installed mobile PWA at a first-party auth origin, when they tap sign in, then popup sign-in is used and no redirect starts.
- Given sign-in is already pending, when another caller invokes sign-in, then it receives the existing operation and Firebase is called only once.
- Given sign-in succeeds, when the User authenticates, then `track('login', { method: 'google' })` has fired.
- Given the Google popup rejects, when the failure surfaces, then `track('login_failed', { method: 'google', code, … })` fires with the Firebase error code and the error is rethrown to the caller (the success `login` event and attestation do not run).
- Given a healthy pool, when the User signs in, then the Board is dealt and `track('join_event')` fires with no error surfaced.

## Test coverage

`src/auth/AuthContext.test.tsx` (Vitest RTL-jsdom) mounts the real `AuthProvider` with the Firebase boundary mocked and drives the auth callback directly:

- A pool-below-24 `joinAndDeal` rejection surfaces the "24 a card needs" message; tapping Retry re-invokes `joinAndDeal` (a second call), clears the error, and fires `track('join_event')`—covering the healthy-deal path on the retry.
- A non-guard rejection surfaces the connection-worded fallback.
- `signIn` fires `track('login', { method: 'google' })` on success; on a popup rejection it fires `track('login_failed', …)` with the Firebase code and rethrows (no `login`, no attestation); iOS mobile tabs and installed desktop PWAs use one redirect and no popup, installed iOS PWAs keep popup sign-in, repeated calls start one transaction; redirect completion persists the acknowledgement once — WITH the session-storage marker present and matching (Phase 4b P1 round 3 on #836) — while a marker-lost or cross-tab-mismatched return still fires `login` but withholds the attestation, an ordinary mount's null result emits nothing, and a marker-less rejection stays out of analytics; and `web.app` history-replaces to `firebaseapp.com` before authentication—on the empty-session settle, on a mid-session sign-out, and from a sign-in tap, all through one deduplicated handoff that a pending app-owned redirect return defers (with the settle timer re-arming on settlement).
- The durable `gcb.signin.redirectPending:<attempt-token>` record completes a redirect return when `getRedirectResult` resolves `null` too: `onAuthStateChanged` publishing the restored User while any such record is live and this is the mount's own first-ever auth-state settle fires `login` exactly once, even when both signals fire for the same return—but never persists the acknowledgement by itself. An expired record and an absent record each emit neither. The pending, acknowledgement, login-logged, and session-marker records all survive an unverified signal (b), including an unmount/reload before a later verified result; a `getRedirectResult` rejection clears them only when the same-origin marker confirms it belongs to this app's own attempt. A single attempt is also proven to never report both `login_failed` and `login`, in either firing order between the two completion signals. Cross-tab exposure is covered directly: a Firebase-verified completion only attests from live pending and acknowledgement keys addressed by its session token; an unverified completion never attests; a second mount does not re-log `login` for the same still-pending attempt; and an interleaved newer attempt survives terminal cleanup because removal targets only the older attempt's token-addressed key, with no compare-then-remove race.
- The iPadOS desktop-UA masquerade heuristic is pinned at the boundary: `MacIntel` with touch points routes through redirect sign-in, while `MacIntel` without touch points keeps popup authentication.
- A deal left in flight across a sign-out and a sign-in as a different account is dropped when it rejects late (the stale-attempt guard), leaving the new account's surface untouched; and a retry keeps the error surface mounted (dealing) until it settles rather than flashing a blank Board.

`src/w1-auth-google.test.tsx` (Vitest RTL-jsdom) covers the App wiring and the retry affordance:

- With a `dealError` present, `App` renders the `role="alert"` retry surface as the Card tab's content inside the still-mounted shell (`.app` and `.nav` both present), and its Retry button invokes `retryDeal`.
- With the error active, tapping the Prompts tab navigates to `/items` and mounts the ItemPool page (the recovery path), and tapping Card again re-shows the retry surface.
- `DealError` renders the message as an alert, calls `onRetry` when Retry is tapped, and disables/relabels the button while a retry is in flight.
