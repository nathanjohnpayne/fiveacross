# Private reads and attended device recovery

The owner approved memory-only private and Admin reads in [#1411](https://github.com/nathanjohnpayne/fiveacross/issues/1411#issuecomment-5975988796), then approved [attended legacy recovery and a minimal offline render witness](https://github.com/nathanjohnpayne/fiveacross/issues/1411#issuecomment-5976278917). Trusted-device consent for private persistence is not offered.

## Client boundary

Private profiles, own pending submissions/Claims and Admin queues use an independent named Firebase app. Its Auth and Firestore cache are memory-only. The primary authenticated user is copied using the public Auth API; a second named app does not inherit sign-in automatically. Each account or private-client retirement gets a fresh private app; timely same-UID ID-token callbacks copy refreshed Auth into the existing memory client without retiring its subscription keys or captured leases. Initialization or fresh-client Auth-copy failure gets at most three fresh-app retries after 250 ms, one second and two seconds; each retry retires earlier leases and advances the Auth incarnation, so a failed bridge cannot carry confirmed online block readiness. Account, connection, recovery or stop transitions cancel the old retry episode. Exhaustion stays unavailable until explicit user Retry, a new Auth/connection/recovery episode or document reload. An explicit private-UI Retry starts one fresh bounded bridge budget and Auth incarnation, never reuses an old confirmed answer or falls back to persistent private reads. Gameplay connection Retry first checks the live current-actor bridge: an unavailable or failed client starts that fresh episode. An initialized client is replaced only for an explicitly identified connection-class private SDK read failure or an authority timeout while that SDK read remains pending, whose captured UID/client/generation and caller Event/attempt are still current (#1732). Successful reads and permanent authority rejection disarm that provenance; terminal publication also retires previously captured Retry callbacks before they can bootstrap or replace the client; profile transaction commits/writes, bridge waits, offline-witness locks, permanent denial and unrelated gameplay failures do not qualify. Unrelated gameplay Retry retains the app, generations, action leases and confirmed block answer. Replacement uses the existing bounded bridge episode, retires old leases/confirmation and grants no new authority by itself; private reads must still settle under the existing authority gates. A stale UI actor cannot restart the replacement account or dispatch its deal, and offline Retry does not restart the bridge. Bootstrap readiness waits through scheduled same-account bridge retries within one absolute five-second deadline, including a waiter arriving after a transient failed publication. Exhaustion rejects promptly; a timeout cannot capture a client that becomes ready later. Scheduled success inside that bound lets the profile/server-attestation bootstrap continue without explicit Retry. Readiness rechecks the primary actor before binding services, and captured action leases remain unchanged. An exhausted or timed-out wait still exposes the existing connection Retry; an actual server denial remains a permanent failure and cannot authorize a deal. Unknown shared content stays withheld with actionable online Feed/Tally retry messages, while offline cold starts retain the explicit reconnect message. Changing Auth on an existing Firestore instance alone does not erase its cached documents.

An account change retires private UI state synchronously before primary Auth commits it. A failed or timed-out active same-UID Auth copy retires the old memory client and starts the bounded fresh-client bridge episode; no failed copy retains old private authority. Offline transitions retire private profiles and Admin clients; the owner-approved same-session block-set exception below remains in memory. Private listeners are keyed by account and incarnation, accept current server snapshots, and clear on denial. Admin entry requires a current server Event snapshot naming the same authenticated Admin. Every action captures one private lease and Event before yielding; reads, transaction retries, staged writes and successful completion must still belong to that lease. A retired action cannot obtain the next account's client. A gameplay transaction can commit just before that retirement while its local completion is refused; a current-incarnation retry sees the existing identity and reports a no-op. The client does not roll back that committed write, and a local join analytic tied to the refused completion may be omitted. App Check forwards the primary app's existing attestation without creating another CAPTCHA. Its SDK token cache is distinct from the memory-only Auth/Firestore data cache: forwarded application-attestation tokens may be persisted by the SDK, contain no account profile or Admin documents, and do not authorize a user action without Auth and server Rules. Forwarding uses the signed token expiration as refresh scheduling metadata, never a synthetic extension or proof of signature validity.

A fully committed server answer remains visible within its private subscription key during server-backed own pending writes and removal-barrier checks. The hook retains the last confirmed data, never promotes a pending first answer or the write's speculative fields to authority. A settled, server-backed private collection snapshot publishes directly unless its document-ID membership is missing an ID from the last committed answer. Only that removal candidate waits for the captured memory client’s pending writes to settle: removing a query row can report `hasPendingWrites: false` before acknowledgement. Settling that queue does not validate the captured snapshot: rejection callbacks can settle before the rollback listener is delivered. For the current removal candidate, the hook then reads a fresh server-backed answer on the captured memory query before publication. Each subscription permits one drain/server-read barrier in flight and retains at most one latest removal candidate for a rerun; a burst cannot dispatch overlapping barriers. Permission-denied rejection of either step for the current candidate clears confirmation and marks failure; a superseded rejection cannot overwrite a newer callback. Every other barrier rejection keeps the last committed answer visible without changing its membership. A later settled removal snapshot may retry after a per-subscription cooldown of 250 ms, doubling on transient failures up to two seconds and resetting after a successful barrier. There is no automatic retry of the failed candidate: without a later settled snapshot, a removed row may remain visible, as previously accepted. A newer pending, cache-only or non-removal callback discards the queued candidate and cooldown timer; any newer callback or retired subscription cancels the earlier candidate’s publication. Subscription retirement and listener denial also discard queued work; no persistent client supplies this barrier. Current same-scope pending metadata therefore does not unmount an authorized Admin console/queue or erase a saved profile; an action's rejected write can still show its error. Cache-only answers, listener denial, recovery quarantine and private-incarnation retirement clear this retained answer. Event-scoped private rows additionally retire on Event change; the global own-profile key remains UID-scoped.

Avatar uploads use that lease's captured Storage client, check retirement after image preparation before starting a write, and recheck after each Storage await before proceeding. A write already dispatched before retirement may finish under its captured credentials; the client does not roll it back or continue it through a new account.

Authenticated canonical hostname occupancy checks also use a captured memory client: unavailable recovery/Auth state or retirement after the server read returns `check-failed`, never a free address. Anonymous public routing and posture reads keep the public client.

The primary persistent multi-tab Firestore remains the gameplay store. Cached Boards and queued Marks are preserved. Its durability is not authority to deal, approve, restore or access Admin data. Own-profile bootstrap may use memory-only reads during recovery so the active account can recover its gameplay queue; private profile and Admin views stay closed until recovery finishes.

Timely same-UID ID-token callbacks preserve the named memory app, listener keys and action leases while the public Auth API copies current credentials into that app. Refresh copies are serialized and bootstrap copies the latest same-account subject before publishing, including a callback on the same mutable User object. A late old copy cannot publish into a retired generation or replace another account. Healthy hourly refresh therefore keeps confirmed Feed/Tally state, Admin drafts and in-flight bootstrap/action completion available; it does not start another gameplay queue drain or reconfirmation gate. Server Rules remain authoritative, listener denial and cache-only answers retain their clearing behavior, and failed Auth copying, actual account changes, offline/recovery transitions, explicit private-client Retry and stop still retire private clients and stale leases. The explicit same-session offline block-set exception below remains separate.

Each active same-UID refresh copy has the [owner-approved five-second deadline](https://github.com/nathanjohnpayne/fiveacross/issues/1700#issuecomment-5999530058) (#1700), starting when its serialized copy begins rather than when its token callback queues. A current timeout retires the old named client and starts the existing independent bounded fresh-client episode using the latest same-account subject; newer work cannot remain queued behind the retired client. Timely copies keep the app, generation, captured leases and private UI intact. Completion and retirement clear the copy’s owned timer; actor, offline, recovery and stop retirement release its local waiter. The SDK call is not cancelled: its eventual success or rejection is consumed and cannot revive the old authority or affect a newer client. Initial bootstrap-copy hangs and the separate five-second facade readiness wait retain their existing behavior.

## Legacy transition

A missing per-project recovery marker holds ordinary private views closed, including on a fresh installation: cache absence is not inferred from a missing marker. The signed-in shell shows an actionable Device recovery link on gameplay and setup routes, explaining that profile, submissions and organizer tools require recovery while Boards and queued Marks remain available. No cache is cleared automatically. Recovery links add the dedicated query flag to load a fresh document; returning removes it for another fresh application load. The dedicated recovery document loads through the credential-safe entry seam instead of the application graph, so it does not start gameplay, React data effects, analytics or application writers. Ordinary entry URLs without that query key start loading the application graph without first awaiting the recovery-navigation import; URLs containing it retain the helper's first-value parsing and require the value `1` to select recovery. Credential capture still precedes every deferred import.

Own Claims remain quarantined until recovery finishes; they are not an additional gameplay-bootstrap exception. This also affects `ConfirmWinMoments`: it announces an Admin confirmation only after observing that owned Claim pending in a server snapshot. On a fresh unrecovered document there is no such observation. A Claim confirmed before recovery is first seen as history afterward, so the confirm-path emitter does not retroactively post its win's Feed Moment. Admin-resolved Board credit and stats, existing Board rendering and queued Marks remain available under their existing contracts. A pending Claim already witnessed by that same process before going offline can still qualify when confirmation becomes visible later. The device recovery notice must explain this announcement consequence alongside private profile, submission and organizer access; completing recovery before the pending-to-confirmed transition restores observation, not missed historical announcements.

The operator must recover and verify queued Marks online for **every historical account**, then close other app tabs/windows. These are attended confirmations, not assertions proved by `waitForPendingWrites`: the real SDK regression proves that the active account's empty queue can coexist with another account's recoverable Mark. Temporary retention of the quarantined historical cache is accepted during this recovery.

Only after both confirmations does recovery establish server access for the captured signed-in account, drain that account, terminate the legacy instance and clear persistence through supported SDK APIs. Server proof, draining and termination are bounded, and account/online state remains checked. Once SDK clearing starts, its timeout reports waiting but leaves the recovery document quarantined until that actual operation settles; Return, retry and application links remain unavailable. A never-settling clear requires closing the browser rather than using this document to reopen gameplay. The page cannot prevent manual external navigation or another browser window. Failed, timed-out or stale recovery never records completion, including late successful clearing after its timeout. A retry reloads the dedicated document. Successful clearing records and reads back the marker before returning to the application. This is logical SDK cache removal, without a forensic secure-erasure guarantee.

## Offline attestation

The server's timestamped `users/{uid}.attestedAdultAt` remains the honor-system self-statement. The whole private profile is no longer read from the persistent gameplay cache. The owner-approved disk exception is a per-project, per-UID boolean containing no profile fields or timestamp. It may lift provisional rendering only when that UID already has a cached Board. It never grants deal or server-read authority. A current definitive server absence retires it immediately in process, removes its stored flag when possible, or writes the same-key false tombstone if removal fails. A revoked lookup retries persistence once when storage becomes usable and still refuses rendering. Unreadable or unwritable storage grants no provisional rendering. Every cooperating same-origin document serializes witness writes, lookups and revocation retries through the same project/UID Web Lock. Its acquisition is bounded to one second, with no unlocked fallback or late mutation; absent, denied or timed-out locks refuse provisional rendering. The callback performs only synchronous storage work. A lookup writes and reads back only its existing true Boolean, creating no probe or absent-account key. A successful participating revocation cannot be resurrected by that check; this guarantee does not cover a nonparticipating old build or another origin. Witness ordering is scoped to each private memory database: only the latest-started authority read, unless superseded by a committed attest, may record its result. Superseded reads retain their actual server return value but cannot erase a later committed true witness or restore one revoked by a newer read; a fresh post-commit absence still revokes. Current server absence retires this process before the lock wait; an in-memory intent fence refuses an older queued positive after a newer authoritative record, and a positive writer rechecks its captured private lease inside the lock. Cache readers recheck their UID, project and Event after waiting. If both writes fail and a fresh process starts after storage recovers before any retry succeeds, the old flag can reappear because no revocation was persisted. The [owner accepted this narrow fresh-process render residual](https://github.com/nathanjohnpayne/fiveacross/issues/1411#issuecomment-5980901495) to preserve returning-player offline Board rendering. Its limitation test records accepted policy, not complete persistence remediation. Same-session optimistic attestation remains unchanged.

The first updated build must receive a current authoritative online attestation (or complete a current attest) to seed its new minimal witness before relying on offline Board rendering. An old build's cached profile is never converted into this flag or read as a fallback. If the update first opens offline without that new witness, or Web Locks are unavailable, the Board remains behind the existing Loading gate until reconnect; cached Boards and queued Marks are retained. Operators must include online witness priming in the attended rollout checks before testing a subsequent offline reload.

## Reciprocal block reads and shared content

Reciprocal block-filter bootstrap uses the named memory client even while legacy recovery is outstanding, like the existing own-profile gameplay bootstrap and server-only pair maintenance. It neither reads legacy private data nor records recovery completion. Raw own-block panels and other ordinary private views remain quarantined. The own-block panel explains recovery with the fresh-document attended link before any rows/actions, and offline requires reconnect without borrowing the reciprocal-filter witness. Its online first committed own-direction answer is bounded to ten seconds; unavailable or denied reads offer scoped Retry with connection/access guidance. Healthy local Retry replaces only the own listener; a failed/unready bridge keeps its separate private-session Retry. Cache, denial and scope retirement clear the own answer, while server-backed pending updates retain only previously committed rows. Only a server-confirmed set may qualify a newly opened session to render shared content. When that same account/Event goes offline mid-use, it retains its confirmed set in memory and continues showing cached Feed/Tally content through the existing block filter. Offline cold starts/reloads withhold shared content until an online confirmation and show explicit reconnect messages; they never present an unknown set as an empty Feed or Tally. Account/Event changes, failed Auth-copy retirement, explicit Auth Retry and listener denial retire the retained set; denial cannot qualify a later offline session. The private manager distinguishes Auth, connection and recovery transitions. Only the explicit mid-use offline/reconnect path may carry a same-scope confirmed set across connection generations; a replacement client needs a new server answer before online shared content is admitted. Timely same-UID credential copies keep the existing memory witness and subscriptions. A same-UID token callback while offline leaves the existing retirement stamp unchanged and retains the confirmed set for offline rendering. An actual Auth retirement stamp survives later connection publications: reconnect requires a fresh server answer, even if React did not observe the intermediate Auth publication. Private block listeners never populate the persistent read cache. Durable blind block batches, including their own direction/pair write payloads, remain in the gameplay queue; server-only unblock/repair reads use the captured memory client.

Online bootstrap and reconnect withhold readiness until the primary persistent gameplay queue drains, then create a fresh private pair listener and require its current, non-pending server answer. A healthy captured memory client gets at most three readiness attempts: queue-drain windows of five, ten and twenty seconds, with one- and two-second retry delays; each drained attempt separately allows ten seconds for its first committed pair answer. Cache/pending snapshots cannot satisfy that deadline. A failed attempt shows the existing unavailable/Retry state while bounded automatic retries continue; permission or authentication denial is terminal for automatic retry and clears the retained witness. Explicit Retry starts a fresh local readiness episode without rotating healthy private Auth or retiring Admin/profile state; a failed bridge still uses its separate private-client Retry. Retired attempts, account/Event/client changes and unmount fence late callbacks and cancel local timers. SDK queue waiters are not cancellable, and queued block writes/Marks are never cleared. This ordering covers recovered queued blocks when no process-local relay remains; an answer obtained before draining cannot qualify readiness. A retryable online failure or healthy local Retry preserves only the already-confirmed same-scope offline witness; it cannot admit online content before drain and a fresh answer. Cold offline/reload remains withheld with explicit reconnect copy. No block data or new hint is persisted (#1681/#1682).

## Validation

`tests/offline/private-cache-auth.test.ts` uses public Firebase SDK APIs and the Auth/Firestore emulators to prove independent Auth wiring, account cache separation, late-action refusal, offline retirement, durable Marks across reload and the other-account queue constraint. `src/hooks/useData-private.test.ts` covers actual private listener routing, cache-only refusal, account/incarnation changes, denial, recovery and badge retirement. `src/auth/privateCacheRecoveryPage.test.ts` and `src/entry-private-cache.test.ts` exercise the actual DOM workflow, failure/reset controls and credential-safe graph ordering. `src/auth/privateCacheRecovery.test.ts` covers stage ordering, failure, timeout and stale-account refusal; `src/auth/offlineAttestationWitness.test.ts` covers the minimal witness. Admin/profile caller tests prove captured-client behavior rather than only testing a helper in isolation. The stateful daily join regression in `src/data/w1-attestation.test.ts` applies a committed identity before retiring its lease, proving refused acknowledgement and a no-op retry; it does not claim actual-SDK or emitted-analytics integration. Real Chromium acceptance separately verifies queued Mark recovery and supported clearing through the actual SDK, and document navigation through the actual entry/recovery graph with fixture application/SDK boundaries. SDK clearing does not prove the attended all-account or other-tab statements.

Source tests and a merged PR do not establish installed-client or deployed behavior. Hosting rollout and attended recovery on affected devices remain separate acceptance steps; no production data/configuration mutation follows from this source policy.
