# Vercel must serve Firebase Auth helpers from its own origin

The production Vercel mirror runs at `gaycruisebingo.vercel.app`. Its `VITE_FIREBASE_AUTH_DOMAIN` must be that same hostname so popup and redirect sign-in state remains first-party in storage-partitioned browsers. Pointing the SDK directly at `gaycruisebingo.firebaseapp.com` avoids the blocked custom domain but makes Firebase's auth iframe cross-origin, which can fail with "Unable to process request due to missing initial state" in Safari and in-app webviews.

`vercel.json` transparently reverse-proxies every request under `/__/auth/*` to the Firebase Hosting helper namespace at `https://gaycruisebingo.firebaseapp.com/__/auth/*`. This must remain a rewrite, not a redirect: the browser-visible origin must stay `gaycruisebingo.vercel.app` throughout the helper flow. The rule covers the handler, iframe, JavaScript helpers, and any future helper path Firebase adds beneath the namespace.

After the auth proxy, a catch-all rewrite serves `/index.html` for client-side routes such as `/feed` and `/leaderboard`. The auth proxy must remain first so Firebase helper requests are never handled by the SPA fallback.

## Three Vercel projects, one `vercel.json`

Two further Vercel projects serve the brand family's backup hosts from this same repository and the same `main` branch, both built against the `fiveacross` Firebase project (#585, #625, [ADR 0008](../docs/adr/0008-five-across-second-firebase-project.md)): `fiveacross.vercel.app` and `vacaybingo.vercel.app`. Vacay is an *Edition* of the `fiveacross` project rather than a project of its own—ADR 0008 splits the data plane by cohort, not by brand—so both hosts share a proxy destination and differ only in the Edition their build bakes in. Their auth helper must reach `fiveacross.firebaseapp.com`, not `gaycruisebingo.firebaseapp.com`, so the proxy above cannot be a single unconditional rule for all three.

It is resolved **inside one `vercel.json`**, by exact host-conditional rewrites: `/__/auth/:path*` with `has: [{ type: 'host', value: { eq: '<mirror-host>' } }]` proxies to `https://fiveacross.firebaseapp.com/__/auth/:path*`, one rule per mirror host. The Gay Cruise Bingo helper also requires its exact production mirror hostname. Unmatched hosts, including all previews, receive no production Auth proxy; every helper rule precedes the SPA catch-all.

One rule per host rather than a single `{ inc: [...] }` list, even though the two rules are otherwise identical: `eq` is the matcher already proven in production here, and a single shared list that misbehaved would take out both mirrors at once instead of one. Revisit if the list grows past a handful.

**A mirror serves the branded app in place and must never redirect to the brand's canonical domain** (#625). A redirect would hand the visitor back to precisely the hostname that was unreachable, which is the only situation the mirror exists for.

The condition must use the `{ eq }` object form. A bare string `value` is an unanchored regular expression to Vercel and would also match `fiveacross.vercel.app.evil.example`; exact host matching is the same invariant `FIRST_PARTY_AUTH_HOSTS` keeps in `src/auth-domain.ts`, because both consoles register one literal hostname.

The alternative—a long-lived mirror branch carrying its own `vercel.json`—was rejected: it makes the backup host a *fork of `main`* that has to be re-synced by hand, and a backup host silently serving stale code is the failure this mirror exists to prevent. Build-time templating cannot work at all, because Vercel reads `vercel.json` from the source before the build command runs. See [`docs/app/preview-deploys.md`](../docs/app/preview-deploys.md) § The Five Across mirror.

### Mirror currency is manual, and the staleness trade was reconsidered (#676)

The paragraph above rejects a design whose mirrors must be re-synced by hand. That reasoning still holds *against a forked `vercel.json`*—which would let the mirror's rewrites, and therefore which Firebase project its auth helper reaches, drift from this spec's contract—but it no longer implies that mirror *content* updates automatically. `vercel.json` carries `git.deploymentEnabled: { "**": false, "preview": true }`, so neither a merge nor a branch push deploys anything; each mirror is published by an explicit `npx vercel deploy --prod --project <name>`, and is only as current as that last command.

The staleness this accepts is deliberate, and narrower than what the rejected design would have cost. All three mirrors build from `main`, so the rewrite contract above cannot fork; only the deployed bundle can lag. The automation it replaces did not actually prevent lag either—Vercel silently cancels queued builds under account-wide pressure, and both brand mirrors were observed 22h and 7h stale with the Git integration connected. What it did reliably produce was three production builds per merge against a cap whose exhaustion refuses deployments team-wide for 24 hours, taking out the ship-network fallback precisely when the primary host is unreachable. A mirror you must remember to publish is a worse day-to-day and a better worst-case than a mirror that cannot be published at all.

The operational consequence belongs in the runbooks, not here: after any deploy that matters, publish and verify each mirror per [`docs/app/deploy-targets.md`](../docs/app/deploy-targets.md) § Deploying a mirror, each one only after its own Firebase primary — a mirror is a second front end for the same backend, and the two primaries deploy independently. Every branch is denied but the historical `preview` exemption, whose build now refuses publication until isolated test configuration is reviewed.

The deployment configuration is completed outside the repository: `gaycruisebingo.vercel.app` must remain in Firebase Authentication's authorized domains, and `https://gaycruisebingo.vercel.app/__/auth/handler` must remain an authorized redirect URI on the Google OAuth web client.

Preview hosts have no production Auth trust (#1420). The stable preview alias is absent from `FIRST_PARTY_AUTH_HOSTS`, and every production helper rewrite is exact-host conditional. Until an isolated test project/web-app configuration and test Auth routing are reviewed, Vite rejects all `VERCEL_ENV=preview` builds. This does not revoke old deployments or console registrations. Owner inventory, configuration authorization and deployed isolation readback remain separate; see ADR 0007 and `docs/app/preview-deploys.md`.

Every surface uses `signInWithRedirect` when the configured auth handler is same-origin (#765). In iOS Safari, Firebase's popup can become a separate browser tab; the returning handler can then lose the `oauthHelperState` that the outbound helper stored in that tab's `sessionStorage`, producing "Unable to process request due to missing initial state." In installed desktop Chrome/Edge app windows, the OAuth popup can be blocked or hidden because the standalone window has no address bar, making the sign-in tap appear to do nothing. A top-level redirect keeps the helper round trip in the app tab/window, while the same-origin proxy above prevents Safari storage partitioning. The decision no longer consults the user agent or display mode; only a cross-origin handler (local development, the Auth Emulator) continues to use `signInWithPopup`.

The sign-in operation is single-flight at the Auth provider boundary. Repeated taps or callers while popup/redirect startup is pending receive the existing promise and must not create another Firebase transaction. Redirect completion consumes Firebase's result once, records the successful login, and persists the 18+ acknowledgement that gated the original tap.

## Regression guard

- **Given** the Vercel deployment configuration **when** its rewrites are inspected **then** `/__/auth/:path*` must map to the equivalent path at `gaycruisebingo.firebaseapp.com`, preserving the same browser-visible Vercel URL. (Test: `src/vercel-auth-proxy.test.ts`.)
- **Given** a request under `/__/auth/*` on either brand mirror host (`fiveacross.vercel.app`, `vacaybingo.vercel.app`) **when** Vercel evaluates its rewrites **then** it matches a host-conditional rule, ahead of the Gay Cruise Bingo rule, that maps to the equivalent path at `fiveacross.firebaseapp.com`; that condition matches the hostname exactly rather than as an unanchored pattern; and no unconditional production auth rule exists. (Test: `src/vercel-auth-proxy.test.ts`.)
- **Given** a direct request for a client-side route **when** Vercel evaluates its rewrites **then** the request must fall back to `/index.html` only after every Firebase Auth proxy rule has had priority. (Test: `src/vercel-auth-proxy.test.ts`.)
- **Given** either brand mirror host **when** the app initializes Firebase there **then** `authDomain` is that same hostname—never the brand's canonical domain, which would defeat the mirror—while a per-deployment host on a mirror project keeps the configured domain and stays outside the pre-mount gate. (Test: `src/auth-domain.test.ts`.)
- **Given** the stable preview alias **when** the app initializes Firebase there **then** it keeps the configured domain and receives no first-party production trust, as do per-deployment hosts and other branch URLs. (Test: `src/auth-domain.test.ts`.)
- **Given** the Vercel deployment configuration **when** its Git settings are inspected **then** every branch is denied via `**` (the slash-crossing wildcard, since working branches are `claude/…` and `*` would match none of them), and `preview` is the sole exemption—limiting Git-triggered builds while the preview exemption remains subject to the isolation build refusal. (Test: `src/vercel-auth-proxy.test.ts`.)
- **Given** any surface on a same-origin auth handler (iOS Safari tab, installed iOS PWA, iPadOS desktop-UA masquerade, installed desktop PWA, desktop browser tab) **when** the Player signs in **then** exactly one `signInWithRedirect` transaction starts and no popup starts. (Test: `src/auth/AuthContext.test.tsx`, "uses one top-level redirect on a same-origin handler from a … (#765)" and "starts one top-level redirect on a same-origin handler and ignores an abandoned acknowledgement".)
- **Given** a cross-origin auth handler **when** the Player signs in **then** popup sign-in starts and no redirect starts. (Test: `src/auth/AuthContext.test.tsx`, "keeps popup sign-in only where the OAuth handler is cross-origin (#765)".)
- **Given** sign-in is already pending **when** another caller invokes sign-in **then** Firebase is called only once. (Test: `src/auth/AuthContext.test.tsx`, "coalesces repeated sign-in calls into one Firebase auth transaction".)
- **Given** a mobile redirect returns with a Firebase user **when** the app consumes the redirect result **then** it persists the checked 18+ acknowledgement exactly once. (Test: `src/auth/AuthContext.test.tsx`, "persists the checked 18+ acknowledgement after returning from mobile redirect sign-in".)
- Live verification (manual, post-deploy): the built bundle contains `authDomain: "gaycruisebingo.vercel.app"`; requesting `/__/auth/handler` through the Vercel origin returns Firebase's `fireauth.oauthhelper` page without a redirect; and opening Google sign-in loads the auth iframe from the Vercel origin.

- **Given** any `VERCEL_ENV=preview` build **when** Vite loads its configuration **then** the build fails before loading Firebase settings until reviewed isolated test configuration exists; production mirror builds keep their current behavior. Tests: `src/build-config.test.ts`, plus actual Vite preview refusal and production fixture-build validation.

The build also refuses `VERCEL=1` with missing or unknown `VERCEL_ENV`. If all platform system variables are disabled, source alone cannot identify a Vercel build; verifying system-variable exposure remains a deployed configuration prerequisite, not a proven live state.
