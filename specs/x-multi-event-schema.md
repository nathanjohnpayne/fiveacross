# Multi-event schema readiness (design-only)

The data model is already Event-scoped: everything a Player touches lives under `events/{eventId}/…`, so a second Event is simply a new Event doc plus a build pointed at it. v1 deliberately ships a SINGLE active Event with NO room-browsing / join-code UI—a PRD non-goal ("Full multi-tenant 'rooms' product", `docs/projects/gaycruisebingo/prds/gaycruisebingo.md:39`) consistent with [ADR 0003](../docs/adr/0003-pool-is-pre-cruise.md) (the pool is an activity that runs before the Event opens, "plus latecomers and future Events"; no re-deal or square-swap at launch) and the architecture goal that the app "stay reusable for future cruises without a rewrite" (`docs/architecture/0002-application-architecture.md:13`). This spec remains the schema and second-Event runbook; #807 has since implemented its defensive client-state prerequisite without adding the deferred selection product (`specs/event-scoped-client-state.md`). Every file:line below cites the current tree, not the issue-time snapshot (e.g. the `EVENT_ID` constant the issue placed at `firebase.ts:37` is now the startup-resolved live binding in `src/firebase.ts`—see the seam section).

**Decision summary:** a second Event = update the seed's baked Event metadata (name/dates/prompt pool), seed the new Event doc, sweep the baked Event branding, then point traffic at it one of two ways: bake `VITE_EVENT_ID=<new-id>` into a single-Event build (the legacy shape), or—since #542/#543 shipped hostname resolution (ADR 0009)—leave `VITE_EVENT_ID` empty and add a `hostnames/{host}` routing doc so a hostname-resolved build serves the Event on that origin with no rebuild of the React app (the static `index.html`/OG/PWA-manifest identity baked at build time is not corrected per hostname until #546 lands—see the branding note below). No index or Functions changes; the only rules surface added for resolution is the world-readable `hostnames` collection (#542). No re-deal of existing Boards; no cross-Event browsing; no join codes. The formerly build-time `EVENT_ID` constant is now a startup-resolved live binding (an `/e/<eventId>` path prefix still costs more—see the seam section).

## What already parameterizes cleanly (evidence)

- **Client data layer—every game ref is built under the captured `events/{eventId}/…` scope.** Converter-attached helpers in `src/data/paths.ts`, the manual listeners in `src/hooks/useData.ts`, and raw write paths in `src/data/**` receive or capture the active Event before they build a ref. Proof media is Event-scoped too: `src/data/storage.ts` writes `proofs/${eventId}/${uid}/${proofId}.${ext}`. The old seven-importer inventory is no longer exhaustive: components and hooks also read `EVENT_ID` to scope React state and to pass an action's captured Event through async work. The governing runtime inventory is [`specs/event-scoped-client-state.md`](event-scoped-client-state.md), not this design-time file list.
- **Firestore rules are fully `{eventId}`-parameterized.** The whole game surface nests inside `match /events/{eventId}` (`firestore.rules:28`)—`items` (`:42`), `players` (`:68`), `boards` (`:80`), `proofs` (`:85`), `claims` (`:157`), `tally` + `markers` (`:173`, `:184`), `doubts` (`:201`), `moments` (`:225`)—and admin power is per-Event by construction: `isAdmin(eventId)` reads that Event doc's own `admins` array (`firestore.rules:8-11`). Even the proof `storagePath`/`mediaURL` pinning interpolates `eventId` (`firestore.rules:139`, `:144`). N events need zero rules edits.
- **Storage rules mirror it.** `match /proofs/{eventId}/{uid}/{file}` (`storage.rules:29`) with per-Event moderation via `isEventAdmin(eventId)` (`storage.rules:7`, `:36`).
- **Cloud Functions are Event-agnostic.** `moderateProof` derives the Event from the uploaded object's path (`functions/src/index.ts`, `// proofs/{eventId}/{uid}/{proofId}.jpg`) and writes the flag back to `events/${eventId}/proofs/${proofId}`—it serves any number of Events with zero config. Since #126 it is conditionally exported behind the off-by-default `ENABLE_VISION_MODERATION` flag, so it deploys as a CloudFunction only when Cloud Vision is enabled (see `specs/w4-gate-vision-moderation.md`); the module also carries the #101 moderation-notification triggers (`notifyProofModeration` / `notifyItemModeration`, #120), so `moderateProof` is no longer the sole export. The crawler `share` OG endpoint was removed with the server-side OG pipeline (ADR 0005, #39). All of these are Event-agnostic—they derive the Event from the document or object path, needing no per-Event config.
- **Indexes are declared per collection id, not per Event path.** The single composite index (`players` by `bingoCount`/`squaresMarked`/`firstBingoAt`) uses `"queryScope": "COLLECTION"` (`firestore.indexes.json:4-5`), which applies to every collection named `players` regardless of its parent Event—a new Event inherits it automatically.
- **The seed is multi-Event in its TARGET *and* (since #563) its payload.** Per-Event payload modules live in `scripts/seed-data/<event-id>.mjs`, selected by `VITE_EVENT_ID` or the resolved project's default — the historical description below predates that split. Originally: `scripts/seed.mjs:123` reads `process.env.VITE_EVENT_ID` (defaulting to `med-2026`) and writes `events/${EVENT_ID}` (`:132`) with deterministic prompt ids, so re-running it against a new id is idempotent—and (since #563) the payload comes from the per-Event `scripts/seed-data/<event-id>.mjs` modules rather than one baked `EVENT_SEED`. The only env-driven inputs are the Event id (`:123`) and the `ADMIN_UID` roster (`:124`), so a second Event edits the payload before seeding (runbook step 1).
- **The schema and admin-alert lifecycle consume Event retirement.** `EventDoc.status` is `'active' | 'archived'` (`src/types.ts`). Admin-alert enqueue/delivery reads it, the active→archived trigger settles pending work, and the scheduled sweep revisits archived Events as a retrying backstop (`functions/src/adminAlerts.ts`; `specs/admin-notification-emails.md`). That is an operations lifecycle, not a player-data authorization boundary: archived Events are not yet made read-only by the current Firestore/Storage rules.
- **Cross-Event surfaces are global by design.** `users/{uid}` profiles (`firestore.rules:14-26`; `UserDoc` in `src/types.ts:77-86`, including the 18+ `attestedAdultAt` self-attestation) and `avatars/` (`storage.rules:23`) are deliberately outside the Event subtree: a Player's identity, avatar, and attestation carry to the next Event, while their Board/Player rows and stats are per-Event docs that start fresh.

## What hardcodes the single Event (honest inventory)

- **`src/firebase.ts`—`EVENT_ID` was the one real hardcode; it is now a startup-resolved live binding (#543).** `bootstrapEventResolution` installs the resolved id via `applyResolvedEventId` before `main.tsx` mounts; a **non-empty** `VITE_EVENT_ID` is the build-mode switch that marks a single-Event build and short-circuits resolution to the env value (`.env.example`, ADR 0009), while an empty one resolves the id from `window.location.hostname` via `hostnames/{host}`. Every Event path in the app still derives from this single symbol via the seven `src/data/` importers (`paths.ts:2`, `api.ts:18`, `proofs.ts:2`, `moments.ts:2`, `profile.ts:2`, `admin.ts:2`, `storage.ts:2`), each reading it lazily inside a helper—the live-binding contract. A single-Event bundle therefore serves exactly one Event; a hostname-resolved bundle serves whichever Event the origin's routing doc names.
- **Subscription and client-state keys are Event-aware (#807).** `specs/event-scoped-client-state.md` owns the implemented contract: refs and effect keys share one captured Event id, returned state goes neutral synchronously on a scope mismatch, and retired callbacks cannot refill a later Event—or a later subscription lifetime after B→A. The global `users/{uid}` profile listener is the deliberate exception.
- **Telemetry already carries the Event dimension.** `registerAnalyticsDimensions` installs `event_id` and `event_slug` on both sinks after startup resolution (`specs/posthog-analytics.md`). #807 Event-partitions the durable transition cursor/outbox and local request acknowledgements. A future product switcher would still have to re-run the bootstrap installers and analytics registration; #807 ships no such surface.
- **Event-specific branding is baked outside the schema.** Since the #586 Editions system, `index.html` and the OG tags are populated at build time from `VITE_EDITION` via `src/editions.ts` and `vite.config.ts` placeholder substitution (`%EDITION_APP_NAME%`, `%EDITION_META_DESCRIPTION%`, and friends)—not the literal per-Event copy this section previously named. That substitution happens once, at build time: for a **single-Event build**, a rebuild with the new Event's `VITE_EDITION` sweeps it, same as before. For a **hostname-resolved build** (the "no rebuild" flow below), the document title and the `apple-mobile-web-app-title` meta tag ARE corrected at runtime: `bootstrapEventResolution` (`src/data/hostnames.ts`) calls `applyEditionDocumentIdentity` (`src/editions.ts:433-443`) after resolution, which rewrites both from the resolved Edition's brand (pinned by `src/editions.test.ts:304-327`). What stays fixed at build time, to whichever Edition built the bundle, and is NOT corrected per hostname is the crawler-facing metadata—the OG/meta-description block a crawler fetches from `index.html` without running JS (`og:title`, `og:description`, `og:image`, `og:url`, `og:site_name`)—and the PWA manifest `name`/`short_name`, which installs from the manifest FILE rather than the DOM; `src/editions.ts` documents this narrower gap explicitly and defers the fix to a not-yet-implemented per-hostname edge Worker (#546). Until #546 lands, a hostname-resolved build genuinely can leak one Edition's identity in its link-preview OG tags and installed-PWA name when serving a different Edition's Event on that host—and that leak reaches the native install prompt, not just crawlers. The runtime repair (`applyEditionDocumentIdentity`, `src/editions.ts:433-443`) rewrites exactly two things: `document.title` and the `apple-mobile-web-app-title` meta tag. That corrects the browser tab title and, since iOS/Safari reads that same meta tag for its home-screen label (`specs/w1-pwa.md:45`), iOS's manual "Add to Home Screen" hint too. It does NOT touch the PWA manifest's `name`/`short_name`—left alone by design (`src/editions.ts:427-431`), because rewriting the manifest file client-side is the kind of cleverness that can strand an installed app with an identity no server can correct; a hostname-resolved build gets a correct manifest only once the per-hostname edge Worker (#546) ships. Android/Chrome's native install prompt reads the manifest's `name` for its label (`specs/w1-pwa.md:45`), not the DOM, so on a hostname-resolved build that dialog shows the build-time Edition's name—not the resolved one—until #546 lands. These are deployment/branding concerns, not data-model blockers—and the schema already carries the per-Event equivalents (`EventDoc.name`/`startsOn`/`endsOn`)—but see the qualification on step 4 below before treating "no rebuild" as branding-complete.
- **One cross-Event query exists and is deliberately deferred.** `useTallyCards` still subscribes to `collectionGroup('markers')` across the project and filters paths to its captured Event in the callback. #807 fixes its lifecycle and displayed state only. #1072 owns the marker `eventId` field, backfill/legacy compatibility, Event predicate, collection-group index, and rules rollout that remove the over-the-wire cross-Event read before #804 gates it.

## Rules / indexes / hosting implications of running N Events

- **Rules: no changes for the intended sequential shape—but what the rules provide is PATH-SCOPING plus per-Event ADMIN scoping, NOT tenant isolation.** The analysis that originally followed this sentence has been superseded by the non-self-writable admission contract in `specs/event-membership.md` and its #804/#806 implementation tickets. #807 changes no rule. #1072 must land before #804 narrows the recursive marker rule, and the separate Mark/Echo batch-access proof remains a blocking prerequisite of #804 rather than client-state work hidden in #807.
- **Indexes: ordinary per-Event collection queries inherit their collection-scope indexes.** The existing Tally Card collection-group query is the exception: once #1072 adds its Event predicate, it also adds the corresponding `markers` collection-group-scope index. #807 changes no index.
- **Hosting: one bundle = one Event only for a single-Event build.** `firebase.json` serves a single `dist` with an SPA rewrite. Sequential Events on the legacy shape first register a named deploy target containing the complete Firebase web-app identity, Event, Edition, and audience posture, then build and deploy that target’s Hosting command (runbook step 4). Concurrent Events no longer need one hosting site per Event: the startup-time resolution seam SHIPPED (#543), so one hostname-resolved bundle (empty `VITE_EVENT_ID`) serves any number of Events, each routed by its origin's `hostnames/{host}` doc—subject to the tenant-isolation rules caveat above.
- **Firestore: Events coexist in one project.** A finished Event's subtree stays where it is (flip `status: 'archived'` once something consumes it); nothing about starting Event N+1 touches Event N's data.

## How to run a second Event (the runbook)

**Given** a reader asks "how do we run a second Event?" **when** they read this spec **then** the answer is: update the seed payload, create the new Event doc, sweep the baked branding, and point a build at it—no new UI (ADR 0003).

1. Update the seed payload for the new Event. Since #563 this is a NEW module: add `scripts/seed-data/<event-id>.mjs` (its own `EVENT_SEED` — `name`/`startsOn`/`endsOn` — and pools) and register it in `scripts/seed-data/index.mjs`; historically it was a manual edit of `scripts/seed.mjs`, which hard-coded the Med 2026 payload as the only pool, while the only env-driven inputs are the Event id (`:123`) and the `ADMIN_UID` roster (`:124`)—so running step 2 with only a new `VITE_EVENT_ID` would stamp the OLD Event's name/dates (and pool) onto `events/<new-id>`. Edit those constants first; the shape tests (`src/test/w1-event-seed.test.ts`) pin `settings`/`claimMode` and the 30–50 unique-prompt density band, not the name or dates, so a metadata edit passes them and a replacement pool must stay in that band. And the free-space copy is not in this script at all: the centre square's text is baked into the CLIENT bundle—`FREE_TEXT` in `src/data/seed.ts:2`, imported by the deal path (`src/data/api.ts:21`) and dealt onto every new Board by `joinAndDeal` (`api.ts:153`)—so an Event that changes it edits `src/data/seed.ts` too, and that edit ships only with step 4's rebuild (`SEED_ITEMS` in the same module is a test-only mirror of the pool; nothing else in the app reads it). (A future seed change could take name/dates from env or a config file; that does not exist today and is not required for a sequential second Event.)
2. Seed the next Event: `VITE_EVENT_ID=<new-id> ADMIN_UID=<uid,uid> GOOGLE_CLOUD_PROJECT=gaycruisebingo node scripts/seed.mjs`—creates `events/<new-id>` with its admin roster and prompt pool (`scripts/seed.mjs:123`, `:132`). `GOOGLE_CLOUD_PROJECT` is part of the script's own documented usage (`scripts/seed.mjs:7`): on the ADC path (`:126-128`) `initializeApp` gets no explicit project id, so without the env var the Admin SDK falls back to whatever ambient project the environment supplies. It is only skippable when the gitignored `serviceAccountKey.json` fallback sits in the project root (`:126-128`), since the key file names its project itself. One-off dependency prerequisite on a fresh checkout: `firebase-admin` is deliberately ABSENT from `package.json`—the seed is its only consumer and dynamic-imports it at run time (`scripts/seed.mjs:113`, `:118-119`), so install it first with `npm i -D firebase-admin` (or ephemerally, `npm i --no-save firebase-admin`) per the script's own header (`scripts/seed.mjs:4`) and the seed docs (`docs/app/README.md:65-68`).
3. For a single-Event build, set `VITE_EDITION` for the new Event BEFORE rebuilding so `index.html`'s substituted app-shell description, the OG url/image, and the PWA manifest name/short_name (`src/editions.ts`, `vite.config.ts` placeholder substitution) match it—see the branding note above. Setting `VITE_EDITION` alone is enough only when the new Event gets its OWN Edition AND that Edition already has a row in the `BRANDS` table (`src/editions.ts`). If the Event's Edition is genuinely new—an identifier not yet in `BRANDS`—`editionBrand()` treats any id absent from `BRANDS` as unknown and silently falls back to the GCB brand (`src/editions.ts:258-275`), and `defaultThemeForEdition()`/`themesForEdition()` in `src/theme/themes.ts` fall back the same way; setting `VITE_EDITION` to that new id therefore builds successfully but ships with Gay Cruise Bingo's wordmark, copy, and Theme set. A genuinely new Edition must get its `BRANDS` row and its `EDITION_DEFAULT_THEME`/Theme-registry entries added in `src/editions.ts` and `src/theme/themes.ts` BEFORE `VITE_EDITION` is set to select it. When the new Event instead reuses an EXISTING Edition, `VITE_EDITION` cannot make these fields match the new Event, because today's brand table hardcodes Event-specific facts as Edition-level static strings: `gcb`'s `metaDescription`/`ogImageAlt` name the July 2026 Trieste-to-Barcelona sailing verbatim (`src/editions.ts:58`, `:61-62`), and `vacay`'s `ogUrl` points at `bodega-bay.fiveacross.app` specifically (`src/editions.ts:121`). A second Event under the same brand (a second GCB sailing, a second Vacay trip) must also edit those fields in `src/editions.ts` as part of this step, or it ships the FIRST Event's dates, URL, and preview identity under the new Event's name. Editions cannot express per-Event static metadata today without this code edit; that is a real gap, not an oversight this runbook can route around. All three fields live in the client bundle, so any of these edits ship with step 4's hosting rebuild—no Cloud Function redeploys for a branding sweep. (Before ADR 0005/#39 removed the crawler `share` Function, changing its baked OG copy was the one case that also redeployed a Function; that surface is gone.)
4. Point traffic at the Event. Single-Event build (legacy shape): register a reviewed named target before building—its complete Firebase web-app identity, `VITE_EVENT_ID=<new-id>`, explicit `VITE_EDITION`, and explicit `VITE_ADULT_CONTENT` live in `scripts/build-target.mjs` and its ignored `.env.<target>` file. Add the matching package commands, then deploy with `npm run deploy:<target>:hosting`; do not use an ambient `.env.local` or an unqualified deploy. Hostname-resolved build (#543): no rebuild of the React app—leave `VITE_EVENT_ID` empty in the deployed bundle and seed a `hostnames/{host}` routing doc (`eventId`, `status: 'active'`, `edition`, `canonicalHost`, and—for an Event whose pool holds no explicit Prompts—an explicit `adultContent: false`) for the new origin instead. "No rebuild" here assumes the routing doc's `edition` already has a `BRANDS` row: `setActiveEdition()` (`src/editions.ts:265-267`) rejects any id absent from `BRANDS` and falls back to `DEFAULT_EDITION` (`gcb`, `src/editions.ts:31`, `:275`), so pointing this branch at a genuinely new Edition still serves Gay Cruise Bingo's identity—not the new Event's—until step 3's `BRANDS`/Theme-registry code change ships and the shared hostname-resolved bundle is rebuilt with it; only an Event reusing an Edition already registered in `BRANDS` gets a true no-rebuild rollout. That last field is not optional in practice for a tame Event: the resolver un-gates only on a literal `false` (missing or malformed reads as `true`, so every routing document written before #608 keeps its 18+ gate), and the server derivation only ever raises the flag, never lowers it—so a routing doc seeded without it shows the 18+ acknowledgement forever. A single-Event build has a build-time equivalent, `VITE_ADULT_CONTENT=false`—but it is a **seed, not a pin**: it paints the first frame and is then confirmed against `hostnames/{host}` like any other ungated claim, because an opt-out with no channel to withdraw it would mean an Event that could never turn adult without a rebuild. So a single-Event build that wants to stay non-adult **also needs a routing document for its origin**; if none exists, the posture returns to gated on the first successful read. Gay Cruise Bingo sets `VITE_ADULT_CONTENT=true` explicitly. The `--only` scoping remains the established backend-before-Hosting pattern, always through the same named target command.
5. Optionally flip the previous Event to `status: 'archived'` (`src/types.ts`). This retires its pending admin-alert work through the trigger/scheduled backstop, but does not yet enforce a read-only player surface; the rules/archive interlock belongs to the later membership/addressing work.

Rules, indexes, and Functions all ship untouched—a sequential second Event is copy/config only, and no branding edit reaches a Cloud Function anymore (ADR 0005/#39 removed the crawler `share` Function that once carried baked OG copy). Players keep their global identity (`users/{uid}`, avatar, 18+ attestation) and join the new Event, which deals a FRESH Board under `events/<new-id>/boards/{uid}`. There is NO re-deal or square-swap of an existing Board (ADR 0003), NO cross-Event browsing, and NO join codes.

## Recommended migration seam (deferred)

- **Now (v1):** startup still resolves one Event and there is no room-browsing / join-code UI, but #807 has hardened every Event-owned listener, queue, retry, intent, and persisted acknowledgement against stale cross-Event state. That work stands even without a switcher (`specs/event-scoped-client-state.md`).
- **Second Event (sequential):** the runbook above—no rules or logic changes; today's edits are copy/config only: the seed's baked Event metadata (`scripts/seed.mjs:27-30`, `:70-103`), the client free-space text if it changes (`src/data/seed.ts:2`), and the branding sweep (runbook step 3—all client-bundle copy now, so it ships with the hosting rebuild and touches no Cloud Function).
- **IMPLEMENTED (#543, hardened by #807).** `EVENT_ID` is a startup-resolved live binding in `src/firebase.ts`, installed by `bootstrapEventResolution` before `main.tsx` mounts. Synchronous helpers may read it lazily; an async public operation captures it at entry and passes that value through every await so work begun in A cannot redirect into B. Event-owned React and module state additionally carry the Event in their lifecycle keys (`specs/event-scoped-client-state.md`).
- **The original plan, for reference:** keep `EVENT_ID` a startup-resolved constant and resolve the id once at startup in `src/firebase.ts:48`—from the HOSTNAME (one subdomain per Event) or per-site build env, falling back to `VITE_EVENT_ID`. That variant really is a one-file change: hostname/env resolution touches no routing, every consumer is a lazy helper function that reads the exported symbol per call, and the test suites already substitute it wholesale (`vi.mock('../firebase', …)` with a stand-in `EVENT_ID`—`'med-2026'` at `src/data/w2-tally.test.ts:32`, `'test-event'` at `src/components/w1-prompt-pool.test.tsx:31`), so there is no signature churn in the seven importing modules. An `/e/<eventId>` PATH PREFIX is the more invasive alternative, not a `firebase.ts`-only change: the SPA registers only absolute routes (`/`, `/feed`, `/leaderboard`, `/items`, `/admin`—the frozen tab table, `src/components/tabs.ts:29-38`) and wildcard-redirects anything unmatched back to `/` (`src/App.tsx:47-51`), so `/e/foo` would be swallowed by the fallback and every tab `NavLink` (`src/components/TabBar.tsx:16`) would strip the prefix on navigation. Supporting the prefix means parsing it out of `location.pathname` before the router exists AND threading it into a `<BrowserRouter basename>` in `src/main.tsx:71` (mounted with no basename today) so the Route table and NavLinks re-base together—router + nav work across multiple files, plus a sweep of prefix-unaware absolute URLs (OG/share links)—for no benefit over subdomains here.
- **SUPERSEDED IN PART (#799).** Read the bullet above as a rejection of path addressing for **live, installable Events on a namespace apex**, which is the only case it was weighing when it was written—and not as a rejection of path addressing generally. [ADR 0009](../docs/adr/0009-event-resolved-from-hostname.md) § "Why not one origin with a path prefix" re-derived the same rejection on stronger grounds (installed-app isolation is a property of the ORIGIN, not routing churn), and in doing so narrowed it—but narrowed it precisely, and this line must not be read as "those costs vanish off the apex." What actually changes per surface: a **read-only archive** installs nothing, captures nothing and caches nothing durable, so the isolation argument genuinely has nothing left to protect there. A **brand-mirror host** is different: its path Events keep camera capture, durable origin-scoped storage, a shared quota, cross-Event eviction and all-or-nothing site-data clearing. Those couplings are **explicitly accepted and bounded** by `specs/path-addressing-and-root.md` (D2 accepts the shared camera grant so a break-glass surface can still capture proof; D4 requires per-Event namespacing of every key the app controls and accepts what the browser arbitrates), **not absent**. What the mirror does give up, to buy back the rest of the isolation argument, is installability: D4 makes an origin that does path addressing non-installable throughout, flagship included. `specs/path-addressing-and-root.md` is now the governing contract and reaches the opposite conclusion for two cases this bullet never considered—**archived Events parked at a path on a namespace apex**, and **every Event served from a brand-mirror `*.vercel.app` host**, where subdomains are not a purchasable alternative at all because that namespace is Vercel's rather than ours. The apex case is **archived-only**: an active Event cannot be made read-only only for one same-origin pathname at the Firestore boundary, so #134 changes the routing documents, `apexPath`, and `EventDoc.status` atomically before that path serves. The routing-churn inventory above (the frozen tab table, `App.tsx`'s wildcard fallback, the `NavLink` re-basing, the absolute-URL sweep) remains accurate and is the implementation cost that spec's basename decision accepts; what no longer holds is "for no benefit over subdomains here," because the canonical root now has a create-Event page to serve and archives have no subdomain worth spending.
- **Enforceability clarification (#799).** “Installs nothing” and “non-installable” in the preceding historical summary mean the product serves no manifest or app-provided install affordance and refuses every path-addressed route in an installed/standalone context. They do **not** claim a web app can disable browser or OS chrome, which can create a wrapper independently; `specs/path-addressing-and-root.md` D4 is the governing, enforceable contract.
- **Explicitly NOT the product seam:** an in-session Event picker, room browser, join codes, or the declined cross-Event admin hub. #807 implemented the Event-keyed state prerequisite without authorizing any of those surfaces. A future switcher remains a product and bootstrap decision: it must re-run resolution-owned Edition/adult-content/canonical-host/analytics installers as well as consume the now-safe client-state boundary.
