# w2-feed-moments — Feed = Proofs + Moments (first BINGO / Blackout / First to BINGO; bare Marks post nothing)

The Feed is the live, public stream the group watches together (ADR 0002) — the honor-system source of truth in place of server verification. Proofs already flow into it (`specs/w2-proof-capture.md`); this ticket adds Moments and merges the two into one newest-first stream. A **Moment** broadcasts a big social beat — a BINGO, a Blackout, or the First to BINGO — and, unlike a Proof, carries **no attached evidence**: it marks *that* something happened, not what it looked like. A **bare Mark posts nothing to the Feed** (ADR 0002): only a Proof or a Moment appears there; a plain honor Mark self-publishes to its per-Prompt Tally (`specs/w2-tally.md`) and nowhere on the Feed.

This ticket landed after #16/#18, so two contracts already shipped: the `MomentDoc` type (`src/types.ts` — `kind: 'bingo' | 'blackout' | 'first_bingo'`, plus `uid`, `displayName`, `photoURL`, `createdAt`; no media, no `proofId`) and the `events/{eventId}/moments/{momentId}` rules block (`firestore.rules`). The `MomentDoc` type is read, not modified. The moments rules block was designed strictly within as it shipped, then **tightened in the PR #99 review rounds** (Codex P2): the create rule now bounds `createdAt` near `request.time` (finding 3) and the admin update path was removed for full immutability (finding 4). A second review round hardened the client-side broadcast machinery (findings A–D: held-broadcast revalidation, the account-switch data race, cache-hydration baselines, and the regained-line witness). See § Review-round hardening (PR #99).

**The broadcast source moved to the action path (issue #104).** PR #99's broadcast machinery drove the public Moment write off Board's SNAPSHOT DIFFING (the `wasBingo`/`wasBlackout` edge refs + a component-held `pending` ref). That coupling was the root of all five review rounds, and it had a residual bug: a win crossed while a gate was still closed was HELD in a Board-lifetime ref, so a Player who left the Card route before the gate opened lost the Moment forever (the ref died on unmount; the returning board baselined the already-standing win). Issue #104 moves the broadcast decision OFF snapshot diffing and ONTO the mark that completed the win — the completing write path's transition verdict (`setMark`'s, consumed in `doMark`; `attachProof`'s, reported via ProofSheet — PR #110 round 2 finding 1), enqueued into a MODULE-scope pending queue that survives unmounts. The snapshot machinery now serves ONLY the cosmetic Celebration animation. See § The action-driven broadcast model (issue #104), which also states which PR #99 hardening invariants are PRESERVED (on the action path), which became MOOT (they were artifacts of snapshot diffing), and which are NARROWED.

## Data model (merged-main type + rules, #16/#18)

A Moment is a top-level doc under the Event: `events/{EVENT_ID}/moments/{momentId}`. The shape is exactly `MomentDoc` minus its `id` (the `id` is the doc id, surfaced on read by `momentConverter`). The rules block allows:

- **create** if `isOwner(request.resource.data.uid)` (a forged uid is denied — you can only broadcast your own beat), the `kind` is one of the three `MomentKind`s, `displayName` is a non-empty ≤100-char string, and `createdAt` is a number **within +60s / -24h of `request.time`** (the same near-now window proofs uses — PR #99 finding 3) so a bad clock or a forged far-future stamp cannot pin a Moment above all Feed activity forever.
- **read** if signed in (public — the Feed everyone watches; no anonymity, ADR 0002).
- **update** — **none. A Moment is fully immutable** (PR #99 finding 4): the update path was removed. `MomentDoc` carries no moderation/status field, so an admin update could only rewrite content — and an admin-writable update defeated the create-only dedup (an admin-player's repeat broadcast became an authorized overwrite). Moment moderation is delete-only; a moderation/status field is deferred to #37/#41.
- **delete** if `isAdmin(eventId)` or the owner. Since #377 the owner-delete arm is actually *used*: it is half of the retraction path (delete + tombstone) in § Retracting a published win.

Two facts about that block are **load-bearing to this design and pinned honestly**:

1. **The doc id is bound to the payload kind on create (#103)** — the event singleton `first_bingo` must carry `kind: 'first_bingo'`, and every other id must equal `${uid}-${kind}`, mirroring the writer's deterministic scheme (`src/data/moments.ts`); see § Once-only semantics. Combined with **update being denied for everyone** (PR #99 finding 4), a second write to an already-written deterministic id is a doc-exists `update`, which no one — not even an admin — can do, so it is denied. This is the strongest dedup the rules allow, and it is what the writer relies on.
2. **The create rule has no `hasOnly()`/`keys()` constraint**, so it does **not** reject a Moment that carries extra `mediaURL`/`proofId` fields. The ADR 0002 "a Moment carries no evidence" guarantee is therefore a **writer + type** contract — `src/data/moments.ts` writes exactly the `MomentDoc` fields, and `MomentDoc` has no media/`proofId` field — **not** a rules-layer one. The rules test pins the actual (permissive) rule behaviour so no one mistakes the rule for enforcing it.

## The change

- `src/data/moments.ts` (new) — three broadcast functions, `broadcastBingo` / `broadcastBlackout` / `broadcastFirstBingo`, each writing one `MomentDoc` row via a raw (converter-free) ref in the mark path's offline-queueable, fire-and-forget style (mirroring `setMark`): the write pends durably in the persistent cache when offline (ADR 0006) and never blocks the celebration UI, and an online rejection is logged (never silently swallowed). All three share ONE write path, `writeMomentOnce` (round 3 finding C): a `getDocFromCache` pre-check skips the write entirely when the Moment already exists locally — otherwise a duplicate deterministic-id `setDoc` would optimistically overwrite the cached copy and its refreshed `createdAt` would pin the old Moment to the Feed top until the server's denial (indefinitely while offline). The payload is `Omit<MomentDoc, 'id'>` — no media, no `proofId`, ever. `displayName` is bounded through the shared `markerDisplayName` helper (imported from `src/data/attribution.ts`, unchanged) to the rules' non-empty ≤100 contract, so a broadcast can never be rejected for a malformed name. Plus `hasPriorBingoWitness(uid)` (round 2 finding D): a cache-only, never-rejecting read of the player's own `${uid}-bingo` Moment doc — the durable witness of a prior win Board consults before queueing a ceremonial First-to-BINGO candidate (see § Review-round hardening (PR #99)). Plus (issue #104) the **module-scope pending-Moment queue** — `enqueueWinMoments`, `enqueueFirstBingoMoment`, `peekPendingMoments`, `clearPendingMoment`, `dropPendingWins`, `pendingActionGeneration`, `firstBingoCandidateCurrent` (+ a test-only `resetPendingMoments`) — a per-app+uid `Map` of `{ bingo, blackout, firstBingo }` flags, keyed the same durable way `markChains` is in `api.ts`, plus a SEPARATE per-uid monotonic **action generation** map (PR #110 finding 1: bumped by `dropPendingWins` ONLY on an actual BINGO fall — round 4 narrowed it from every-unmark, because its sole consumers are the ceremonial machinery and a non-falling unmark or a blackout-only fall does not change whether the bingo stands or un-witness anything; unconditional bumping suppressed a legitimate First-to-BINGO whose witness read was mid-flight — and never reset by an emptied flags entry, so a stale async continuation can be detected). `dropPendingWins` is the fall-observer clear (clears the fallen kinds — a bingo fall also drops the ceremonial candidate and bumps); `clearPendingMoment` is the drain fire-clear (never bumps). The ceremonial candidate is STAMPED with the generation at enqueue, and `firstBingoCandidateCurrent` tells the drain whether it is still current (PR #110 round 2 finding 3 — a moved generation means the drain kills it, never fires it). A win a mark COMPLETES is enqueued here (off the completing verdict — `setMark`'s in `doMark`, `attachProof`'s via `onAttached`); the flags survive Board unmounts and route changes, so the drain that fires them can run from a later mount (see § The action-driven broadcast model).

## Once-only semantics (deterministic ids + the create-only rule)

The design picks the **strongest dedup the rules allow** and layers it under the mark's transition verdict + the module-scope pending queue (issue #104; the same guarantees held under PR #99's snapshot edge refs, which the action path replaced):

- **BINGO — once per CARD (#372; was once per Player).** Broadcast on the TRANSITION into having a bingo on a Day's board — `setMark`'s `bingoTransition` verdict (`previousBingoCount === 0 && bingoCount > 0`), the synchronous fact that THIS mark completed the first line on that card — never on every completed line or every render. Doc id `${uid}-bingo-d${dayIndex}` on a daily event: the dedup scopes to the (Player, Day) pair, so a second Day Card's bingo posts its own Moment while re-marking the same card cannot. The day-less `${uid}-bingo` remains the legacy single-board form (one card the whole Event, so per-Player IS per-card there), with a cache-only legacy same-day dedupe on the writer. A re-fire *for the same card* (a lose→regain in one session, a reload with a bingo already standing, or a second tab) either never crosses the transition (an unmark can only reduce the mask, and a further mark while a line stands reports `bingoTransition: false`), is skipped by the writer's write-once cache pre-check (round 3 finding C — the Moment is already in the local cache), or hits the deny-all `update` rule on the existing id and is denied (PR #99 finding 4: denied for everyone, admins included).
  - **Why it changed.** The once-per-Player id predates daily cards: with ONE board per Player for the whole Event, per-Player and per-card were the same thing. Daily cards (#246) gave each Day its own board and its own bingo transition, so from then on every bingo after a Player's first re-targeted that one immutable doc, hit the deny-all `update`, and was swallowed as the designed once-only path — the celebration fired on each Day while the Feed silently received nothing (#372). Blackout hit the identical wall and was fixed the same way one ticket earlier (#267); bingo was simply left behind.
  - **Prior-win witness.** `hasPriorBingoWitness` consequently has no single doc to read: given the Event's `dayIndexes` it probes each non-excluded Day's own `${uid}-bingo-d${d}` (cache-only, bounded by the schedule), and still honors the legacy day-less doc for pre-#372 winners. This makes the #288 tutorial exclusion EXACT rather than inferential — a warm-up win owns its own id, so it is simply never probed, and the tutorial branch's singleton consult is not needed to compensate for a shared id.
  - **The singleton fallback still applies, via self-write.** The #332 birth-time race lands on the day-scoped id too: a concurrent drain can write THIS win's own `${uid}-bingo-d${actedDay}` while the witness read is in flight. A doc recognized as this action's own write is skipped rather than read as prior evidence, and the read then falls through to the `first_bingo` singleton consult — the same conservative decider the day-less path uses — instead of declaring witness-clean off our own drain. Recognition needs BOTH halves (#372, Codex P2 on #386): `selfWriteDayIndex` pins WHICH doc this action writes, `selfWriteGeneration` pins WHEN. The generation alone is too coarse — it bumps only on a bingo FALL, so a Day-3 win and a later Day-5 win with no fall between share one, and the Day-3 doc would be waved through as the Day-5 action's own write. The id alone is too coarse the other way — a same-Day regain targets the same doc, and only the generation (bumped by its fall) tells the two apart.
- **Blackout — once per CARD (#267; was once per Player).** Broadcast on `setMark`'s `blackoutTransition` verdict (`isBlackout(next) && !isBlackout(cells)`). Doc id `${uid}-blackout-d${dayIndex}` on a daily event — the dedup scopes to the (Player, Day) pair, so a second Day Card's blackout posts its own Moment while re-marking the same card cannot; the day-less `${uid}-blackout` remains the legacy single-board form (one card the whole Event, so per-Player IS per-card there), with a cache-only legacy same-day dedupe on the writer. On a real 5×5 board the first-line (BINGO) transition always precedes the full-card (Blackout) transition across marks, so a Blackout never suppresses the earlier first-BINGO broadcast.
- **First to BINGO — once per Event, ceremonial and self-reported (ADR 0001).** Doc id is the Event-**singleton** `first_bingo` (it can never collide with a per-Player id: those use a hyphen before the kind and a uid prefix). Board derives it client-side from the known-players roster: it claims First to BINGO only when the roster is **server-confirmed** AND, as far as that confirmed view shows, **no other Player has a `firstBingoAt` yet** (while the roster is unconfirmed the claim is HELD, not guessed — PR #99 finding 2). The singleton id makes it structurally once-per-Event: the first create wins; a later create becomes an `update` and is denied.

  **The regained-line witness (round 2 finding D).** `firstBingoAt` is BY DESIGN volatile — `computeMark` clears it when the last line falls — and the schema deliberately carries no durable first-win field. So the roster check alone would let a Player who had a line, unmarked it, and regained one later mint the event singleton despite not being first EVER (their own history is invisible to `othersBingoed`, which only inspects OTHER players). The fix uses **the Moment collection as its own memory**: the Player's own bingo Moment is create-only and immutable, so its presence is a durable witness that a prior win existed even after the line was unmarked. Since #372 that witness is PER CARD — on a daily Event `doMark` hands over the schedule and the read probes each non-excluded Day's own `${uid}-bingo-d${d}`, falling back to the legacy day-less `${uid}-bingo` for pre-#372 winners (see § BINGO above for the self-write/singleton handling). Before enqueuing a ceremonial candidate for a bingo-completing mark, `doMark` calls `hasPriorBingoWitness(uid, { dayIndexes, excludeDayIndexes, selfWriteGeneration, selfWriteDayIndex })` — a cache-only `getDocFromCache` read (instant, offline-safe, and same-session writes are visible via latency compensation): witness present → the ceremonial candidate is NOT enqueued (the regained line still enqueues + attempts the plain bingo Moment, which the write-once cache pre-check skips, or the create-only rule denies on a cold cache — fine); cache miss (fresh device) → fall back to the roster check at drain time. **Narrowed residual (accepted, ADR 0001):** a fresh-device, cache-cold, roster-blind regained line — the Player's prior win is neither in this device's cache nor visible as another player's `firstBingoAt` — can still claim the singleton. At friend-group scale this is acceptable for a self-reported ceremony; the honour is recorded, never adjudicated.

**The id↔kind binding makes the deterministic ids enforceable (create-side, issue #103).** The three ids above are a real dedup only if the rules hold a caller to them. The moments create rule binds the doc id to the payload kind: the event singleton `first_bingo` must carry `kind: 'first_bingo'`, and every other id must equal `${uid}-${kind}` — plus, for the two PER-CARD kinds (blackout since #267, bingo since #372), the day-scoped `${uid}-${kind}-d${dayIndex}` form, accepted only when the payload's integer `dayIndex` matches the id AND indexes a real scheduled Day — the writer's scheme exactly. `first_bingo` is deliberately excluded from the day-scoped form: it is the event-wide singleton, and a day-scopable id would mint one ceremony per Day. Before #103 the id was fully caller-chosen, so any signed-in Player could create `moments/first_bingo` with a *mismatched* kind (e.g. `kind: 'bingo'`). The read-side filter (`hasCanonicalMomentId`) hid such a doc from every Feed, but because a Moment is **fully immutable** (finding 4 — no update path) the squatted singleton could never be overwritten, so the legitimate First-to-BINGO create — which targets that same id — was denied **forever** as a doc-exists update: a denial-of-ceremony squat. (Only `first_bingo` was exposed: the per-Player ids embed the writer's own uid and create already requires `isOwner`, so a peer cannot squat another Player's `${uid}-bingo` / `${uid}-blackout`.) Binding the id to the kind on create closes the hole; the read-side filter (§ Review-round hardening, "Canonical Moment ids before render") **remains as defense-in-depth**, enforcing the same deterministic ids on the render path so read and write never diverge.

**The race, documented honestly.** First to BINGO is a ceremony, not a verified fact (ADR 0001). Under an offline/latency race two Players may each briefly believe they are first — each optimistically shows their own local `first_bingo` Moment from the persistent cache — but exactly one create reaches the server (whichever syncs first), the other is rolled back to the winner, and both clients converge. At friend-group scale this is acceptable; the Feed's `first_bingo` reflects who broadcast first, which under a bad offline race can differ from the Leaderboard pin's earliest-`firstBingoAt`. The honour is recorded, never adjudicated.

## Retracting a published win (#377)

Once-only says a win posts **at most once**. It said nothing about a win that stops standing: `moments/{momentId}` has no `update` path, and although the rules already permitted an owner to delete their own Moment, nothing in the client ever called it. `dropPendingWins` covered only the *pre*-publish case (a win completed then unmarked before its gate opens never posts), so **after** publish, unmarking the completing square left the Moment standing in the Feed forever. Decided with @nathanjohnpayne on [#372](https://github.com/nathanjohnpayne/gaycruisebingo/issues/372#issuecomment-4994900828): the Feed should not claim a bingo the card no longer supports.

**The shape is retract-ONCE, not delete-then-repost — and that distinction is the whole design.** The deterministic per-card id is the strongest anti-gaming primitive in the system (§ Once-only semantics): `${uid}-bingo-d${dayIndex}` can post exactly once per (Player, Day), create-only, immutable, enforced server-side. A bare delete path breaks that bound — retract-then-re-mark recreates the same id with a fresh `createdAt`, and the Feed sorts by `createdAt` desc, so mark/unmark/re-mark would bounce one win back to the **top** of the Feed repeatedly: an engagement-farming loop introduced by the very feature meant to keep the Feed honest.

So a retraction **deletes the Moment and creates a tombstone at the same id**, and the moments create rule denies any create whose tombstone exists. That (Player, Day) win is then **spent** — retracted once, never repostable.

**Worth stating plainly so the scope stays honest: retraction does nothing against deliberate gaming.** A player claiming squares they did not earn simply does not unclick. Retraction's value is *Feed truth* for honest self-correction, and it must not cost the once-per-card bound to get it.

### The tombstone (rules)

`events/{eventId}/momentRetractions/{momentId}` — id-mirroring the Moment it retracts, so "is this win spent?" is one `exists()` lookup at a known path.

- **create** if `isOwner(request.resource.data.uid)`, the payload is exactly `{ uid, kind, dayIndex?, createdAt }` (`hasOnly`), `kind` is one of the two **per-card** kinds, `createdAt` is in the house +60s / -24h window, and the doc id is bound to the payload by the **same** discipline the moments create rule uses: `${uid}-${kind}`, or the day-scoped `${uid}-${kind}-d${dayIndex}` when the payload's integer `dayIndex` matches the id and indexes a real scheduled Day. All four canonical retractable forms are therefore reachable — the two per-card ids and the two legacy day-less ones — and nothing else is. A peer cannot pre-tombstone another Player's win (the id embeds the payload uid, which must be the caller): that would be a denial-of-win squat, the same shape #103 closed on the create side.
- **read** if signed in — public, like the Feed it describes. Nothing renders it, but a client may want to know a win is spent before optimistically re-posting it, and it carries no information the Moment did not already publish.
- **update** — none. A tombstone is a permanent fact, exactly like the Moment it replaces.
- **delete** if `isAdmin(eventId)` — **not** the owner. An owner-deletable tombstone is just the delete-then-repost loop with an extra step. Admin delete is the moderation escape hatch for a genuine mis-retraction, mirroring the write-once per-day honor doc at `days/{dayIndex}/meta/{dayIndex}`.

The moments create rule gains exactly one clause — `!exists(.../momentRetractions/$(momentId))`, last in the conjunction so `&&` short-circuiting keeps the extra document read off every create that fails a cheaper clause. Keyed on the **Moment id** rather than on kind/Day, it covers all four id forms without re-deriving anything. `first_bingo` can never carry a tombstone (`kind` excludes it, and the singleton id matches no `${uid}-${kind}` form), so the ceremonial create path is untouched: the event-wide honor keeps its existing admin-delete-only moderation and gets no per-Player retraction lever.

**Accepted cost, decided up front:** a genuine mis-unclick (unmark by accident, then re-mark) loses that Day's Moment permanently. This fails in the safe direction — silence, never a false claim — should be rare, and an admin can delete the tombstone for a real correction.

### The client path

`retractPublishedWins(uid, fell)` (`src/data/moments.ts`) is the published-side twin of `dropPendingWins`, called with the **same** `fell` verdict at the **same** two fall-observer sites — Board's unmark verdict in `doMark`, and the cells effect's passive falling edge — so the pre- and post-publish halves of one fall can never drift apart. Fire-and-forget: a retraction never blocks the unmark it follows.

- **Delete + tombstone ride ONE `writeBatch`.** All-or-nothing: a crash or denial between two separate writes would leave the win deleted-but-not-spent (freely repostable — the exact loop this closes) or spent-but-still-displayed. Offline-queueable like every other write here (ADR 0006).
- **Nothing is retracted unless the Moment is actually in the local cache.** Load-bearing, not an optimization: minting a tombstone for a win that never published would spend the (Player, Day) slot without a Moment ever having existed, permanently silencing a legitimate future win. The cache is a trustworthy witness because `useMoments` subscribes to the whole moments collection, so a published Moment is cached on any running client. A cold-cache device simply does not retract (the acting device does) — that residual is silence, never a false tombstone.
- **BOTH id forms are probed**, because both can legitimately hold the live Moment for a (Player, Day): the per-card id, and the **legacy day-less** one. The latter is not hypothetical — the writers' legacy same-day dedupe (#267/#372) means a Day's live Moment can genuinely sit at `${uid}-${kind}` with a day-stamped payload. On a daily Event the legacy doc is retracted only when its payload's `dayIndex` names the fallen Day (a doc stamped for a different Day describes a different card and must survive); its tombstone mirrors **that** id form, day-less. A day-less caller (legacy single-board Event) retracts the day-less id unconditionally and probes no day-scoped form.
- **The passive falling edge retracts only off a SERVER-CONFIRMED board** (`boardConfirmed && initialized.current`). A retraction is permanent, so — unlike the queue drop beside it — it must not fire off a cache-only snapshot, where a stale local copy can briefly show a win gone that the server still holds. Dropping a *queued* flag off the same snapshot stays safe (the drain revalidates and the flag re-enqueues on a fresh rising verdict), so that behaviour is unchanged. The player's own unmark needs no such gate: it is their deliberate action and its verdict is the authority on what fell.
- **`writeMomentOnce` gained a retract-once pre-check**, the exact twin of the write-once one and for the same latency-compensation reason: the rules deny the create server-side, but Firestore applies the optimistic write **locally** first, so a re-marked, already-retracted win would flash back to the top of the Feed until the denial — indefinitely while offline, which *is* the farming loop the tombstone exists to close. Cache-only and best-effort: the tombstone is cached on the device that wrote it (latency compensation), which is the device a re-mark realistically comes from; a cache miss falls through to the server, which denies.

### Explicitly OUT of scope: the honor pin stays write-once (accepted residual)

`days/{dayIndex}/meta/{dayIndex}` is create-only with no update path and admin-only delete, and it **stays that way**. It is a permanent first-claim; write-once is what makes the honest race sound (ADR 0001); and a wrong pin is both rare and already admin-deletable.

**So a retracted bingo leaves its Day honor pinned.** That is an accepted residual — documented here, not fixed — because opening an owner-delete path on a public, permanent doc is not worth the rare correction. The cruise-wide `firstBingoAt` on the player row is self-writable and *does* roll back when the last line falls, so it will diverge from the pinned honor after a retraction; same accepted residual. The ceremonial `first_bingo` singleton is likewise untouched (it has no tombstone path at all), so a retracted first win keeps its Feed ceremony.

One further consequence worth naming: `hasPriorBingoWitness` reads the Moment collection as its own memory, so a retracted Moment stops being a witness. A later bingo on another Day can therefore read witness-clean and mint a ceremonial candidate it would previously have been suppressed for. The `first_bingo` singleton is create-only, so an already-claimed ceremony still cannot double-post, and the drain-time roster gate still applies — the exposure stays inside the ADR 0001 honor-system posture already documented for the fresh-device residual.

### The open question, stated honestly

The flap vector is reasoned from code inspection, **not measured**. PostHog carries `mark_square` and `bingo` events, so whether mark/unmark flapping happens at all is worth checking. Not a blocker — the tombstone is safe regardless — but if nobody flaps, a simpler shape may be defensible.

## The action-driven broadcast model (issue #104)

**Broadcast source = the mark that completed the win.** PR #99 drove the public Moment write off Board's snapshot diffing: a `wasBingo`/`wasBlackout` edge ref detected a transition across renders, a component-held `pending` ref held it while a gate was closed, and `flushPending` fired it once the gate opened (revalidating the win against the current cells). Five review rounds all traced back to that coupling, and it left one residual bug (issue #104): the `pending` ref was **component-lifetime**, so a win crossed while a gate was still closed was lost if the Player left the Card route before the gate opened — Board unmounted, the ref was discarded, and the returning board baselined the already-standing win.

Issue #104 re-homes the broadcast on the **action path** (hardened by the PR #110 review — see § PR #110 hardening below):

1. **The write paths return the verdict.** `computeMark`/`setMark` (api.ts) and `attachProof` (proofs.ts — PR #110 round 2 finding 1; the transaction callback returns it, so a retry reports the committed fold) — both return-shape changes only — report `bingoTransition` / `blackoutTransition`: the rising edge THIS mark crossed, computed inside the folded next-state against the prior cells. `doMark` already consumed `res.bingo` for analytics; ProofSheet reports its result to Board via `onAttached`.
2. **The completing mark enqueues — behind the shared attribution guard, through one pipeline.** `toggle` and `doMark` bail outright (no write, no sheet, no enqueue) unless the rendered board is attributable to the active uid — the SAME `cellsAttributable` derivation (`board.uid === uid`) the Celebration baseline uses (PR #110 finding 2: during an account switch a tap can land on a render still showing the previous uid's board). Both completing paths — honor (`doMark` → `setMark`) and proofed (`ProofSheet` → `attachProof` → `onAttached`) — feed `broadcastWinVerdict`, which on a rising edge enqueues the matching kind(s) into a **module-scope pending queue** (`src/data/moments.ts`, keyed by app+uid like `markChains`); the ceremonial first_bingo candidate is enqueued after `hasPriorBingoWitness` — an ASYNC read guarded by the **action generation token** (PR #110 finding 1, P1; recheck corrected in round 2 finding 2): the continuation enqueues only if the per-uid generation captured before the await is unchanged — every OBSERVED BINGO FALL bumps it (round 4: a non-falling unmark or a blackout-only fall does not, so a ceremony whose bingo stands continuously survives them). (It is deliberately NOT gated on the pending bingo flag — a concurrent drain can legitimately FIRE the plain bingo mid-read, and that clear must not forfeit the ceremony; standing-ness is the drain's job — and NOT gated on the current account — round 3 finding D: the queue is uid-keyed, so the enqueue cannot leak and the candidate waits for the acted account's return; the shared `revalidateAfterAwait` helper makes both checks structural.) This birth-time read is the SOLE witness site (round 3 finding A). The candidate is stamped with the generation at enqueue (round 2 finding 3a). The queue is module state, so it **survives Board unmounts and route changes** — the headline fix. **The birth-time-witness race (#332):** a concurrent gate-open/snapshot drain can broadcast THIS win's own plain bingo while the witness read is in flight, and the just-written `${uid}-bingo` doc must not read as a prior win and suppress the ceremony (observed ~2/8 under e2e stress). `writeMomentOnce` therefore stamps the current action generation whenever it genuinely writes `${uid}-bingo` (its cache pre-check found no existing doc — so a regain's re-broadcast, which the pre-check skips, leaves no stamp), and `hasPriorBingoWitness` — passed the caller's pre-await generation via `selfWriteGeneration` — treats a found doc with a matching stamp as SELF-evidence: it falls through to the first_bingo singleton consult (claimed → still witnessed; absent → witness-clean, the drain's roster gate decides) instead of returning witnessed. A stamp from another generation, a stampless regain, and a caller that passes no generation (the confirm pipeline) all keep the plain prior-win read. **Cold-cache residual (accepted, same class as the fresh-device residual above):** on a tab whose cache is cold for an OLDER server-side `${uid}-bingo`, the drain's pre-check misses, stamps, and optimistically writes — the server will deny the duplicate create, but a witness read completing inside that pre-denial window reads the pre-existing win as self-evidence and can mint a candidate for what is really a regain. The exposure is bounded by the same structural backstops as the documented fresh-device residual: the drain-time roster gate still applies, and the `first_bingo` event singleton is create-only, so an already-claimed ceremony can never double-post; a truly unclaimed singleton on a cold-cache regain is the accepted ADR 0001 honor-system posture.
3. **The queue drains when the gates open — revalidating at fire time.** `drainMoments` (Board) reads the queue and fires each held Moment whose gate is open: identity-known for all three, a server-confirmed roster additionally for first_bingo (re-deciding `othersBingoed` against it). Before ANY publish it **revalidates the win against the freshest attributable cells** (PR #110 finding 3, restoring the PR #99 round-3 invariant on the queue path): `hasBingo`/`isBlackout` recomputed, a NON-EMPTY attributable board required (`isBlackout([])` is vacuously true — the empty-board guard is load-bearing again). The completing action passes its own folded `res.cells` (the render-current snapshot has usually not echoed yet); gate-open and snapshot drains use the render-current attributable cells. On revalidation failure the drain **HOLDS, never drops** — a drop would race the latency-compensation echo and re-lose held wins, the #104 bug class; the CLEARS for fallen wins belong to the fall's observers (step 4). The CEREMONIAL branch is fully SYNCHRONOUS at publish time (round 3 findings A + B): it kills a candidate whose generation moved since enqueue (`firstBingoCandidateCurrent`, round 2 finding 3a), then decides the survivor — publish-time `othersBingoed` against the roster AS OF THIS DRAIN, fire or decided-and-lost — and consumes it in the SAME synchronous block, so no async gap exists between the roster decision and the write. There is deliberately NO drain-time witness re-read (round 3 finding A removed round 2's): a roster-held original win fires its plain bingo in an EARLIER pass, so any later re-read sees this pipeline's OWN `${uid}-bingo` Moment and would suppress the very ceremony that win raised; the prior-win question belongs to BIRTH time (step 2), the only moment it is answerable without self-interference. Drain attempts run from `broadcastWinVerdict`, from the gate-change `useEffect` (`identityKnown`/`rosterConfirmed`), and from **every attributable board snapshot** (the cells effect) — which is how a win held across an unmount posts on a later mount, once its board arrives to revalidate against.
4. **Snapshot diffing serves the Celebration UI + the fall observers.** The `wasBingo`/`wasBlackout` refs + celebrate `useEffect` fire the local animation (no direct public writes), and the same effect now also OBSERVES passive falls (PR #110 finding 3): a listener snapshot showing a previously-standing win gone (bingo/blackout true→false — another tab unmarked, or a rules rollback) clears the corresponding queued flag via `dropPendingWins`, which also bumps the action generation. `doMark`'s unmark verdict is the other fall observer. `localActionsPending` and the component-held `pending` ref remain removed.

### PR #110 hardening (Codex review of the action path)

The PR #110 review ran two rounds on the queue machinery. Round 1 surfaced one P1 and two P2s; round 2 surfaced three more P2s — one a regression the restructure introduced (the proofed path), one correcting round 1's own over-tight prescription, one a ceremonial-staleness gap. All fixed:

- **The stale witness continuation (round 1, P1; recheck corrected in round 2 finding 2).** Between `await hasPriorBingoWitness()` and its continuation the pending win can change: the player unmarks and loses the bingo, the unmark verdict drops the queued flags — and a continuation that re-enqueued on the uid check alone would let a later drain publish the IMMUTABLE event singleton for a win that no longer stands. Fixed with the **action generation token**: `pendingActionGeneration(uid)` (moments.ts) is monotonically increased by `dropPendingWins` on an OBSERVED BINGO FALL (round 4 narrowed the bump — see below) and kept in a map separate from the flags so an emptied-then-recreated flags entry cannot reset it. The continuation captures the generation immediately before the await and enqueues only if it is unchanged. Round 1 ALSO required the pending bingo flag to still stand; **round 2 finding 2 removed that flag recheck as over-tight**: a concurrent gate-open/snapshot drain can legitimately FIRE the plain bingo mid-read — a clear that says the win STOOD, not that it fell — and the recheck forfeited the ceremony for exactly that healthy case. The token still catches every interleaved BINGO fall (all bingo-fall clears bump); whether the win still STANDS at publish is the drain's fire-time revalidation (`bingoNow`), not the continuation's job. The round-1 "concurrent drain forfeits the ceremonial" residual is thereby REMOVED, not accepted.
- **The stale-board tap (round 1, P2).** During an account switch the board subscription can still expose the previous uid's board for a render; the snapshot path always guarded with `cellsAttributable`, but the action path initially trusted the setMark verdict without it — a tap in that stale render could fold the previous account's cells into the current uid's board write and broadcast a Moment for the current uid off the previous account's card. Fixed by sharing the guard: `doMark` bails first thing (no `setMark` call at all — the write itself would be wrong) unless `board.uid === uid`; round 2 widened the same guard to `toggle`, so a stale render cannot open a ProofSheet against the wrong card either.
- **The unrevalidated drain (round 1, P2).** A win held behind the identity gate could drain later with no check that it still stood: the module queue is per-tab, but the BOARD changes via the listener — another tab unmarks, or a rollback/deletion snapshot lands — producing no local unmark verdict, so the stale flag survived and the drain published. Fixed on both prongs: `drainMoments` **revalidates at fire time** against the freshest attributable cells (non-empty board required — the round-3 vacuous-`isBlackout([])` guard restored), and the cells effect **observes passive falling edges** (win true→false in listener data) and clears the queued flag via `dropPendingWins`. The drain holds (never drops) on revalidation failure — see the table row above for why. **Zombie residual (accepted):** a bingo/blackout flag whose fall this tab never observes (e.g. the win fell while unmounted, and no later snapshot ever shows it standing) idles un-fireable until reload — revalidation blocks it from ever publishing, so the failure mode is silence, not a false Moment. (The CEREMONIAL flag additionally gets the round-2 finding-3 treatment below, because for it "a bingo stands" can become true again via a regain.)
- **The proofed-path regression (round 2 finding 1, P2).** Removing snapshot-broadcasting silently removed the ONLY emission path `proof_required` wins had: an unmarked-square mark in that mode goes ProofSheet → `attachProof`, never `doMark`/`setMark`, so a proofed mark completing a BINGO/Blackout updated board/player and created the Proof but emitted NO Moment even with the player on-route — a regression vs the pre-#104 snapshot path. Fixed by threading the verdict, mirroring setMark: `attachProof` now RETURNS the same `{ cells, bingo, blackout, bingoTransition, blackoutTransition }` shape (`AttachProofResult`, return-shape change only — the transaction callback returns it, so a retried transaction reports the committed attempt's fold; the write set is untouched), ProofSheet reports it via an `onAttached` callback, and Board routes BOTH completing paths through one `broadcastWinVerdict` pipeline (enqueue → ceremonial witness + generation gauntlet → drain with the folded cells). **The admin_confirmed attach decision (documented):** the attached cell goes `pending` and the win mask (`marked && status !== 'pending'`) excludes it, so an admin-confirmed attach structurally crosses NO transition and fires nothing at attach time. Consistency with the attach-time tally marker (#87) was considered and REJECTED: the marker records WHO MARKED and is deleted by `rejectClaim` on rejection, but a Moment announces a WIN and is IMMUTABLE with no cleanup path — a pending claim an admin then rejects must not leave a permanent win announcement. The admin-confirmed win's Moment belongs to the confirm write — the #41 deferral, now covering BOTH on- and off-route uniformly.
- **The stale ceremonial candidate (round 2 finding 3, P2; the drain-time witness it introduced was REMOVED in round 3).** A firstBingo candidate held behind the roster gate survives unmounts (by design); round 2 worried that after an UNOBSERVED fall and a same-page-load regain the drain would publish the singleton "for the regain". Prong (a) stands: every candidate is **stamped with the action generation at enqueue** (`firstBingoCandidateCurrent`), and the drain KILLS (never fires) a candidate whose uid generation has moved since — an observed BINGO fall invalidates it (round 4 narrowed the bump to actual bingo falls, and every in-app bingo-fall bump also clears the candidate, making the stale-kill belt-and-braces against future bump sites). Prong (b) — a drain-time witness re-read — was WRONG and round 3 finding A removed it: see the round-3 block below for the re-analysis.

**Round 3 (design consolidation — the ceremonial pipeline simplified to birth-time witness + synchronous publish-time revalidation):**

- **Self-suppression (round 3 finding A, P2).** A roster-held ceremonial fires its plain bingo in an EARLIER drain pass; when the roster opens, round 2's drain-time witness re-read found that just-written `${uid}-bingo` Moment in the local cache and suppressed the ceremony — the original win reclassified as its own prior win. (Round 2's read-before-write ordering only covered the same-pass case, and its tests stubbed the witness rather than modeling latency-compensation-faithful cache behavior.) Fixed by REMOVING the drain-time witness re-read: the prior-win question — "is this win a regain?" — is answerable only at BIRTH time, before the pipeline's own plain bingo posts, and that is where the sole witness check now lives (`broadcastWinVerdict`). **The round-2 scenario, re-analyzed:** a regain-born candidate is still suppressed — its OWN birth-time witness sees the earlier posted bingo — and an OBSERVED fall still kills the held candidate (the bingo-fall clear + the generation stamp). The one class that fires under the new design and was suppressed under round 2 is the held ORIGINAL-win candidate after an UNOBSERVED fall + regain — which is, in-tab, indistinguishable from the win having stood the whole time (an unobserved fall is zero signal by definition), i.e. indistinguishable from finding A's must-fire case. Firing is the honest resolution of that equivalence class: the claim was raised by a real, birth-witnessed first win by the SAME player, `othersBingoed` is still re-checked at publish time, and the create-once singleton remains the cross-client backstop — a FALSE singleton (another player's, or a duplicate) remains impossible. The residual beyond that is the pre-existing ADR-0001 roster-blind class, unchanged.
- **Stale roster across the async gap (round 3 finding B, P2).** Round 2's ceremonial branch decided `othersBingoed` synchronously but wrote AFTER the async witness read — a competing earlier `firstBingoAt` delivered mid-read could slip past the decision. Fixed structurally by the same simplification: with no drain-time read, the ceremonial decision and write are ONE synchronous block, and the roster consulted is `feedCtx.current` as of that block — the roster gate is evaluated at PUBLISH time on every drain attempt. The remaining async continuation (the birth-time witness) only ENQUEUES; publish always goes through the synchronous drain.
- **The ＋ proof button bypassed the guard (round 3 finding C, P2).** The per-cell ＋ button (and the TallyBadge who-list open) stop propagation past `toggle`, so a stale previous-uid render could still open ProofSheet and submit an attach under the new uid. Both handlers now carry the same `cellsAttributable` guard themselves — the sweep found no other stop-propagation cell handlers.
- **Post-await revalidation, structural (round 3 finding D, P2).** Round 2's drain-time witness continuation wrote `broadcastFirstBingo` with an actor captured before the read and no uid recheck — a shared-browser account switch mid-read produced a rules-denied write AND a consumed candidate (ceremony lost). Under the simplification that continuation no longer exists (the write is synchronous); the invariant is made structural for what remains: every async continuation revalidates through ONE shared helper (`revalidateAfterAwait(actedUid, capturedGeneration?)` in Board) synchronously after its last await — `generationUnchanged` gates stale actions, `isCurrentAccount` gates steps that touch the current context. **Chosen and documented semantics:** the birth-time ENQUEUE deliberately does NOT require the current account — the queue is uid-keyed, so a candidate enqueued for the acted uid under a switched account cannot leak; it waits and drains when that account returns (nothing a denied write could destroy). Only the immediate DRAIN is skipped on a switched account. Consumption is CONSUME-ON-DECISION: the drain's synchronous ceremonial block fires or decides-and-loses and clears in the same instant; HOLD paths (identity, roster, board, standing-ness, switched account) never consume.

**Round 4 (the bump narrowed to actual bingo falls):**

- **Non-falling unmarks staled valid ceremonies (round 4, P2).** `dropPendingWins` bumped the generation UNCONDITIONALLY on every unmark — so an unmark that left another line standing (`fell.bingo` false: the player still holds a valid BINGO) staled the in-flight witness continuation or made an already-queued candidate kill-on-drain, losing the event-level First-to-BINGO for a win that never fell. Fixed by gating the bump on `fell.bingo`: only an event that changes whether the bingo stands may stale the ceremonial machinery — a non-falling unmark cannot un-witness anything. A blackout-only fall deliberately does NOT bump either: no consumer reads the generation for blackout, and bumping there would reintroduce the same bug shape (an unrelated blackout fall forfeiting a valid bingo ceremony). Every call site traced: doMark's unmark verdict passes the actual fall flags, and the passive falling-edge observer calls per-kind — both now bump exactly on observed bingo falls. The constraints hold: observed bingo falls still clear the candidate AND bump (a fallen-and-regained bingo still cannot fire as first-BINGO — the regain's own birth-time witness suppresses it), stale continuations of wins that actually fell are still refused, and the failure mode remains suppressed-or-correct, never a false singleton. Side effect: every in-app bump site now also clears the candidate, so `firstBingoCandidateCurrent`'s stale-kill is belt-and-braces against future bump sites rather than a reachable path today (stated honestly).

The pending queue is module state, so it is per-page-load: a queued-but-undrained broadcast **still dies on a full page reload** (not merely a route change — the narrower loss). This is honest and bounded: the deterministic id + the returning board baselining the standing win (the Celebration baseline) mean a lost-on-reload win produces **no duplicate and no spurious fire** — at worst one possibly-lost Moment for a win that straddled a reload. That is the SAME class of loss as the prior unmount bug, strictly narrower (only a full reload, not any unmount / route change). The cross-device / admin-confirmed off-route path stays deferred to #41 (below).

### Non-honor write-path emission

Broadcasts are driven by a completing mark's verdict on BOTH player-action write paths (PR #110 round 2 finding 1 closed the proofed-path gap the first cut of #104 opened):

- **proof_required** wins broadcast their Moment from the ATTACH verdict: `attachProof` returns the same transition shape `setMark` does (`AttachProofResult`), ProofSheet reports it via `onAttached`, and Board's shared `broadcastWinVerdict` pipeline enqueues + drains it exactly like an honor win — same identity/roster gates, same witness gauntlet, same fire-time revalidation. (attachProof cannot run offline — its transaction rejects — so a proofed verdict is always an online fact; the queued Moment still rides the offline-queueable `setDoc` if connectivity drops after attach.)
- **admin_confirmed** attaches cross NO transition at attach time — the pending cell is excluded from the win mask, and broadcasting a win for a rejectable pending claim would strand an immutable Moment (see § PR #110 hardening, the admin_confirmed attach decision). The win and its Moment materialize at the ADMIN's confirm write, which is #41's deferred emission — uniformly for on- and off-route players.

## Review-round hardening (PR #99)

> **History.** This section documents PR #99's SNAPSHOT-DIFFING broadcast machinery. Issue #104 replaced that machinery with the action path above; read § The action-driven broadcast model § "disposition" for which of these invariants are PRESERVED (re-homed), MOOT, or NARROWED. The rules-layer findings (3, 4) and the writer/read-side findings (round 3 C, round 4 B) are UNCHANGED and still current; the client snapshot-machinery findings (1, 2, 5, round 2 A–D, round 3 A–B, round 4 A) describe the retired mechanism.

The PR #99 Codex review ran three rounds. Round 1 surfaced six P2 findings; five are fixed here (the sixth is deferred — see § Deferred: admin-confirmed off-route wins): three client-side (two gates on the broadcast + a per-account reset), two `firestore.rules` boundary defects. Round 2 surfaced four more P2s in the round-1 broadcast machinery (A–D below), all fixed client-side. Round 3 surfaced three consequences of the round-2 fixes — the swallowed pre-confirmation offline win (folded into the cache-hydration rule below), the vacuously-true empty-board revalidation (folded into the held-flags rule), and the optimistic duplicate overwrite (the write-once pre-check) — all fixed client-side.

**Held broadcasts — gated, revalidated, per-account (round 1 findings 1 + 2 + 5, round 2 findings A + B).** A crossed BINGO/Blackout edge no longer writes directly. It enqueues the matching kind(s) into a per-uid `pending` ref; `flushPending` writes each only once its gate is open — and only if the win STILL STANDS at fire time (a held flag is a candidate, not a promise). The deterministic doc id keeps a held-then-fired broadcast idempotent, and the celebration UI still fires on the edge itself (never held).

- **Identity gate (finding 1).** All three broadcasts require a KNOWN saved identity — the same `identityKnown` tri-state `setMark` gates on. During the player-row loading window `displayName` has fallen back to the auth/Google name; stamping that into an IMMUTABLE Moment would publish a returning Player's stale name forever. So an edge crossed while identity is unknown holds; when identity resolves, `flushPending` fires it once with the saved name.
- **Roster gate (finding 2).** First-to-BINGO additionally requires a **server-confirmed** roster (`useLeaderboard().hasServerData`). An initial empty `players` from a still-loading (or cache-only) subscription is not proof nobody has bingoed; claiming the ceremony off it would falsely pin a non-first Player. So the first_bingo candidate holds until the roster is server-confirmed, then re-decides `othersBingoed` against it. The per-Player BINGO does not wait on the roster — only the ceremonial claim does.
- **Held flags follow the board — dropped when the win falls (round 2 finding A, hardened by round 3 finding B).** A flag queued while a gate was closed could go stale: the Player unmarks and LOSES the win before the gate opens, and round 1 would then post a Moment for a board that no longer had one. Two complementary fixes, both required: the **falling edge** (bingo/blackout going true→false) clears the corresponding pending flag (a bingo fall also clears the ceremonial candidate), handling the common case; and `flushPending` **revalidates at fire time** — it recomputes `hasBingo`/`isBlackout` from the cells the component CURRENTLY holds (carried in the same latest-value ref as the identity/roster) and drops, without firing, any flag whose win no longer stands (first_bingo included: no standing bingo → no ceremonial claim). The revalidation itself requires a **real, non-empty, attributable board** (round 3 finding B): `isBlackout([])` is vacuously TRUE (`[].every(Boolean)`), so without a `cellsNow.length > 0` gate a held blackout would fire against a board that was deleted or de-attributed between the hold and the flush; `hasBingo([])` is already false, but the guard is uniform on both paths so neither rests on a vacuous-truth accident. The revalidation is the invariant; a lose→regain crosses a fresh rising edge and legitimately re-queues, yielding exactly one write when the gate opens.
- **Per-uid reset, synchronous in render + attribution-gated (finding 5, hardened by round 2 finding B).** The edge refs (`initialized`/`wasBingo`/`wasBlackout`) and the `pending` ref are per-account. Round 1 reset them in a `useEffect` keyed on `uid` — but on a uid switch while Board stays mounted, `useBoard`/`useMyPlayer` still return the PREVIOUS uid's rows for the render(s) before their keyed effects clear, so the same commit's cells effect could seed the new account's baseline from the OLD board and make the new user's first real snapshot read as a fresh edge. Two fixes, both required: the reset now runs **synchronously during render** (React's adjust-during-render pattern — a ref tracks the uid the edge state belongs to; a mismatch restores the uninitialized baseline before ANY effect runs, idempotently); and the cells effect **seeds from attributable data only** — `BoardDoc` carries its owner's uid, and a board whose `uid` differs from the current account is ignored entirely (it also contributes NO cells to fire-time revalidation). The stale-render board is therefore never seeded, and the new uid's own first snapshot re-establishes init-without-firing.

**Cache hydration is baseline, not a transition — except the player's own action (round 2 finding C, bounded by round 3 finding A).** Under the ADR 0006 persistent cache the first snapshot(s) after mount can be cache-only, and round 1 seeded the edge baseline from the FIRST snapshot regardless — so a stale cache lacking a BINGO the server already had made the server confirmation read as a live transition and post a Moment for a win that already stood. Now, while the board is NOT server-confirmed (`useBoard().hasServerData` false), every PASSIVE snapshot re-seeds `wasBingo`/`wasBlackout` and never fires an edge (`initialized` stays false); the FIRST server-confirmed snapshot is baseline too (init-without-firing — any standing win it reveals already stood server-side); edge DETECTION runs only after it. Live play under a confirmed board is unaffected: `hasServerData` is a latch that never un-sets, and a local optimistic Mark arrives as the next snapshot via latency compensation and fires normally.

**The exception (round 3 finding A, hardened by round 4 finding A): the player's OWN Mark on a still-unconfirmed board is a live edge, not hydration.** The round-2 rule as stated swallowed a win completed OFFLINE: on an offline reload the board never confirms until reconnect, so the player's own just-completed line was baselined — the edge never fired, even after reconnect (the first confirmed snapshot baselines it as already standing) — violating the offline-queueable Moments AC. Board already knows when a snapshot is the player's own doing: `doMark` increments a `localActionsPending` ref (decremented on the synchronous-throw path where no write happened), and the cells effect consumes one marker per snapshot. This is deliberately a count, not a boolean: two fast offline taps can produce two local snapshots before server confirmation, and the second snapshot may be the one that completes BINGO. A snapshot marked local while the board is unconfirmed falls through to LIVE edge detection against the pre-action baseline (by the time a tap is possible the cells have rendered, so a pre-action baseline always exists), and the queued Moment rides the offline queue exactly as designed — `setDoc` pends and drains on reconnect. Passive unconfirmed snapshots keep the baseline behavior, and the later server confirmation re-baselines the same standing state without firing a second edge (`initialized` is still false until confirmation). Scope honestly stated: the local-action marker covers `doMark` — the honor-mode path, which is the only Mark that can commit offline (`attachProof`/claim resolution ride transactions that reject offline), so the proof-required and admin-confirmed paths cannot reach this window.

**Canonical Moment ids before render (round 4 finding B; create-side counterpart added in #103).** The create rule now binds the doc id to the payload kind (§ Once-only semantics, #103), so a forged singleton like `{ kind: 'first_bingo' }` at `moments/spoof` is rejected at write. The read side keeps `hasCanonicalMomentId` as **defense-in-depth**: `useMoments()` filters before sorting/capping so `first_bingo` renders only at the event singleton id `first_bingo` and per-Player moments only at `${uid}-bingo` / `${uid}-blackout` — hiding, e.g., the harmless `${uid}-first_bingo` orphan the create rule still permits (its id matches `${uid}-${kind}`). Read and write now honor the SAME deterministic-id invariant the writer depends on.

**createdAt bounded near request.time (finding 3).** The moments create rule now requires `createdAt` within the same +60s / -24h window of `request.time` that proofs use, so a bad clock or a forged far-future stamp can no longer pin a Moment above all Feed activity forever. The client keeps writing `Date.now()` — in bounds by construction for an online write. **Offline-drain residual (accepted, ADR 0001):** a Moment queued offline drains with its ORIGINAL `Date.now()` stamp, not the reconnect time, so one created and then held offline for **more than 24h** would trip the lower bound and be rejected on drain. At friend-group cruise scale a >24h offline gap before a BINGO/Blackout Moment reaches the server is implausible, and the honest alternative — an unbounded stamp — is the defect finding 3 closes; the bound wins. (Proofs cannot queue offline at all — `attachProof` rides a `runTransaction` that rejects offline — so they never hit this drain case; Moments, which ride an offline-queueable `setDoc`, do, hence this note.)

**Full immutability — no admin overwrite (finding 4).** The admin `update` allowance was removed: a Moment is now immutable for everyone. The create-only dedup is only sound if a re-broadcast to an existing id is denied for ALL callers; the prior admin-writable update let an admin-player's repeat broadcast become an authorized overwrite — including clobbering the `first_bingo` singleton under a stale-roster race. `MomentDoc` has no moderation/status field (only `kind`/`uid`/`displayName`/`photoURL`/`createdAt`), so an admin update could only rewrite content — there is nothing to moderate in place. Moment moderation stays delete-only; introducing a status field + a moderation-only update diff (`request.resource.data.diff(resource.data).affectedKeys().hasOnly([...])`) is deferred to #37/#41, which own that schema evolution.

**The write-once cache pre-check (round 3 finding C).** The create-only rules deny a duplicate deterministic-id write server-side — but Firestore applies **latency compensation first**: the duplicate `setDoc` briefly overwrites the LOCAL cache copy, and its refreshed `createdAt` pins the old Moment to the top of the Feed until the denial rolls it back — indefinitely while offline, where no denial ever arrives. So the writer extends the witness pattern to ALL broadcasts: `writeMomentOnce` (the single write path behind `broadcastBingo`/`broadcastBlackout`/`broadcastFirstBingo`) first reads the deterministic ref with `getDocFromCache`; if the Moment already exists locally the write is **skipped entirely** (a debug log — this is the designed once-only path, not an error). On a cache miss the write proceeds: a cold-cache duplicate still resolves server-side via the create-only rule, and the visible-flash window only exists when the doc IS cached — exactly the case the pre-check catches.

**The regained-line witness (round 2 finding D)** is specified with the once-only semantics — see § Once-only semantics, "The regained-line witness", including the narrowed fresh-device residual.

## Deferred: admin-confirmed off-route wins — RESOLVED in #41 (`specs/w3-claim-modes.md`)

**The gap (finding 6).** In `admin_confirmed` claim mode a Mark starts pending and only becomes a win when an Admin resolves the Claim. No Moment was emitted for it: the broadcast is driven by the WINNER's own mark (`doMark`'s transition verdict, issue #104), but an admin-confirmed win materializes via the ADMIN's write, not the player's mark — so the player's `doMark` never sees the transition. A confirm-time win therefore landed on the leaderboard/stats without ever posting the celebratory Moment. (Before #104 the on-route case emitted incidentally, via the mounted board's snapshot edge; #104 removed that snapshot-broadcast, so on-route and off-route were consistent — the whole admin-confirmed emission was #41's.)

**Resolution (mechanism b).** #41 landed the player-side listener: `src/components/ConfirmWinMoments.tsx`, mounted ONCE at the App shell OUTSIDE the tab Routes, watches the Player's OWN Claims (`useMyClaims`, a `where('uid','==',uid)`-scoped read the rules already permit), and on a `pending → confirmed` flip whose board write reflects a standing win, emits the SAME Moment the live edge would have — attributed to the WINNER, as the winner (`isOwner` create). Mechanism (a) — rules letting an Admin create a Moment for another uid — was rejected: it re-opens exactly the cross-uid forgery/dedup surface finding 4 closed. The moments create rule stays own-uid-only and immutable; **no rules change was needed.** The emit decision is the pure `planConfirmBroadcasts` (`src/data/moments.ts`).

**Invariant (satisfied).** A confirmed win produces the SAME Moment the live edge would have — the same kind at the same deterministic id, attributed to the WINNER (not the confirming Admin) — exactly once, and never a false singleton. The confirm-path decision is TRANSITION-gated exactly like the action path (a confirm that completes no NEW line, or one made while a bingo already stood, emits nothing), the ceremonial `first_bingo` applies the SAME server-confirmed-roster / held-while-unconfirmed / regain-suppressed gates as the live drain, and the listener's working state is uid-keyed module scope (mirroring this ticket's pending-Moment queue) so an account switch parks held work rather than losing it. Exactly-once is the deterministic-id, create-only, fully-immutable dedup this ticket ships, now the shared backstop for BOTH paths. Full detail, the four Codex #116 hardening properties, and the claim→test mapping live in `specs/w3-claim-modes.md`.

## Claim → test

Basename-aligned to this spec (the checker matches `specs/w2-feed-moments.md` → a `w2-feed-moments.test.*` under `tests/**` or `src/**`); every claim maps to a real assertion.

### Rules — a Player broadcasts their OWN Moment; forgery denied; fully immutable; createdAt bounded; extra fields not rejected

Runner: `npm run test:rules` (Firestore emulator). Test: `tests/rules/w2-feed-moments.test.ts`.

- A signed-in Player may create their own Moment (each of the three kinds) at a caller-chosen id; a forged uid (another Player's beat) is denied.
- The shape contract: an invalid `kind`, an empty `displayName`, an over-100-char `displayName`, and a non-numeric `createdAt` are each denied; exactly-100 is allowed.
- The once-only backstop (PR #99 finding 4): a second write to an already-written deterministic id is a doc-exists `update` and is denied for **everyone** — an owner re-broadcast, an admin repeat-broadcast, and an admin content rewrite all fail. This is what makes the deterministic id structurally once-only, and it holds for admin-players too.
- `createdAt` is bounded near `request.time` (PR #99 finding 3): a near-now stamp is accepted, a far-future stamp (+1h) and a far-past stamp (-2d) are each denied — the same +60s / -24h window proofs use.
- **Honesty pin:** a create carrying extra `mediaURL`/`proofId` fields is **accepted** — the rules do not reject it; the no-evidence guarantee is a writer/type contract (see the unit test), not a rules-layer one.
- Moment reads are public; an owner may delete their own Moment and an admin may delete any; a non-admin peer may not.

### Rules — retract-once: the tombstone (#377)

Runner: `npm run test:rules` (Firestore emulator). Test: `tests/rules/w2-feed-moments.test.ts`.

- A Player may tombstone their own win at each of the **four** canonical retractable ids: `${uid}-bingo-d${dayIndex}` / `${uid}-blackout-d${dayIndex}` and the legacy day-less `${uid}-bingo` / `${uid}-blackout`.
- **The headline AC:** post → delete → tombstone → the same id can never be re-posted. Without the tombstone that last create would *succeed* (the doc is gone, so it is a create, not an update) with a fresh `createdAt` — straight back to the top of the Feed. A sibling Day is untouched: the denial is keyed on the exact Moment id.
- The same spend holds for the legacy day-less forms, so the retract-once bound is not per-card-only.
- Forgery is denied both ways — a Player cannot tombstone another Player's win id, nor mint one carrying another Player's uid (a denial-of-win squat); the victim's own Moment still posts afterwards.
- The tombstone id is bound to its payload exactly as the moments create rule binds a Moment's: a Day mismatch, a day-suffixed id with no `dayIndex`, a non-integer `dayIndex`, an out-of-schedule Day, a kind mismatch, and an arbitrary id are each denied; extra fields are denied (`hasOnly` — deliberately stricter than the moments create rule, which accepts them); `createdAt` carries the house near-now bound; the canonical create is accepted, and a day-LESS id with a day-stamped payload stays valid (the binding constrains the day-suffixed form, not the field's presence).
- The ceremonial `first_bingo` cannot be tombstoned at either the singleton id or the `${uid}-first_bingo` orphan, and the singleton itself still posts.
- The tombstone is immutable (no update for owner or admin) and **not** owner-deletable — an undoable tombstone would restore the repost loop; an admin may delete it, after which the win posts again.
- Tombstone reads are public.

### Unit — the broadcast writer + the Feed merge

Runner: `npm test` (Vitest, jsdom). Test: `src/data/w2-feed-moments.test.ts`.

- `broadcastBingo` writes exactly ONE Moment at `${uid}-bingo` with `kind: 'bingo'` and EXACTLY the `MomentDoc` fields — no `mediaURL`, `storagePath`, or `proofId` (ADR 0002).
- `broadcastBlackout` writes one at `${uid}-blackout` (`kind: 'blackout'`); `broadcastFirstBingo` writes one at the Event-singleton `first_bingo` (`kind: 'first_bingo'`).
- The attributed name is bounded to the rules' ≤100 cap.
- Each broadcast is a single offline-queueable `setDoc` — never `addDoc`, never `runTransaction`.
- The write-once cache pre-check (round 3 finding C): a broadcast whose Moment is already in the local cache performs NO `setDoc` at all; a cached exists-false snapshot and a cache miss (rejection) both let the write proceed — the cold-cache duplicate still resolves server-side via the create-only rule.
- `hasPriorBingoWitness` (round 2 finding D) reads the player's own `${uid}-bingo` doc from the LOCAL cache only (`getDocFromCache`), resolves `true` when the cached witness exists, `false` when it does not, and `false` — never rejecting — on a cache miss (the fresh-device fallback path).
- **The pending-Moment queue (issue #104):** `enqueueWinMoments` sets the per-uid `{ bingo, blackout }` flags off a mark's transition verdict (a no-op enqueue with neither transition never resurrects a drained flag); `enqueueFirstBingoMoment` sets the ceremonial flag separately (Board gates it on the witness first); the queue is per-uid isolated and SURVIVES across calls (module state — an unmount between enqueue and drain cannot lose it); `clearPendingMoment` clears one drained kind and drops the entry once empty; `resetPendingMoments` clears all (test-support).

- **The candidate stamp (PR #110 round 2 finding 3):** `enqueueFirstBingoMoment` stamps the candidate with the current generation; `firstBingoCandidateCurrent` is true only while that stamp matches — a bump with the flag surviving (a no-drop unmark) makes it STALE (the drain kills it), a fresh re-enqueue is current again, and a queued plain bingo alone is never a candidate.
- **The transition verdict (issue #104)** that drives all of the above is unit-tested where it is computed — `src/data/w1-board-mark-win.test.ts`: `computeMark`/`setMark` report `bingoTransition` only on the mark that completes the first line (not a further mark while a line stands, not an unmark), `blackoutTransition` only on the mark that fills the card, and an `admin_confirmed` pending mark crosses neither (→ the confirm-path emission is #41's).
- **Retraction (#377):** `retractPublishedWins` deletes the per-card Moment and sets its id-mirroring tombstone in ONE `writeBatch` (atomicity is the point); retracts **nothing** when the win never published (a cold cache mints no tombstone — that would spend the slot for free); retracts only the kind that fell (a blackout fall leaves a still-standing bingo alone); reaches a LEGACY day-less Moment that covers the fallen Day and gives it a day-LESS tombstone, while leaving a legacy Moment stamped for a *different* Day standing; a legacy (day-less) Event retracts its one card's Moment unconditionally and probes no day-scoped id; a `fell` with nothing set is a no-op that reads nothing. Plus the retract-once pre-check on the writer: a broadcast whose tombstone is in the local cache performs no `setDoc` at all, while a different Day is unaffected.
- `mergeFeed` interleaves Proofs + Moments strictly newest-first, keeps the `slice` cap, and returns an empty stream for `([], [])` — a bare Mark (neither a Proof nor a Moment) contributes nothing.
