# GA4 event catalog + 18+ consent notice (`src/analytics.ts`, `src/components/ConsentNotice.tsx`)

`src/analytics.ts` owns the GA4 event catalog and the single `track(name, params?)` entry point every call site uses instead of importing `firebase/analytics` directly. This spec pins the completed 12-event PRD set (10 events already fired at their call sites pre-ticket; this ticket adds `demand_proof` and `install_pwa` to the catalog and type) and the lightweight 18+ analytics disclosure that ships alongside it. It is exercised by `src/w2-ga4-events.test.tsx` (unit + RTL-jsdom, covering both `src/analytics.ts` and `src/components/ConsentNotice.tsx`).

## The catalog is the complete, de-duplicated 12-event PRD set (plus later operational events)

`GA4_EVENTS` enumerates every catalogued event name in one place, and `track()`'s `name` parameter is typed to that union so a call site can only pass a catalogued name.

- **Given** the exported `GA4_EVENTS` catalog **when** read **then** it contains the 12 PRD events plus the operational `login_failed` (added later by #163, defined below), in order—`login`, `login_failed`, `join_event`, `add_item`, `report_item`, `mark_square`, `attach_proof`, `demand_proof`, `bingo`, `blackout`, `theme_change`, `share_click`, `install_pwa`—with no duplicate names. (Test: "enumerates the 12 PRD events plus the operational login_failed (#163)".)
- Later tickets added further catalogued events, each documented at its own call site and in the catalog test's enumeration: `text_size_change` (#215, inserted after `theme_change`—so the bullet above is the original 12+1 SET, not a positional prefix of today's array), then `reshuffle_card` (#378, `specs/reshuffle.md`), `heart_post` (`specs/feed-hearts.md`), `most_loved_photo_frozen` (#560, `specs/most-loved-photo.md`), the operational `mark_rejected` (#387, above), and `unmark_square` + `echo_mark` (#721, below) appended at the end, in that order. The catalog test in `src/w2-ga4-events.test.tsx` remains the canonical in-order enumeration.

## `mark_rejected`—operational mark-batch-rejection event (#387, post-w2)

`mark_rejected` is an operational observability event in the `login_failed` family, not a PRD event. `setMark`'s atomic mark batch is fire-and-forget; an ONLINE rejection (rules denial) rolls back the optimistic write and the player watches their square revert—the 2026-07-17 incident (#387), where a rules-deploy/stale-bundle skew rejected every mark from stale PWA shells and the failure was visible only in sampled session-replay console logs. The rejection handler in `src/data/api.ts` now fires `track('mark_rejected', { code, index, marked, dayIndex, daily })` alongside its `console.error`, so the next skew is queryable and alertable in PostHog. Params are PII-free (the Firebase error `code`, the cell index, the toggle direction, the Day, and the daily-mode flag); the emit is guarded and observability-only—no retry surface, no toast, and the optimistic return contract of `setMark` is unchanged (`specs/w1-board-mark-win.md` § Write-failure semantics, as amended by #387).

- **Given** a mark batch **when** its online `commit()` rejects **then** `track('mark_rejected', …)` fires with the error code and Mark context. (Test: "fires the mark_rejected observability event with the error code + Mark context (#387)", in `src/data/w1-board-mark-win.test.ts`.)

## `mark_square`, `unmark_square`, and `echo_mark`—the mark-transition instrumentation fix (#721, post-w2)

The Bodega Bay POC surfaced a 5x disagreement between PostHog `mark_square` (6 events, 2 people) and the Day-4 email standings (25 squares marked): `mark_square` had exactly one production call site, inside `Board.tsx`'s `doMark`, reachable only from the honor pledge (`marked: true`) and the instant unmark (`marked: false`)—every OTHER path that transitions a Square to marked (a proof attach, an admin confirming a claim) fired nothing, and Echo Marks (a Square pre-marked by achievement on another Day Card, not by a tap) also fired nothing. This was missing instrumentation, not a broken sink—no mark path bypassed `track()`; the other paths simply never called it. #721 closes the gap with a `source` discriminator, not by widening `mark_square`'s existing `{ mode, marked }` shape, because a boolean or an unlabeled event name cannot answer "which of the three Claim Modes did this Mark take" without re-deriving it from other state.

- **Given** any of the three Claim Modes **when** a Square transitions to `marked: true` **then** `track('mark_square', { source, mode, marked: true, dayIndex })` fires, `source` one of `'pledge'` (the honor pledge, `components/Board.tsx`'s `doMark`), `'proof'` (a proof attach, `components/ProofSheet.tsx`'s `submit`, gated on `attachProof`'s OWN committed-transaction read—not the sheet's opening snapshot, which a concurrent mark from another device can make stale—so the ＋ affordance on an already-marked Square, and a race where another device marks the Square between the sheet opening and this submit's commit, both fire nothing here), or `'admin_confirm'` (an admin-confirmed claim reaching `confirmed`, `data/admin.ts`'s `confirmClaim`, gated on that resolve's own before/after read of the claim's cell—a stale claim with no matching board/cell, or a second admin's transaction replaying against the winner's already-confirmed cell, fires nothing). `dayIndex` is the ACTED Day, captured from the same value the write itself used (`viewedIndex` in daily mode)—never derived from the app-wide `day_index` default dimension (`registerDayIndexDimension`, registered once from `todaysDayIndex` at startup), which would misattribute a Player marking an older Day. The `admin_confirm` source additionally carries `uid`, the claim OWNER's id: this call runs in the confirming ADMIN's own session, so without it the event would attribute to the admin's distinct id with no way to recover whose Square it was. (Tests: "the pledge marks in one tap and closes it" and "a pledge on a VIEWED, non-today Day stamps mark_square with the acted Day, not today" in `src/components/w4-honor-pledge.test.tsx`; "a submit that marks a previously-unmarked Square also fires mark_square" and "a concurrent mark that lands BETWEEN the sheet opening and the commit does not double-fire mark_square" in `src/components/w2-proof-capture.test.tsx`; "confirming echoes the Prompt onto sibling carriers" in `src/data/echo-marks.test.ts`.)
- **Given** a marked Square **when** the Board's instant tap unmarks it (`toggle` → `doMark`, `nextMarked: false`) **then** `track('unmark_square', { mode, dayIndex })` fires instead of `mark_square { marked: false }`—a distinct event NAME, not a boolean read on the same name, so a raw `mark_square` count is never polluted by an unmark without a consumer having to filter it out by hand. This is the ONE unmark path #721 instruments; an admin rejecting a claim (`admin.ts`'s `rejectClaim`) and deleting a proof (`data/proofs.ts`'s `deleteProof`) also unmark a Square and remain uninstrumented—both already fired no event before #721 (so neither regresses), and the acceptance bar is "unmarks are distinguishable from marks when they fire," not "every unmark path fires." (Test: "Cancel leaves the Square unmarked; unmarking a marked Square stays instant with no sheet" in `src/components/w4-honor-pledge.test.tsx`.)
- **Given** the Echo Marks system pre-marking one or more Squares from an achievement on ANOTHER of the Player's Day Cards (deal-time, reshuffle, the mark-time cascade onto siblings, the open-time reconcile heal, or an admin confirming an admin_confirmed claim whose Prompt cascades onto sibling Day Cards in the SAME transaction—`specs/echo-marks.md`) **when** the echo(es) commit **then** `track('echo_mark', { trigger, dayIndex, count })` fires once PER RECEIVING Day, `trigger` one of `'deal'` / `'reshuffle'` / `'mark'` / `'open_reconcile'` / `'admin_confirm'` naming which of the five propagation paths fired it—the first four in `src/data/api.ts`, the fifth in `src/data/admin.ts`'s `confirmClaim` (added #727 round 3, Codex P2: confirming an admin_confirmed claim echoes the Prompt onto the owner's OTHER Day Cards exactly like a mark-time cascade, and until this fix those Days' `squaresMarked` increments fired no counterpart event, reopening the exact gap #721 closed for the other four paths)—`dayIndex` the RECEIVING board's Day (never the acted/source Day—a mark-time Mark or an admin confirm that echoes onto several sibling Days fires one event per sibling, grouped by that sibling's own `dayIndex`, so the per-Day reconciliation below holds for every touched Day, not only the acted one), `count` the number of Squares NEWLY echoed onto that Day's bucket by this write (a reshuffle that re-echoes a Prompt the discarded card already wore reports the NET increase over the discarded card, floored at zero—never the replacement's raw echo total, which would double-report a Square whose bucket did not move). The open-time reconcile path additionally recovers an `echo_mark` an earlier session's stranded offline write never got to fire: the stats-lag heal every echo write path already relies on to repair a lost pin/bucket continuation (`runReconcileEchoes`'s `bucketLag`/`rootLag` check) also fires the recovered event there, sized to the ACTUAL server-confirmed bucket delta, so a reload that kills the in-memory `committed.then(...)` continuation before it fires does not permanently lose the count. `echo_mark` is deliberately its own event, not a `mark_square` source: an echo carries no Player action on the RECEIVING card, so folding it into `mark_square` would reintroduce the exact source-conflation #721 fixes, one level down. (Tests: `src/data/echo-marks.test.ts`, one assertion per propagation path plus the multi-sibling grouping, net-new-after-reshuffle, and open-time-recovery cases.)

### Reconciliation—how the events relate to `dayStats[*].squaresMarked`

**Current Echo delivery contract (PR #727 round 4).** An `echo_mark` now ships once per countable echoed Square with `{ uid, dayIndex, count: 1, transitionId }`. `transitionId` is persisted on that Square in the same Firestore write and includes the event, player, receiving Day, card seed, cell, and Echo generation. A tab or another device may replay the same ID on a later open; that is intentional at-least-once delivery. Reconciliation must count distinct `transitionId` values in PostHog, never raw delivery rows. This supersedes the historical device-local watermark and stats-lag recovery description: browser storage and a monotonic `squaresMarked` total cannot determine whether a transition is new after a reversal or on another device. A reshuffle assigns identities only to its net-new echoes, so a replacement that merely re-echoes an already-counted Square has no countable ID.

`standingsThrough()` (`functions/src/dailyEmailContent.ts`, out of scope for #721—`functions/**` is untouched) sums `players/{uid}.dayStats[d].squaresMarked`, which `game/logic.ts`'s `countMarked` recomputes from the WHOLE board on every write, `marked && status !== 'pending'`. The two views were never meant to agree exactly—`mark_square` (plus `echo_mark`) counts discrete PLAYER-VISIBLE transitions; `squaresMarked` is absolute board state, multiplied by Echo Marks (one achievement echoing onto five Day Cards contributes five)—but the relationship between them is now traceable instead of accidental:

- **Honor mode:** one `mark_square { source: 'pledge' }` per Square = one `squaresMarked` increment. The pledge's `doMark` calls `setMark`, which writes `status: 'confirmed'` in the same batch `countMarked` reads—1:1.
- **`proof_required` mode:** one `mark_square { source: 'proof' }` per Square = one `squaresMarked` increment, same reasoning (`proofs.ts`'s `attachProof` writes the cell `confirmed` immediately when the mode isn't `admin_confirmed`)—1:1.
- **`admin_confirmed` mode:** TWO `mark_square` events per credited Square, not one. The proof attach writes the cell `marked: true, status: 'pending'` immediately (`data/proofs.ts`)—firing `mark_square { source: 'proof' }`—but `countMarked` excludes `pending`, so `squaresMarked` does NOT move yet. Only when an admin confirms (`confirmClaim`, `status: 'confirmed'`) does the Square credit, firing a SECOND event, `mark_square { source: 'admin_confirm' }`. So in this mode, summing ALL `mark_square` events double-counts against `squaresMarked`; the `admin_confirm`-sourced count alone is the 1:1 one. This is by design, not a bug: `source: 'proof'` answers "did the Player submit a claim," `source: 'admin_confirm'` answers "did it get credited," and #721's acceptance bar is that a Player's action is measurable at BOTH moments, not that the two collapse into one number. A `confirmClaim` call that does NOT actually credit the Square—a stale claim, or the losing side of two admins racing the same confirm—fires no second event at all, so this identity never over-counts either.
- **Echoes:** every `echo_mark` is a `squaresMarked` increment on the RECEIVING Day's bucket (an echo always lands `confirmed`, never `pending`), and it is NEVER counted by any `mark_square`/`unmark_square` event—the Square changed with no tap behind it. This holds for the admin-confirm cascade too (round 3, #727): confirming an admin_confirmed claim fires exactly one `mark_square { source: 'admin_confirm' }` for the CLAIM'S OWN cell, and a separate `echo_mark { trigger: 'admin_confirm' }` per sibling Day the same confirm echoes onto—the two never overlap the same Square. Every `squaresMarked` INCREMENT is counted exactly once, either by the mode-appropriate `mark_square` source (per the three bullets above) or by an `echo_mark`, and the fix that closes #721 makes that half of the relationship (Codex round 1 finding 7, `runReconcileEchoes`'s `bucketLag`/`rootLag` heal) idempotent against a stranded continuation: a durable per-`(uid, dayIndex)` report watermark (`claimEchoMarkReport`, `src/data/api.ts`) is shared by every `echo_mark` emitter for the 'mark' and 'open_reconcile' triggers, so a reload that strands one of the two independent promises off a batch commit—the analytics send or the `dayStats` write—can never cause the OTHER to re-report an increase this device already sent (Codex P2 on #727). The admin_confirm trigger (round 3) needs no such watermark: its sibling echoes fire from the ONE Firestore transaction `resolve()` already commits synchronously (no separate stats-write continuation to race), and a stale or replayed confirm naturally reports nothing—see `resolve()`'s own `res.changed` gate, `src/data/admin.ts`.
- **Reconciliation is a one-directional bound, not an exact identity.** `squaresMarked[d]` can never EXCEED `markCount[d] + echoCount[d]` (where `markCount` sums the mode-appropriate `mark_square` source per the three bullets above and `echoCount` sums `echo_mark`'s `count` params)—every increment is counted, and #727 (above) closes the one way that bound could have been violated in the increment direction. It CAN legitimately fall SHORT of that sum: an honor-mode instant unmark (`unmark_square`) reverses a `squaresMarked` increment without decrementing `markCount`—a raw event count is a monotonic tally, never retracted—and `rejectClaim` (`data/admin.ts`) and `deleteProof` (`data/proofs.ts`) also unmark a Square while firing no event at all (#721 deliberately left both uninstrumented—see the `unmark_square` bullet above). A reshuffle can similarly retire old echoes without an offsetting negative event. So `squaresMarked[d] = markCount[d] + echoCount[d]` holds only for a `(uid, dayIndex)` that has never had a reversal; treat the two as an upper-bound check, not a query-time equality, or a standings query built on exact equality will silently under-count every Player who ever unmarked, had a claim rejected, or deleted a proof.

## `login_failed`—operational sign-in-failure event (#163, post-w2)

`login_failed` is an operational observability event, not one of the 12 PRD events; it was added after this ticket by #163. `track('login')` fires only on a _successful_ Google sign-in, and Firebase handler errors render on the OAuth helper page where PostHog is not loaded—so a failed sign-in was previously invisible in analytics. `signIn()` in `auth/AuthContext.tsx` wraps desktop `signInWithPopup` and mobile `signInWithRedirect` startup in `try`/`catch`; app-owned redirect completion also handles `getRedirectResult` rejection. Each rejection fires `track('login_failed', { method: 'google', code })` with an allowlisted Firebase error code or `auth/unknown`; raw provider messages are never sent. Popup/startup errors are rethrown to preserve the caller contract. The params are PII-free, matching the catalog's privacy posture.

- **Given** a Google sign-in **when** the Firebase popup, redirect startup, or redirect completion rejects **then** `track('login_failed', …)` fires with the Firebase error `code` and the success `login` event does not fire. (Popup regression test: "fires track('login_failed', …) with the Firebase error code and rethrows when the popup rejects (#163)", in `src/auth/AuthContext.test.tsx`.)
- **Known gap:** an error rendered only inside Firebase's helper document can still occur before the app reloads and resumes analytics; the sign-in-screen pageview → `login` funnel remains the secondary signal for that case.

## `demand_proof` and `install_pwa` fire through the existing `track()`, not a second path

Both new events are catalog/type additions only—this ticket does not build the Doubt flow (`demand_proof`'s call site, owned by #33) or the install-prompt flow (`install_pwa`'s call site, owned by #30). Both route through the same `track()` any other event uses.

- **Given** a Doubt is raised **when** `track('demand_proof', params)` is called **then** it invokes the underlying `logEvent` with the `demand_proof` name and those params. (Test: "fires demand_proof through logEvent with its params (10 -> 12)".)
- **Given** the PWA install prompt is accepted **when** `track('install_pwa')` is called **then** it invokes `logEvent` with the `install_pwa` name. (Test: "fires install_pwa through logEvent (10 -> 12)".) Both route through the one `track()` implementation every other catalogued name uses—there is no per-event branch to special-case (verified by reading `track()`'s body, not a dedicated per-name test).

## `track()` never throws

`track()` is the single point every feature calls into for analytics, so it must stay a safe no-op regardless of whether GA4 is available or the underlying SDK call fails.

- **Given** `analytics` is unavailable (`null`—unsupported browser, no measurement id, etc.) **when** `track()` is called **then** it does not throw and does not call `logEvent`. (Test: "never throws and never calls logEvent when analytics is unavailable (null)".) The same guarantee holds if the underlying `logEvent` call itself throws, because the call is wrapped in `track()`'s `try`/`catch` (verified by reading the implementation, not a dedicated test for the SDK-throws case).

## The existing 10 events fire with sensible params (verified by source audit, not a new test)

Pre-ticket call sites already exist for the other 10 events and are unchanged by this ticket: `login` (`auth/AuthContext.tsx`, `{ method: 'google' }`), `join_event` (`App.tsx`, no params), `add_item` (`components/ItemPool.tsx`, no params), `report_item` (`components/ItemPool.tsx` + `components/ProofFeed.tsx`, no params), `mark_square` (`components/Board.tsx`, `{ mode, marked }`—later corrected and expanded by #721, see § Mark-transition instrumentation below), `attach_proof` (`components/ProofSheet.tsx`, `{ type }`), `bingo` / `blackout` (`components/Board.tsx`, no params), `theme_change` (`components/ThemeSwitcher.tsx`, `{ theme }`), `share_click` (`components/Celebration.tsx`, `{ surface }`). Every one of these calls `track()` with a name that is a member of `GA4_EVENTS`, so tightening `track()`'s `name` parameter from `string` to `GA4EventName` type-checks against all ten unchanged (enforced by `npm run typecheck`, not a runtime test—a call site with a name outside the catalog would fail to compile).

## 18+ analytics consent notice

A lightweight, dismissible disclosure—not a full consent-management platform and not a gate on analytics itself (`firebase.ts` already loads GA4 unconditionally when supported)—mounted at `src/main.tsx`, a stable, non-frozen mount point outside the auth-gated tree so it is visible even on the signed-out SignIn screen. Copy and region handling are an open decision (#15); this ships that issue's recommended default: a lightweight in-app notice with no region gating.

- **Given** a device that has not dismissed the notice **when** `ConsentNotice` renders **then** it shows disclosure text mentioning both the 18+ audience and analytics. (Test: "renders the 18+ analytics disclosure on first visit".)
- **Given** the notice is showing **when** the Player dismisses it **then** it stops rendering and the dismissal is persisted to `localStorage` so it does not reappear. (Test: "dismisses on click and persists the dismissal to localStorage".)
- **Given** a device that already dismissed the notice **when** `ConsentNotice` mounts again **then** it does not render. (Test: "does not render on a later mount once dismissed".) Separately, if `localStorage` is unavailable (private browsing, quota, etc.), dismissing still hides the notice for the current session rather than throwing, because both `isDismissed()` and `dismiss()` wrap their storage access in `try`/`catch` (verified by reading the implementation, not a dedicated test for the storage-unavailable case).
