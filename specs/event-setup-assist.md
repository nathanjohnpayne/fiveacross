# Event setup assists—Drafting with Claude inside Steps 3 and 4 (`event-setup-assist`)

The contract for [#1958](https://github.com/nathanjohnpayne/fiveacross/issues/1958), a child of the setup-wizard epic [#786](https://github.com/nathanjohnpayne/fiveacross/issues/786): four credit-backed assists that write words into the organizer wizard—squares, a top-up of squares, a spicy verdict on a typed square, and each Day's Place, Tonight pair and Free Space—behind one callable, `draftWithClaude`, and one authorship rule: nothing a model writes enters the draft until the organizer keeps it. It extends [`specs/event-setup-wizard.md`](event-setup-wizard.md) and changes none of it; every row an assist offers is judged by that spec's § Validation predicates and enters the draft through the transforms that spec already names.

Design shape comes from `plans/daily-cards-wireframes.html` § "Five Across · Drafting with Claude" (`#sec-setup-assist`: frames `#frame-setup-assist-brief`, `-review`, `-landed`, `-look`, the states table `#sec-setup-assist-states`, and the dashed ✦ entry rows on `#frame-setup-squares` and `#frame-setup-look`), which is explicitly exploratory. Every binding fact below comes from the code the wizard spec cites or from the Claude API as documented at the time of writing; where the frames and this spec disagree, this spec wins and the deviation is recorded here.

**Status is `proposed` because five decisions in § Open decisions are the owner's**, and because the plumbing has not been built. The code constraints under § Contract are what the implementing PR is checked against; the v1 default named under each open decision is what it builds unless the owner rules otherwise first.

Why this exists: the occasion matrix binds no starter pack (every `OccasionDef.starterPackId` in `src/data/occasions.ts` is `null`), #786 Decision 2 (2026-10-02) made the owner the editorial gate for any pack that gets authored, and the platform holds a $200 Claude developer-credit grant that nothing spends. Per-Event drafting with organizer approval is the PRD's own later opportunity ("AI-assisted prompt drafting with organizer approval", PRD § Later opportunities), pulled forward because the pack problem it solves is what stands between Step 3 and the under-15-minutes goal. These assists add nothing to, and remove nothing from, the platform blockers Step 5 lists.

## Glossary

- **Assist**: an offer inside an existing wizard step—a sheet or a row—never a step of its own. Five steps stay the ceiling.
- **Brief**: the organizer's free-text description of the group, typed on the brief sheet. Optional. Held in wizard-session state while the wizard is mounted, sent to the callable, forwarded to the API; Five Across stores it nowhere, and Anthropic retains it under its API terms (§ Open decisions 1 and 4).
- **Row**: one proposed Prompt, `{ pool, text, spicy? }`, streamed back by the `squares` or `top-up` task. A row is not in the draft. It is undecided until kept or dropped.
- **Keep**: the authorship act. A kept row commits through `addPrompt` (`src/data/draftSquares.ts`) the moment it is tapped; a kept Day proposal commits through the Look transforms in `src/data/draftLook.ts`. There is no other way into the draft.
- **Task**: the callable's discriminator—`squares`, `top-up`, `spicy-check`, `day-copy`. One callable, four behaviours.
- **Draft unit**: what the per-account daily allowance counts. `squares`, `top-up` and `day-copy` each spend one; `spicy-check` spends none.
- **Allowance**: the per-signed-in-account, per-UTC-day cap on draft units, enforced server-side and returned on every response as `remaining`.
- **Ledger**: the server-only monthly usage document `aiUsage/{yyyy-mm}` that sums tokens and estimated spend across every account, with a dollar ceiling.
- **Register**: the Edition's own vocabulary (`editionLexicon` in `src/editions.ts`—Vacay says *trip*, *stop*, *the whole group*), restated for the prompt so squares read as the players' Edition rather than the platform's.

## Contract

### The callable

`draftWithClaude` is an `onCall` exported from `functions/src/index.ts` beside `submitPrompt` and `approvePrompts`, with the handler in `functions/src/draftWithClaude.ts` taking injected deps (`{ db, now, anthropic, logger }`, the `submitPrompt` posture, so the unit suite runs with a fake Firestore and a fake Anthropic stream and no runtime). Options: `serviceAccount: ADMIN_SDK_SERVICE_ACCOUNT` (it reads and writes the allowance and ledger documents), `secrets: [ANTHROPIC_API_KEY]`, `timeoutSeconds: 120`, `maxInstances: 10`. It is registered in `scripts/callable-invoker-families.mjs`, because the #1283 predeploy hook refuses an HTTPS export that belongs to no invoker family.

It requires `request.auth`—a signed-in caller—before anything else, and refuses `unauthenticated` otherwise. The allowance is per account, a device-local draft id is a trivial thing to reset, and the organizer must be signed in to be granted Admin at launch anyway. With `DRAFT_WITH_CLAUDE_APP_CHECK` true it also requires `request.app` (`failed-precondition`), the same off-by-default posture as `SUBMIT_PROMPT_APP_CHECK`.

It writes no Event document and no draft. Drafts are device-local (#786 Decision 1); the callable takes a slice of one and returns words. Its only Firestore writes are `aiAllowances/{uid}` and `aiUsage/{yyyy-mm}`.

### Request

The wire types live in `src/domainTypes.d.ts` (`DraftWithClaudeRequest`, `DraftWithClaudeChunk`, `DraftWithClaudeResponse`) and are imported type-only by `functions/`, as `SubmitPromptRequest` is. The shape, with the bounds the server enforces (`invalid-argument` on any violation, before any admission or model work):

```ts
interface DraftWithClaudeRequest {
  task: 'squares' | 'top-up' | 'spicy-check' | 'day-copy';
  /** What the draft already knows. Never the slug, never unlock times, never Themes. */
  draft: {
    occasion: OccasionId;           // must resolve in the matrix
    edition: string;                // must be a known Edition id
    name: string;                   // 1–80 raw; trimmed before forwarding
    startsOn: string;               // ISO date
    endsOn: string;                 // ISO date, >= startsOn
    forceAdult: boolean;            // the Basics audience choice
    claimMode: EventDoc['claimMode'];
    cardFormat: DraftCardFormat;
    days: Array<{ index: number; date: string; pool: PoolId; tutorial: boolean }>; // <= MAX_DAYS, contiguous; each date a real ISO date (isIsoDate)
  };
  brief?: string;                   // <= 600 characters RAW; trimmed before forwarding; may be empty
  tone?: 'gentle' | 'playful' | 'unhinged';   // default 'playful'
  spicyShare?: number;              // 0–1; honoured only when draft.forceAdult is true
  targets?: Partial<Record<PoolId, number>>;  // squares / top-up: 1–40 per pool, assigned pools only
  existing: Record<PoolId, string[]>;         // the newest 200 texts in each pool, newest first, each 1–80 (the client selects; the server refuses more, or a text outside 1–80)
  examples?: string[];              // top-up 'more-like-these': kept texts, newest first, <= 120 (three pools at the 40 target), each 1–80
  angle?: 'more-like-these' | 'top-up-pool' | 'different-angle';  // top-up: REQUIRED; refused on any other task
  pool?: PoolId;                    // top-up 'top-up-pool': REQUIRED, the one pool to fill; refused otherwise
  text?: string;                    // spicy-check: REQUIRED, the typed square, 1–80 raw; refused on any other task
}
```

The block above is written as one shape for reading; on the wire it is a discriminated union on `task`, and the handler refuses a request missing a task's required field or carrying another task's (`top-up` without `angle`, `top-up-pool` without `pool`, `spicy-check` without `text`, `squares` with `angle`) as `invalid-argument` before admission, so no unit or reservation is ever spent on a request the prompt cannot be built from. Every string that reaches the model turn is bounded on its raw length and trimmed before forwarding—`name`, `brief`, each `existing` and `examples` entry, `text`—and every `date` must be a real ISO date, because the admission reservation assumes a bounded input and App Check is off by default. `draft.days` is accepted only as `{ index, date, pool, tutorial }`: the model is told which Day deals which pool (an arrival Day writes arrival squares, a closing Day farewell squares, a `tutorial` Day warm-up ones) and nothing else about the schedule. `targets` may name only pools in `assignedPools(draft)` (`src/data/draftValidation.ts`); a target for a pool no Day deals from is `invalid-argument`, matching the sheet, which does not offer it. `spicyShare` under `forceAdult: false` is ignored and the request forbids sexual content outright; the client never sends it in that case, and the server ignores it if it does. `existing` and `examples` entries are each bounded 1–80 like a kept Prompt text, because they are forwarded into the model's user turn: without the per-string bound, 120 oversized examples would make each allowed call an unexpectedly expensive one before the ledger could close the ceiling, and App Check is off by default. `existing` is a selection, not the whole pool: the client sends the newest 200 texts per pool, newest first, so a pool grown past 200 by hand or by repeated drafts never makes every later assist `invalid-argument`; the near-duplicate advisory still compares against the whole pool client-side.

### Response and chunks

With `request.acceptsStreaming` the callable forwards each validated row through `response.sendChunk` as it is parsed out of the model's streamed JSON array, and the client reads `httpsCallable(functions, 'draftWithClaude').stream(request, { signal })`, consuming `stream` for chunks and `data` for the final response; `signal` comes from the sheet's own `AbortController`, armed with a 90 s first-row timer (the admission chunk does not disarm it) rather than the SDK's whole-call timeout, so that once rows flow the handler's own model deadline is the only clock: the Anthropic request runs under a 100 s SDK timeout, and the remaining 20 s of the callable's `timeoutSeconds: 120` are reserved for aborting the stream, the ledger write that releases the reservation, and the final response, so a slow run ends as Partial or Interrupted with its accounting done rather than being killed by the platform mid-reconciliation. A non-streaming caller gets the same final response with every row in it and must set a callable timeout above the handler's 120 s (`{ timeout: 150_000 }`), because the Web SDK's default is 70 s and a valid draft can finish between the two; the streaming path this spec defines carries its own clock below. The first chunk of every streamed run is `{ admitted: { remaining } }`, sent right after the admission transaction and before the model is called, so the sheet holds the server's balance even when the run is later stopped and the final response never arrives; it is not a row and does not count as one for the Unreachable boundary or the first-row timer. After it, chunks are `{ row: SquareRow }` for `squares` and `top-up` and `{ day: DayCopy }` for `day-copy`; `spicy-check` streams nothing.

```ts
type SquareRow =
  | { pool: 'main'; text: string; spicy: boolean }
  | { pool: 'easy' | 'closing'; text: string };          // no spicy key: unrepresentable, as DraftCuratedPrompt says
interface DayCopy { index: number; place: string; placeEmoji: string; tonight: [string, string]; freeText: string }
type DraftWithClaudeResponse =
  | { task: 'squares' | 'top-up'; rows: SquareRow[]; skipped: SkipCounts; stopReason: 'end_turn' | 'max_tokens' | 'refusal'; remaining: number }
  | { task: 'spicy-check'; verdict: { spicy: boolean; reason: string } | null; stopReason: 'end_turn' | 'max_tokens' | 'refusal'; remaining: number }
  | { task: 'day-copy'; days: DayCopy[]; skipped: SkipCounts; stopReason: 'end_turn' | 'max_tokens' | 'refusal'; remaining: number };
/** Rows the server dropped before sending, by reason; the client adds its own under the same keys. */
type SkipCounts = Partial<Record<'overLength' | 'blank' | 'spicyOnCurated' | 'unassignedPool' | 'badTonight' | 'badEmoji' | 'unknownDay' | 'duplicateDay' | 'malformed', number>>;
```

`remaining` is on every response and in the admission chunk of every streamed run: it is `12 − drafts` after this call's charge, read from `aiAllowances/{uid}`, and the only number the sheet ever prints for the allowance. A stopped or dropped run therefore still leaves the sheet holding a server number; after a refund the sheet keeps that number (one too low) until the next admission chunk or response corrects it, rather than adding one itself. `stopReason` is a field, not an error: `refusal` is the Declined state and `max_tokens` the Partial state in § States, and neither throws. A refusal can arrive mid-stream, after rows were delivered. The handler then discards the partial, as the API guidance says to, so the final `rows` is empty, and the client withdraws every undecided row from the sheet; rows the organizer had already kept stay in the draft, because a keep made them the organizer's own Prompts (§ Squares), editable and deletable in Step 3 exactly like typed ones, and the Declined copy says so. With `fallbacks: 'default'` a decline that is rescued mid-stream is not a refusal: the fallback model continues the same stream from the partial, marked by a `fallback` content block the handler ignores, so delivered rows stand and nothing is withdrawn. Keeps are deliberately not deferred to a successful terminal result—letting the organizer start keeping at row one is the point of streaming, and a row that passed admission and was chosen is the organizer's whatever the classifier later says about the rest. `skipped` counts rows the server dropped before sending, by reason (§ Validation); the client adds its own refusals under the same keys, so the skipped line can name a cause ("1 skipped · over 80 characters", "3 skipped · 2 over 80 characters, 1 blank") instead of inventing one. A `spicy-check` whose model stops at `max_tokens` or whose fallback chain ends in `refusal` returns `verdict: null` with the `stopReason` rather than a fabricated `spicy: false`; the add bar then stays silent and the square stands as added, exactly as without the assist.

### Errors

`HttpsError` codes, in the order the handler checks them: `unauthenticated` (no uid); `failed-precondition` (App Check enforced and no app); `invalid-argument` (any request bound above); `resource-exhausted` with `details: { reason: 'allowance' | 'spicy-checks' | 'platform-ceiling', remaining }` from the admission transaction (each reason is its own § States row—Allowance spent, Checks spent, Platform ceiling—and `spicy-checks` never disables drafting); `unavailable` when the Anthropic SDK fails after its own retries (connection errors, 429, 5xx) or the stream ends with no `message_start`; `deadline-exceeded` when the handler's own budget runs out; `internal` otherwise, with the bounded code logged (`firestoreErrorCodeForLog`) and the thrown value never echoed. A refusal is not an error (above). The thrown message never contains the brief or any row text. Every code maps to a § States row: `resource-exhausted` to its three rows, `unavailable` and `deadline-exceeded` to Unreachable or Interrupted by whether a row was delivered, and the four that should not happen in normal operation—`unauthenticated` from a session the client thought was signed in, `failed-precondition`, `invalid-argument` (the client validates the same bounds before sending) and `internal`—to the one Request-refused row, which is honest rather than specific because none of them is something an organizer can act on beyond trying again later. The first three are refused before admission, so no unit was charged. `internal` is branched on delivery like `unavailable` and `deadline-exceeded`: before any row it is Request refused and refunds by the nothing-delivered rule; after a row (the post-stream ledger write failing, for instance) it is Interrupted, because kept rows are already the organizer's, the unit is not refundable, and "nothing changed" would be false.

### Model and prompt

Claude Opus 5.5, `claude-opus-5-5`, through `@anthropic-ai/sdk` from `functions/package.json`. Thinking is the model's default (adaptive; the `thinking` parameter is omitted) at `output_config.effort: 'low'`—squares are not a hard reasoning task, and effort is the one depth control on this model. Output is constrained with `output_config.format` to the task's JSON schema (`SquareRow[]`, the Day-copy list, `{ spicy, reason }`), so a row's shape is a schema fact within what the API's schema subset can say—object and array types, `enum`, `const`, `anyOf`, `required`, and `additionalProperties: false` on every object: a main row requires `spicy: boolean`, a curated row has no `spicy` property. What the subset cannot say is enforced by the validators on both sides instead (§ Validation): structured outputs reject string-length constraints (`maxLength`) and array bounds (`minItems`/`maxItems`) with a 400, so the 80-character bound is stated in the prompt and checked at admission, never written into the schema, and the Tonight pair is modelled in the model's schema as two required string properties (`tonightFirst`, `tonightSecond`) that the handler maps to the `[string, string]` tuple on the wire. The schemas are hand-written JSON and nothing strips an unsupported keyword on the way out, so `tests/functions/draft-with-claude-prompt-parity.test.ts` pins that no schema carries `minLength`, `maxLength`, `minimum`, `maximum`, `minItems` or `maxItems`. `fallbacks: 'default'` with the `server-side-fallback-2026-07-01` beta is on, so a safety-classifier decline is re-run on a fallback model inside the same call and only a whole-chain `stop_reason: 'refusal'` reaches the organizer. `max_tokens` is a per-task spend bound rather than headroom—8192 for `squares` and `top-up`, 2048 for `day-copy`, 256 for `spicy-check`—because hitting it is the Partial state the sheet already handles, and a runaway response is money. Requests stream (`client.beta.messages.stream`); the handler parses complete array elements as they arrive and validates each before `sendChunk`.

The prompt is a module, `functions/src/prompts/draftWithClaude.ts`, exporting the system block per task and the schemas. Its path is deliberate: `REVIEW_POLICY.md` § Phase 4b trigger 3 routes `**/prompts/**` to full review, so the editorial gate Decision 2 gave the owner over packs lands on the system prompt, once, rather than on every Event's squares. The fixed part—the register rules per Edition, the pool definitions (what an arrival, main, closing and warm-up Day deal), the audience rule, the format—is one system block carrying `cache_control: { type: 'ephemeral' }`, so repeat drafts pay for it once; everything volatile (the brief, the existing texts, the examples, the targets) comes after it in the user turn. `functions/` cannot import `src/` at runtime, so the registers are restated in the module and `tests/functions/draft-with-claude-prompt-parity.test.ts` pins them to `editionLexicon` in `src/editions.ts`, the `communityPromptRouting.generated.ts` posture without the generator.

The prompt tells the model three things the schema cannot, and the first two apply to the generation tasks (`squares`, `top-up`, `day-copy`) only: under `forceAdult: false` write nothing sexual and set no `spicy` (tone is a register knob—Gentle, Playful, Unhinged shape voice and dare level—and none of them means sexual); under `forceAdult: true` write about `spicyShare` of the main rows explicit and flag them; and steer clear of the `existing` texts, which are sent so a second draft does not repeat the first. `spicy-check` is a classifier, not a writer, and carries the opposite instruction: the audience rule is the reason the question is being asked, so it answers whether the text reads as sexual to a stranger regardless of `forceAdult`. A prompt that told it to set no `spicy` under All ages would answer `false` for exactly the squares it exists to catch, so the generation prohibition is scoped by task in the module and `tests/functions/draft-with-claude-prompt-parity.test.ts` pins that the `spicy-check` system text carries the classification instruction and not the prohibition. The `squares` prompt writes for each assigned pool its target count in that pool's register; `top-up` carries the angle (`more-like-these` with the kept texts as the taste to match, `top-up-pool` for one named pool, `different-angle` for the opposite register); `spicy-check` asks whether one text reads as sexual to a stranger and for one line of reason; `day-copy` asks, per Day and in the register, for a Place, one emoji, exactly two Tonight entries and a Free Space motto, with the kept squares as the voice to match.

### Secret, params and deploy surface

`ANTHROPIC_API_KEY` is `defineSecret('ANTHROPIC_API_KEY')` in `functions/src/params.ts`, exactly as `RESEND_API_KEY` is: a Secret Manager secret set per project with `firebase functions:secrets:set`, never an env var, never in `functions/.env*`, bound to the one function that uses it through `secrets:`. It is a key from a dedicated Anthropic Console workspace for Five Across with its own spend limit—the third cap in § Allowance and ledger, and the one that holds if the other two have a bug. `DRAFT_WITH_CLAUDE_APP_CHECK` (`defineBoolean`, default `false`) and `AI_MONTHLY_USD_CEILING` (`defineInt`, default `40`) are declared beside it, and both get assigned lines in `functions/.env.example` and, before the deploy that creates the callable, in the real `functions/.env.<projectId>` files—an omitted line, not an empty value, is what makes a non-interactive deploy hang on a prompt (#767). The ceiling default is a fifth of the grant per month, chosen so that a month of unexpected traffic cannot spend more than that without a human changing a number; it is a param so the owner changes it per project without a code change.

### Allowance and ledger

Two server-only documents, both `allow read, write: if false` in `firestore.rules` beside `bugReportRateLimits`, both leaf-only (no subcollection), both written only by the callable through the Admin SDK:

- `aiAllowances/{uid}`: `{ day: 'YYYY-MM-DD', drafts: number, checks: number, updatedAt }`. `day` is the UTC calendar day of the server clock; a document whose `day` is not today reads as zero. `drafts` counts draft units (cap 12); `checks` counts `spicy-check` calls (cap 120—ten per draft unit, so a typed-square habit cannot exhaust the drafts and a loop cannot run free). The copy says "back tomorrow" and never names a local midnight.
- `aiUsage/{yyyy-mm}`: `{ calls, inputTokens, outputTokens, cacheReadInputTokens, cacheCreationInputTokens, estimatedUsd, reservedUsd, updatedAt }`, summed across every account for the UTC month from each response's `usage.iterations`—one entry per billed attempt, primary and fallback alike, each priced by the model that ran it—not from the top-level `usage`, which covers only the attempt that produced the returned message and would omit a billed mid-stream decline and misprice fallback output. The price table in `functions/src/aiUsage.ts` is test-pinned per model id (`claude-opus-5-5` at `$4` input, `$20` output, `$0.20` cache read, `$5` cache write per million tokens, the list prices at the time of writing, plus the fallback targets at theirs); an iteration naming a model the table does not know is priced at the highest rate in the table and logged, so an unpublished fallback route can only over-count. The ledger is an estimate and the Console limit is the truth.

Admission is one Firestore transaction before any model work: read both documents; refuse `platform-ceiling` if `estimatedUsd + reservedUsd >= AI_MONTHLY_USD_CEILING`; refuse `allowance` if the task spends a unit and `drafts >= 12`, or `spicy-checks` if `checks >= 120`; otherwise increment the allowance, add the task's reservation to `reservedUsd`, and commit. The reservation is the task's worst case under the same price table the ledger uses: `ATTEMPTS_PER_CALL` input attempts (a test-pinned constant, 2—the primary and one fallback; `fallbacks: 'default'` publishes no chain depth, so the constant is a documented assumption and the Console limit is the backstop beyond it), each the request's bounded input priced as a cache write (the costliest input rate, since the cached system block is written on a miss), plus the task's `max_tokens` cap at the output rate, all at the costliest model in the table—so that concurrent calls cannot admit against a stale ledger: a v2 callable at `maxInstances: 10` still admits up to 80 requests per instance by default, and without a reservation a burst of signed-in accounts could pass admission hundreds of times before any post-stream increment landed. The post-stream write releases the reservation and adds the actual from `usage.iterations` with its cache fields (or the conservative abort estimate); a handler that dies between the two leaves its reservation in place, and the month's rollover retires it, which errs toward refusing late in a bad month rather than overspending. The invariant this buys is bounded by the constant: a chain that made more attempts than `ATTEMPTS_PER_CALL` exceeds its reservation by those attempts' input, which is what the Console workspace limit is for. The admission month (`yyyy-mm`) and day are captured in that transaction and reused by the post-stream write and the refund, so a run that straddles midnight is charged to the month and day whose ceiling admitted it. The unit is charged before the send, because a charge persisted before the call is the only one that survives a crash mid-stream. It is refunded (decremented in a second transaction) in exactly one case, the one the Unreachable state shows: the run ended with no row delivered to the client and the stop was not a refusal—the SDK failed before or after `message_start`, the handler hit its deadline, or the client went away before the first row (the admission chunk is not a row). A delivered row is one that reached the client—as a chunk on the streaming path, or inside the final response of a non-streaming call, which therefore keeps its unit when it returns rows; the handler counts delivered rows and decides the refund when the run ends, whatever ended it; the condition is "nothing delivered", not "nothing generated", because the organizer can only see the former. A refusal keeps its unit even with nothing delivered. The refund transaction carries the admission day and is a no-op unless `aiAllowances/{uid}` still names that day—a run admitted before midnight UTC and refunded after it would otherwise decrement the new day's count. A refusal, a `max_tokens` stop, a stream interrupted after rows arrived, and a Stop after the first row all keep their unit. A Stop—or Done, Escape or unmount—before the first row is, to the handler, indistinguishable from a dropped connection or the first-row timer, so it refunds like one: the organizer saw nothing either way, and no cancellation reason crosses the wire to say otherwise. The ledger is incremented after the stream ends, from the final message's `usage.iterations`, or—when the stream was aborted and no final message exists—conservatively, as one attempt per `fallback` block observed plus one: each attempt charged the request's input tokens as `message_start` reported them (a mid-stream fallback re-reads the same input, and its own usage would only have arrived in the final `usage.iterations`), and the run charged the task's `max_tokens` cap as output regardless of any `message_delta` seen (a delta is usage so far, not a bound), all priced at the costliest model the run named (`message_start`'s model or the `to` model of any `fallback` block), so an aborted run can only over-count the ledger, never under-count it; two concurrent calls can both pass admission and overshoot the ceiling by one call each, which is why the Console limit exists.

### Analytics and logs

Two names join `GA4_EVENTS` in `src/analytics.ts` and go through the one `track` seam (#96): `ai_draft_requested` with `{ task, main, easy, closing }` (the targets, or the Day count) and `ai_draft_kept` with `{ task, kept, dropped, edited, skipped }`. Counts only, never the brief, never a square, never a Place. Function logs follow the same rule: task, codes, counts, token totals, the bounded error code—no request or response text at any level.

## Behaviour per task

### Squares

The dashed ✦ row on Step 3 ("Draft squares with Claude · From the occasion, the place and a line about the group · you keep each one") opens the brief sheet, a sheet in the `AdminSheet` lineage, not a step. Its top band prints what the draft already knows—the occasion and the register its Edition binds, the name, the dates, the audience, the marking mode, the card format, the Day list with each Day's pool, the count of squares already typed—and asks for the one thing no field holds: who these people are. The brief is optional; an empty brief still writes a competent occasion, a full one writes *this* one. It is held in wizard-session state—the mounted wizard's own state, not the draft and not storage—so Step 4's Day copy can carry it in the same session; it is gone on reload (§ Open decisions 1). Beside the field, one privacy sentence in the sheet's own words (§ Open decisions 4): first names are fine; the brief and the squares already in the draft go to Claude through Five Across's own server, which keeps a count and not a copy; Anthropic handles them under its API terms and may keep them for a limited time (up to 30 days under its standard retention policy). The sentence distinguishes the two parties on purpose: Five Across's non-storage is a fact this spec can establish, the processor's retention is Anthropic's policy, and a sentence that said the brief "is not kept" would be claiming the second from the first.

Tone is Gentle / Playful / Unhinged. The spicy row reads the audience from Basics: under All ages it is static ("Spicy squares off · All ages, set in Basics") and the request forbids sexual content; under 18+ it is a share control. The sheet never claims the 18+ gate stays off either way—the posture is derived server-side from the flags (ADR 0012) and Step 5 shows the resolved result.

"How many" is per pool, because the gate is per pool: each assigned pool gets a target defaulting a few above `MIN_POOL`—`MIN_POOL + 8` (32) for main, `MIN_POOL + 4` (28) for the curated pools, so rows can be dropped without dipping under—capped at 40, beside the pool's current count from the same `countPrompts` the launch gate uses ("2 there · 24 needed"). A pool no Day deals from is not offered, the same idle state Step 3's counter shows. Below the targets, the allowance line prints the server's `remaining` from the last admission chunk or response this session, and "12 drafts a day" before any; it never counts for itself, and a stopped run still updated it because the admission chunk arrived first. A row disabled by Allowance spent or Platform ceiling re-enables when the window the copy names has passed by the device clock (the next UTC midnight or month boundary), so a wizard left mounted across the boundary can call again; the server's answer to that call is authoritative either way. Offline, Write is disabled with "needs a connection"; signed out, the ✦ row itself reads "Sign in to draft with Claude" and the add bar works as before.

Write calls the `squares` task. The review sheet replaces the brief sheet and fills as rows arrive under per-pool headings—"main · 26 kept · 24 needed ✓", "easy · 15 kept · 24 needed · still writing", "closing · waiting"—where the kept count is `countPrompts` over the pool as it stands, the organizer's own earlier squares included, so the heading says the moment a pool clears its minimum. Each row offers ✓ and ✕, and an edit that opens the text with Claude's original beneath it; the editor caps at `MAX_PROMPT_TEXT` like the add bar, and a keep re-runs `admitSquareRow` on the edited value—`addPrompt` trims and refuses blank but does not enforce the 80-character bound, and a kept over-long text would fail `parseEventDraft` on the next save and vanish on reload—so an edit that fails admission leaves the row undecided with the reason, and the kept text is what enters the draft. A ✓ commits that row through `addPrompt(draft, pool, text, spicy)` immediately—a reload mid-review loses nothing kept—and so passes the same trim, the same 80-character refusal and the same main-only `spicy` drop a typed square does. A ✕ leaves the row visible, struck through, because a vanished row is indistinguishable from one never written and the organizer may change their mind. "Keep all remaining" commits every undecided row through the same transform, one by one; it is explicit, never the default. "Stop writing" aborts the stream and keeps what is there. "Done" closes the sheet with the running count and commits nothing; while a run is still writing, Done, Escape and unmount all abort the same `AbortController` that Stop uses, because a stream no sheet can review would keep generating and billing rows.

A near-duplicate sub-line ("near your 'Windblown group selfie'") appears under a row whose normalized text—trimmed, `toLocaleLowerCase()`, the same key `duplicatePromptTexts` uses—matches a text already in the pool or already kept this session. It is advisory, as the wizard spec makes duplicates advisory: keep is still allowed. The skipped line ("1 skipped · over 80 characters") counts rows the client refused before showing them (§ Validation).

### Top-up

After a keep, the ✦ row on Step 3 survives as "More from Claude · More like these · Top up one pool · A different angle", because drafting appends and seeding replaces: `seedPack` swaps every pool for the pack and says so before the tap, a draft is a set of rows the organizer chose one by one, and a second draft never deletes a first. The three angles call the `top-up` task with `angle` set: `more-like-these` carries the kept rows as `examples`—the texts kept this session, newest first, capped at 120, which is the most one full draft can keep (three pools at the 40-per-pool target), so the first advertised follow-up after a full keep never trips the bound—so the second batch is written to the organizer's demonstrated taste rather than the brief alone; `top-up-pool` names one `pool`, because the shortfall the gate reports is per pool and writing 88 rows across three pools to fix a shortage of six closing squares spends the allowance badly; `different-angle` asks for the opposite register, for an organizer who kept too little to know what they want yet. The review sheet, the keep, the counts and the allowance are the ones § Squares describes; all three angles share the one allowance.

### Spicy check

The smallest assist and the most careful. When the organizer adds a main-pool square under All ages, the add bar calls the `spicy-check` task with the typed text and, on a verdict of `spicy: true`, turns the answer into a question rather than a change (on no verdict—`stopReason` of `max_tokens` or `refusal`, or any error—it stays silent and the square stands as added, never a fabricated `false`): "✦ Reads as 18+. Flag it spicy? That turns on the 18+ acknowledgement for everyone who joins." "Flag it" sets the flag through `setMainPromptSpicy` on the entry the add created—the client keeps that entry's object identity, which every transform preserves for entries it does not touch (the wizard spec's row-keying rule), and resolves its position in the current `draft.prompts.main` when the verdict arrives, so a deletion earlier in the pool while the check was pending cannot flag a different square, and a captured entry no longer present makes the verdict a no-op—exactly as the organizer's own tap would; "Keep it off" leaves the square unflagged, which is the organizer's right and the derivation's problem—the acknowledgement is theirs to under-state, as it already is by hand. The question says what the flag costs in the derivation's own terms, because an organizer who picked All ages in Basics is about to learn that the choice was half the verdict (ADR 0012).

It runs only for a main-pool add: `spicy` is unrepresentable on the curated pools (`DraftCuratedPrompt.spicy?: never`) and a verdict there would be a toggle that looks honoured and is silently dropped (#785). It does not run under 18+, where the audience already admits explicit squares and the organizer manages the flag by hand, nor while offline or signed out, and it never delays the add—the square is in the draft before the answer arrives, and the question is attached to its row. It spends no draft unit but has its own daily cap (§ Allowance and ledger): once the day's checks are spent the add proceeds exactly as it would without the assist, the add bar says so once (§ States, Checks spent), and the drafting rows are untouched, because a spent check cap says nothing about the draft allowance. It runs on the same model at the same low effort for now (§ Open decisions 3).

### Day copy

The dashed ✦ row on Step 4 ("Fill in the Days with Claude · Place, two Tonight entries and a free space per Day · keep or change each") calls the `day-copy` task once per schedule, carrying the kept squares as `existing`, the brief when the session still holds it (after a reload it runs from the kept squares alone), the Days with their pools and dates, and the register. It renders only for a daily-cards draft with at least one Day: a one-card Event has no Days, and a Custom draft that reaches Look with none gets `dayCountIssues`' "Add a Day" first, as it does today. The model answers against a schema whose Tonight pair is two required string properties (the API's schema subset has no array bounds, § Model and prompt), which the handler maps to the two-entry `tonight` tuple, so the "exactly two" rule `DayDef` and `firestore.rules` share holds by construction on the wire and is re-checked by both validators rather than hoped for.

Each Day renders Claude's Place, emoji, Tonight pair and Free Space as a proposal with its own keep and change: "change" opens the field with the suggestion as the starting text, and every keep commits through the Look transforms the step already has—`setDayPlace`, `setDayPlaceEmoji`, `setDayTonight` (slot 0 and slot 1), `setDayFreeText`—so a kept value is stored as typed and judged trimmed exactly as a hand-entered one. A Day the organizer has already filled by hand is not overwritten: the proposal renders beside the typed value and only a keep replaces it.

What is deliberately not suggested: unlock times (a clock decision with a reviewed 06:00 default and a zone the organizer chose in Basics) and Themes (`applyProposedDayThemes` already fills every unthemed Day from the occasion's `dayThemes`, the list is three registered palettes long per Edition, and a model picking among three contrast-audited token sets would be theatre dressed as help). The Free Space is the exception that proves it: it is copy—each Day's motto, the cheapest personality lever the organizer has—so it is written with the rest. The call is small (four Days of short strings, about $0.03) and spends one draft unit.

## States, refusals and caps

Every state the frames imply but do not draw. A row is a contract: what the organizer sees, what the system did, and why that rather than the obvious alternative.

## Validation

No new predicate joins the launch gate, and no new `DraftIssueCode` exists. The wizard spec's § Validation runs unchanged over a draft that kept assisted rows, because the rows entered through `addPrompt` and the Look transforms and are `{ text, spicy }` and Day fields like any other. What this spec adds is admission—what a row must satisfy to be *shown*—applied twice, on the server before `sendChunk` and on the client before render, because a response is data and the schema is a strong hint rather than a proof:

- **`admitSquareRow`** (`src/data/draftAssist.ts`, mirrored in `functions/src/draftWithClaude.ts`): `text` is a string whose trimmed length is at least 1 and whose raw length is at most `MAX_PROMPT_TEXT` (80)—raw, because `firestore.rules` applies `text.size()` to the value as persisted and `promptTextIssues` measures the same way; `pool` is one of `POOL_ORDER`; `spicy` is a boolean when `pool` is `main` and absent otherwise. A row failing any of these is dropped and counted under its reason (`overLength`, `blank`, `spicyOnCurated`, `malformed`). Both sides also drop a row for a pool the draft does not assign (`unassignedPool`), which the schema cannot know but the request's `days` do: the server applies `assignedPools` over the draft slice it was sent and never streams such a row, and the client re-checks against its own draft.
- **`admitDayCopy`**: `index` names a Day in the draft; `place` and both `tonight` entries are non-blank after trim and at most 60 characters raw; `placeEmoji` is exactly one grapheme (`Intl.Segmenter`); `tonight.length === 2`; `freeText` is non-blank and at most `MAX_PROMPT_TEXT`. A Day failing is skipped whole under its reason (`badTonight`, `badEmoji`, `unknownDay`, `overLength`, `blank`), never partially kept. Each requested Day index is accepted at most once: a later entry for a Day already seen is dropped under `duplicateDay`, and a requested Day with no entry renders as "nothing came for this Day" rather than looking complete by count, because the schema cannot impose uniqueness.
- **Near-duplicate key**: `text.trim().toLocaleLowerCase()`, the same normalization as `duplicatePromptTexts`, compared against the pool's existing texts and the rows kept this session. Advisory.
- **Keep paths**: a kept square goes through `addPrompt`; a kept Day field through the one Look transform for that field. Neither path is bypassed by "Keep all remaining", which iterates the same call, and neither is reachable by a row that was not admitted.
- **Server-side request bounds** (§ Request) are the only validation the callable performs on the draft slice; it does not re-run the launch gate, because it launches nothing.

## Open decisions (owner)

Each is the owner's call, not this spec's; v1 builds the default named unless the owner rules first.

1. **Does the brief persist in the draft across a reload?** `EventDraft` has no field for it, so keeping it is a `DRAFT_SCHEMA_VERSION` bump in `src/data/eventDraft.ts` (#787's forward-migration lever) plus a `brief` field with its own 600-character bound in `parseEventDraft`. v1 default: not persisted; the brief lives in wizard-session state for as long as the wizard is mounted—which is what lets Step 4's Day copy send it—and a reload costs retyping a sentence, with Day copy running from the kept squares alone until it is retyped.
2. **Per-Prompt provenance.** A kept row is an ordinary `{ text, spicy }`, indistinguishable afterwards from a typed one; recording "written by Claude" is a `DraftMainPrompt`/`DraftCuratedPrompt` change behind a `DRAFT_SCHEMA_VERSION` bump, and the provisioner would have to decide whether to carry it onto `ItemDoc`. v1 default: none—the organizer's keep is the authorship, so there is nothing a provenance flag would entitle anyone to do differently, and the Launch checklist needs no "written by Claude" row for the same reason the 18+ row needs none.
3. **Does `spicy-check` move to a cheaper model?** It runs on `claude-opus-5-5` at low effort for now. Measured against a few hundred typed squares, it is the one task here `claude-haiku-5-5` could carry without anyone noticing; that is a measurement to make, not a default to assume. The model id is a per-task constant in the prompt module so the switch is one line.
4. **The privacy sentence versus a policy page.** A first name in a brief, or in a square the organizer already typed (every task forwards the pool's `existing` texts), is personal data leaving the device: it travels to Five Across's callable and on to Anthropic's API under Five Across's key and that API's commercial data terms, and the callable keeps a count, not a copy, while Anthropic's standard API retention keeps inputs for up to 30 days. v1 default: one sentence on the sheet, beside the field, in the words § Squares gives, naming both parties.
5. **Does Step 3 require sign-in today?** The ✦ row needs an account (the allowance is per account) and reads "Sign in to draft with Claude" when signed out, while the add bar keeps working. Whether the step itself should gate on sign-in—which would make every draft an account's draft well before Launch—is the owner's call. v1 default: the row gates, the step does not.

## Deliberately not in scope

- **Persisting undecided rows or resuming a stream.** Both need draft fields that do not exist (§ States, Reload mid-draft).
- **Starter packs.** `STARTER_PACKS` stays empty and every `starterPackId` stays `null`; the assists are the per-Event alternative, not a pack authoring tool. A pack, when the owner authors one, seeds through `seedPack` as before.
- **Anything structural.** The schedule shape, Day count, pool assignment, `tutorial`, unlock times, Themes, the slug, the marking mode, the audience, the Daily mix. The assists write words.
- **Moderation of kept text beyond the spicy verdict.** The Community Prompt admission queue and Cloud Vision are different surfaces for different authors; an organizer's own squares are theirs.
- **Post-launch assists.** Nothing here reaches Admin; the callable takes a draft slice and nothing else.
- **An Event-wide Free Space.** The wizard spec records that `EventDoc` has no field for it; `day-copy` writes the per-Day `freeText` that exists.
- **A cheaper model, a persisted brief, provenance.** Each is an open decision above, not a silent default.
- **Server-side drafts.** Still modelled as a seam only (#786 Decision 1); the callable writes no draft.
