# Update-reload prompt: tell players a new deploy is ready and let them reload onto it (`src/components/UpdatePrompt.tsx`)

Before this ticket (#178), `vite-plugin-pwa` ran with `registerType: 'autoUpdate'`: a new deploy's service worker activated silently under the running page, so a tab or installed PWA left open—the norm during an Event, where a session lasts days—kept executing the old bundle indefinitely, never told that fixes or features had shipped, and could hit failed dynamic imports once its old hashed chunks left the precache. This ticket switches to `registerType: 'prompt'` (`vite.config.ts`): the new service worker installs and **waits**, and a new `UpdatePrompt` component surfaces that state as a themed bottom banner offering **Reload** (activate the waiting worker, reload onto the new build) or **Not now** (decline *that build*—see § "Not now" declines a BUILD, not a session). This is the same player-facing feature Nathan's other apps (friendsandfamily-billing's `UpdateToast`, overridebroadway's `UpdateChecker`) implement by polling a version file; here it rides the service-worker update lifecycle the app already ships, with a periodic `registration.update()` check standing in for the poll. Exercised by `src/components/app-update-reload-prompt.test.tsx` (RTL-jsdom).

## `needRefresh` drives the banner; Reload activates the waiting worker; Not now declines that build

`useRegisterSW` (`virtual:pwa-register/react`) exposes `needRefresh`, which flips true when a new service worker has installed and is waiting.

- **Given** no update is pending **when** `UpdatePrompt` mounts **then** it renders nothing. (Test: "renders nothing (and never sets the body class) while no update is pending".)
- **Given** a new version is waiting (`needRefresh` true) **when** the banner shows **then** it announces the update ("A fresh build just docked—your marks are safe.", copy retimed and restyled by #219, see `specs/d15-pwa-toasts.md`; the "just docked" title is the `gcb` Edition's value and the string is Edition-scoped since #608—`src/editions.ts`) and tapping **Reload** calls `updateServiceWorker(true)`—the plugin's activate-then-reload path (it messages the waiting worker to `skipWaiting` and reloads once it takes control). (Test: "shows the banner when a new version is waiting, and Reload activates it with a page reload".)
- **Given** the banner is up **when** the player taps **Not now** **then** the banner hides and the waiting worker is left untouched—Reload, every window closing, and the floor lever all still release it. (Test: ""Not now" hides the banner without touching the waiting worker".)

## "Not now" declines a BUILD, not a session (#605)

`needRefresh` reports a **state**—"a worker is waiting"—not an event. `workbox-window`'s `register()` dispatches a `waiting` event carrying `wasWaitingBeforeRegister: true` whenever `registration.waiting` already exists, and `vite-plugin-pwa` turns that straight into `onNeedRefresh()`. So every launch re-registers, re-observes the same waiting worker, and re-raises `needRefresh`. The original dismissal was `setNeedRefresh(false)`—React state with no storage behind it—so the toast came back on **every** launch for one and the same build, and a player who kept declining kept being asked while staying on a stale build. That is #605: a client still running the 2026-07-31 build four days and many deploys later, prompted at every launch. The behaviour was working as built; what was missing was any notion of *which* build had been declined.

A dismissal therefore names a build. The waiting worker's identity is not visible from the page—every worker is served from `/sw.js`, so `scriptURL` is identical and the build stamp exists only inside the script—so the page asks it: `GET_BUILD_STAMP` over a `MessageChannel`, answered by `src/sw.ts` on the caller's port with its baked-in `__BUILD_STAMP__`. The reply is stored in one `localStorage` slot (`gcb.update.dismissedBuild`, `src/updateDismissal.ts`), matched exactly, and overwritten by each later decline. Suppression hides the **offer** only: `needRefresh` stays true underneath, so the #342 floor lever still reaches a declined build.

- **Given** the player declined a waiting build **when** the app is launched again and that same worker is still waiting **then** no banner is offered and no body clearance is reserved. (Test: ""Not now" declines the WAITING BUILD, so the same build does not re-ask on the next launch (#605)".)
- **Given** a decline is on record **when** a **different**, newer worker is waiting **then** the banner is offered again—the suppression covers one build, never the offer itself. (Test: "a genuinely NEWER waiting build prompts again after a decline (#605)".)
- **Given** a declined build is suppressed in an open tab **when** a **replacement** worker installs and reaches `waiting` in that same tab **then** the identity question is re-opened and the newer build is offered. The trigger is the waiting `ServiceWorker` object's identity, not `needRefresh`: that flag is already true while a build is suppressed, so workbox re-raising it is a no-op React never sees, and keying off it alone would suppress every later build for the tab's lifetime. The component notices a replacement three ways—the worker already waiting at registration, `updatefound` followed by that worker reaching `installed`, and a changed `registration.waiting` observed by the periodic update check (which also covers a worker installed by another tab). (Test: "re-opens the offer when a REPLACEMENT worker starts waiting mid-session (#605)".)
- **Given** the waiting worker does not answer the query—a worker built before this handler existed, or no service worker at all **when** the player declines **then** nothing is recorded and the next launch prompts again. Fail-open is deliberate: with no identity to key on, a persisted dismissal could only be an indefinite one, so the transition costs exactly one more prompt rather than risking a silent forever-mute. (Test: "declining a build the waiting worker cannot name suppresses nothing—the pre-#605 transition (#605)".)
- **Given** a declined build is waiting **when** the served floor condemns the running build **then** the forced activation still fires, because the decline suppresses the banner and not `needRefresh`. (Test: "a DECLINED build is still force-activated when the floor condemns the running one (#605/#342)".)
- **Given** the player taps **Not now** **when** a floor bump arrives afterwards **then** the force still fires, and `needRefresh` is still true—the decline hides the offer through its own state and never clears the flag, which remains accurate (a worker really is waiting) and is what the #342 force path keys off. The earlier `setNeedRefresh(false)` left that path resting entirely on #342's `sawWaitingSW` ref latch, a latch added for that very dismissal behaviour. (Test: ""Not now" leaves needRefresh true, so a floor bump AFTER the decline still forces (#605/#342)".)
- **Given** the identity query has not settled yet—the banner is offered without waiting when nothing has been declined **when** the player taps **Not now** **then** the decline still names the waiting build, because the handler awaits the same in-flight query rather than reading a not-yet-settled value. (Test: "records the decline even when the player taps "Not now" before the build is identified (#605)".)
- **Given** a decline is on record **when** the app launches **then** the banner is held until the identity query settles, so a declined build cannot flash up before the answer lands; with **no** decline on record the banner is not held at all, since no answer could suppress it and a worker that never replies would otherwise delay the offer by the query timeout.
- **Given** storage refuses the read or the write **when** a decline is made or checked **then** nothing throws and nothing is suppressed. (Tests: "fails open—and never throws—when storage refuses", "records nothing for an unidentifiable build, so it can never suppress indefinitely", "keeps only the most recent decline—one slot, overwritten".)
- **Given** a waiting worker carrying this handler **when** it is asked for its build stamp **then** it answers on the caller's port and does **not** promote itself—releasing the worker remains Reload's job alone. (Tests: "answers GET_BUILD_STAMP on the caller`s port, so the page can name the waiting build (#605)", "tolerates a GET_BUILD_STAMP that arrives with no port to answer on".)

**What the tests here do not prove.** jsdom runs no service worker, so `src/updateDismissal.test.ts` and the component's "relaunch" cases model the round trip with a fake registration and an unmount/remount pair. That is a faithful model of the browser's behaviour (workbox re-announces an already-waiting worker on every registration) but it is a model: no unit test can show that a browser delivers `GET_BUILD_STAMP` to a worker in the `waiting` state, any more than the directly-dispatched handler tests in `src/sw-worker.test.ts` could show that navigations reach a `fetch` listener (#517, where exactly that assumption was false in production). Delivery is only ever established in a browser.

## A long-lived tab discovers new deploys: periodic `registration.update()`, offline-tolerant

The browser only re-checks `sw.js` on its own schedule (navigations, and at most daily); a tab that stays open on an unreliable network would otherwise not learn about a deploy for a very long time. `onRegisteredSW` arms a 60-second `setInterval` calling `registration.update()`—the cadence the other apps' version polls use. `firebase.json` already serves `/sw.js` with `Cache-Control: no-cache` (see `specs/w4-hosting-index-shell-cache.md`), so each check observes a new deploy immediately.

- **Given** the service worker registered **when** the interval elapses **then** `registration.update()` is called once per tick. (Test: "arms a periodic registration.update() check so a long-lived tab discovers a new deploy".)
- **Given** the device is offline (`navigator.onLine === false`, common mid-Event) **when** a tick fires **then** the check is skipped—no wasted round trip; the next tick retries. (Test: "skips the update check while offline (navigator.onLine === false)".)
- **Given** a check fails transiently (rejected `update()`) **when** the rejection lands **then** it is swallowed—no unhandled rejection; the next tick retries. (Test: "tolerates a registration.update() rejection (transient network failure) without unhandled errors".)
- **Given** an environment with no usable registration (no SW support) **when** `onRegisteredSW` fires with `undefined` **then** no interval is armed. (Test: "does nothing when registration is unavailable (no SW support)".)

The interval is deliberately not torn down: `UpdatePrompt` mounts once at `main.tsx` and lives for the page's lifetime, matching `useRegisterSW`'s own register-once model. On the transition deploy itself, pages still running the previous `autoUpdate`-built client have no prompt listener; they pick up the new worker on their next full app launch as before—one release where open tabs aren't prompted, self-resolving.

## Remote build floor can force a stale cached shell onto a newer waiting worker

For emergency stale-shell eviction (#342), `public/build-floor.json` carries an ISO `floor` timestamp and production bundles bake an ordered `__BUILD_STAMP__` at build time. `UpdatePrompt` reads `/build-floor.json` with `no-store` and a cache-busting query; if the running bundle's stamp is older than the served floor and a newer service worker is already waiting, the component calls `updateServiceWorker(true)` immediately instead of rendering the dismissible banner. The shipped floor is inert (`1970-01-01T00:00:00.000Z`) and is bumped manually only when cached clients must be forced forward; malformed floors, fetch failures, and builds at or newer than the floor fail open to the normal prompt.

- **Given** a new version is waiting and the running build is below the served floor **when** the floor read settles **then** `UpdatePrompt` activates the waiting worker with `updateServiceWorker(true)` and never exposes the **Not now** offer. (Test: "force-activates a waiting SW without offering the banner when the running build is below the served floor".)
- **Given** the served floor is inert or older than the running build **when** a new version is waiting **then** the normal reload offer remains available and no forced activation occurs. (Test: "keeps the normal offer when the served floor is inert (older than the build)".)
- **Given** the first floor read is still pending **when** a waiting worker exists **then** the banner is held until that read settles, so the user cannot dismiss before the force decision is known. This wait is bounded by the floor fetch timeout; a failed read resolves to the safe normal-prompt path.
- **Given** an operator bumps the floor after a tab has already mounted **when** the 10-minute floor re-read observes the newer floor **then** an already waiting worker is still force-activated, even if the player previously tapped **Not now**. `UpdatePrompt` latches that a waiting worker exists separately from the dismissible `needRefresh` state so dismissal cannot defeat the emergency lever. (Test: "a floor bump observed AFTER \"Not now\" still forces the reload—dismissal cannot defeat the floor".)

## The floor also has an out-of-tree path, because the in-tree one dies with the app (`src/shellRecovery.ts`)

Everything above assumes the React tree is alive: the floor read, the waiting-worker latch, and `updateServiceWorker(true)` all live inside `UpdatePrompt`. The 2026-07-24 blank-screen incident broke that assumption. The cells-map migration (`specs/cells-map.md`) flipped the Board `cells` wire shape, so clients on a pre-migration precached shell threw during render; React unmounts the **whole root** when an error escapes with no boundary, which took `UpdatePrompt` down with the app. The waiting worker then had no one left to activate it, and the floor lever could not fire either—its own check had just been unmounted. Those clients served the broken shell forever, on every reload.

So the floor now has **two** paths, and the in-tree one is no longer the only one. The friendly path above is unchanged and still preferred: a waiting worker, a banner or a silent force, activation via `updateServiceWorker(true)`. The recovery path is new, runs from `src/main.tsx` module scope (never from a component), and does **not** depend on a waiting worker existing—it unregisters every service worker, deletes the workbox precache, and reloads, because a stranded client's worker is waiting precisely because nothing is alive to tell it to activate. The `proof-media` runtime cache is deliberately preserved. `src/components/ErrorBoundary.tsx` invokes the same teardown when it catches a crash. Exercised by `src/shellRecovery.test.ts` and `src/components/ErrorBoundary.test.tsx`.

- **Given** the running build is below the served floor **when** the module-scope check settles **then** the shell is torn down and the page reloads, whether or not a newer worker is waiting. (Test: "resets a build BELOW the floor—the stranded-client rescue".)
- **Given** the running build is at or above the floor, or the floor is inert or unreadable **when** the check settles **then** nothing happens. (Tests: "leaves a build AT OR ABOVE the floor alone", "does nothing when the floor is inert (the shipped default)", "does not reload when the floor cannot be read (offline mid-cruise)".)
- **Given** a tab has already spent its one automatic attempt **when** another reset is requested **then** it is refused, so a floor set newer than every build cannot reload-loop. The latch is `sessionStorage`-scoped, so closing the tab restores the attempt. (Test: "fires at most ONCE per tab, so a misconfigured floor cannot reload-loop".)
- **Given** the attempt cannot be **durably** recorded—a readable-but-unwritable store, where `setItem` resolves but nothing persists **when** a reset is requested **then** it is refused rather than run unbounded. The floor stays armed, so the rescue is deferred, not cancelled. (Tests: "reports FAILURE when the store silently drops the write", "declines to reset when the attempt cannot be durably recorded".)
- **Given** the origin cannot be positively confirmed reachable **when** a reset is requested **then** the teardown is skipped and the page merely reloads onto the same cached shell. The precache is the only copy of `index.html` and the bundle the device has; deleting it without a replacement in reach replaces the recovery panel with the browser's offline error page, and the installed PWA cannot reopen until connectivity returns. `navigator.onLine === false` is trusted as proof of *offline*, but its `true` is explicitly **not** trusted as proof of *online*—unreliable networks and captive portals, this app's primary surface, leave it true while the origin is unreachable. So the destructive path demands a completed same-origin request: a `no-store` fetch of `/build-floor.json`, which is deliberately un-precached (the workbox glob excludes `.json`) and served `no-cache`, so a real 200 proves the ORIGIN answered rather than a cache. A bare `res.ok` is explicitly not enough, because `fetch` follows redirects by default and a captive portal that bounces the request to its own login page returns a perfectly readable 2xx. Three independent barriers must hold, since a portal only has to defeat one: the request is made with `redirect: 'error'` so a bounce rejects rather than resolves; the FINAL response URL must still be same-origin, covering interceptors that proxy in place rather than redirect; and the body must parse as the build-floor document, which no login page will. There is deliberately no "connectivity already proven" bypass for `enforceBuildFloor`: `fetchBuildFloor` carries none of those barriers, so accepting its success as proof would let a portal returning parseable floor JSON back in through the side door. Every teardown runs the same probe. (Tests: "does NOT tear down when the origin is unreachable despite navigator.onLine === true", "does NOT tear down when the origin answers non-OK", "does NOT tear down when the probe was REDIRECTED (captive portal bounce)", "does NOT tear down when the final URL is CROSS-ORIGIN (in-place interception)", "does NOT tear down when the body is not a build-floor document", "requests the probe with redirect:error so a bounce rejects outright", "has NO connectivity-proven bypass—every teardown runs the hardened probe", "runs the hardened probe before tearing down, even on the floor path", "reloads WITHOUT tearing down the shell while offline", "skips the probe entirely when definitely offline", "does not even probe the floor while definitely offline".)
- **Given** the app crashes before `initPostHog` has settled—the startup case this whole path exists for **when** the boundary reports `app_crash` **then** the event is queued, persisted to `sessionStorage`, and replayed once the SDK is live, after the pending identify so it is attributed rather than orphaned anonymous, and sent with `sendBeacon` so the reload cannot drop it in flight. Init is fire-and-forget and awaits ingest-host probes while `main.tsx` renders synchronously, so a startup crash reliably lands in the not-ready window where a plain capture would simply vanish. The persistence matters because the queue's main customer reloads immediately: the boundary starts `resetShell()` right after queueing, and its same-origin probe can finish long before the EXTERNAL ingest probes—the blocked-proxy case on a restricted network—so a memory-only queue would die with that navigation. The persisted queue is drained exactly once, so a failed replay cannot re-send on every later load. (Tests: "replays a capture that arrived BEFORE init settled (#513—the startup-crash report)", "replays a queued capture that survived a RECOVERY RELOAD (#513)", "drains the persisted queue exactly once, so a replay cannot re-send forever", "replays a queued capture AFTER the pending identify, so it is not orphaned anonymous", "beacons the crash report so the auto-reload cannot drop it".)

## The worker rescues itself when the page cannot help (`src/sw.ts`, `src/sw-rescue.ts`)

Both paths above still assume something in the CLIENT BUNDLE runs—the banner needs React, and the module-scope check needs `main.tsx` to be evaluated at all. Neither reaches a client stranded on an OLDER shell: its old bundle has no floor check, its React tree is dead, and its newer worker sits in `waiting` forever because `updateServiceWorker(true)` is only ever called by a page that is no longer running. That was the cohort the 2026-07-24 incident produced, and #513 could not recover it (Phase 4b P1 on #513, filed as #514).

The way out is that a **waiting worker has already been installed**—the browser evaluated its script and fired its `install` event. Logic placed in `install` therefore runs on a stranded client, in a context the dead page cannot affect, and can call `skipWaiting()` to promote *itself*. The browser re-checks `/sw.js` on navigation and it is served `no-cache` (`firebase.json`), so a stranded player simply reloading is enough to deliver this code. #514 switches `vite-plugin-pwa` to `injectManifest` for this reason: a generated worker had nowhere to put an install-time check. Everything generateSW previously did is ported verbatim into `src/sw.ts`—precache and `cleanupOutdatedCaches`, the navigation fallback and its `/__/*` denylist (`specs/sw-auth-handler-denylist.md`), the proof-media `CacheFirst` (#363), and the `SKIP_WAITING` handler the prompt path depends on.

The decision itself is pure and lives in `src/sw-rescue.ts`, unit-tested without a service-worker environment. A worker force-activates only when the ACTIVE shell is below the served floor **and** the new worker is not itself below it. Each activation records its own `__BUILD_STAMP__` in a dedicated `gcb-shell-meta` cache so the next worker can tell what it is replacing; an unrecorded stamp—every worker built before #514, which is exactly the stranded cohort—reads as ancient.

- **Given** an armed floor and an active shell below it **when** a new worker installs **then** it calls `skipWaiting()` without waiting to be asked, then claims the clients and navigates each window to its own URL, so a blank crashed tab lands on the new shell with no cooperation from the page. (Tests: "rescues a shell that is below an armed floor", "rescues a shell that recorded NO stamp—every pre-#514 worker, i.e. the stranded cohort".)
- **Given** the inert shipped floor (`1970-01-01T00:00:00.000Z`) **when** any worker installs **then** it never force-activates, including on the very first deploy of this feature, when no client has a recorded stamp. `UNKNOWN_ACTIVE_STAMP` is deliberately one millisecond after the epoch so that an unrecorded shell is not "below" the inert floor—if those two values ever meet, shipping the feature force-activates the entire fleet. (Tests: "NEVER forces under the inert shipped floor, even with no recorded stamp", "pins UNKNOWN_ACTIVE_STAMP strictly after the inert floor".)
- **Given** an active shell at or above the floor **when** a new worker installs **then** the normal `registerType: 'prompt'` path is untouched and the player still gets the banner. (Test: "leaves an up-to-date shell alone under an armed floor".)
- **Given** a floor newer than every existing build **when** a worker installs **then** it does not force-activate, because promoting onto a shell the same floor condemns is churn rather than rescue. (Test: "does not force when THIS worker is also below the floor".)
- **Given** a floor document that did not demonstrably come from this origin—a redirected response, a cross-origin final URL, or a body carrying no `floor` string **when** a worker installs **then** it is discarded and no activation follows. Inside the worker a forged floor is not merely a bad reachability signal but an ACTIVATION COMMAND: a captive portal answering with a parseable `{ "floor": … }` would otherwise have the worker `skipWaiting()`, claim every client, and reload every window on the portal's say-so. The same three barriers as `originReachable` (`src/shellRecovery.ts`) therefore apply—`redirect: 'error'`, a same-origin final URL, and a parseable floor payload—because a portal only has to defeat one. (Tests: "requests with redirect:error so a portal bounce rejects outright", "rejects a REDIRECTED floor response", "rejects a floor whose FINAL url is cross-origin (in-place interception)", "a forged floor cannot reach the activation decision at all".)
- **Given** a missing, malformed, non-string, or unreachable floor **when** a worker installs **then** it never force-activates, and `install` still completes—a worker that cannot install is a worker that can never rescue anyone. The floor read is bounded by its own timeout so a captive portal that accepts connections and never answers cannot stall installation. (Tests: "fails closed on a missing, malformed, or non-string floor", "a null floor can never force an activation", "is bounded, so it cannot stall the install it runs inside".)
- **Given** the floor probe fails transiently—the ordinary case on an unreliable network **when** a worker installs **then** it retries within that same `install`, because this worker gets exactly one. A waiting worker never re-runs `install`, and the browser finds `/sw.js` byte-identical on later navigations and does nothing, so a probe lost to a flaky connection would otherwise mean the rescue silently never fires—and the probe happens during a reload on a bad connection, the worst available window. The retries are bounded, each attempt is cache-busted separately so an intermediary cannot answer the retry from the failed attempt, and no delay follows the last one. The honest remaining limit, corrected after Phase 4b flagged the earlier wording as an overclaim: if all attempts fail, this worker still finishes installing and settles into `waiting`, and it will **never** get another `install`. Whether restored connectivity recovers it depends entirely on which worker is in charge. If the ACTIVE worker carries this feature, its own throttled re-check picks up the armed floor on a later navigation and evicts. If the active worker predates the feature—the transition case, and precisely the cohort the rescue targets—nothing recovers it: navigation `fetch` events go to that legacy worker, the waiting one receives no events, and only a byte-different `sw.js` (i.e. another deploy) or every window closing will move it. That is the same transition limit the operating rule below addresses, and it is why the rule is to arm the floor BEFORE deploying. Baking the floor into the build would remove the network dependency but tie the emergency lever to a redeploy, which is precisely what #342 built `build-floor.json` to avoid. (Tests: "retries a transient failure—the worker only ever gets ONE install", "stops at the attempt budget and does not sleep after the last one", "does not retry once a floor is read—including the inert one", "cache-busts each attempt separately".)
- **Given** a forced-activation marker written by a worker whose installation was then discarded—Workbox's separate precache listener rejecting on one unavailable asset is enough **when** a later, unrelated worker activates **then** it ignores the marker and clears it, because the marker carries the build stamp of the worker that wrote it. Otherwise an orphaned boolean would have some later worker claim and navigate every open tab, possibly long after the floor was disarmed. (Tests: "is IGNORED by a different worker—an orphaned marker cannot ambush one", "CLEARS an orphaned marker rather than leaving it to ambush a later worker".)
- **Given** the browser tears the worker down between `install` and `activate`, which the lifecycle permits **when** it activates **then** it still claims and navigates, because the decision is persisted in `gcb-shell-meta` rather than held in module state. Losing it would leave `skipWaiting()` done but the navigation skipped, so the reload that DISCOVERED the update finishes on the old broken shell and the stranded player has to reload a second time—the exact dead end this feature exists to end. The flag is consumed as it is read, so a later ordinary activation cannot inherit a stale force and yank the player's windows. (Tests: "still claims and navigates when the worker was TORN DOWN between install and activate", "consumes the persisted decision, so a LATER ordinary activation does not re-navigate".)
- **Given** storage that refuses the stamp record **when** it is read or written **then** neither throws, and the next worker reads `null`—the safe reading (ancient), never a wrong one. The record lives in `gcb-shell-meta`, which `src/shellRecovery.ts` deliberately does not sweep (it deletes only `workbox-precache*`), so it survives a client-side reset. (Tests: "never throws when the Cache API refuses", "uses a dedicated cache the shell teardown does not sweep".)

### The active worker re-reads the floor too, or the lever would need a redeploy

The install-time check alone cannot deliver what #342 promised. A worker installs, reads the floor—**inert**, which is what it ships as, so this is the normal state for every client—and settles into `waiting`. Arming the floor afterwards changes nothing: later update checks find the same byte-identical `sw.js` and never dispatch `install` again, and the dead page cannot message the waiting worker. The floor would then only work when paired with a deploy, which is exactly the coupling `build-floor.json` was created to remove. So the ACTIVE worker re-reads it as well.

A worker has no timers that survive termination, so the re-check rides the `fetch` event an ordinary navigation already generates. It never calls `respondWith`, so routing is untouched—workbox's own handlers still serve the request—and it is throttled by a persisted timestamp, because a worker is killed whenever it goes idle and an in-memory throttle would reset constantly.

**Its listener MUST be registered before workbox touches routing, and that ordering is load-bearing (#517).** A `fetch` listener added after workbox's router never receives navigation events at all: once the router calls `event.respondWith()`, the browser stops dispatching that request to later listeners. Requests workbox does not handle still arrive, so the listener looks alive while navigations silently bypass it—which is exactly what shipped in #515 and reached production, where the re-check never ran once. Instrumenting the deployed worker showed it seeing `cors` and `no-cors` requests and never `navigate`. The order is asserted directly, because the behavioural test alone passes even when the listener is mis-ordered.

- **Given** a worker serving a build the floor now condemns **when** a navigation wakes it **then** it drops the precache and unregisters itself, sending the next navigation to the network for a fresh shell. It does this whether or not a replacement is already waiting: an active worker cannot read a waiting worker's build stamp, so promoting one could swap a condemned build for another condemned build—and the replacement would inherit the throttle record just written, so it would not re-evict for the full interval either. Going to the network sidesteps the comparison entirely, because whatever is deployed is necessarily at or above the floor. Deliberately drastic, reachable only on an armed floor, and the same trade `src/shellRecovery.ts` makes client-side—including sparing `proof-media`. (Tests: "EVICTS rather than promoting a waiting worker, whose build it cannot vouch for", "evicts itself when there is no replacement to promote".)
- **Given** the inert floor, a non-navigation request, or a re-check already performed inside the throttle window **when** the worker wakes **then** nothing happens. (Tests: "does nothing under the inert floor", "ignores non-navigation requests entirely", "throttles: a second navigation does not re-read the floor", "registers the fetch listener BEFORE workbox touches routing", "the fetch handler reaches the floor record on a navigation".)
- **Given** a FIRST install, where there is no existing worker at all **when** the floor is armed **then** no forced activation occurs. `readActiveStamp()` returns null both for a legacy pre-#514 worker and for a brand-new registration, and treating the latter as ancient would have a fresh client claim and re-navigate a page already running the current build—discarding whatever the player did while the initial precache was still installing, sign-in included. `registration.active` is what tells them apart. (Test: "does not force-activate when there is no existing worker at all".)

**The one case neither check covers, and the operating rule it implies.** A client stranded on a PRE-#514 shell is controlled by a worker that has none of this logic—so navigation `fetch` events go to that legacy worker and the active-worker re-check never runs, while the newly installed worker sits in `waiting` receiving no events at all. For that cohort the only code that can act is a *newly installing* worker, and a worker reads the floor exactly once, during `install`. The operating rule therefore is: **arm the floor BEFORE deploying, not after**—armed-then-deploy means the new worker reads an armed floor during its install and rescues; deploy-then-arm means it already installed under the inert floor, `sw.js` is byte-identical on every later check so `install` never re-fires, and the arming reaches nobody in that cohort until the next deploy. This is documented as a runbook in `DEPLOYMENT.md` § "Emergency: evicting stale cached shells". It is a genuine limitation of the transition, not of the steady state: once a client runs a build carrying the rescue, its active worker re-reads the floor on its own and a later arming reaches it with no deploy at all.

`/build-floor.json` stays out of the precache glob (which covers only `js,css,html,svg,png,woff2`) precisely so a stale worker can never answer its own eviction notice from cache.

### The rescue decides on what each tab is EXECUTING, not on the shell being SERVED (#516)

`gcb-shell-meta` records the stamp of the worker that most recently ACTIVATED, which is not the build every open tab is running. Two tabs on build A, one of which accepts B's reload prompt: activation records B, so a floor armed between A and B reads "the active shell is fine" and abandons the tab still executing A. So each page names itself. `src/main.tsx` posts `{ type: 'CLIENT_BUILD', stamp: __BUILD_STAMP__ }` to the controlling worker at module scope, before any rendering (`src/swClientBridge.ts`), so even a page that crashes on mount has registered; the worker keeps that `clientId → stamp` map in `gcb-shell-meta` so it survives the teardown the lifecycle permits, and evicts entries whose `clientId` no longer appears in `clients.matchAll()`. An uncontrolled page has no controller to post to, so the post is retried on `controllerchange` **and** sent to `registration.active` once `container.ready` resolves. That second path is not belt-and-braces: this worker never calls `clientsClaim()`, so an uncontrolled page is a permanent state rather than a transient one — a first-ever visit, the load right after `shellRecovery.clearShell()`, and every run of the uptime synthetic (a fresh browser profile each time) would otherwise never register at all, and an unregistered live window is a CONDEMNED one.

For the same reason the uptime synthetic (#142) is excluded from the reload watcher but **not** from naming its build. `src/main.tsx` skips `armUncontrolledUpdateReload` for the probe, because a probe run is never a reload, and still calls `postClientBuild`, because naming a build is a `postMessage` that reloads nothing. A silent probe is a same-origin window `clients.matchAll()` can see and the registry cannot, which is exactly the shape the decision reads as an ancient stranded tab: it would force-activate the fleet on an armed floor with no stale tab anywhere and then navigate the probe out of the load it is asserting, turning an incident deploy into a false outage alert. It is the same trap the `/__/*` sign-in-popup filter avoids from the other side. The invariant is that absence from the registry means the page's module scope never ran, so nothing that does run it may opt out.

- **Given** two tabs on different builds and a floor that condemns only the older one **when** a new worker installs **then** it force-activates — the decision is taken against the OLDEST of the served shell and the open windows — and navigates only the tab actually below the floor, leaving the up-to-date tab's in-progress work alone. (Tests: "forces, and navigates ONLY the tab below the floor", "rescues a tab still EXECUTING an old build behind an up-to-date served shell", "navigates exactly the windows the floor condemns".)
- **Given** an open window that never registered at all **when** a new worker installs **then** that ABSENCE is itself force evidence: the decision runs over every live `clientId` from `clients.matchAll()`, and an id with no registry entry stands in as `UNKNOWN_ACTIVE_STAMP` exactly as an unrecorded shell does. This is the rollout case and it is the one that matters most — on the very deploy that introduces `CLIENT_BUILD`, every open tab is running a build that cannot post it, so a decision taken over the registry alone would rescue nobody the first time it ran. A live set that could not be read is NOT such evidence and falls back to the registry. The inert shipped floor still forces nobody, because the stand-in stamp sits one millisecond after the epoch. (Tests: "rescues an open window that never REGISTERED at all — the rollout case", "rescues a live tab that never registered, behind an up-to-date shell and registry", "does NOT invent a stranded window when the live set could not be read", "still forces nobody under the inert floor, unregistered windows included".)
- **Given** a window that never registered, or a forced activation whose floor could not be persisted **when** the worker claims **then** that window is navigated anyway: an unregistered client is running a pre-#516 build or died before its module scope ran, which is precisely the stranded cohort, so "unknown" reads as condemned the same way an unrecorded shell stamp does. (Tests: "navigates a window that never registered, and every window with no usable floor", "keeps everything when the live set cannot be read at all".)
- **Given** two tabs posting `CLIENT_BUILD` at the same moment, or a sweep in a replacement worker overlapping a write in the active one **when** both run **then** neither entry is lost, because the registry is ONE CACHE RECORD PER WINDOW rather than one shared map. A shared map makes every registration a read-modify-write, and these read-modify-writes are run by workers that cannot coordinate: a page posts `CLIENT_BUILD` to the ACTIVE worker while a replacement sweeps the same record from its own `install`, and those are two separate globals, so a serializing promise chain is module state each of them holds a private copy of. Both would read the same map and the later `put` would discard the earlier entry — losing the stale tab costs the install decision its evidence, and losing a current tab makes it look unregistered and navigates it for nothing. Per-key records need no coordination at all: a registration writes exactly one key, its own, a sweep deletes only the keys it decided are dead, and nothing reads a value in order to write it back. (Tests: "gives every window its OWN record, so no write can reach another window`s", "loses neither of two windows naming themselves at the same instant", "loses nothing when a sweep in ANOTHER worker overlaps a write in this one", "a sweep deleting a dead window leaves a live one`s record untouched".)
- **Given** a live window whose `CLIENT_BUILD` write is still in flight **when** the decision reads the registry **then** the absence is CONFIRMED by up to `UNREGISTERED_CLIENT_CONFIRM_ATTEMPTS` (3) further reads before it is believed, stopping as soon as every live id has a record, and a record that lands in between talks the worker out of forcing. Absence is the strongest evidence this rescue has, and it is assembled from reads nothing orders: a window posts to the ACTIVE worker while the decision runs in the INSTALLING one, so a tab that opened moments ago is enumerable before its record is readable. `CLIENT_STAMP_SWEEP_GRACE_MS` cannot cover that gap, because it shields records that EXIST and this one does not yet. A single confirmation read assumed delivery to the ACTIVE worker and its Cache API write both land inside one `UNREGISTERED_CLIENT_CONFIRM_MS` window, but nothing bounds either — a background-throttled tab could still be absent after that one look (post-review #756 on #720). Retrying narrows, without closing, that false-positive window: it is still not a causal acknowledgement, only more chances for the write to have landed. The confirmation is taken lazily — only once an absence is about to change the answer, so the ordinary decline pays nothing — and it runs again in `activate` for the window that opens between the decision and the claim, where believing the absence costs not a needless force but a navigation that discards what the player is doing. A window that genuinely never registers stays condemned however long it is given, which is the rollout cohort and the whole point. (Tests: "takes a second look when a live window has no record, and finds the late arrival", "does not wait at all when every live window is already registered", "still reports a window that genuinely never registers — the stranded cohort", "turns the force decision AROUND once the late record lands", "takes more than one look — a background-throttled client can miss the first", "gives up after UNREGISTERED_CLIENT_CONFIRM_ATTEMPTS looks, not forever", "stops as soon as every live id has a record — the common case pays for one wait", "does not condemn a current tab whose registration was merely still in flight", "still rescues the rollout cohort, which never registers however long it waits", "does not navigate a window that registers between the decision and the claim".)
- **Given** a window that opened after the sweep's `clients.matchAll()` snapshot was taken **when** that sweep runs **then** its record survives anyway, because a record younger than `CLIENT_STAMP_SWEEP_GRACE_MS` (five minutes) is never swept whatever the live set says. The snapshot is necessarily stale — enumerating the clients is itself async — so a genuinely-alive window can be genuinely absent from it, and deleting its record is the same lost registration the per-key shape exists to prevent, arriving by a different road. Age is the one property of a record a stale snapshot cannot make wrong. The cost is bounded and harmless: a closed tab lingers for a few minutes, and both consumers look entries up by LIVE client id, so a lingering one is ignored. (Test: "never sweeps a record younger than the grace, whatever the live set says".)

### A page that was uncontrolled when it registered still notices a deploy (#621)

`vite-plugin-pwa` reloads on `controlling` only when `event.isUpdate`, and `workbox-window` fixes that flag at REGISTER time from `Boolean(navigator.serviceWorker.controller)`. A page uncontrolled then — a first-ever visit, or the load right after `shellRecovery.clearShell()` — carries `isUpdate: false` for its whole life. Worse, an uncontrolled page controls nothing, so a worker installed after a deploy does not even stop in `waiting`: it activates immediately, swaps the precache, and leaves the tab executing the previous build with no banner and no reload. `armUncontrolledUpdateReload` (`src/swClientBridge.ts`) is the second trigger — it watches the REGISTRATION rather than the controller, and reloads when the worker in charge turns out to be carrying a build strictly newer than the page's own. It is armed only on an uncontrolled page, because a controlled one already reloads via `vite-plugin-pwa` and arming both would reload twice.

- **Given** an uncontrolled page **when** a deploy activates underneath it **then** the page reloads once, and only once per page lifetime. **Given** a controlled page **then** it does not reload, because `vite-plugin-pwa` already does. (Tests: "reloads when a deploy activates underneath the running page", "does not arm on a CONTROLLED page, whose reload vite-plugin-pwa already drives", "reloads at most once per page lifetime".)
- **Given** an uncontrolled tab ALREADY running the build the incoming worker serves **when** that worker activates over another **then** it does not reload. "A worker replaced another" proves an activation happened, not that this page is behind it, and the two come apart in exactly the case the rescue is built for: a forced activation is triggered by the OLDEST open window, and `shouldNavigateClient` then filters the navigation targets down to the clients actually below the floor, precisely so an up-to-date tab keeps its in-progress work. That tab is uncontrolled (this worker never calls `clientsClaim()`), so it watches the same activation, and reloading from the page side undid the care the worker side had just taken. So the stamp is asked for on EVERY path; only what SILENCE means differs. An unanswerable FIRST worker changes nothing, because a needless reload would discard whatever the player did while the initial precache installed; an unanswerable REPLACEMENT still reloads, because a page that cannot confirm it is current after a demonstrable takeover is more likely stale than not, and staying stale for the rest of its life is the bug this exists to fix. (Tests: "leaves a tab ALREADY running the build the incoming worker serves alone", "still reloads a tab a REPLACEMENT worker leaves behind".)
- **Given** a FIRST worker — one that replaces no previous `active` — **then** it is trusted only once it names the page's own build. A first worker is not guaranteed to match: `UpdatePrompt` registers only after React mounts, and hostname resolution or a slow bundle download leaves room for a deploy to land between the document and the `/sw.js` fetch, so the page can be executing build A while the first worker to activate carries B. The page asks that worker for its stamp (`GET_BUILD_STAMP`, shared with #605 via `askWorkerBuildStamp`) and reloads only when the worker's build is STRICTLY NEWER — a worker that cannot answer, or one carrying the same or an older build, changes nothing, because the reload is served from that worker's precache and reloading backwards is not a repair. The same comparison runs against `registration.active` as soon as `container.ready` resolves, since `ready` does not resolve until some worker is active and that worker's `updatefound` is therefore already history. (Tests: "reloads when the worker already active at arm time serves a NEWER build", "reloads when a first worker ACTIVATES carrying a newer build than the page", "leaves the page alone when that worker carries the same build", "leaves the page alone when the worker cannot name its build", "never walks the page BACKWARDS onto an older worker", "does NOT reload on a first worker that carries the build this page is running".)
- **Given** a modal sheet on screen in a visible tab **when** the deploy activates **then** the reload waits rather than yanking the player mid-interaction; a hidden tab is nobody's foreground and reloads straight away. (Tests: "waits rather than yanking a tab with a modal sheet on screen", "still reloads a hidden tab with no capture in progress".)
- **Given** an open claim sheet **when** the deploy activates **then** the reload waits WHETHER OR NOT the tab is visible, and is re-asked when the sheet closes as well as on the next `visibilitychange`. `ProofSheet` renders as `.sheet.claim-sheet` and carries neither `role="dialog"` nor `aria-modal="true"`, so the generic modal query above never saw the one sheet a reload actually destroys — a selected photo, a recorded clip, or typed callout text, all React state and nothing else until the player submits. The signal consulted is the existing `isClaimSheetOpen()` (`src/hooks/useToastStack.ts`), the same one `UpdatePrompt` defers its banner on, read without a hook because this module runs at page module scope. The visibility gate is skipped because backgrounding the tab is part of capturing the proof: the camera and the file picker take the foreground. (Tests: "waits while the claim sheet is open, and reloads once it closes", "waits even on a HIDDEN tab, because taking the photo is what hid it".)
- **Given** a bug report in progress — in EITHER phase, the dialog or the pick-a-screen bar **when** the deploy activates **then** the reload waits, visible tab or not, until the whole flow closes. The description, the screenshot, and the route it was taken on live in `BugReportProvider` state and nowhere else until submit, so a reload destroys the report rather than interrupting it, and the pick phase is the dangerous one twice over: its container is a `role="group"` the generic modal query cannot see, and it is the phase that explicitly invites the reporter to go wander the app while the draft is held. Matching only the dialog turned "Capture a different screen" into a reload — the dialog unmounts, the DOM watcher re-asks, and nothing is left in the way. The signal is declarative rather than another bespoke selector: any surface holding work that exists only in React state marks itself with `data-unsaved-work` (`UNSAVED_WORK_ATTRIBUTE`, `src/swClientBridge.ts`) and `midInteraction` asks one question, ahead of the visibility gate, so a future sheet with an unsaved draft joins by adding the attribute. (Tests: "waits for the WHOLE bug-report flow, pick mode included", "keeps waiting when the report sheet parks into pick mode", "waits even on a HIDDEN tab while a report draft is open".)
- **Given** any ORDINARY page surface holding a typed draft — the Admin → Messages compose form and its inline copy editor, the curated Prompt-pool add bar AND its inline text editor, the player's own "Add a prompt" bar, a Day's uncommitted Tonight line — **when** the deploy activates **then** the reload waits, visible tab or not, until the draft is committed or cleared. None of those is a modal or the claim sheet, so the two bespoke signals above never saw them and a deploy simply ate the draft; `data-unsaved-work` is what they declare instead. The attribute is CONDITIONAL on there actually being unsaved work — an admin merely parked on the Messages panel, or an inline editor opened and untouched, must not pin the tab to a condemned build for the rest of its life — and the DOM watcher already observes that attribute, so clearing it releases the deferred reload with no visibility change needed. (Tests: "marks the compose form only once something has been typed", "marks the body on its own, not just the title", "releases the reload once the broadcast is posted", "marks the inline editor only once the copy actually differs", "a half-typed curated add holds back the automatic post-deploy reload", "a retained inline prompt edit holds back the automatic post-deploy reload", "a half-typed suggestion holds back the automatic post-deploy reload", "an uncommitted Tonight edit holds back the automatic post-deploy reload".)
- **Given** a draft that NORMALIZES to what is already stored — a Tonight line retyped as `A·B` where `A · B` is saved, an inline prompt edit that differs only in surrounding whitespace — **when** the surface's commit decides that is a no-op **then** the marker must already be absent, because the commit writes nothing and resets nothing and the draft therefore never converges on the stored text by itself. Each surface asks its marker question of the value the commit would WRITE, not of the raw characters in the field: `normalizeTonight` for the schedule row, the same `.trim()` comparison `save` uses for the Prompt-pool and Messages inline editors. A marker whose release condition can never be met is worse than no marker — it is checked ahead of the visibility gate, so it does not delay the post-deploy reload, it cancels it for the life of the surface. (Tests: "a formatting-only Tonight edit is not unsaved work", "an inline edit that differs only in whitespace is not unsaved work".)

## Theming, placement, and coexistence with the other bottom bars

The banner must look native to the app in whichever theme the player selected. `.update-prompt` (`src/index.css`) shares the `.install-prompt` bottom-banner shell via comma-joined selectors—same theme tokens (`--bg` panel wash, `--border` top rule, `--dim` copy, `.btn primary`'s `--primary` fill), same `env(safe-area-inset-bottom)` clearance, same `body:has(.tabs)` rule stacking it above the signed-in tab bar—so reskinning via `[data-theme]` covers it with zero per-theme work, and the CSS-only claims are verified by code review for the same jsdom-has-no-layout-engine reason as `specs/w1-pwa.md`. **Superseded by #219 (see `specs/d15-pwa-toasts.md`):** both banners can now be visible at once, stacked via a shared `useToastSlot` coordinator—the update banner ranks above the install nudge (urgent outranks invitational) rather than fully suppressing it. The install banner is also no longer offered on app-load; it waits for the Player's first Mark.

Registration side effect worth naming: importing `virtual:pwa-register/react` flips `vite-plugin-pwa`'s `injectRegister: 'auto'` to app-owned registration—the build stops emitting/injecting `registerSW.js`, and `useRegisterSW` performs the `/sw.js` registration itself when `UpdatePrompt` mounts. `specs/w1-pwa.md` § SW registration and the hosting-cache test (`src/data/w4-bug-report-client.test.ts`, now asserting `sw.js` stays `no-cache`) were updated accordingly, and `firebase.json` dropped the obsolete `registerSW.js` glob entry.

`UpdatePrompt` mounts at `src/main.tsx` alongside `ConsentNotice` / `InstallPrompt` (the stable, non-frozen mount point outside the auth-gated tree, #17), so a deploy can prompt a reload on every screen including signed-out SignIn. Like `InstallPrompt`, it toggles an `update-prompt-visible` class on `<body>` while the banner is up; `body.update-prompt-visible` joins every `body.install-prompt-visible` clearance rule in `src/index.css`—`.app`'s ~64px of extra bottom padding, and the `bottom: calc(140px + env(safe-area-inset-bottom))` lift for the fixed `.bug-report-trigger` / `.guidelines-trigger` controls, which would otherwise sit under the banner at their usual 76px mark (Codex P2 on #179; the ~64px estimate and its caveats are documented in `specs/w1-pwa.md`).

- **Given** the banner is showing **when** it appears/dismisses/unmounts **then** `update-prompt-visible` is added to and removed from `<body>` in lockstep. (Test: "toggles update-prompt-visible on <body> while the banner is up, and clears it on dismiss".)
