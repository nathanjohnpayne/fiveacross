# Update-reload prompt: tell players a new deploy is ready and let them reload onto it (`src/components/UpdatePrompt.tsx`)

Before this ticket (#178), `vite-plugin-pwa` ran with `registerType: 'autoUpdate'`: a new deploy's service worker activated silently under the running page, so a tab or installed PWA left open — the norm on a cruise, where a session lasts days — kept executing the old bundle indefinitely, never told that fixes or features had shipped, and could hit failed dynamic imports once its old hashed chunks left the precache. This ticket switches to `registerType: 'prompt'` (`vite.config.ts`): the new service worker installs and **waits**, and a new `UpdatePrompt` component surfaces that state as a themed bottom banner offering **Reload** (activate the waiting worker, reload onto the new build) or **Not now** (session-only dismiss — the waiting worker still activates on the next full app launch, so nobody stays stale forever). This is the same player-facing feature Nathan's other apps (friendsandfamily-billing's `UpdateToast`, overridebroadway's `UpdateChecker`) implement by polling a version file; here it rides the service-worker update lifecycle the app already ships, with a periodic `registration.update()` check standing in for the poll. Exercised by `src/components/app-update-reload-prompt.test.tsx` (RTL-jsdom).

## `needRefresh` drives the banner; Reload activates the waiting worker; Not now dismisses for the session

`useRegisterSW` (`virtual:pwa-register/react`) exposes `needRefresh`, which flips true when a new service worker has installed and is waiting.

- **Given** no update is pending **when** `UpdatePrompt` mounts **then** it renders nothing. (Test: "renders nothing (and never sets the body class) while no update is pending".)
- **Given** a new version is waiting (`needRefresh` true) **when** the banner shows **then** it announces the update ("A fresh build just docked—your marks are safe.", copy retimed and restyled by #219, see `specs/d15-pwa-toasts.md`) and tapping **Reload** calls `updateServiceWorker(true)` — the plugin's activate-then-reload path (it messages the waiting worker to `skipWaiting` and reloads once it takes control). (Test: "shows the banner when a new version is waiting, and Reload activates it with a page reload".)
- **Given** the banner is up **when** the player taps **Not now** **then** the banner hides for the session and the waiting worker is left untouched — it activates on the next full app launch, so a dismissal only defers, never strands. (Test: ""Not now" dismisses the banner for the session without touching the waiting worker".)

## A long-lived tab discovers new deploys: periodic `registration.update()`, offline-tolerant

The browser only re-checks `sw.js` on its own schedule (navigations, and at most daily); a tab that stays open at sea would otherwise not learn about a deploy for a very long time. `onRegisteredSW` arms a 60-second `setInterval` calling `registration.update()` — the cadence the other apps' version polls use. `firebase.json` already serves `/sw.js` with `Cache-Control: no-cache` (see `specs/w4-hosting-index-shell-cache.md`), so each check observes a new deploy immediately.

- **Given** the service worker registered **when** the interval elapses **then** `registration.update()` is called once per tick. (Test: "arms a periodic registration.update() check so a long-lived tab discovers a new deploy".)
- **Given** the device is offline (`navigator.onLine === false`, common mid-cruise) **when** a tick fires **then** the check is skipped — no wasted round trip; the next tick retries. (Test: "skips the update check while offline (navigator.onLine === false)".)
- **Given** a check fails transiently (rejected `update()`) **when** the rejection lands **then** it is swallowed — no unhandled rejection; the next tick retries. (Test: "tolerates a registration.update() rejection (transient network failure) without unhandled errors".)
- **Given** an environment with no usable registration (no SW support) **when** `onRegisteredSW` fires with `undefined` **then** no interval is armed. (Test: "does nothing when registration is unavailable (no SW support)".)

The interval is deliberately not torn down: `UpdatePrompt` mounts once at `main.tsx` and lives for the page's lifetime, matching `useRegisterSW`'s own register-once model. On the transition deploy itself, pages still running the previous `autoUpdate`-built client have no prompt listener; they pick up the new worker on their next full app launch as before — one release where open tabs aren't prompted, self-resolving.

## Remote build floor can force a stale cached shell onto a newer waiting worker

For emergency stale-shell eviction (#342), `public/build-floor.json` carries an ISO `floor` timestamp and production bundles bake an ordered `__BUILD_STAMP__` at build time. `UpdatePrompt` reads `/build-floor.json` with `no-store` and a cache-busting query; if the running bundle's stamp is older than the served floor and a newer service worker is already waiting, the component calls `updateServiceWorker(true)` immediately instead of rendering the dismissible banner. The shipped floor is inert (`1970-01-01T00:00:00.000Z`) and is bumped manually only when cached clients must be forced forward; malformed floors, fetch failures, and builds at or newer than the floor fail open to the normal prompt.

- **Given** a new version is waiting and the running build is below the served floor **when** the floor read settles **then** `UpdatePrompt` activates the waiting worker with `updateServiceWorker(true)` and never exposes the **Not now** offer. (Test: "force-activates a waiting SW without offering the banner when the running build is below the served floor".)
- **Given** the served floor is inert or older than the running build **when** a new version is waiting **then** the normal reload offer remains available and no forced activation occurs. (Test: "keeps the normal offer when the served floor is inert (older than the build)".)
- **Given** the first floor read is still pending **when** a waiting worker exists **then** the banner is held until that read settles, so the user cannot dismiss before the force decision is known. This wait is bounded by the floor fetch timeout; a failed read resolves to the safe normal-prompt path.
- **Given** an operator bumps the floor after a tab has already mounted **when** the 10-minute floor re-read observes the newer floor **then** an already waiting worker is still force-activated, even if the player previously tapped **Not now**. `UpdatePrompt` latches that a waiting worker exists separately from the dismissible `needRefresh` state so dismissal cannot defeat the emergency lever. (Test: "a floor bump observed AFTER \"Not now\" still forces the reload — dismissal cannot defeat the floor".)

## The floor also has an out-of-tree path, because the in-tree one dies with the app (`src/shellRecovery.ts`)

Everything above assumes the React tree is alive: the floor read, the waiting-worker latch, and `updateServiceWorker(true)` all live inside `UpdatePrompt`. The 2026-07-24 blank-screen incident broke that assumption. The cells-map migration (`specs/cells-map.md`) flipped the Board `cells` wire shape, so clients on a pre-migration precached shell threw during render; React unmounts the **whole root** when an error escapes with no boundary, which took `UpdatePrompt` down with the app. The waiting worker then had no one left to activate it, and the floor lever could not fire either — its own check had just been unmounted. Those clients served the broken shell forever, on every reload.

So the floor now has **two** paths, and the in-tree one is no longer the only one. The friendly path above is unchanged and still preferred: a waiting worker, a banner or a silent force, activation via `updateServiceWorker(true)`. The recovery path is new, runs from `src/main.tsx` module scope (never from a component), and does **not** depend on a waiting worker existing — it unregisters every service worker, deletes the workbox precache, and reloads, because a stranded client's worker is waiting precisely because nothing is alive to tell it to activate. The `proof-media` runtime cache is deliberately preserved. `src/components/ErrorBoundary.tsx` invokes the same teardown when it catches a crash. Exercised by `src/shellRecovery.test.ts` and `src/components/ErrorBoundary.test.tsx`.

- **Given** the running build is below the served floor **when** the module-scope check settles **then** the shell is torn down and the page reloads, whether or not a newer worker is waiting. (Test: "resets a build BELOW the floor — the stranded-client rescue".)
- **Given** the running build is at or above the floor, or the floor is inert or unreadable **when** the check settles **then** nothing happens. (Tests: "leaves a build AT OR ABOVE the floor alone", "does nothing when the floor is inert (the shipped default)", "does not reload when the floor cannot be read (offline mid-cruise)".)
- **Given** a tab has already spent its one automatic attempt **when** another reset is requested **then** it is refused, so a floor set newer than every build cannot reload-loop. The latch is `sessionStorage`-scoped, so closing the tab restores the attempt. (Test: "fires at most ONCE per tab, so a misconfigured floor cannot reload-loop".)
- **Given** the attempt cannot be **durably** recorded — a readable-but-unwritable store, where `setItem` resolves but nothing persists **when** a reset is requested **then** it is refused rather than run unbounded. The floor stays armed, so the rescue is deferred, not cancelled. (Tests: "reports FAILURE when the store silently drops the write", "declines to reset when the attempt cannot be durably recorded".)
- **Given** the origin cannot be positively confirmed reachable **when** a reset is requested **then** the teardown is skipped and the page merely reloads onto the same cached shell. The precache is the only copy of `index.html` and the bundle the device has; deleting it without a replacement in reach replaces the recovery panel with the browser's offline error page, and the installed PWA cannot reopen until connectivity returns. `navigator.onLine === false` is trusted as proof of *offline*, but its `true` is explicitly **not** trusted as proof of *online* — ship Wi-Fi and captive portals, this app's primary surface, leave it true while the origin is unreachable. So the destructive path demands a completed same-origin request: a `no-store` fetch of `/build-floor.json`, which is deliberately un-precached (the workbox glob excludes `.json`) and served `no-cache`, so a real 200 proves the ORIGIN answered rather than a cache. A bare `res.ok` is explicitly not enough, because `fetch` follows redirects by default and a captive portal that bounces the request to its own login page returns a perfectly readable 2xx. Three independent barriers must hold, since a portal only has to defeat one: the request is made with `redirect: 'error'` so a bounce rejects rather than resolves; the FINAL response URL must still be same-origin, covering interceptors that proxy in place rather than redirect; and the body must parse as the build-floor document, which no login page will. There is deliberately no "connectivity already proven" bypass for `enforceBuildFloor`: `fetchBuildFloor` carries none of those barriers, so accepting its success as proof would let a portal returning parseable floor JSON back in through the side door. Every teardown runs the same probe. (Tests: "does NOT tear down when the origin is unreachable despite navigator.onLine === true", "does NOT tear down when the origin answers non-OK", "does NOT tear down when the probe was REDIRECTED (captive portal bounce)", "does NOT tear down when the final URL is CROSS-ORIGIN (in-place interception)", "does NOT tear down when the body is not a build-floor document", "requests the probe with redirect:error so a bounce rejects outright", "has NO connectivity-proven bypass — every teardown runs the hardened probe", "runs the hardened probe before tearing down, even on the floor path", "reloads WITHOUT tearing down the shell while offline", "skips the probe entirely when definitely offline", "does not even probe the floor while definitely offline".)
- **Given** the app crashes before `initPostHog` has settled — the startup case this whole path exists for **when** the boundary reports `app_crash` **then** the event is queued, persisted to `sessionStorage`, and replayed once the SDK is live, after the pending identify so it is attributed rather than orphaned anonymous, and sent with `sendBeacon` so the reload cannot drop it in flight. Init is fire-and-forget and awaits ingest-host probes while `main.tsx` renders synchronously, so a startup crash reliably lands in the not-ready window where a plain capture would simply vanish. The persistence matters because the queue's main customer reloads immediately: the boundary starts `resetShell()` right after queueing, and its same-origin probe can finish long before the EXTERNAL ingest probes — the shipboard blocked-proxy case — so a memory-only queue would die with that navigation. The persisted queue is drained exactly once, so a failed replay cannot re-send on every later load. (Tests: "replays a capture that arrived BEFORE init settled (#513 — the startup-crash report)", "replays a queued capture that survived a RECOVERY RELOAD (#513)", "drains the persisted queue exactly once, so a replay cannot re-send forever", "replays a queued capture AFTER the pending identify, so it is not orphaned anonymous", "beacons the crash report so the auto-reload cannot drop it".)

## The worker rescues itself when the page cannot help (`src/sw.ts`, `src/sw-rescue.ts`)

Both paths above still assume something in the CLIENT BUNDLE runs — the banner needs React, and the module-scope check needs `main.tsx` to be evaluated at all. Neither reaches a client stranded on an OLDER shell: its old bundle has no floor check, its React tree is dead, and its newer worker sits in `waiting` forever because `updateServiceWorker(true)` is only ever called by a page that is no longer running. That was the cohort the 2026-07-24 incident produced, and #513 could not recover it (Phase 4b P1 on #513, filed as #514).

The way out is that a **waiting worker has already been installed** — the browser evaluated its script and fired its `install` event. Logic placed in `install` therefore runs on a stranded client, in a context the dead page cannot affect, and can call `skipWaiting()` to promote *itself*. The browser re-checks `/sw.js` on navigation and it is served `no-cache` (`firebase.json`), so a stranded player simply reloading is enough to deliver this code. #514 switches `vite-plugin-pwa` to `injectManifest` for this reason: a generated worker had nowhere to put an install-time check. Everything generateSW previously did is ported verbatim into `src/sw.ts` — precache and `cleanupOutdatedCaches`, the navigation fallback and its `/__/*` denylist (`specs/sw-auth-handler-denylist.md`), the proof-media `CacheFirst` (#363), and the `SKIP_WAITING` handler the prompt path depends on.

The decision itself is pure and lives in `src/sw-rescue.ts`, unit-tested without a service-worker environment. A worker force-activates only when the ACTIVE shell is below the served floor **and** the new worker is not itself below it. Each activation records its own `__BUILD_STAMP__` in a dedicated `gcb-shell-meta` cache so the next worker can tell what it is replacing; an unrecorded stamp — every worker built before #514, which is exactly the stranded cohort — reads as ancient.

- **Given** an armed floor and an active shell below it **when** a new worker installs **then** it calls `skipWaiting()` without waiting to be asked, then claims the clients and navigates each window to its own URL, so a blank crashed tab lands on the new shell with no cooperation from the page. (Tests: "rescues a shell that is below an armed floor", "rescues a shell that recorded NO stamp — every pre-#514 worker, i.e. the stranded cohort".)
- **Given** the inert shipped floor (`1970-01-01T00:00:00.000Z`) **when** any worker installs **then** it never force-activates, including on the very first deploy of this feature, when no client has a recorded stamp. `UNKNOWN_ACTIVE_STAMP` is deliberately one millisecond after the epoch so that an unrecorded shell is not "below" the inert floor — if those two values ever meet, shipping the feature force-activates the entire fleet. (Tests: "NEVER forces under the inert shipped floor, even with no recorded stamp", "pins UNKNOWN_ACTIVE_STAMP strictly after the inert floor".)
- **Given** an active shell at or above the floor **when** a new worker installs **then** the normal `registerType: 'prompt'` path is untouched and the player still gets the banner. (Test: "leaves an up-to-date shell alone under an armed floor".)
- **Given** a floor newer than every existing build **when** a worker installs **then** it does not force-activate, because promoting onto a shell the same floor condemns is churn rather than rescue. (Test: "does not force when THIS worker is also below the floor".)
- **Given** a missing, malformed, non-string, or unreachable floor **when** a worker installs **then** it never force-activates, and `install` still completes — a worker that cannot install is a worker that can never rescue anyone. The floor read is bounded by its own timeout so a captive portal that accepts connections and never answers cannot stall installation. (Tests: "fails closed on a missing, malformed, or non-string floor", "a null floor can never force an activation", "is bounded, so it cannot stall the install it runs inside".)
- **Given** the browser tears the worker down between `install` and `activate`, which the lifecycle permits **when** it activates **then** it still claims and navigates, because the decision is persisted in `gcb-shell-meta` rather than held in module state. Losing it would leave `skipWaiting()` done but the navigation skipped, so the reload that DISCOVERED the update finishes on the old broken shell and the stranded player has to reload a second time — the exact dead end this feature exists to end. The flag is consumed as it is read, so a later ordinary activation cannot inherit a stale force and yank the player's windows. (Tests: "still claims and navigates when the worker was TORN DOWN between install and activate", "consumes the persisted decision, so a LATER ordinary activation does not re-navigate".)
- **Given** storage that refuses the stamp record **when** it is read or written **then** neither throws, and the next worker reads `null` — the safe reading (ancient), never a wrong one. The record lives in `gcb-shell-meta`, which `src/shellRecovery.ts` deliberately does not sweep (it deletes only `workbox-precache*`), so it survives a client-side reset. (Tests: "never throws when the Cache API refuses", "uses a dedicated cache the shell teardown does not sweep".)

`/build-floor.json` stays out of the precache glob (which covers only `js,css,html,svg,png,woff2`) precisely so a stale worker can never answer its own eviction notice from cache.

## Theming, placement, and coexistence with the other bottom bars

The banner must look native to the app in whichever theme the player selected. `.update-prompt` (`src/index.css`) shares the `.install-prompt` bottom-banner shell via comma-joined selectors — same theme tokens (`--bg` panel wash, `--border` top rule, `--dim` copy, `.btn primary`'s `--primary` fill), same `env(safe-area-inset-bottom)` clearance, same `body:has(.tabs)` rule stacking it above the signed-in tab bar — so reskinning via `[data-theme]` covers it with zero per-theme work, and the CSS-only claims are verified by code review for the same jsdom-has-no-layout-engine reason as `specs/w1-pwa.md`. **Superseded by #219 (see `specs/d15-pwa-toasts.md`):** both banners can now be visible at once, stacked via a shared `useToastSlot` coordinator — the update banner ranks above the install nudge (urgent outranks invitational) rather than fully suppressing it. The install banner is also no longer offered on app-load; it waits for the Player's first Mark.

Registration side effect worth naming: importing `virtual:pwa-register/react` flips `vite-plugin-pwa`'s `injectRegister: 'auto'` to app-owned registration — the build stops emitting/injecting `registerSW.js`, and `useRegisterSW` performs the `/sw.js` registration itself when `UpdatePrompt` mounts. `specs/w1-pwa.md` § SW registration and the hosting-cache test (`src/data/w4-bug-report-client.test.ts`, now asserting `sw.js` stays `no-cache`) were updated accordingly, and `firebase.json` dropped the obsolete `registerSW.js` glob entry.

`UpdatePrompt` mounts at `src/main.tsx` alongside `ConsentNotice` / `InstallPrompt` (the stable, non-frozen mount point outside the auth-gated tree, #17), so a deploy can prompt a reload on every screen including signed-out SignIn. Like `InstallPrompt`, it toggles an `update-prompt-visible` class on `<body>` while the banner is up; `body.update-prompt-visible` joins every `body.install-prompt-visible` clearance rule in `src/index.css` — `.app`'s ~64px of extra bottom padding, and the `bottom: calc(140px + env(safe-area-inset-bottom))` lift for the fixed `.bug-report-trigger` / `.guidelines-trigger` controls, which would otherwise sit under the banner at their usual 76px mark (Codex P2 on #179; the ~64px estimate and its caveats are documented in `specs/w1-pwa.md`).

- **Given** the banner is showing **when** it appears/dismisses/unmounts **then** `update-prompt-visible` is added to and removed from `<body>` in lockstep. (Test: "toggles update-prompt-visible on <body> while the banner is up, and clears it on dismiss".)
