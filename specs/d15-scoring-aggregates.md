# Event-wide scoring aggregates + per-day honors (`d15-scoring-aggregates`)

Implements `plans/daily-cards-spec.md` § "Scoring and social surfaces". With ten Day Cards, a Player's `PlayerDoc.bingoCount`/`squaresMarked`/`firstBingoAt` root fields stop being one Board's totals and become Event-wide aggregates over `PlayerDoc.dayStats` (one bucket per Day Card, seeded by `dealDayCard` and folded on each Mark). Each Day keeps its OWN daily honor (per-day First to BINGO), while the Event-wide First to BINGO headline is anchored to non-Tutorial Days only. This ticket owns the aggregation logic and the Leaderboard / day-meta surfaces; the scheduled Function triggers that fire the finale beats belong to `d15-scheduler-unlock`, and the finale copy/UI belongs to `d15-finale`.

Per the ticket's **needs-phase-4** posture (ADR 0001 / `specs/recon-recompute-stats.md`): ranking stays client-authoritative—no server-side player-stats recompute Cloud Function is added, and `functions/src/index.ts` is untouched. The per-Day honor's write-once guarantee is enforced by the EXISTING `firestore.rules` create-only-no-update gate on `days/{dayIndex}/meta/{dayIndex}` (shipped by `d15-firestore-rules`), not by a new trigger.

## Contract

- `src/game/logic.ts`—pure aggregation helpers (framework-free, the correctness-critical core):
  - `sumDayStats(dayStats)`—sums `bingoCount`/`squaresMarked` across EVERY Day Card, tutorial Days included (the opening Day's card is real pre-freeze play).
  - `eventFirstBingoAt(dayStats, isTutorialDay)`—the earliest `firstBingoAt` across non-Tutorial Days only; Tutorial Days are excluded even when numerically earliest.
  - `aggregatePlayerStats(dayStats, isTutorialDay)`—the Event-wide root shape `{ bingoCount, squaresMarked, firstBingoAt }` derived from a Player's `dayStats`.
  - `boardFirstBingoAt(row, daily, dayIndex)`—the First-to-BINGO stamp ONE Board's write path PRESERVES rather than re-stamps: in daily-cards mode that Day's own `dayStats[dayIndex].firstBingoAt`, and for a legacy single-Board row the root `firstBingoAt` (that one Board's stamp). Every completing-Mark path reads it—`Board`→`setMark`, `Board`→`ProofSheet`→`attachProof`, and `deleteProof`—so a proof-backed win can never inherit another Day's instant. The root is an aggregate over every Day, so reading it in a per-Day write copies an earlier Day's timestamp into the Day being written and awards the wrong daily honour; because the copy is then summed back into the same root, no later read surface can tell which Day produced the instant.
  - Every write path selects through this ONE helper wherever it reads a Player row, not only where a caller hands it one. Two re-reads sit downstream of the callers above and each re-selects the field the same way, because a row read closer to the write OVERRIDES the caller's argument: `setMark`'s cached-Player read (`runSetMark`, the normal Board flow—a cached row is KNOWN state and always wins, so selecting the root there would silently defeat the per-Day argument Board passed) and `attachProof`'s in-transaction read (which must not be clobbered by a concurrent Mark). A caller-supplied stamp is the fallback for an UNREADABLE row only—never for a live Board bucket that explicitly holds no stamp, which is the authoritative "no bingo stands on this Day" a concurrent unmark just wrote, and reviving the caller's value over it would re-date a brand-new win. `deleteProof` takes no caller stamp at all, so it has no such fallback.
  - `foldDayStat(...)`—the Mark write-path composition: folds `computeMark`'s per-Board result into `dayStats[dayIndex]` and re-derives the summed root, carrying `computeMark`'s `firstBingoAt` OMIT (the #75 unknown-state preserve) through to the `{ merge: true }` write.
  - `tutorialDayIndexSet(days)`, `perDayHonors(players)`, `effectiveCruiseFirstBingoAt(player, isTutorialDay)`, `cruiseFirstBingoUid(players, isTutorialDay)`—the read-surface derivations for the Leaderboard pin and honors strip, with a legacy fallback to the root `firstBingoAt` for a roster that predates Day Cards (no `dayStats`).
  - `ceremonialDayIndexSet(days)`—the Days whose Marks never move the summed root totals, keyed on each Day's STATED Scoring Policy via `scoringForDay` (`src/game/scoring.ts`), never on its pool (ADR 0011). Distinct from `tutorialDayIndexSet`: the two flags answer different questions, and a Day can be either, both, or neither. A ceremonial Day's own daily honour still stands—the exclusion applies to the summed roots and the podium, never to the per-Day bucket.
  - `earlierEligibleHeadlineBingoExists({ roster, candidateUid, isTutorialDay, freezeAt? })` (#1050)—the ONE decision every path that can claim the immutable Event-wide `first_bingo` Moment reads: the live Mark/proof drain (`src/components/Board.tsx`), the pure confirm planner (`planConfirmBroadcasts`, `src/data/moments.ts`), and the held-ceremony release (`src/components/ConfirmWinMoments.tsx`). It answers the HEADLINE question, which is deliberately narrower than the standings one: TUTORIAL Days are excluded and only tutorial Days (a `scoring: 'ceremonial'` Day with `tutorial: false` still counts—`ceremonial` promises only that a Day's marks never move the STANDINGS), and anything at or after `freezeAt` is excluded on the same inclusive boundary `eventFirstBingoWinner` applies. Each rival's instant comes from `effectiveCruiseFirstBingoAt`, so the documented legacy root fallback survives exactly where it applies—a row with NO `dayStats`. `candidateUid` never blocks itself: the candidate's own prior-win history is `hasPriorBingoWitness`'s question at birth time. "Earlier" is measured against the candidate's OWN eligible instant when the roster already carries one, and is a bare presence test otherwise. The comparison is what keeps a LATER rival from voiding a HELD candidate — a claim can be parked at the roster gate for an arbitrarily long time and a rival can win inside that window, and on a presence-only test the two clients then suppress EACH OTHER so the immutable singleton is never written at all. The presence fallback is what keeps the gate conservative when the candidate's own instant is not knowable (a freshly-crossed win whose row has not echoed, a stamp a concurrent unmark cleared, a tutorial-only or post-freeze row): an unknown candidate instant defers to any eligible rival. The comparison is strict on the instant and then falls through to the SAME uid tie-break `eventFirstBingoWinner` applies (ascending), so an exact-millisecond tie blocks exactly one side—the Player the selector does not name—rather than neither; letting both attempt would only re-enter the create-only race this gate exists to settle before the write. Blocking therefore coincides with the shared selector exactly, and by construction rather than by parallel implementation: the gate delegates to `selectHeadlineBingoWinner`, the one selection loop `eventFirstBingoWinner` also runs (eligibility cutoff and ordering live there once), and returns true precisely when that selection over the same roster and cutoff names a Player who is not the candidate, ties included. Reading a rival's ROOT `firstBingoAt` here is the defect this replaces: that root is folded through `rankingExcludedDay`, so it drops ceremonial Days too and an earlier eligible ceremonial winner was invisible to a later client, which then contended for the create-only singleton.
  - `resolvedStandingsFreezeAt(event)` (#1050)—the cutoff every headline surface shares: the scheduler's `frozenAt` stamp when it has run, else `standingsFreezeAtFor`. The Leaderboard pin, the frozen podium, and the ceremonial Moment gate all resolve it through this one helper, so no two screens can cut the same honour at different instants.
  - `standingsFreezeAtFor(event)` / `standingsFrozen(event, now?)`—the Event's Standings Freeze and whether it has passed. The freeze is the CONFIGURED `EventDoc.standingsFreezeAt` when the doc carries a usable one, else the first ceremonial Day's `unlockAt`; `standingsFrozen` is the scheduler's `frozenAt` stamp OR that instant having passed, the stale-cache belt that makes a client offline at sea still fail CLOSED by its own clock. An Event with neither has no scheduled freeze and never freezes on its own. Neither reads a pool (ADR 0011): a competitive final Day now counts right up to the freeze instead of being frozen out by the pool its card happens to deal.
  - **Frozen, unchanged:** `comparePlayers`'s tie-break ORDER (bingos desc → squares desc → earliest first-bingo). Only its inputs change (a sum over Day Cards).
- `src/data/api.ts`—`computeMark`/`setMark` fold a Mark into `dayStats[dayIndex]`, then derive the Event-wide root. The Day is the caller's explicit `dayIndex`, else the cached Board's own `dayIndex`, else Day 0 (the single-Board legacy shape, whose one bucket makes the aggregate equal that Board's totals—no behavior change). The prior stamp `computeMark` folds comes from the cached Player row when one exists, selected through `boardFirstBingoAt` on that resolved Day; only a genuine cache MISS leaves the caller's argument in place, still carrying the #75 `undefined` UNKNOWN. `setMark` gains optional `dayIndex`/`tutorialDayIndexes`.
- `src/data/dayMeta.ts` (new)—`pinDayFirstBingo(dayIndex, who, at, eventId?)`, a write-once per-Day honor at `days/{dayIndex}/meta/{dayIndex}`, mirroring `moments.ts`'s offline-queueable, cache-pre-checked, fire-and-forget writes. The entry captures the Event and builds its ref before the cache await; held honor pins are keyed by `(Event, uid, Day)`, so releasing Event A's identity wait can never pin B. The per-card blackout Moment that NAMES its Day (deterministic PER-CARD id `${uid}-blackout-d${dayIndex}` on daily events—#267; the day-less `${uid}-blackout` remains the legacy single-board form—immutable per rules) is `moments.ts`'s `broadcastBlackout(who, dayIndex?)`—an optional `dayIndex` on the SAME writer every blackout already goes through (fix/d15-blackout-day-naming), not a second dayMeta.ts writer.
- `src/components/Leaderboard.tsx`—ranks by the aggregated Event-wide totals; the "1st BINGO" pin is Event-wide-restricted (tutorial Days excluded); a per-Day honors strip renders each Day's own First to BINGO.

## Acceptance criteria

- **Given** a Player has marks on 3 different Day Cards, **when** the Event totals are derived, **then** their `bingoCount`/`squaresMarked` are the sum across all 3 Day Cards. (Test: aggregate-sum.)
- **Given** a Tutorial Day's first bingo is numerically earliest, **when** the Event-wide First to BINGO is computed, **then** that bingo is excluded and the earliest non-Tutorial Day wins the honor; a non-Tutorial Day-only entry wins normally. (Test: tutorial-exclusion.)
- **Given** a Day that STATES `scoring: 'competitive'` while dealing the closing pool, **when** the ceremonial set and the freeze are derived, **then** the Day is not excluded and the freeze comes from the Event, not from that Day's unlock; and given a Day carrying no `scoring` at all, **then** both derive exactly as the pool-scanning code did. (Test: scoring-policy + legacy-byte-identical.)
- **Given** aggregated totals, **when** the roster is sorted, **then** the tie-break order (bingos → squares → earliest first-bingo) is unchanged over those aggregates. (Test: tiebreak.)
- **Given** a rival whose only bingo is on a `scoring: 'ceremonial', tutorial: false` Day, **when** the shared headline gate is asked, **then** an earlier eligible bingo EXISTS (their standings root is null, their `dayStats` bucket is not); a rival whose only bingo is on a TUTORIAL Day yields none; ceremonial policy alone never excludes a Day; a rival instant at or after the resolved freeze is ineligible while one strictly before it is eligible; a row with no `dayStats` keeps the legacy root behaviour; the candidate's own row never blocks them; a LATER eligible rival does not void a candidate whose own instant the roster already carries while an EARLIER one still does; an unknowable candidate instant falls back to presence; an exact-millisecond tie blocks only the Player the shared selector does not name (uid, ascending); and for every roster and cutoff, ties included, the gate blocks exactly when `eventFirstBingoWinner` over that roster names a different Player. (Test: headline-eligibility matrix + freeze boundary.)
- **Given** a Mark on `dayIndex`, **when** `computeMark`'s result is folded, **then** it writes into `dayStats[dayIndex]` and leaves other Days' entries untouched, and the derived root totals reflect the post-fold sum. (Test: fold-into-dayStats.)
- **Given** a Player whose Day-1 bingo IS their Event-wide root `firstBingoAt`, **when** a proof-backed Mark completes a line on Day 2, **then** `dayStats[2].firstBingoAt` is that Mark's own instant and not the root; attaching proof to an already-marked Square leaves a standing Day bingo's stamp alone; deleting a proof keeps that Day's stamp while another line stands there and clears it with the last one; and a legacy single-Board attach/delete still reads the root unchanged. (Test: per-Day proof stamp.)
- **Given** that same Player with their Player row CACHED—the normal Board flow—**when** a BARE Mark completes a line on Day 2, **then** the cached read selects Day 2's own bucket and stamps that Mark's instant, while the legacy single-Board read still preserves the cached root unchanged. (Test: per-Day cache-read stamp.)
- **Given** a live Day bucket that explicitly holds no stamp because a concurrent unmark removed that Day's last line, **when** a proof re-completes the line while the sheet still carries the old instant, **then** the new win is stamped at `now` and the stale prop is not revived; and given no readable Player row at all, **then** the caller's stamp is honoured. (Test: per-Day proof stamp.)
- **Given** a Day Card reaches blackout, **when** the completing Mark commits, **then** a Moment naming that Day posts to the Feed. (Test: day-blackout Moment.)
- **Given** the Leaderboard, **then** the honors strip renders each Day's pinned first-bingo Player, and the Event-wide "1st BINGO" pin never lands on a Tutorial Day's first bingo. (Test: honors strip + restricted pin.)
- **Given** the per-Day honor doc, **then** each Day's `meta.firstBingo` is write-once and independent of every other Day's (enforced by `firestore.rules`; the client writer is cache-pre-checked). No player-stats recompute Cloud Function is added (ADR 0001).
- **Given** an Event-A honor is waiting on a cache read or saved identity, **when** the client switches to B, **then** the eventual pin remains under A and cannot release, clear, or serialize B's held pin.
