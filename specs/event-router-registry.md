# App Check-compatible Event-router registry (`event-router-registry`)

This is the implementation contract for [ADR 0014](../docs/adr/0014-app-check-compatible-edge-routing-registry.md) and issue #888. It replaces only the edge lookup seam in `specs/event-router.md`; `specs/hostnames-lookup.md` remains the browser-facing source contract, and `specs/event-resolution.md` remains the independent client resolution contract.

**Implementation status.** Tickets A (#970) and C (#972) have landed: the registry service, its per-host Durable Object, the named lookup-only entrypoint, the guarded rehearsal controller, and the router's consumption of that entrypoint all exist and are tested. The Worker's Firestore REST reader, its Firebase api-key/project bindings, its `caches.default` envelope, and the deploy check that required an edge Firebase credential are removed. B's (#971) code half has landed too: the one transaction helper that owns every projected hostname mutation, the dry-run-first backfill/reconciler, the explicit Admin ledger advance, and their lifecycle-specific emulator coverage all exist and are tested, the last against a real Firestore transaction. B's operator half — running the backfill and audit against the real serving hosts — is an R1 step and has not been performed, so no production hostname has yet been mutated through the helper. D (#973, R0–R3 evidence and the Gate 3 verifier) remains open, and no evidence run has been performed. The Worker therefore **remains unrouted**: the only routes any ticket may attach are the bounded synthetic exact routes below, created and removed by the operator-run rehearsal controller, and #529 retains exclusive authority over wildcard, apex, or real-Event attachment.

## Invariants and threat model

1. **App Check is never weakened for the router.** The Worker sends neither an App Check token nor a Firebase request in the target architecture.
2. **The router is not authorization.** A stale or forged routing projection can make a public shell available or unavailable; it cannot mint a Firebase session or bypass App Check, Firestore Rules, Storage Rules, or Event membership. The client never accepts the edge's `eventId` as its own Resolution.
3. **Firestore is canonical; the edge is a projection.** Only the trusted hostname mutation path changes canonical state. No registry-service path writes back to `hostnames/*`; the separately authorized human recovery tool may use the explicit ledger-repair transaction defined below.
4. **The registry is not a directory.** Public traffic can point-get the value for its already-present hostname only. The public router has no Durable Object namespace binding and neither its service binding nor any public endpoint exposes list.
5. **Address states move monotonically.** Normal publication accepts only the exact successor per-host revision. Recovery never lowers the accepted revision. Retries, gaps, older deliveries, and previously signed payloads cannot overwrite a newer state. A deleted address leaves a permanent tombstone and is not reusable.
6. **One transactional store owns acceptance and lookup.** The per-host Durable Object atomically stores the committed projection, revision, recovery lock, and audit history. No KV, Cache API, database, queue acknowledgement, or other external write participates in the accepted state.
7. **Lookup-gated paths fail closed.** Missing bindings, invalid schemas, unsupported versions, unavailable Durable Objects, and unknown/inactive/tombstoned hosts never proxy the origin on a path that consults the registry. The existing namespace-valid `/__/auth/*` pass-through intentionally bypasses lookup and remains separately guarded. There is no stale or Firestore fallback.
8. **A projection answers only for the address it was projected from.** Every lookup envelope derived from a committed record carries the canonical hostname that record was written for, and the router compares it byte for byte against the address it asked about before it interprets that record's status, Edition, root marker or revision. A mismatch is `replica-malformed`, and so is a committed-derived envelope that names no hostname at all, so a registry too old to stamp one fails closed rather than being read unbound. The denormalised `slug` cross-check that preceded this compares one label, and both Namespaces share it: `bodega-bay.fiveacross.app` and `bodega-bay.vacaybingo.com` are indistinguishable to it, which is precisely the substitution this invariant refuses.

The actors considered are an unauthenticated Internet caller, a modified browser client, a bearer-token thief, a compromised publisher runtime, a compromised public-router deployment, and a compromised registry-service deployment. The protected assets are routing integrity/availability, the hostname registry's non-enumeration property, Firestore data, cross-cloud credentials, and bounded platform cost. GCP/Cloudflare account administrators and a compromised Firebase Hosting origin are outside this contract; both already control the served system. Hostnames, Event IDs, Slugs, Editions, statuses, and individual replica revisions are public metadata, not secrets.

## Architecture and ownership

```text
trusted hostname writer
      │ one Firestore transaction
      ├── hostnames/{host}             public point-get source
      └── routerReplicas/{host}        private desired state + revision
                    │ Firestore event, retry enabled
                    ▼
       replica publisher Function      dedicated service identity + KMS signer
                    │ Google OIDC ID token + signed request bytes
                    ▼
       registry service ──────────────► per-host Durable Object
                    ▲                         │ atomic committed projection
                    │                         │ + revision/recovery/audit
public request ─► Event router               │
                    ├── named lookup-only WorkerEntrypoint: lookup(host)
                    └── active + matching ───► Firebase Hosting origin
```

| Surface | May read | May write | Explicitly may not do |
|---|---|---|---|
| Browser/app | one named `hostnames/{host}` under existing rules | no hostname/replica writes | list either registry; read `routerReplicas` |
| Hostname writer | hostname plus its replica ledger | both in one transaction | report success before replica convergence |
| Publisher Function | its event payload, metadata-server ID token, one KMS signing operation | authenticated signed sync request | call Firestore/Admin SDK; export a key; hold a Cloudflare API token |
| Registry service/DO | validated request and one named object's storage | one host's transactional state | read Firestore; bind another store; attach routes; select an origin |
| Public router | one registry `lookup(host)` result after the host guard | nothing | bind/list Durable Objects; call Firestore; accept edge identity as app Resolution |
| Audit operator | Firestore source/ledger list plus authenticated per-host DO state | nothing in audit mode | consume the publisher identity or enumerate through the edge |
| Source/control attestor | one transactionally consistent Firestore source/ledger read and the nonsampled Function/IAM/KMS control readbacks supplied by the human command | derive and sign the exact fresh canonical projection, equal ledger payload, and control observations with a human-only keyless identity/key | invoke recovery; sign a source/ledger mismatch, invented projection, or control claim without the interactive provider reads |
| Recovery operator | one separately attested Firestore source/ledger observation, provider control-plane/log readback, and one compared DO state | lock, monotonic source-attested repair, audit history, and a separately authorized exact-host WAF rule | use the publisher/source-control-attestor identity or key; lower a revision; invent a projection; attach wildcard/real-host routes |
| Regional probe runner | one public response from its configured deployment region | signed observation to the private attestation endpoint | choose its region label; recover state; satisfy more than its one identity slot |

### Google service identity and edge authentication

Use a dedicated runtime service account, provisionally `event-router-replica-publisher@fiveacross.iam.gserviceaccount.com`. It receives only the roles required for a v2 Firestore event receiver/logging plus `cloudkms.cryptoKeyVersions.useToSign` on one dedicated `RSA_SIGN_PKCS1_2048_SHA256` CryptoKey. Cloud KMS does not support IAM policies on an individual CryptoKeyVersion ([Cloud KMS permissions and roles](https://cloud.google.com/kms/docs/reference/permissions-and-roles)), so this CryptoKey is the narrowest real grant boundary. It contains no unrelated versions: only the publisher's current version is enabled at steady state, and only the current plus replacement versions are enabled during the bounded rotation overlap. The account receives **no** `datastore.*`, Firebase Admin, Secret Manager, service-account-key, public-key-viewer, or Cloudflare permission. Control-plane grants needed to attach the identity belong to deployer/service agents, not the runtime principal, and are reported separately in IAM verification.

Cloudflare has no Google credential, so signature verification never calls KMS at runtime. During reviewed provisioning, a separate deployer identity with only `cloudkms.cryptoKeyVersions.viewPublicKey` reads each publisher, recovery, source/control-attestor, and regional-probe signing version through [`getPublicKey`](https://docs.cloud.google.com/kms/docs/reference/rest/v1/projects.locations.keyRings.cryptoKeys.cryptoKeyVersions/getPublicKey). The command requires the exact version name and `RSA_SIGN_PKCS1_2048_SHA256`, verifies `pemCrc32c`, parses the RFC 7468 PEM as DER SubjectPublicKeyInfo, and computes lowercase hex `SHA-256(SPKI DER)`. It commits the exact `{role, subject, epochOrSlot, keyVersion, algorithm, pem, spkiSha256}` into immutable reviewed registry configuration. Public keys are not credentials, but their mapping is integrity-critical: configuration rejects duplicate role/epoch/slot, version, or fingerprint mappings and fails if the PEM reparse does not reproduce the fingerprint. The registry imports only that pinned SPKI into WebCrypto for `RSASSA-PKCS1-v1_5`/SHA-256; no runtime path has OAuth, `getPublicKey`, or a mutable key-discovery endpoint.

For each delivery the Function obtains a Google-signed ID token from the metadata server for one configured audience and sends it as `Authorization: Bearer`. The endpoint verifies `alg=RS256`, a signing key from `https://www.googleapis.com/oauth2/v3/certs`, `iss=https://accounts.google.com`, exact `aud`, `exp`, `iat` no more than 60 seconds in the future, and the configured stable numeric `sub`. Email is diagnostic only. JWKS refresh is single-flight; an unknown `kid` permits one refresh per five-minute cooldown. Refresh failure returns retryable `503`, while a bad token returns generic `401`.

OIDC authenticates the workload but is still a bearer credential, so the Function asks Cloud KMS to sign `v1\nPOST\n<path>\n<issued-at-ms>\n<publisher-epoch>\n<sha256-of-exact-body>` and sends the key-version resource name, canonical positive-decimal publisher epoch, issued-at, and base64 signature in fixed headers. The registry maps each allowed epoch to one exact subject/key-version/algorithm/SPKI-fingerprint record, accepts a signature timestamp within 60 seconds, and verifies the signature with that pinned public key before applying a payload. Each registry path that parses a key-version name — the sync header, recovery authorization, stored recovery history, pinned verification configuration, and semantic telemetry — applies one shared strict validator: `projects/<no-slash-or-whitespace>/locations/<no-slash-or-whitespace>/keyRings/<[A-Za-z0-9_-]>/cryptoKeys/<[A-Za-z0-9_-]>/cryptoKeyVersions/<positive decimal>`, matching the Cloud KMS id alphabet, so a name carrying whitespace or an out-of-alphabet segment is rejected identically everywhere. The private key never leaves KMS. A stolen OIDC token cannot sign altered bytes; an intercepted complete request can replay only the identical revision/epoch. Ordinary rotation provisions and deploys the new public-key record and epoch before the publisher changes versions, overlaps for one maximum token lifetime plus retry window, then removes the old mapping only after audit shows no use. A key-version name whose configured PEM/fingerprint differs, or a signature valid under any other pinned role/epoch, is rejected.

The exact audience is the separately deployed registry service's `workers.dev` origin plus `/__internal/hostname-replicas/v1`; it is immutable deployment configuration on both sides. That service has no wildcard route. Its default export owns the public `fetch` surface and admits only the signed sync, audit, recovery, and regional-probe challenge/attestation paths below. A separately exported named `RegistryLookupEntrypoint extends WorkerEntrypoint` has exactly one public RPC method, `lookup(host)`, and no `fetch` method. The Event router's Wrangler service binding explicitly sets `entrypoint = "RegistryLookupEntrypoint"`; omitting that field or binding the default export fails configuration validation. Cloudflare documents that the optional service-binding [`entrypoint`](https://developers.cloudflare.com/workers/wrangler/configuration/#service-bindings) selects a named export and that `WorkerEntrypoint` methods form the bound [RPC API](https://developers.cloudflare.com/workers/runtime-apis/bindings/service-bindings/rpc/). The Event router's own `workers.dev` behavior remains out-of-Namespace and is never treated as public data-plane evidence. Local tests inject token/signature acquisition and verification; no test key or bypass compiles into production.

## Data and mutation contract

`routerReplicas/{host}` is denied to every Firebase client (`get`, `list`, and all writes). It persists after hostname deletion and has exactly:

```ts
type RouterReplicaDesired = {
  schemaVersion: 1;
  revision: string; // canonical positive decimal, no leading zeroes; compare as BigInt
  host: string;     // hostnameKey(host), identical to the document ID
  desired:
    | { kind: 'route'; eventId: string; status: 'active' | 'disabled' | 'archived'; slug: string; edition: Edition; pathNamespace: 'fiveacross.app' | 'vacaybingo.com' | null }
    | { kind: 'root'; root: 'doorway' | 'not-found'; edition: Edition; pathNamespace: 'fiveacross.app' | 'vacaybingo.com' | null }
    | { kind: 'tombstone' };
  updatedAt: Timestamp; // observability only; never orders writes; stored as a Firestore timestamp, never as text
};
```

The sync request is `POST /__internal/hostname-replicas/v1`, exact `application/json`, at most 2 KiB, and contains the five fields above (`schemaVersion`, `revision`, `host`, `desired`, `updatedAt`) with `updatedAt` encoded as RFC 3339. That encoding is a statement about the request body, not a licence to store the field as a string: the deployed publisher reads the document off an Eventarc `document.v1.written` payload and `replicaPayloadFromFirestoreEvent` in `router-publisher/src/runtime.ts` accepts `updatedAt` only as a `timestampValue`, so a ledger document written with a Firestore string is refused before it can be published and the edge never converges on it. The lifecycle helper therefore writes the field through an injected SDK `Timestamp` constructor, and reading a RECEIPT is a different function from validating a STORED row: the stored `routerReplicas/{host}` document must carry a `Timestamp` and text is refused there, because the Eventarc parser accepts only a `timestampValue`, so a partial Admin write storing text produces a document whose trigger can never publish it and which must not pass as a converged mutation pre-state or be classified converged by the reconciler. A receipt is normalised JSON and still carries text. Both readers canonicalise to ONE RFC 3339 string before comparing or digesting, since a source-attestor receipt is normalised JSON rather than a Firestore snapshot. The canonical form is the `toISOString()` text — UTC, `Z` offset, exactly three fractional digits — and a string reaches it by being parsed and re-emitted rather than echoed: `2026-09-20T12:00:00Z`, `2026-09-20T12:00:00+00:00` and a `Timestamp` name one instant, so echoing the spelling a reader happened to receive would give one ledger several document digests and make a source/edge comparison report a mismatch that is an artifact of the encoding. A string is required to be RFC 3339 before it is parsed, because `Date.parse` also accepts texts RFC 3339 does not and an offsetless one would be read as local time; sub-millisecond digits are truncated rather than refused, matching what a Firestore `Timestamp` loses at `toDate()`, so millisecond resolution is the canonical resolution of the whole layer. An impossible calendar date is REFUSED rather than canonicalised: `Date.parse` rolls one forward instead of rejecting it — `2026-02-30T12:00:00Z` answers 2 March and `2025-02-29T12:00:00Z` answers 1 March — so a reader that trusted the text shape and a finite parse would digest, publish and store an instant the ledger never named. Each reader therefore reads the year, month, day, hour, minute and second back out of `Date.UTC` and refuses unless every component survives the round trip, which is also what makes the leap-day rule exact rather than approximated. All three programs apply it: the projection module refuses with its existing `malformed-ledger`/`malformed-timestamp` codes, the publisher refuses the Eventarc payload, and the worker refuses the sync request, because the edge does not trust the hop in between. The source attestor in `recovery-controller.mjs` reads a receipt's `updatedAt` through the projection module's predicate before it digests or signs anything, refuses a non-canonical instant as `malformed-ledger`, and signs the canonical text, so the evidence it produces is one the worker accepts and one ledger has one `ledgerDocumentDigest` whatever spelling the receipt carried. The rule is applied to the stored `Timestamp` as well as to the text, by re-checking the canonical `toISOString()` result through the same predicate: the two encodings have to ACCEPT the same instants, or the helper could stamp a ledger whose timestamp the publisher refuses and the edge would never converge on it. The EMITTED text is checked for the same reason the written components are, and neither check subsumes the other: components are judged before the offset is applied, so a text at either end of the supported range can validate and still canonicalise outside it — `0100-01-01T00:00:00+01:00` answers `0099-12-31T23:00:00.000Z`, below the year bound, and `9999-12-31T23:59:59-01:00` answers the expanded `+010000-…` form, which is not RFC 3339 at all. Extra/missing fields, a non-canonical hostname/revision, an unknown status/version/Edition/root/path namespace, a reserved or invalid label, a route whose `slug` does not equal the host's first label (Namespace apex exception preserved), an invalid body signature, and any non-POST method fail before storage. `pathNamespace` is explicit null or one of the two namespace apexes and is valid only on the matching Namespace apex/brand mirror, never an Event subdomain or GCB host. Root shape is valid only on the apex/mirror classes defined by `specs/path-addressing-and-root.md`, except for the controller-only synthetic root-test class below, and forbids `eventId`, `status`, and `slug`. A root-test host must match `r2-root-<20 lowercase base32>.<Namespace>`, carry `pathNamespace:null`, and be transactionally created from its permanent `routerRehearsals/{host}` reservation by the controller; all ordinary claim/mutation paths globally reject the `r2-`/`r2-root-` prefixes. Validation reuses the router's Namespace, Slug, and Edition modules. `edition`, root shape, and capability are copied because #546 and the accepted path-addressing spec must render per-host identity and `/.well-known/fiveacross-path-capability` without another lookup. `adultContent`, `canonicalHost`, `preview`, `apexPath`, membership, Event data, and any hostname catalogue are not projected.

Every ledger write is bounded by the 2 KiB sync ceiling, measured on the shape that goes on the wire — the document with `updatedAt` as RFC 3339 text — and refused as `projection-exceeds-sync-limit` rather than committed: nothing else bounds a projected value, so an oversized `eventId` or revision would otherwise write a Firestore revision `publishRouterReplica` refuses and the edge never sees, with every trigger retry failing on the same bytes. The constant is stated in the projection module and pinned equal to the worker's `SYNC_MAX_BYTES` by the parity suite. The projection digest is SHA-256 over the UTF-8 JSON array `[1, revision, host, "route", eventId, status, slug, edition, pathNamespace]`, `[1, revision, host, "root", root, edition, pathNamespace]`, or `[1, revision, host, "tombstone"]`; constructing that array is the only canonicalizer. Explicit JSON `null` prevents absent/capable values from colliding. The Durable Object ID is derived from the normalized hostname and is never exposed to the public router.

The object's transactional state is:

```ts
type RegistryState = {
  committed: null | { revision: string; digest: string; payload: RouterReplicaDesired };
  minimumPublisherEpoch: string; // canonical positive decimal; initialized to 1
  highestAuthenticatedPublisherEpoch: string; // canonical non-negative decimal; max authenticated sync epoch, initialized to 0
  highestQuarantinedPublisherEpoch: string; // canonical non-negative decimal; max epoch fenced by integrity recovery, initialized to 0
  recoveryLock: null | { lockId: string; acquiredAt: string; expectedCommitted: null | { revision: string; digest: string }; operatorSub: string; incidentUrl: string; reason: string };
  recoverySequence: string; // canonical non-negative decimal
};
```

Recovery records live under sequence-addressed keys in the same object's storage rather than in an unbounded array. A transaction that changes committed/lock state increments `recoverySequence` and writes the corresponding record atomically; no path updates or deletes an existing record. Short-lived regional-probe challenges/attestations use a separate key prefix, expire after five minutes, and are consumed atomically by the attestation/recovery action that accepts them; they are evidence inputs, not recovery history.

Normal sync first requires an allowlisted subject/key for the signed epoch and rejects an epoch below `minimumPublisherEpoch`. In one DO-storage transaction it raises `highestAuthenticatedPublisherEpoch` to the maximum authenticated epoch even when the revision is later rejected, then rejects any non-null `recoveryLock` with retryable `503 recovery-locked` or applies this table. “No committed change” below means the route projection/revision is unchanged; the authenticated-epoch high-water may still be the transaction's only state mutation.

| Incoming revision | Payload relation | Result |
|---|---|---|
| lower | any | `200 ignored-stale`; no committed change |
| equal | byte-equivalent canonical payload | `200 replay`; no committed change |
| equal | different payload | `409 revision-conflict`; no committed change; alert |
| exactly current + 1 | valid | atomically commit payload/revision/digest; `200 applied` |
| greater than current + 1 | any | `409 revision-gap`; no committed change; retry/alert |

An uninitialized object accepts revision 1 only. The transaction response is emitted only after storage commit. If the response is lost, retry sees equal state and succeeds as replay. There is no external side effect whose outcome can outlive or contradict that transaction.

## Audit and recovery

The audit command obtains the authoritative hostname set by listing `hostnames` and `routerReplicas` with the existing interactive, Admin-authorized operator credential. It never asks Cloudflare to list. For each known host it calls `GET /__internal/hostname-replicas/v1/<percent-encoded-host>?afterRecoverySequence=<cursor>` with a short-lived ID token impersonating a dedicated keyless audit service account. The registry pins that account's numeric `sub` and an audit-only audience. The cursor is absent/`0` on the first page and otherwise is the preceding response's canonical `nextAfter`; malformed or unknown-ahead cursors return `400`. The response exposes committed revision/digest, minimum/authenticated/quarantined publisher epochs, recovery-lock metadata, lookup outcome, and at most 100 append-only recovery records ordered by sequence. It exposes no route payload, public list, or mutation. `nextAfter` is the last returned sequence only when more records exist; the command follows pages to null.

Recovery uses `POST /__internal/hostname-replicas/v1/recover` with exact `application/json` and the `RecoveryRequest` union above. A different human-impersonated recovery service account, audience, and dedicated KMS signing key authorizes the complete request; the registry verifies it only against that role's pinned version/algorithm/SPKI fingerprint, and the publisher has neither. Concretely, the recovery role sends its OIDC token as `Authorization: Bearer <token>` plus `X-Registry-Role-Slot`, `X-Registry-Key-Version`, `X-Registry-Body-Signature` (base64), and `X-Registry-Issued-At` (positive-decimal ms); the KMS signature covers the canonical string `v1\nrecovery\n<method>\n<path-and-query>\n<issued-at-ms>\n<sha256-of-exact-body>`, the recovery counterpart of the publisher string above, and the registry verifies it against the pinned slot's subject/key-version/SPKI record within the 60-second window. The accepted scheme, role, method, path, issued-at, and exact request-body digest persist on the recovery record, and `recoveryOperatorSignatureBytes` in `worker/src/registry/recovery.ts` rebuilds the exact signed bytes from them. The `/probe-challenge` and `/probe-attest` regional-probe requests use the same headers and canonical string with role `regional-probe`. Independently, the human source-attestor command transactionally reads the raw `hostnames/{host}` and `routerReplicas/{host}` documents with its interactive Admin credential. It strictly derives `CanonicalHostnameProjection` from the current hostname document (absence derives only `tombstone`), recomputes the exact ledger projection digest, and refuses to sign unless canonical host/desired bytes equal the ledger host/desired bytes. A malformed source, missing/malformed ledger, mismatch, or direct partial write must be repaired through the explicit Admin ledger-repair transaction first, followed by a new read transaction; attestation never repairs or blesses drift.

Only after equality holds does the command impersonate the human-only source-attestor service account and ask its separate KMS key to sign `v1\nsource-audit\n<host>\n<revision>\n<digest>\n<observed-at>\n<attestation-issued-at>\n<sha256-of-canonical-source-projection>\n<sha256-of-exact-ledger-payload>\n<source-document-digest>\n<ledger-document-digest>`. The same attestor signs publisher control evidence under the disjoint prefix `v1\npublisher-quarantine\n<observed-at>\n<attestation-issued-at>\n<sha256-of-canonical-control-evidence>`. The registry pins a source-attestor subject/audience plus exact key version/algorithm/SPKI fingerprint distinct from publisher and recovery, verifies its short-lived OIDC token from `X-Source-Attestor-Authorization: Bearer <token>` and each embedded signature against that public key, requires the signed attestation time within 60 seconds, and never persists either token. Thus recovery authority alone cannot mint source or publisher-control evidence.

The complete request body is bounded to 16 KiB before parsing and the recovery signature covers the SHA-256 digest of the exact received bytes plus every expected state, action, source/control attestation, provider request record, incident URL, and reason; a UTF-8 BOM or invalid UTF-8 is rejected rather than normalized. `sourceAudit` must be no older than five minutes nor future. The registry independently requires its canonical projection and ledger payload to carry the request host, requires their desired bytes to match, and recomputes the ledger payload's revision/digest; a stale or poisoned ledger that differs from the canonical hostname-derived projection is inadmissible. `PublisherControlEvidence` is also at most five minutes old, permits at most 16 active epoch mappings and 16 entries in each nested member/version list, exactly two Function-runtime readbacks, two CryptoKey policy/version readbacks, two service-account policies, and three Policy Troubleshooter decisions, and stores SHA-256 digests of the nonsampled provider API responses. A nonempty HTTPS incident URL and reason are mandatory. Extra/missing fields, the same subject/key used for recovery and attestation, an oversized evidence list, or evidence on the wrong action are rejected.

Public recovery evidence comes only from three pre-provisioned regional probe runners. Each runner has a distinct keyless service identity and dedicated KMS signing key whose exact version/algorithm/SPKI fingerprint maps in immutable registry configuration to exactly one deployment region. It first signs a challenge request to `POST /__internal/hostname-replicas/v1/probe-challenge`; the per-host DO issues a random, one-use `probeNonce` bound to subject, phase, host, expected state, and a five-minute expiry. The runner puts that nonce in the exact public request query, records the response, then within 60 seconds submits the exact signed `ProbeObservation` to `/probe-attest`. The registry derives the configured runner region from the accepted subject/key/fingerprint mapping—no body/header may name it—and stores a random one-use attestation ID with the consumed challenge, observation, subject, key version, fingerprint, and receipt time.

Runner testimony is necessary but is not provider proof. The human recovery command also uses a 1Password-backed, read-only Cloudflare Logs token to query the nonsampled Log Explorer `http_requests` dataset for every Ray ID and, for a blocked phase, the `firewall_events` dataset. [`firewall_events`](https://developers.cloudflare.com/logs/logpush/logpush-job/datasets/zone/firewall_events/) supplies the provider-recorded Ray ID, edge colo, host, time, response status, action, source, rule ID, rule ref, and match index; the [Log Explorer API](https://developers.cloudflare.com/log-explorer/api/) supplies an exact Ray-filtered readback. The command includes the normalized record plus each raw response digest in `ProviderRequestEvidence`; no sampled Security Events/GraphQL result is admissible.

Each Ray-filtered provider query must return exactly one matching request; a reused/colliding Ray ID is rejected and re-probed. The command normalizes Cloudflare's path-only `ClientRequestPath` separately from the raw query portion of `ClientRequestURI`, stores that portion without the leading `?` as `query`, and recomputes `queryDigest = SHA-256(query)`. The DO pairs that record with its attestation and challenge: Ray ID, host, exact path, exact nonce-only query, query digest, status, and freshness must match; provider event/readback times must be no older than five minutes nor future; and exactly three provider-recorded Ray IDs and `edgeColoCode` values must be distinct. A blocked record additionally requires `action=block`, `source=firewallcustom`, the exact active `ruleId`/`ref`, match index 0, and the custom block-response digest observed by the runner. A canonical record requires no firewall event and must match the runner's reason/revision/origin observation. Missing, delayed, duplicate, sampled, or mismatched provider evidence fails closed. Neither the registry runtime nor a probe runner receives the Logs token.

Recovery is a closed state machine. Every step requires an exact committed-state compare, the recovery identity/signature, and an atomic history append; `apply`, `clear-lock`, and `abort-lock` additionally require the current `lockId`, which `acquire-lock` mints:

1. **Contain and acquire.** The human command installs an exact-host Cloudflare WAF block with a separate 1Password-backed token limited to `Zone WAF Edit` on the two served zones. It generates a random `blockNonce`, configures the exact rule with a unique `ref` and canonical JSON block body `{"recoveryBlock":"<blockNonce>"}`, then reads back the exact zone/ruleset/rule, enabled `block` action, canonical expression `http.host eq "<normalized-host>"`, ref, and custom-response digest. Three fresh blocked attestations plus three matching provider HTTP/firewall records form `WafEvidence`. The DO recomputes the body digest from the nonce, revalidates the exact rule/response fields, three distinct provider colos/Rays, expected committed state, and source freshness, consumes the IDs, then atomically creates `recoveryLock`. Publisher sync is rejected for the entire lock lifetime. If state changed before acquisition, CAS fails and the operator starts from a new audit.
2. **Apply canonical source.** `apply` retains the lock and may write only the freshly attested `sourceAudit.ledgerPayload` after the canonical-source/ledger equality checks above; the same transaction replaces committed state and appends history. It may repair a different payload at the equal revision or jump to a higher source revision, recording every skipped revision range; it never lowers the high-water mark. If the DO is ahead of Firestore, recovery fails `409 source-behind`: an explicit Admin recovery transaction must first advance `routerReplicas/{host}` beyond the DO revision with the current canonical hostname projection, then a new read transaction and fresh signed audit may apply it. An equal-revision repair or any incident where publisher integrity is not proven requires `publisherReplacement`. The human command obtains nonsampled Cloud Functions v2 runtime/revision readbacks, CryptoKey IAM policies and enabled-version lists, service-account impersonation policies, the registry's active mapping digest, and three [Policy Troubleshooter](https://cloud.google.com/policy-intelligence/docs/reference/policytroubleshooter/rest/v3/iam/troubleshoot) decisions for the quarantined subject against replacement-key signing plus replacement-account ID/access-token creation. It normalizes them into `PublisherControlEvidence` and has the source-attestor sign it.

   The registry verifies the mapping digest and exact normalized active-publisher mapping set against its own configuration and requires the attested numeric OIDC subjects, service-account emails, IAM members, canonical Cloud Functions and IAM full resource names, runtime revisions, key versions, algorithms, SPKI fingerprints, enabled versions, policy etags/members, and raw response digests to agree. The replacement key policy may grant signing only directly to the replacement service-account IAM member—no quarantined subject, group, domain, or broad principal—and the replacement service-account policy may grant no token-creation path to the quarantined IAM member or a broad principal. All three Policy Troubleshooter access decisions must echo the exact quarantined service-account email as principal, canonical `//cloudkms.googleapis.com/...` or `//iam.googleapis.com/...` replacement resource, permission, and request time and be `CANNOT_ACCESS`; `UNKNOWN_INFO`, `UNKNOWN_CONDITIONAL`, missing inherited policy visibility, or any grant fails closed. `quarantinedEpochCeiling` must be at least `highestAuthenticatedPublisherEpoch`, `highestQuarantinedPublisherEpoch`, and every active mapping usable through the quarantined runtime/key/fingerprint readback; `nextPublisherEpoch` must be greater and map to the attested replacement subject/key/fingerprint. The same DO transaction applies the source, stores the bounded evidence/history, raises `highestQuarantinedPublisherEpoch` to the ceiling, and raises `minimumPublisherEpoch` to `nextPublisherEpoch`; it does not claim authentication until a replacement sync arrives. A simple missing-delivery jump may send null only when publisher integrity is established through an independent trusted-publisher proof; omission itself is never proof.
3. **Prove and clear.** Before WAF removal, private audit must show lock held, source = committed, no drift, and any required replacement publisher epoch active while every quarantined-accessible epoch is fenced. The command removes the exact-host rule while the lock still rejects all publisher changes, then obtains three canonical attestations and matching provider HTTP records. A failure reinstalls the WAF rule and keeps the lock. `clear-lock` requires fresh source = committed and atomically validates/consumes three distinct attestations/provider colos/Rays whose host/result/revision equal committed state, appends them, and clears the lock. Queued publisher retries may proceed only afterwards; if Firestore advanced during recovery, the fresh-source compare prevents clear until that revision is applied.
4. **Abort without mutation.** `abort-lock` is allowed only when a fresh source audit exactly equals committed state and new `WafEvidence` independently re-proves the exact rule through three distinct provider colos/Rays. The transaction consumes those attestations, records the provider evidence/reason, and clears the lock without changing committed state or bypassing the monotonic rule, but it does not authorize WAF removal: public traffic stays contained. Returning that host to service requires a new fresh `acquire-lock` followed by the same canonical `clear-lock` evidence path; removing the WAF directly after abort is a contract violation.

The recovery history record includes action (`acquire-lock|apply|clear-lock|abort-lock`), before/after, skipped range, canonical-source and equal-ledger projections plus both document digests and attestor identity/key/fingerprint/signature, bounded publisher Function/IAM/KMS/mapping/fingerprint evidence and raw-response digests, WAF rule/config/provider-log evidence where required, the three consumed public probe challenges/observations with runner subject/key/fingerprint/region and receipt time, recovery-operator subject/key version/fingerprint/signature and exact request-body digest, incident URL, and reason. It excludes OIDC/API tokens, is append-only, and is paginated. No adaptive analytics or sampled log is an admission source. A compromised publisher cannot invoke recovery; a compromised recovery identity still lacks the independent source-attestor signature needed to write a fresh, non-decreasing projection for one compared host.

## Provisioning, mutation, and deletion

One transaction helper owns every projected hostname mutation. Current `adultContent` derivation may continue updating its non-projected field without a revision. Any mutation of `eventId`, `status`, `slug`, `edition`, `root`, or `pathNamespace`, and any create/delete, must also read the persistent replica ledger, increment its revision, and write the matching desired state in the same transaction. `apexPath` remains target/client resolution data and is deliberately not copied. A direct or partial Admin SDK write is a contract violation caught by audit.

That helper is `applyHostnameMutation` in `scripts/event-router-registry/hostname-lifecycle.mjs`, and every intent below is one call to it. It reads `routerRehearsals/{host}`, `hostnames/{host}` and `routerReplicas/{host}` before it writes anything, derives the desired state from the RESULTING hostname document rather than from the caller's patch — so source and projection cannot disagree by construction — and buffers its writes until the transaction body returns, which is what makes `apply: false` the default: a dry run runs the same planner over the same reads and shows the write set an apply would buffer. It is a preview rather than a replay, though. The apply mints its own clock, so `updatedAt` and `observedAt` may differ from the preview's (they coincide only under an injected fixed clock, which is how the lifecycle suite proves the two modes plan the same writes); a transaction retry re-plans from a fresh read; and a mutation that lands in between changes the write set. An operator who needs the exact previewed bytes applied would need a frozen plan and clock, which this helper does not offer, so the preview is read as the shape of the write, not its bytes. Every ordinary claim and mutation refuses the globally reserved `r2-` and `r2-root-` classes (one prefix test closes both, since the root class extends the Event one) and refuses any host carrying a permanent `routerRehearsals/{host}` reservation, in the same transaction that would have written; #970's guarded controller remains the only writer of a classed reservation or a synthetic state, and it does not come through this helper. The derivation itself lives in `hostname-projection.mjs` and is the reconciler's too, so a drift report is a fact about the system rather than an artifact of two derivations; `hostname-projection.parity.test.mjs` pins it against the #970 recovery controller's synthetic-only copy over the classes both accept. A mutation is refused outright when the ledger does not already project the hostname document it is layered on, because the repair for that is the explicit Admin advance below followed by a fresh read, never a mutation stacked on drift.

Two barriers cannot be observed from inside a Firestore transaction, so both are explicit attested inputs that fail closed when absent. **Provisioning** a host that carries `pathNamespace` requires the path-addressing deployment barrier as a record naming the release, the deployed router version, the bumped resolution-cache schema version, and when forced advancement was armed; `specs/path-addressing-and-root.md` § "Enabling a host is a deployment-barrier operation" is what that record attests to, and a missing, incomplete, or future-dated one refuses. Provisioning is the only intent that takes that record, and deliberately so: under the frozen root-host table `pathNamespace` is a constant per host rather than a capability a mutation can toggle. The derivation pins it to null off the table and to the table's value on it and refuses every other value, so the create is the only write that can first publish it, and no later mutation of that host can turn it on or off. Enabling the capability on a host that is already serving is the live repoint that section describes, and it has no intent here. **Deleting** a host requires the operator to name the revision the private audit read back from the Durable Object's committed state, and a revision that is not the ledger's current one refuses rather than stranding a serving route with no source.

**Root/route conversion (#1251).** Converting a document between a route and a root marker is never an ordinary update: `update` refuses it by name (`root-route-transition-barrier`), and three whole-document writes own it—the archive's mirror-root conversion below, and the pair `convert-to-root` and `convert-to-route`. Both conversions move a host only between NON-SERVING states and spend exactly one revision, so every intermediate state is an ordinary valid projection that the reconciler classifies `edge-behind` and then `already-correct`; going live is always the barriered `update` to `active` that follows. **`convert-to-root`** takes `root` and the audited `converged` revision and digest, and turns a `disabled` route whose revision the edge has committed into its host's class marker: `fiveacross.app` and `vacaybingo.com` take `root: 'doorway'` (the live apex repoint of `specs/path-addressing-and-root.md` § D1) and a brand mirror takes `root: 'not-found'`. The other marker, and any host outside the root-host table, is refused `root-marker-ineligible`; an `active` or `archived` route `convert-requires-inactive`; a marker source `convert-to-root-requires-route`; evidence that is not the ledger's revision and digest `convert-requires-convergence`. `gaycruisebingo.com` refuses `root-conversion-requires-archive`, because § D1 lets a marker replace the GCB Event only after its archive address is live, which only the archive transaction proves. A brand mirror also reads its route's Event and refuses `root-conversion-flagship-live` while that Event is not `archived` or carries the `archiving` quiesce (a missing Event document is allowed), because § D1 keeps a mirror on an active flagship. The marker is built exactly as the mirror-root conversion builds it, so the non-projected fields survive. **`convert-to-route`** takes `eventId`, `replacementHost` and the `converged` evidence, and turns a brand mirror's converged `root: 'not-found'` marker into a `disabled` route to an explicitly provisioned replacement flagship. Any other host refuses `convert-to-route-requires-mirror`: the two doorway apexes never carry an Event again under § D1, and a second GCB sailing on `gaycruisebingo.com` is a human decision. A doorway source refuses `convert-requires-inactive` and a route source `convert-to-route-requires-root`. The replacement proof is point reads, never a listing: `replacementHost` may be neither the mirror nor another mirror (`replacement-host-ineligible`), and must be an existing, source-ledger-converged `active` route (`replacement-not-serving`) for the same `eventId` carrying the mirror's Edition (`replacement-mismatch`); `events/{eventId}` must exist (`replacement-event-missing`), be `active` and carry no quiesce (`event-not-live`). The slug is taken from the replacement's document, never from the caller. The Event-scoped fields are cleared as on a repoint to another Event, because the marker carries the retired flagship's public face, and `adultContent` is set only when the replacement carries `true`; dropping it otherwise is safe because the #608 trigger (`reconcileHostnameAdultContent` in `functions/src/adultContent.ts`) restamps any document that names an adult Event. The replacement-home proof is checked at conversion and at a mirror repoint; the activation that follows re-checks Event liveness but not the home, so the operator activates while the replacement still serves. Neither intent takes a WAF input: both start from a state the edge has already committed as non-serving for the Event, and an exact-host block on a root host would also block every `/<slug>` beneath it. The disable window is real: a `disabled` route answers not-found for the whole host, so on `fiveacross.app` every archived Event's `fiveacross.app/<slug>` URL and the path-capability endpoint are unavailable from the disable until `convert-to-root` converges; a direct active-route-to-doorway swap is a deferred human decision. Both compose with the delete barrier rather than bypassing it: a serving host is never a conversion source, and the doorway `convert-to-root` produces is refused by `delete` like any other. Three narrow tightenings keep a later call from walking around the proof: activating a route on any root host also requires its Event document to exist (`replacement-event-missing`); a repoint that moves a brand mirror to another Event requires the same `replacementHost` proof (`replacement-proof-required` without it, `replacement-mismatch` unless the new slug is the replacement's) and refuses the key anywhere else as `invalid-input`; and an `edition` supplied for a route on a root host must be that host's table Edition (`host-scoped-field`).

- **Provision:** validate Namespace/Slug/reserved labels; reject any existing hostname or tombstone; create `hostnames/{host}` initially `disabled` and the matching route projection at revision 1. Wait for publisher acceptance and edge inspection before activation, which is CHECKED rather than trusted: a `disabled` → `active` update requires the same audited `converged` revision and digest a repoint takes, matched against the prior ledger, and refuses `activation-requires-convergence` otherwise — without it a caller could provision or repoint and go live at a projection the edge had never accepted. Disabling and every non-projected update need no evidence; the barrier is about going live. A route may not be created for an Event the platform has retired: the transaction reads `events/{eventId}` and refuses `event-not-live` when it is `archived` or carries the `archiving` quiesce, and `update` applies the same check when it moves a document to `active` while `repoint` applies it to the Event being moved TO. `unarchive-barrier` guards a document's own history and could not see this: a mapping created `disabled` after the Event archived had never been `archived` itself, so activating it served the archived Event at its own hostname again, which is what § D8 retires. A MISSING Event document is not refused, because provisioning a hostname before the Event exists is an ordinary operator order. An omitted `pathNamespace` is PERSISTED as an explicit `null` rather than stored as an absence: the derivation reads absent as `null`, so the two project alike, but `recovery-controller.mjs` validates the raw hostname document and requires `source.pathNamespace === null`, so a document that merely omits the field is publishable and can never be attested — which is exactly the recovery it would need after a drift. The stored document says what the projection says.
- **Ordinary update:** non-projected fields do not churn the edge. A status change, an Edition correction, or a move of an existing root marker between `doorway` and `not-found` produces one new revision. `pathNamespace` is deliberately not in that list — it is fixed per host, so no update can change it and no update takes the deployment-barrier record. Converting a document between a route and a root marker is refused by name (`root-route-transition-barrier`); the archive interlock and the conversion pair above own it. Active `eventId`/`slug` changes are rejected. The helper never takes `preview`, `canonicalHost` or `isCanonical` from caller input on an update or a repoint and refuses either intent carrying one as `owner-restricted-field`: each has one reviewed writer (`specs/hostnames-lookup.md`) that validates what it writes, and a second, unvalidated writer could redirect analytics and email origin selection or mint a second canonical mapping. `adultContent` is the one non-projected field an update writes.
- **Repoint:** active → disabled and converge; change `eventId`/`slug` while disabled and converge; active and converge. Skipping or combining barriers is prohibited. An Edition-only correction need not disable the host, but manifest verification remains part of convergence. **The "and converge" is checked, not assumed:** the intent requires a `converged` input naming the revision AND the digest the private audit read back from the Durable Object, and refuses `repoint-requires-convergence` unless both equal the stored ledger's. A disabled `status` in Firestore says only that the disabling revision was written, so without this the identity could move while the edge still served the previous Event — and the digest is the half that does the work, since a poisoned object reports the ledger's revision over a different payload. The check sits after the disabled-status check, so an operator who skipped the disable still reads `repoint-requires-disabled`. A repoint requires an actual identity CHANGE, not an identity key: `changes` must move `eventId` or `slug` off its current value, and otherwise refuses `repoint-requires-identity`, because restating the current `eventId` beside an Edition change would satisfy the projection-inequality check and then reset the Event-scoped fields of a host still serving the same Event. An Edition-only correction is an ordinary update. A repoint REPLACES the document rather than patching it, because when it changes `eventId` it moves the host to a different Event and the previous Event's public face must not travel with it: `adultContent`, `apexPath`, `canonicalHost`, `isCanonical` and `preview` are Event-scoped and are reset — `adultContent` unless the caller supplies a new value, the rest always. The helper never re-supplies `canonicalHost`, `isCanonical` or `preview` for the new Event, and neither does anything else yet: their reviewed writers (`scripts/migrate-bodega-canonical-host.mjs` and `scripts/provision-bodega-preview.mjs`) are hard-pinned to the Bodega Event and its fixed host inventory, so a host moved to any other Event carries none of the three until a validated owner write for that Event exists (#1274). The absence degrades safely rather than wrongly: every reader treats a missing `canonicalHost` as the document's own host and a missing `isCanonical` as not canonical, so the host serves as its own origin and the sign-in gate draws no card, where accepting caller-supplied values would have let the move name a wrong canonical mapping. A slug-only repoint keeps the Event, so it resets nothing and a lowering of `adultContent` refuses `adult-content-monotone` exactly as on an update. The host-scoped fields — `pathNamespace`, and `edition` and `status`, which have barriered moves of their own — survive. Resetting is also the only way to REMOVE an obsolete `preview`, since no deletion sentinel is plumbed through this helper; this, the archive's mirror-root conversion, `convert-to-root` and `convert-to-route` are the four lifecycle writes that replace a whole hostname document. On a brand mirror a repoint to another Event also owes the `replacementHost` proof above, and an `edition` supplied for a root-host route must be the host's table Edition.
- **`adultContent` only rises.** It records a client's acknowledgement and the #608 derivation treats it as monotone, so an ordinary update that lowers it for the same Event refuses `adult-content-monotone`; a second writer able to clear it would be a way around the acknowledgement rather than a second way to set it. A repoint that changes `eventId` is not a lowering and still clears it, because it changes which Event the host serves.
- **Disable/archive:** write inactive state and its revision atomically. Normal completion waits for DO convergence. Immediate withdrawal installs the exact-host WAF block before the source mutation. Disabling is an ordinary update; archiving is its own intent, because it is the interlock `specs/path-addressing-and-root.md` § D8 defines rather than a status change — every Event mapping moves `active` → `archived`, the one target mapping gains `apexPath`, each mirror-root mapping becomes the non-serving `root: 'not-found'` marker retaining its Edition and path capability but no Event field and no `apexPath`, `EventDoc.status` becomes `archived`, and every mapping's ledger takes exactly one new revision, all in one transaction. An ordinary update may neither write `status: 'archived'` nor write `apexPath`, and it may not move a document back out of `archived` on its own; each refuses. The mirror-root conversion replaces the whole hostname document rather than patching it, as a repoint and both conversion intents do, and shares its route-field removal with `convert-to-root`, because a marker may not keep the route fields and a Firestore `update` cannot drop them; it is built by removing exactly `eventId`, `status`, `slug` and `apexPath` from the stored document, so every other non-projected field survives the conversion unchanged and its own reviewed writer stays the only thing that decides its value; `apexPath` is the one non-projected field the conversion removes, because a marker may not carry the route-only archive address. The target mapping is REQUIRED, not optional: an archive that names none is refused `archive-apex-target-missing` before the transaction reads anything, because retiring every mapping without activating the address that replaces them strands the Event permanently — it stops serving at its own hosts, its apex archive URL never becomes eligible, and an ordinary update may neither add `apexPath` nor un-archive it. Exactly one mapping carries the flag when the transaction completes, and all three halves of that are enforced rather than assumed: at least one, because of the refusal above; at most one newly marked, because the target is a single host and a duplicate mapping is already refused as `invalid-input`; and none carried over, because a non-target mapping that already carries `apexPath` is refused `archive-apex-flag-carried` before anything is written. That last refusal cannot be replaced by reasoning about which states are reachable: `apexPath` is not projected, so a source and a ledger that agree on the projection agree whether or not the source carries the field, and the mapping update is a merge that would preserve it. A flag on an ARCHIVED mapping is the state a previous archive leaves and a flag on an ACTIVE one is what a legacy or partial Admin write leaves; both are refused, and the flag is refused rather than cleared, because which of two flagged mappings the operator meant is not a decision this transaction may make. The archive target is also the one mapping that may not be deleted afterwards: `delete` refuses `delete-apex-archive-target` on any hostname document carrying `apexPath`, because an archived route with the flag is the document that answers the apex archive URL and is therefore serving, however inactive its `status` reads, and tombstoning it would strand the archive exactly as an archive with no target would have. The target's apex must also be able to SIGN A PLAYER IN: `specs/path-addressing-and-root.md` § D7 makes regime (b) conditional on the apex being a registered first-party auth host, and `vacaybingo.com` is not one yet, so a target under that Namespace is refused `archive-apex-target-auth-unready` and Vacay archives belong at `fiveacross.app/<slug>` until the console-only registration lands. The rule reads a Namespace table mirrored from `FIRST_PARTY_AUTH_HOSTS` and derived against the real predicate by `src/slug.test.ts`, so it lifts by registration rather than by editing a host literal. WHICH marker a converted root host takes is decided by its class rather than fixed at `not-found`: § D1 gives a canonical apex its doorway once the flagship archives — the platform's on `fiveacross.app`, the Edition's on `vacaybingo.com`, and the GCB apex becomes its Edition doorway exactly at this transaction — while a brand mirror is deliberately not-found, so that archiving the live GCB Event, which must include `gaycruisebingo.com` for completeness, leaves the canonical surface on its doorway instead of offline. The other marker is refused `root-marker-ineligible`. A configured root host may not appear in `mappings` at all: its `status` gates the whole host, so archiving one as a route would take that host's path capability down and stop every other Event addressed by path there from resolving, and the caller is refused `archive-root-host-requires-conversion` and pointed at `mirrorRootConversions` rather than converted silently. "Every Event mapping" is proved rather than asserted: the transaction queries `hostnames` for the Event's `eventId` and refuses `archive-mapping-incomplete` if that listing names a host the caller did not, because an omitted alias would leave an `active` routing document serving an archived Event at that URL while the interlock reported success. The converse — a named host the Event does not map — is refused per host as `archive-mapping-mismatch` from that host's own document, so the two together are set equality. The listing is a seam on the transaction runner rather than an import, and an archive through a runner that cannot list fails closed: a caller that cannot enumerate an Event's mappings cannot make a claim about all of them. **The Event-document half of this transaction is INCOMPLETE and is tracked rather than claimed** (Codex P1, PR [#1245](https://github.com/nathanjohnpayne/fiveacross/pull/1245)): the intent stamps `EventDoc.status: 'archived'` alone and carries none of the application archive flip's other fields—`archivedAt`, `archivedUnder`, the frozen `archive` record, and `archiving: false`—nor does it require the `beginArchive` quiesce those are bound to, so an Event archived through this helper today would be irreversibly archived with no record for the archived surfaces to render and a later `archiveEvent` answering `already-archived` rather than repairing it. Running as Admin is what makes that reachable: `specs/post-sailing-archive.md` § "The flip is refused from anywhere else" enforces the ordering at the rules boundary, and the Admin SDK is not bound by it. This is precisely the routing half of `specs/path-addressing-and-root.md` § D8 that the post-sailing spec said would have to be revisited once there was something to order the flip against. Composing the intent with `beginArchive` and the validated flip payload—so the quiesce, the generation, the complete record and the routing moves all commit together—is [#1256](https://github.com/nathanjohnpayne/fiveacross/issues/1256), and it MUST land with the operator wiring in [#973](https://github.com/nathanjohnpayne/fiveacross/issues/973) before this intent has a production caller. Nothing calls it today: both modules are injectable libraries with no CLI, and the only archive that runs is the emulator suite's.
- **Delete:** reject active delete, where "active" means whatever the host serves rather than the `status` field a root marker does not have: a `root: 'doorway'` marker is the live platform or Edition doorway of `specs/path-addressing-and-root.md` § D1 and is refused alongside an `active` route, since the tombstone is permanent and would strand it the same way. Its non-serving `root: 'not-found'` sibling is deletable, and deleting it retires the host's remaining path capability. After inactive convergence, atomically delete `hostnames/{host}` and advance `routerReplicas/{host}` to tombstone. Convergence is proved by the audited revision AND the audited committed digest, which must equal the stored ledger's projection digest, refusing `delete-requires-converged-payload` otherwise: revision equality alone is satisfied by a poisoned object carrying that revision over a different and possibly still-serving payload — the state the reconciler classifies as `poisoned`, and one that equal-revision recovery can produce — so it cannot prove what the edge serves, and a tombstone written over it is permanent. Wait for tombstone convergence. Never delete the ledger/DO state or reuse the address.

The explicit human Admin ledger advance is the only repair path: when the Durable Object is ahead of Firestore, `apply` fails `409 source-behind` and no attestation can be signed over a ledger that is behind the edge, so `advance-ledger` writes `routerReplicas/{host}` at one above the greater of the stored revision and the named DO high-water mark, carrying the CURRENT canonical hostname projection and nothing invented. It never lowers a revision, requires an incident URL and a reason, and is the one intent that tolerates a missing or malformed ledger, because repairing exactly that is what it is for. The named high-water mark must be a canonical decimal STRING and is validated as one rather than coerced: revisions are text precisely so they stay lossless under `BigInt`, and a JSON number above `Number.MAX_SAFE_INTEGER` has already been rounded by the time it arrives, so a floor computed from it can name a revision that is not in fact above the Durable Object and the repair earns a stale, conflict or gap answer instead. It does not tolerate a permanent tombstone: reading the current source is what makes the advance a repair, and it is therefore also how an address could be reclaimed, so a ledger that validates as a tombstone refuses (`tombstoned-address`) the moment `hostnames/{host}` exists at all, before the source is derived. Only the converged case — the tombstone with no hostname document — still advances, which is how a retired address the edge is ahead of gets republished as the tombstone it is. A ledger that CLAIMS a tombstone but does not validate refuses `tombstoned-address-malformed` instead, with or without a source document: this is the one intent that tolerates a malformed ledger, so a tombstone corrupted in some unrelated way — an extra field, a timestamp that will not normalise — would otherwise fall through the retirement check and, beside a recreated source, republish a permanently retired address as a live route. Which of the two documents is the corrupt one is a question for a human, so the refusal is an investigation rather than a repair this intent may perform. Both repair intents — this one and `backfill-ledger` — owe two things an ordinary write already keeps, because both publish a source document nothing in this helper wrote. They NORMALIZE it: an omitted `pathNamespace` is written as the explicit `null` onto the hostname document in the same batch as the ledger, because `recovery-controller.mjs` validates the raw document and a pre-helper route could otherwise be published and then never attested. And they keep the DEPLOYMENT BARRIER: a source carrying a non-null `pathNamespace` refuses `path-capability-barrier-required` without the attested record `provision` requires, since for a legacy or partial-Admin source the repair is the first edge publication of that capability and would otherwise arm path routing ahead of the capability-aware Worker, the cache-schema bump and forced advancement. Every caller validates that record through one shared validator in `hostname-projection.mjs`, whose `armedAt` must be a real RFC 3339 instant under the same strict predicate `updatedAt` uses and no later than the caller's authoritative clock: `Date.parse` alone coerces a typo such as `"0"` or `2026-02-30T00:00:00Z` into an old instant that reads as a satisfied barrier, so such a record refuses `path-capability-barrier`. A new read transaction and a fresh signed source attestation follow; the advance blesses nothing by itself, and the attestor command in `recovery-controller.mjs` still refuses unless the canonical host/desired bytes equal the ledger's in that new transaction.

The first implementation includes a dry-run-by-default backfill/reconciler. It lists with Admin credentials outside the request path, computes the exact projection, creates missing ledgers, and refuses conflicting histories. The only public-document change an applied backfill makes is the one the repair intents above make: it normalizes an omitted `pathNamespace` to the explicit `null` on `hostnames/{host}` in the same batch that creates the ledger. A dry run writes nothing. Its audit mode compares canonical host documents, desired-state ledgers, and per-host DO committed/lock/history state. It emits counts plus host/revision identifiers but no bearer tokens or credential material. There is deliberately no runtime acknowledgement write into Firestore: granting the publisher database write permission merely to record its delivery would undo the IAM narrowing.

`reconcileHostnameReplicas` in `scripts/event-router-registry/hostname-reconciler.mjs` is that command. It follows the source listing's page token to its end and each host's audit `nextAfter` to null, and classifies every host as exactly one of `already-correct`, `recovered`, `missing` (nothing committed at the edge), `missing-ledger` (a source document with no ledger, under an edge object that has committed nothing), `missing-ledger-source-behind` (the same, under an edge object that has), `no-documents` (the listing named a host that has neither), `drifted`, `poisoned` (same revision, different digest), `source-behind`, `edge-behind`, `malformed-source`, `malformed-ledger`, `invalid-host`, or `reserved-class`, with a held recovery lock, a quarantined publisher epoch that the minimum floor does not yet sit strictly above, and a permanent tombstone reported as orthogonal flags. The quarantine flag additionally requires a quarantine to have happened: `highestQuarantinedPublisherEpoch` initializes to `0` as the no-quarantine sentinel rather than as an epoch, so the fence is tested only once that high-water mark is above zero, exactly as `worker/src/registry/recovery.ts` reads it. Orthogonal means reported independently of the primary state: the lock and the epoch fence are read from the audit rather than from the comparison, so every audited host carries them, including one classified `missing-ledger`, `missing-ledger-source-behind`, `no-documents`, `malformed-source` or `malformed-ledger` before any ledger is read—which matters most on exactly those hosts, because `missing-ledger` is the row an applied backfill hands to the lifecycle helper and it must not do that under a held lock unremarked. Only `tombstoned` waits for a readable ledger, because only it is a property of one, and `reserved-class` and `invalid-host` carry no flags at all, because neither host is ever audited. `reserved-class` is reserved for the two EXACT rehearsal patterns, not for the whole `r2-` prefix: a claim is refused across the prefix, but a host under it matching neither closed pattern is owned by nothing and every downstream consumer rejects it, so reporting it as controller-owned would hide a partial Admin write behind a class that never produced it — it is `invalid-host`. `invalid-host` is decided BEFORE the audit call for a reason that is not stylistic: the audited endpoint requires `host === normalizeHost(host)` and answers 400 for anything else, so a single non-canonical document id in the source listing failed the audit and aborted the whole run rather than being reported as the one bad row it is. The epoch fields are validated to the shapes the Durable Object actually stores—`minimumPublisherEpoch` as a canonical POSITIVE decimal, the two high-water marks as non-negative, since only they carry the zero sentinel—so an adapter answering a floor of zero is malformed evidence rather than a never-quarantined object. Every page of one audit must describe ONE object state: a later page whose committed reference, recovery lock or epoch fields differ from the first refuses `audit-state-changed`, because consuming records from a later snapshot against the first page's metadata let an `acquire-lock` record chain while the reported lock stayed null, omitting the `locked` flag and letting an apply-mode backfill run during containment. A record must also CARRY `before` and `after` rather than merely parse without them: both are legitimately null at the ends of a history, so a nullish fallback read an omitted field as that legitimate value and a truncated record satisfied the chain. Each audit cursor is bound to the page it arrived with: `nextAfter` must equal the last recovery sequence that page returned, and a non-terminal page that returned no records is refused, because a cursor that merely advances lets an adapter skip ahead — one page carrying sequence 1 with `nextAfter: '100'` and then an empty terminal page reads as a complete one-record history and the host is reported `recovered` over a span nothing verified. Every digest off that wire is required to be a lowercase 64-character SHA-256 hex string, the shape the object emits, because accepting any non-empty value let a truncated or non-hex digest decide a classification — `poisoned` at an equal revision, reachability across a recovery span. Every decimal off the audit wire is required to be a STRING before it is pattern-matched, and that is not pedantry: revisions, recovery sequences, pagination cursors and epochs are canonical decimal text for the same reason every revision in this system is, so that they stay lossless under `BigInt`, and a `String(...)` coercion accepted the JSON-number form of all four — a number above `Number.MAX_SAFE_INTEGER` having already been rounded by the time it is stringified, so the reconciler would compare, report and paginate from a value the object never emitted. "Refuses conflicting histories" is a refusal rather than a finding: a recovery history whose sequences are not contiguous from 1, whose record lowers its own accepted revision, or whose span between two records — or between the last record and the state the object reports — is one no publisher sync could have produced means the audit's own inputs disagree, and every comparison derived from them would describe a state nothing reached. Those spans are checked for reachability rather than for equality because recovery records are NOT a complete log of committed transitions: an ordinary sync commits a new revision without appending one, so a recovered host that is later updated normally has an unrecorded gap, and demanding equality across it refused an entire reconciliation run over valid history. What a span must satisfy is what the object guarantees over it — the revision never falls, and an unchanged revision carries an unchanged digest, because the sync table answers an equal revision `200 replay` or `409 revision-conflict` and commits in neither case. Within one record the digest may change at an equal revision, since § Audit and recovery step 2 lets `apply` repair a different payload there. The only write it can cause is creating a missing ledger, and it causes that by calling the lifecycle helper rather than writing itself, so one transaction still owns every projected mutation. That write is restricted to `missing-ledger`, which is why the state is defined against the edge and not only against the ledger: backfill recreates the ledger at revision 1, an uninitialized object is the only edge that accepts revision 1, and a ledger missing from an object that has already committed something would be published into `409 revision-gap` or `200 ignored-stale` while the report said `backfilled`. That host is the source-behind condition by another name, and its repair is the explicit Admin `advance-ledger` above the DO high-water mark, which this command deliberately does not perform even on an apply run: that intent requires an incident URL and a human reason the reconciler has neither of and may not invent. So `missing-ledger-source-behind` is reported and an operator runs the advance. `backfilled` is the fifteenth key on the report's `counts` object and the one entry that is not a classification: it is what an applied backfill turns a `missing-ledger` row into, and it is present at zero on every report so an audit run and a repair run carry the same shape. An applied backfill carries the path-capability barrier the repair intents require, forwarded from the reconciler's own input and validated there the same way, against the run's injected authoritative clock rather than the process wall clock, and an applied run is refused UP FRONT with `path-capability-barrier-required` when a capability-bearing source is in scope and no record was supplied — a reconciliation that aborts halfway has already repaired part of the listing, which is worse than one that never starts. Scope is the listing rather than the subset that turns out to need a ledger, because which hosts those are is not known until each has been audited. `apply` is also refused on an `audit` run (`audit-mode-cannot-apply`) rather than accepted and ignored: that mode cannot write, so the report's `dryRun` said false over a run that was read-only by construction. `dryRun` is now derived from what the mode can write rather than from the flag alone. Both commands accept an exact set of injected seams — a clock, an SDK timestamp constructor and a transaction runner; a clock, the two listings, and the mutation helper — which is how "no KV, Cache API, or Firestore acknowledgement participates" is enforced rather than merely intended. The archive interlock's `eventId` listing of `hostnames` rides on the transaction runner rather than on the helper's own set, because it is a query the caller's SDK runs inside the transaction rather than a store of its own.

## Lookup, cache, and abuse posture

The resolver calls only `RegistryLookupEntrypoint.lookup(host)`. Every sync/lookup/audit/recovery/attestation path derives the same DO ID and calls `getByName` with the immutable v1 deployment constant `locationHint:'wnam'`; no request, hostname, or caller location can alter it. The hint is applied even when an unknown-host lookup is the object's first touch, so an attacker cannot place a future hostname near itself before publisher admission. Changing the hint requires a versioned placement/migration decision rather than ambient geography. The object returns its committed projection; absent state is unknown. The lookup result carries the committed record's `schemaVersion` and the canonical `host` it was projected from alongside its `revision`, on every arm derived from a committed record — the route and root projections, and the tombstone that reads as `unknown-host` while keeping the revision recovery observes — and an uninitialized object carries none of the three. Because the registry deploys separately, the router validates both BEFORE it reads `desired` or publishes the revision. It validates the version against the exact set of projection versions its own build interprets and treats any other or absent version as `replica-malformed`: a later schema whose `desired` retains the current discriminants is otherwise indistinguishable from this one, and would be served under this one's rules. It compares the hostname byte for byte against the address the lookup was made for and treats a mismatch, or a committed-derived envelope naming none, as `replica-malformed` too: both sides are already `hostnameKey(host)` — the value is the committed payload's own `host`, identical to the object's document ID, never a value derived at lookup time from the caller's argument — so the router compares rather than normalizes, and anything a normalization would have had to repair is a defect it may not read through. Without that field the only cross-check tying a record to the address it came back for is the route's denormalised first label, which the two Namespaces share, so a same-slug sibling host's status, Edition and revision would be accepted for an address that does not own them. The public router receives neither the registry's default `fetch`, DO namespace, nor any list method. From the same result it serves exact `GET /.well-known/fiveacross-path-capability` as `{schemaVersion:1,pathNamespace:'fiveacross.app'|'vacaybingo.com'|null,revision:string}` with `Cache-Control: no-store`; missing/malformed/inactive/tombstone lookup fails closed and returns no capability. Root markers are valid configured origins: `doorway` or `not-found` controls the app's `/` outcome, not whether the edge may serve its shell/capability.

The current `caches.default` envelope is removed and neither service adds application, negative, stale-serve, or Firestore fallback caching. Every accepted lookup is strongly consistent with that object's committed state. The deliberate cost is that a cold global request travels to one object's location; hibernation/reset may add storage-read latency, and a DO outage removes the only lookup. The existing strict digit parser bounds the entire service call at 2,000 ms and every failure closes.

The Namespace/reserved/Slug guard runs before the service binding, so foreign/invalid traffic creates no DO work. A random valid hostname can still instantiate/read an empty object at the fixed hint, so wildcard WAF/rate limits must bound unique-host floods before routes attach. Alerts track lookup count/cardinality, empty-object rate, cold/warm latency by colo, hibernation/reset/error outcomes, CPU/storage requests, and spend. The sync/audit/recovery/probe fetch paths enforce exact route/method/content type and the 2 KiB/16 KiB bounds before JSON/JWT work, use Cloudflare per-IP rate limiting for invalid callers, single-flight cached JWKS, and generic errors. Automated DDoS protection and account spend alerts remain enabled.

Remote evidence needs a real Namespace request path: neither service's `workers.dev` origin qualifies, and waiting for wildcard cutover would make R0–R3 circular. A guarded rehearsal controller therefore owns a bounded exact-route surface, but #970 only builds and privately tests that controller; #972 first authorizes invoking it against the replica-capable Event router, and #973 owns final remote evidence. For each run the controller transactionally reserves at most 64 aggregate hosts in a deny-all `routerRehearsals/{host}` collection. Ordinary synthetic/cold hosts match `r2-<26 lowercase base32>.<Namespace>`; a root-shaped test uses the disjoint globally reserved `r2-root-<20 lowercase base32>.<Namespace>` class. Every ordinary hostname claim globally rejects both prefixes and also checks permanent reservations in its transaction. The controller alone may create a manifest-listed root-test hostname document plus equal replica ledger in the same transaction as its classed reservation; the public router never reads the reservation.

The controller uses a human-only 1Password token scoped to DNS/Workers-route edit on the two zones to create proxied DNS plus an exact `<host>/*` route to the reviewed Event-router script. It refuses an apex, wildcard, non-manifest/non-reserved host, any label outside the two closed classes, a dirty/non-main artifact, or a script version other than the recorded candidate. The signed run manifest records run ID, host class, exact hosts/routes/DNS candidates, script version/source commit, expected synthetic state, creator, and expiry. After each provider create, the controller validates the returned resource ID/host/pattern/candidate readback and immediately commits that actual ID to a durable append-only artifact journal bound to the exact signed manifest and reviewed candidate; route creation cannot begin until its DNS ID is journaled, so a partial run remains cleanable. A valid actual ID in a mismatched readback is removed and verified absent before the validation failure surfaces; an unusable ID fails closed before any next side effect and carries the exact signed candidate as reconciliation evidence. If a journal write or receipt fails after provider creation, the controller immediately removes that exact provider ID and requires an exact absence readback; an unsuccessful compensation error retains the complete bound recovery artifact and actual ID. The injected provider-create seam is required to be failure-atomic on rejection (no provider resource was created); ambiguous rejected creates are forbidden until a durable pre-intent/reconciliation adapter is separately authorized. It supplies separate hosts for active/inactive/root-test/tombstone/unknown recovery and the 30 never-used cold markers. Before route removal, cleanup transactionally tombstones every synthetic hostname/ledger and waits for DO convergence; it reads and validates the durable journal, removes every actual journaled exact route and synthetic DNS record by its provider-assigned ID, verifies provider absence, and alerts until cleanup succeeds. Permanent reservations, replica tombstones, DO state, and recovery history remain. A failed cleanup can expose only manifest-listed, globally reserved synthetic exact hosts, never a real Event, apex, or wildcard. No runtime receives DNS/route credentials, `wrangler.toml` keeps both wildcard blocks commented, and #529 retains exclusive authority for wildcard or real-host attachment.

Cold/warm evidence is executable rather than inferred from a 30-second wait. For each of at least three probe regions, R2 generates ten never-before-used valid synthetic hostnames recorded in the evidence manifest; the first public lookup is the remote cold marker (new fixed-hint object plus first storage read), followed immediately by 20 sequential warm lookups of that same object. Local Miniflare coverage separately disposes/recreates an initialized object isolate to prove committed-state reload after reset; provider eviction timing is never claimed. Across the 30 remote cold markers, cold maximum must be at most 1,500 ms. Across warm samples, p95 must be at most 1,000 ms and maximum at most 1,500 ms. Every lookup must remain under the 2,000 ms router bound with zero wrong results/timeouts. The 24-hour R1 synthetic stream must keep `lookup-unavailable` below 1% with no three consecutive failures; otherwise cutover fails.

## Failure semantics

| Condition | Router/result | Retry/fallback |
|---|---|---|
| uninitialized DO | rendered not-found, `unknown-host` | none; no negative cache |
| valid inactive/tombstone | rendered not-found, `inactive` / `unknown-host` | none |
| malformed/unsupported committed state | rendered not-found, `replica-malformed`; the registry emits `outcome: malformed` and the router emits `event-router.diagnostic` with `replica-malformed` (host only, never the stored bytes) | alert; no Firestore |
| committed-derived lookup bound to another canonical hostname, or naming none | rendered not-found, `replica-malformed`, decided before the record's status/Edition/revision is read; the router emits `event-router.diagnostic` with `replica-malformed` | alert; no Firestore |
| Slug mismatch/missing | existing `slug-mismatch` / `slug-missing` | none |
| registry binding absent, or service/DO lookup rejects/times out | rendered not-found, `lookup-unavailable`; the router emits `event-router.diagnostic` with `lookup-unavailable` | alert; no stale/Firestore fallback |
| `/__/auth/*` on configured router | preserve existing lookup bypass/origin pass-through | missing required bindings still fail closed first |
| publisher token/body signature/epoch rejected | sync `401` | Function throws; no state change |
| JWKS unavailable for unknown key | sync `503` | Function throws; platform retry |
| stale/replayed delivery | `200 ignored-stale` / `200 replay` | idempotent success |
| same revision, different payload | sync `409 revision-conflict` | no change; retry plus page |
| future non-successor revision | sync `409 revision-gap` | missing delivery may heal; otherwise recovery |
| publisher while recovery locked | sync `503 recovery-locked` | retry after source-attested recovery clears |
| audit/recovery caller rejected | `401` | no data/state returned; operator reauthenticates |
| recovery CAS/source/monotonic/probe check fails | `409` | no change; repeat source/DO audit and containment |
| origin fetch fails | existing generic `502 origin-unavailable` | unchanged |

Every public response keeps `x-event-router`; fail-closed responses keep a closed `x-event-router-reason`. A resolved edge record carries `x-event-router-revision`, a validated decimal string, and "resolved" is decided by whether a committed record was READ for this address rather than by whether it was served: an `inactive` route and a tombstone's `unknown-host` each carry the committed revision they were refused from, because the `canonical-after-unblock` probe above observes `{reason, revision}` together for `null`, `inactive` and `unknown-host` alike, and `clear-lock` compares that revision against committed state. An uninitialized object, an unavailable or malformed lookup, and a route whose Slug names a different address carry no revision — there is none the router may attribute to the address. No caller-controlled diagnostic enters a header.

**The lookup envelope's shape is a deployment-ordered contract between two separately deployed Workers, and the canonical-host binding is not skew-tolerant in either direction.** The router's envelope check is an exact key set per arm, so an older router refuses a newer envelope's extra field and a newer router refuses an older envelope's missing one; both answers are `replica-malformed` on every committed host at once, which is a closed refusal and an alert rather than a mis-serve, but it is an outage for the length of the skew. The projection `schemaVersion` does not and must not absorb it: that value stamps the record the PUBLISHER wrote, it is the leading element of the digest canonicalizer, and bumping it would change every committed digest and force a new revision for every host to describe a projection whose bytes did not change. The envelope gained a field derived from the payload's existing `host`; a v1 record is still a v1 record. Deploy the **registry first and the router immediately after**, in one change window: the producer must be emitting the field before the consumer requires it, and the window is acceptable only because the Worker remains unrouted — no wildcard, apex or real-Event route is attached, and the only public surface is the operator-run synthetic exact-route manifest. After both halves ship, neither may be rolled back alone; "DO-schema-compatible" below means the pair is selected together. The tolerant two-release shape — a first router release that ALLOWS `host` without requiring it, then the registry, then a second router release that requires it — was considered and declined for this change: it would leave a release in which a registry too old to stamp the field still has its committed projection read under the pre-#1133 rules, which is the gap #1133 exists to close and the thing that ticket's acceptance pins a replica-shape test against. Single-window pairing is affordable only because there is no attached route to fail. Once #529 attaches wildcard routes at Gate 3, a change of this shape needs an envelope that accepts both readings across one release, or a maintenance window.

Emergency per-host containment is the exact-host WAF rule. Namespace route removal is a withdrawal primitive only after the direct-Hosting destination is demonstrated to preserve the required fail-closed posture; otherwise the WAF remains while the route is changed. Code rollback selects the last known-good **DO-schema-compatible** registry/router. A rollback never restores Firestore REST, KV, or stale cache lookup after R3. Do not delete DO/ledger/history state. Reattachment requires the same source/DO audit and R2 evidence.
