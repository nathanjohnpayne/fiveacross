# Per-Day dealing from the Day Snapshot: no-repeat-across-Event + stratification + snapshot-gated (`d15-dealing`)

Implements `plans/daily-cards-spec.md` § "Unlock mechanics" and § "Data model" (a `BoardDoc` per Day). Before Phase 1.5 the app dealt exactly one Board per Player for the whole Event, once, at join. This ticket makes dealing per-Day: each Day gets its own Day Card, dealt lazily the first time a Player opens the Day at or after its `unlockAt`, drawn only from that Day's frozen Day Snapshot—never a live query against the pool. A Player's deal excludes Prompts already on their earlier Day Cards until the main pool is exhausted (~3⅓ Days), then the exclusion resets. Guarded by `src/game/logic.test.ts` (sampling), `src/data/d15-dealing.test.ts` (the deal gate), and `tests/rules/d15-dealing.test.ts` (the day-scoped write gate).

## Glossary

- **Day Card**: a Player's Board for one Day—the same 5×5 contract as before, now one per Player per Day. "Board" still names the object; "Day Card" is the player-facing name.
- **Day Snapshot**: the frozen list of approved Prompt ids (`DayDef.snapshotItemIds`) captured at a Day's unlock moment by the scheduler (#202). Every deal for that Day draws from the snapshot, so everyone's card reflects the same pool regardless of when they first open it.

## Contract

- **`dealBoard` gains a per-Day sampling mode** (`src/game/logic.ts`). A new optional `opts: DealOptions` carries `excludeIds` (Prompt ids to keep off the card) and `stratify` (false for all-tame tutorial pools). The exclusion is applied before the `MIN_POOL` guard and RESETS—falls back to the full pool—when honoring it would drop the usable pool below `MIN_POOL` (the pool has cycled; repeats resume rather than starving the card). `stratify: false` shuffles the whole pool and takes 24 with no spicy/tame target. The four-arg call site (`joinAndDeal`) is unchanged.
- **`dayDealState` is the single SCHEDULE-level deal gate** (`src/game/logic.ts`). A pure function of `{ unlockAt, snapshotItemIds, now, hasBoard }` returning `locked | waking | ready | dealt`. Both the deal write path and the client read it, so "when do we deal / what do we render" has one source of truth about the Day. It is not the only precondition the write has: the Player's own row carries a second one, below (#1158). The two do not overlap—this one is a fact about the Day and the Player's Board for it, the other is a fact about whether the Player has joined at all—and `dayDealState` deliberately stays pure, so the join marker is read where the row is read rather than folded into it.
- **`dealDayCard(u, dayIndex)` is the per-Day deal write path** (`src/data/api.ts`). It reads the Day's `snapshotItemIds`—never a live `status: 'active'` query—resolves those ids to Prompt text/spicy, excludes the Prompt ids on the Player's earlier Day Cards, and writes `events/{eventId}/days/{dayIndex}/boards/{uid}` plus a merge into `players/{uid}.dayStats[dayIndex]`. It returns `true` only when it dealt a new Day Card; `locked`, `waking`, an already-dealt Day, and a Player row that does not yet carry `joinedAt` are all no-ops. **The join is a precondition** (#1158): every branch of the transaction merges a Day bucket into `players/{uid}`, and a merge onto a row that does not exist CREATES it carrying `dayStats` and nothing else—a nameless leaderboard entry—so the transaction requires the persisted `joinedAt` stamp `joinAndDeal` writes and returns the same `false` no-op otherwise. Unlike the other three that no-op RESOLVES ITSELF: `joinAndDeal` stamps the field a moment later, `Board`'s `playerJoined` flips on that same field, and the lazy deal is re-asked once—which is why the caller sees `false` here rather than a retryable rejection. **A MALFORMED stamp is repaired by the next join, not just an absent one** (Codex P2, #1158 review round 6): the row is self-writable and no field on it is validated, so `joinedAt` can hold a string or an object, and every reader calls such a row unjoined. `joinAndDeal` therefore writes the stamp whenever the stored value is not a number—the exact complement of the gate—so the no-op stays self-resolving instead of repeating forever over a value the join declined to replace. A numeric stamp is never re-written, and `NaN` or `Infinity` counts as numeric on purpose: every predicate reads that row as joined, and the Player is identified by the document id regardless. Both sides read `joinedAt` and nothing else (Codex P2, #1158 review round 4): the stored `uid` is not the marker, because `firestore.rules` validates no field on the row (ADR 0001) while the document id always identifies it, so a guard keyed on the field could call a joined Player unjoined and—since `playerConverter` synthesises the converted `uid` from the id—leave the Card on “Dealing…” with nothing in the effect's inputs left to move.
- **Day-scoped Board wiring** (`src/data/paths.ts`, `src/hooks/useData.ts`). `dayBoardRef(dayIndex, uid)` points at the canonical day-scoped path; `useDayBoard`/`useDayCard` subscribe to it and expose the `dayDealState` so a surface can tell `locked` from `waking` from `ready` from `dealt`. The pre-1.5 `useBoard(uid)` keeps its single-Board callers unchanged.
- **The lazy deal's in-flight guard and manual Retry** (`src/components/Board.tsx`). `Board` fires `dealDayCard` for the viewed Day once its state is `ready` and no card exists, and holds an in-flight key of event, Player, Day and join state (`dealInFlightKey`) so the same attempt is not fired twice while it is pending. Because the join state is part of the key (#1158), an unjoined attempt and a joined one can be in flight together. A failed attempt surfaces a Retry for the viewed Day; Retry clears BOTH join states' keys for that Day and re-fires the deal, so it re-attempts even while an earlier attempt is still pending (#1255). Overlap is safe because the deal transaction re-checks the card and no-ops for the loser. Each key is owned by the attempt that set it: an attempt that Retry replaced may settle late, and it then neither releases its replacement's guard nor publishes the error panel over it.

## Acceptance criteria

- Given a Day with `unlockAt` in the future, when a Player opens it, then no Board is dealt and the locked state renders (`dayDealState` → `locked`; rules test denies the write).
- Given a Day whose `unlockAt` has passed but whose `snapshotItemIds` is not yet stamped, when a Player opens it, then the client shows the "waking up" wait state and does not deal from a live query (`dayDealState` → `waking`; `dealDayCard` no-ops).
- Given a Player whose earlier Day Cards already used some of the still-available main-pool Prompts, when their next Day Card is dealt, then none of those Prompts repeat, until the pool is exhausted and the exclusion resets (`dealBoard` `excludeIds`).
- Given a tutorial Day (easy/closing pool) seeded all-tame, when its Day Card is dealt, then the deal succeeds with no stratification starvation (`stratify: false`).
- A Day Card write path never reads the live `items` collection for its pool—only `snapshotItemIds`.
- Re-opening an already-dealt Day Card is a no-op (no re-deal).
- Given a Player whose row carries no `joinedAt` stamp, or one that is not a number, when the lazy deal fires for a ready Day, then nothing is written—no Day bucket and no card—and the deal is re-asked once `joinAndDeal` stamps or repairs the field, so the Card deals instead of stranding on its dealing state (`src/data/d15-dealing.test.ts` § "dealDayCard — the join is a precondition (#1158)", `src/components/d15-day-card-render.test.tsx`).
- Given an unjoined deal attempt that rejects while a joined attempt for the same Day is still pending, when the Player presses Retry, then a new deal attempt fires rather than the effect skipping back onto “Dealing…”, and if the replaced attempt later rejects, the error panel does not reappear over the running replacement (`src/components/d15-day-card-render.test.tsx`, #1255).
