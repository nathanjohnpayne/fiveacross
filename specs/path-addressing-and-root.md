# Path addressing and the root—historical Events, brand-mirror slugs, and what serves `/` (`path-addressing-and-root`)

Three accepted decisions have to compose here, and each was correct inside the scope it was written for. [ADR 0009](../docs/adr/0009-event-resolved-from-hostname.md) rejected addressing Events by path on one shared origin. [#625](https://github.com/nathanjohnpayne/fiveacross/issues/625), as generalised by [#599](https://github.com/nathanjohnpayne/fiveacross/issues/599), made every registered domain a first-class serving host that never bounces a visitor off itself. And the platform PRD makes self-service Event creation a Phase 5 goal, which gives the canonical root a job it did not have when ADR 0009 was written. This spec decides how the three fit together, because the answer is not one policy: **path addressing is rejected for one class of Event and required for another**, and getting that boundary wrong in two separate designs is the drift [#799](https://github.com/nathanjohnpayne/fiveacross/issues/799) exists to prevent.

Three seams ship from this spec so far: the same-origin path-capability projection the Event router answers from its registry lookup (#972; tests in `worker/src/router.test.ts` and `worker/src/registry/routerRegistry.integration.test.ts`), the reserved-path module with the pure address parser `parseAddress` (§ Reserved paths and the D3 parse, #1387; tests in `src/reservedPaths.test.ts` and the mirror parity tests in `src/slug.test.ts`), and the D8 archive interlock as the event-router registry's archive intent, composed with the application archive flip (#1256; tests in `scripts/event-router-registry/hostname-lifecycle.test.mjs` and `tests/rules/event-router-hostname-lifecycle.test.ts`), which has no production caller until #1488. Nothing calls `parseAddress` yet; resolution and the router basename remain deferred under D3. Otherwise it answers the nine questions #799 enumerates as decisions, states the reserved-path list, the installed-context refusal requirement and the #134 archive interlock as requirements rather than open questions, and names the seams the implementation tickets get filed from. It supersedes, in part, `specs/x-multi-event-schema.md` § "Recommended migration seam (deferred)", which still recommends the opposite; ADR 0009 carries a matching scope note.

## Glossary

**Addressing regime**—the rule pairing a class of serving host with the way an Event is named on it. There are exactly three (§ The three regimes), and they differ in capability, not only in URL shape. Note that "regime" counts *addressing* rules, not surfaces: a mirror's flagship visit at `/` is addressed by host rather than by path, so it belongs to no path regime while still being its own **surface**—which is why D6's entry dimension carries four values against these three regimes. *Avoid:* routing mode, URL scheme.

**Path-addressed surface**—a rendering of an Event reached as `<host>/<slug>` rather than as `<slug>.<namespace>`. Deliberately a **narrower** way to reach the same `eventId`, never an alias of the subdomain's capability set. *Avoid:* path alias, mirror route.

**Canonical apex**—`fiveacross.app`: the platform's own address, and also a namespace apex. **Namespace apex**—an apex under which Event subdomains are issued (`fiveacross.app`, `vacaybingo.com`). **Edition apex**—an apex that brands one Edition and issues no Event subdomains (`gaycruisebingo.com`). **Brand mirror**—one of the three `*.vercel.app` backup hosts (`gaycruisebingo.vercel.app`, `fiveacross.vercel.app`, `vacaybingo.vercel.app`, `src/auth-domain.ts`). *Avoid:* "the apex" unqualified—three different host classes answer `/` differently.

**Root-shaped document**—a `hostnames/{host}` document with no `eventId` and an explicit `root` discriminator: `doorway` serves the Edition doorway; `not-found` preserves host path capability while `/` is not-found. The proposed future root resolution outcome, beside today’s browser `event` and `not-found`; its authenticated canonical shape is not the public browser payload. *Avoid:* landing page (that is what it renders, not what it is).

**Doorway**—what a root marker renders: the host's Edition brand plus, where the host class allows it, the create-Event affordance. *Avoid:* home page (every Event's Card tab is also `/`).

## The three regimes

One table rather than scattered prose, because the whole point of folding #766 and #626 into one design is that a later implementer must not be able to miss that these differ.

The single sentence a reader should leave with: **(a) is the full product; (b) and (c) are narrower reaches at the same `eventId`, and the narrowing is the reason they are allowed to exist on a shared origin at all.**

## Binding constraints this spec designs against

Restated rather than re-litigated, because every decision below is shaped by them.

- **Every serving host serves in place.** #625's mirror-only rule ("the backup must work precisely when the canonical host is blocked"), generalised by #599's 2026-08-05 amendment to the whole system. **A path-addressed archive or mirror-host Event must never HTTP-redirect to a subdomain**, and no domain that legitimately serves is ever bounced off itself.
- **A slug is not a secret**—but be precise about what backs that today, because an archive implementer who over-reads it will assume an isolation that does not exist. `specs/hostnames-lookup.md` says knowing an address grants nothing "because every read of Event data still passes the membership gate," and ADR 0009 is explicit that the gate "remains a target contract, not a property of the current rules." **Today reads are only SIGN-IN-gated:** any signed-in account can read most data under any Event, per `specs/x-multi-event-schema.md`'s honest inventory, and the tenant-isolation workstream that would change this has not landed. Path addressing neither widens nor narrows that—it changes which URL reaches a document, not who may read it—and `/bodega-bay` in a URL bar still discloses nothing `hostnames/{host}` does not already. But **any member-only guarantee about an archive depends on the tenant-isolation workstream, not on this spec**, and must not be claimed before it ships.
- **Fail closed on unknown Events.** `specs/event-resolution.md`'s decision table: not-found is a state the app draws, never inferred-active. An unrecognised path segment gets the same discipline, and it gets it *before* the router exists.
- **Gay Cruise Bingo is not sanitised by universalisation.** The platform PRD § Launch Edition is explicit: "No universalization task should silently sanitize or overwrite the Gay Cruise Bingo edition." D1 is written to that.

## Decisions

Each decision answers one of #799's nine questions. Acceptance criteria for all nine are collected in § Acceptance criteria, keyed `D1`–`D9`, so a reviewer can check the list off directly.

### D1 — What renders at `/`, per host class

`/` is answered by host class, not by one rule.

- **Canonical apex (`fiveacross.app`)** renders the platform doorway: the `fiveacross` brand and the create-Event affordance (D9 decides that affordance's state today). This is the change #766 asked for.
- **`vacaybingo.com`** renders its Edition doorway, not the platform create page. A create affordance is not added there: creation is a platform act performed at the platform's address.
- **`gaycruisebingo.com` remains the canonical, live flagship surface while a Gay Cruise Bingo Event is active.** It is an Event routing document during that time, so `/` renders that Event exactly as it does today; the GCB Vercel host remains its backup mirror, never its only production home. The GCB apex becomes its Edition doorway only after the archive transaction has retired that live Event. Its archived path is then `fiveacross.app/<gcb-slug>`, resolved through the Event's `hostnames/<gcb-slug>.fiveacross.app` routing document, rather than through an invented GCB subdomain namespace. A root marker can replace the GCB Event document only after that replacement archive address is live, so the lifecycle helper refuses any non-archive root conversion on `gaycruisebingo.com` (`root-conversion-requires-archive`). This stateful transition preserves the Edition's single-Event product shape and the platform PRD's rule that no universalization silently erases Gay Cruise Bingo; it does not turn the emergency mirror into a de facto canonical host.
- **Brand mirrors keep serving an active flagship Event at `/`, and get no doorway at all.** This is #625's shipped behaviour and it is deliberately not disturbed while the flagship is live: `hostnames/vacaybingo.vercel.app` names an active Event, and the mirror exists so that a Player whose canonical host is blocked still lands *in the game* rather than on a page about the platform. A doorway there would answer the emergency with a form. Path addressing on a mirror is therefore purely **additive**—`/` keeps an active flagship, `/<slug>` reaches any other Event in the mirrored namespace—and the create affordance never appears on a mirror in either position, because starting a permanent, slug-claiming act from a backup surface adds a failure mode to the surface whose whole job is to have fewer of them. When the flagship archives, its mirror-root mapping becomes the same-transaction `root: 'not-found'` capability marker (D8), so `/` is not-found until an explicitly provisioned **active** replacement flagship repoints that root. That repoint is `convert-to-route` in `scripts/event-router-registry/hostname-lifecycle.mjs`: it requires the replacement to serve already at its own converged production host with the mirror's Edition, writes the mirror route `disabled`, and leaves going live to the ordinary convergence-barriered activation (`specs/event-router-registry.md` § Provisioning, mutation, and deletion). This is particularly important on `gaycruisebingo.vercel.app`: it has no path namespace, so after its one GCB flagship archives it is deliberately not-found rather than a doorway or a hidden archived alias.

| Host and state | Root routing document | What `/` serves |
|---|---|---|
| `fiveacross.app` | root marker | Platform doorway and create affordance |
| `vacaybingo.com` | root marker | Vacay Edition doorway, no create affordance |
| `gaycruisebingo.com`, a GCB Event active | that Event | The GCB Event—the canonical production surface |
| `gaycruisebingo.com`, its Event archived and re-homed | root marker | GCB Edition doorway; the archive is at `fiveacross.app/<gcb-slug>` |
| Brand mirror, active flagship | flagship Event | That active flagship Event, never a doorway |
| Five Across or Vacay mirror, no active flagship | non-serving capability marker (`root: 'not-found'`, `pathNamespace`) | `/` is not-found; `/<slug>` still resolves in the mirrored namespace |
| GCB mirror, no active flagship | non-serving marker with no `pathNamespace` (or no document) | Not-found |

**The root is a resolution outcome, not a hardcoded route.** A host serving a doorway carries a **root marker**: a `hostnames/{host}` document with no `eventId`, carrying `edition`, optional `pathNamespace`, and `root: 'doorway'`. A mirror that must keep path capability after its flagship retires carries the sibling **non-serving capability marker**: no `eventId`, its `pathNamespace`, and `root: 'not-found'`; it answers not-found at `/` but remains the host-capability document D3 needs for `/<slug>`. Resolution gains a third outcome—`{ kind: 'root', edition, pathNamespace }`—beside `event` and `not-found`; `root: 'not-found'` resolves straight to the latter at `/`. Encoding both variants as data keeps `specs/event-resolution.md`'s existing properties intact: the answer is still pre-auth, still cacheable, still `get`-only, still never enumerable, and adding a doorway host stays a data change rather than a deploy.

**A `root: 'doorway'` marker is what makes a doorway; no root-shaped document is what makes path addressing.** Path capability remains the independent `pathNamespace` field, which is why both a serving flagship and a non-serving capability marker can carry it—see D3.

**This is a live repoint, not a greenfield add.** `hostnames/fiveacross.app` today resolves to the Bodega Event (`scripts/provision-bodega-preview.mjs` provisions its postcard on exactly that host alongside the two subdomains). Turning the canonical apex into a doorway means repointing that document from an Event to a root marker, which is the same write [#601](https://github.com/nathanjohnpayne/fiveacross/issues/601)'s post-Event repoint already has to make. The two must be sequenced deliberately rather than discovered in conflict: **the apex does not become a doorway while it is still Bodega's serving address.** The helper path is `convert-to-root`, which runs only after the route is `disabled` and that revision has converged at the edge. The disable window is an outage: while the apex route is disabled, every archived Event's `fiveacross.app/<slug>` URL answers not-found until the doorway converges. The conversion is itself the go-live step, since a doorway has no staged state and no later activation, so it requires the same attested deployment-barrier record `provision` takes, the release that armed the forced advancement and precache retirement required below.

**The repoint must also retire the service worker already installed at that root.** This is the part a data-plus-deploy plan misses entirely. Devices that installed Bodega from `fiveacross.app` hold a **root-scoped service worker** with a precached, env-pinned shell. Omitting the manifest and denylisting path-addressed navigations (D4) does neither of the two things that matter here: it does not unregister that worker, and it does not stop it answering `/`. So the old worker keeps launching the retired Bodega Event—most visibly offline, and also while a replacement worker sits in `waiting` under this repo's deliberate `registerType: 'prompt'`, which never activates without the Player accepting the prompt.

The migration therefore carries an explicit requirement: **release the forced-advancement path and retire the precache for every client that can reach it before treating the doorway as supported.** This repo already owns the machinery rather than needing new invention—`src/sw-rescue.ts` and the `build-floor.json` install-time floor (#342/#514) exist precisely to reach a client whose shell is stale and whose page cannot cooperate—so the release uses that path and verifies its effect on reachable clients rather than merely assuming an ordinary prompt update. But a dormant installed client can return with a much older worker that never learned that protocol; no web deployment can update it before that first navigation. The contract does not falsely promise otherwise: such a client may receive its old root shell once, must update or clear site data from that root, and then re-open the requested URL. A doorway that is correct on the server and shadowed by a stale worker on the device is still an operational compatibility failure, not proof that a path Event mounted or that the new regime is safe to advertise as supported on that client.

**And the repoint alone is not sufficient—a hostname-resolved bundle is a hard precondition.** The registered `gcb` production target still bakes the non-empty `VITE_EVENT_ID=med-2026`, while the registered `fiveacross` target now requires an empty `VITE_EVENT_ID` and resolves its Event by hostname (`scripts/build-target.mjs`, #851). A non-empty value is the build-mode switch that makes `resolveEvent` answer from env and **never consult `hostnames/{host}` at all** (ADR 0009, `specs/event-resolution.md` step 1). Repointing `hostnames/fiveacross.app` under a still-deployed, pre-#851 Bodega-pinned bundle therefore changes nothing: that older build keeps mounting its baked Event. The same short-circuit blocks path parsing generally, so **no** regime in this spec takes effect on an env-pinned build. The precondition, stated so an implementation ticket cannot skip it: **every host that serves a doorway or a path-addressed Event must be served by a hostname-resolved build (empty `VITE_EVENT_ID`).** The Five Across target now satisfies the build contract, but deploying and verifying that target remains an operational prerequisite; any other serving target must be unpinned before it can carry these regimes. The claim above that adding a doorway "stays a data change rather than a deploy" is true only *after* the serving target is hostname-resolved.

**The root does not host the wizard's steps.** #788's shell owns the wizard's own route, `/setup/*` (`specs/event-setup-wizard.md` § Mount point), and the doorway links to it there. That route is a top-level segment, so `setup` is in the reserved path-segment floor (§ Reserved paths): the owner chose to keep the shipped route and reserve the word rather than move the wizard under `/more` (#1223, 2026-10-02). The invariant is a **reserved, platform-only setup route**, not that creation lives under the More tab; any future wizard route must likewise be reserved before it ships, never left at an unreserved top-level segment such as `/create`. Mounting a five-step flow at `/` would put the wizard on the one path that must stay cheap, dependency-light and correct before any Event is known.

### D2 — Path and hostname are not equivalent origins

`fiveacross.app/bodega-bay` is **not** the same identity as `bodega-bay.vacaybingo.com` for sessions, install or offline cache, and is not meant to become one.

For the mirror regime this is arithmetic: a different origin is a different origin, so cookies, storage and permissions are separate by construction. For the apex-archive regime it is a deliberate choice, and the more important half. The path surface shares an origin with every other archive on that apex and with the doorway itself, so it inherits precisely the ceilings ADR 0009 named—one storage quota, origin-scoped permission grants, all-or-nothing site-data clearing, no browser-enforced boundary. The resolution is not to buy those back with application code; it is to **not need them**, by never granting the path surface a capability that depends on them (D4).

**One capability is granted on a mirror path anyway, and the exception is stated rather than smuggled.** Proof capture needs the camera, the camera grant is origin-scoped, and a mirror origin serves many Events—so a grant (or a denial) on `fiveacross.vercel.app` applies to every Event reached under it. That is exactly the coupling ADR 0009 names, and regime (c) **accepts it deliberately** instead of pretending it away. The reason is that the alternative is worse in the only situation the mirror exists for: a mirror is the break-glass surface a Player reaches when the canonical host is blocked, and a break-glass surface that cannot capture proof is a Player locked out of half the game with no other door. Regime (b) needs no such exception—an archive is read-only, so it asks for no camera at all and the isolation argument stays whole there.

The consequences are therefore bounded and worth stating, because a later reader must not "fix" this by quietly granting install too:

- A camera **denial** on a mirror denies proof capture for every Event on that mirror until the visitor clears it. This is a real degradation of the backup, not a theoretical one.
- The coupling does **not** stop at capture, and D4 is explicit about the rest of it rather than implying withheld install UI sweeps it away.
- **Firebase Auth session is the third origin-scoped coupling, accepted and bounded rather than left implicit.** Auth persistence is origin-scoped, so one sign-in serves the doorway and every path beneath it—sign in at one archive and you are signed in at the next, and at the create doorway. Be precise about what that does and does not do. It does **not** escalate authority: Firestore rules key on the `uid`, and that identity is the same person whichever origin they signed in from, so no data becomes reachable that a fresh sign-in would not also have reached. What it changes is **session lifetime and blast radius on a shared device**—sign-out is origin-wide, and a borrowed phone left signed in at one archive is signed in for all of them. Regime (a) does not have this property, because each Event subdomain is its own origin and its own session; that is one more reason a live Event's home stays there.
- The accepted exception is scoped to a **mirror path**. It is not a precedent for regime (b), and it is not a precedent for install anywhere.

So the contract to state plainly, because the tempting reading is the wrong one: the path surface is a *narrower reach at the same `eventId`*, not an alias of the subdomain. A Player signed in on a live Event subdomain is not thereby signed in on a mirror path; that is one sign-in per origin, the same as any two web apps. An apex path deliberately has no concurrent live-event case: D8 admits it only after the Event becomes archived, because an active Event's write permission cannot be made origin- or pathname-specific at the Firestore boundary.

**Serve-in-place forbids fixing this with a redirect, and does not forbid saying so.** A path surface must never navigate a visitor to the subdomain automatically. It **may** render an explicit, user-initiated affordance—#625 already specified its exact shape for the mirror case, and the same shape applies to an apex archive path: "when the canonical IS reachable, a dismissible 'continue on `<canonical>`' banner, never automatic." A banner the Player chooses to follow is not a domain bouncing a visitor off itself. On an archived Event there is no such link to offer, because there is no longer a subdomain serving (D8).

### D3 — Resolution and the router `basename`

**The original browser resolution design is withdrawn pending a separately reviewed architecture.** D3 previously required an anonymous browser to read canonical `hostnames/{host}` for `pathNamespace`, root markers and target eligibility, then subscribe to those canonical documents. That conflicts with the owner-approved #1419 boundary: canonical routing/recovery metadata requires authentication; the browser reads only strict `publicHostnames/{host}` with the seven routing fields and four nested preview fields. `pathNamespace`, `root` and `apexPath` are absent from that public projection. This spec no longer authorizes those canonical browser reads, a canonical fallback, or additional public fields.

**Product decisions remain; the missing transport does not become an implied API.** Parse a candidate first segment before resolution, distinguish speculative from effective `basename`, resolve before mount, and never turn a missing or ineligible path target into the doorway or flagship. An ordinary live-subdomain route keeps an empty effective basename. The exact browser capability, root-outcome and apex-target eligibility mechanisms are deferred until a separately reviewed architecture can satisfy the private/public boundary. Current `src/eventResolution.ts` resolves only `event` or `not-found`; it does not implement path resolution or a root outcome. Future Event mapping and posture reads must use the approved public projection without listing or client writes.

**Canonical path metadata still governs the operator and signed edge registry.** `pathNamespace` names an apex that issues Event subdomains; absence means no path capability. Five Across and Vacay mirror roots may carry it independently of their flagship/root outcome. GCB has no such namespace because its Edition apex issues no Event subdomains. These are authenticated canonical/registry constraints, not fields an anonymous Firestore client may read. The existing same-origin capability endpoint below exposes only the reviewed minimal projection; it does not provide a browser root outcome, target mapping or `apexPath` eligibility, and is not evidence that the deferred D3 architecture has shipped.

### Constraints retained for the deferred resolution architecture

- **A target cache cannot grant serving-host capability.** A future architecture must validate current serving capability before reusing a derived-target entry, keep targets isolated by derived address and capability binding, and invalidate pre-capability root/flagship cache state before it can influence install UI. It must achieve that without reading authenticated canonical metadata in the browser. Today's public V2 Event-mapping cache does not supply these capabilities.
- **The resolved target and serving capability answer different questions.** Future target posture subscriptions must read strict `publicHostnames` for the resolved Event address; the mechanism for observing serving capability retirement remains deferred. The current `watchAdultContent()` uses the serving hostname and does not implement this future path-target switch.
- **The whole pre-paint resolution must share one timeout budget.** Capability validation and an uncached public target lookup cannot each extend the existing `timeoutMs` bound. This is a future timing constraint, not authorization for the withdrawn pair of canonical Firestore reads.

**The deferred service worker consumes the implemented minimal server projection, not a guessed pathname rule.** A browser service worker cannot query Firestore before deciding whether to return its precached SPA shell, while `pathNamespace` deliberately remains a data field rather than a build-time host list. The path-addressing rollout therefore adds one same-origin, reserved endpoint: `/.well-known/fiveacross-path-capability`. The hostname-aware edge layer answers it from exactly the serving host's own routing lookup — since [#972](https://github.com/nathanjohnpayne/fiveacross/issues/972) that is the registry's committed projection of the authenticated canonical `hostnames/{host}` document (`specs/event-router-registry.md`) rather than a direct read of the document — and returns only a schema-validated `{ schemaVersion: 1, pathNamespace: string | null, revision: string }`, with `Cache-Control: no-store`. It returns neither an Event id nor a slug catalogue, is gated on that lookup so a missing, malformed, inactive or tombstoned host yields no capability at all, and is a projection of the serving host's routing state rather than a second routing authority. The deferred capability-aware navigation handler must fetch that endpoint before choosing the Workbox shell: a valid non-null namespace lets it treat an eligible first segment as a path address, while `null` preserves the normal app-route shell on a host without path addressing. If the endpoint cannot be read and there is no fresh capability result, the handler takes the conservative route for a candidate slug—network pass-through, never the precached shell—while the shared reserved-path parser keeps known app routes such as `/feed` available offline. This availability trade-off is intentional: a temporary network failure may withhold an unknown route, but it must never mount a mirror flagship or doorway shell for a path Event.

**Enabling a host is a deployment-barrier operation, even though the capability's source of truth is data.** The endpoint and capability-aware worker ship first; the release arms forced advancement for reachable root-scoped workers and retires their precaches (D4); only then may the `pathNamespace` field and the eligible target routing documents be published. That ordering prevents an older prompt-waiting worker, which can reach the update path, from serving its env-pinned flagship shell for the first supported path visit. It cannot prevent a dormant client carrying a pre-capability worker from doing so once; D4 names that unavoidable legacy outcome and its explicit recovery instead of calling the barrier universal. This remains a future rollout barrier: the endpoint is implemented, but the capability-aware client/worker and complete browser resolution architecture are not. The edge reads its signed registry; a future browser must respect the strict public lookup boundary rather than read the canonical host field.

**An unresolvable slug renders not-found, never the doorway.** `fiveacross.app/nope` must not silently become `fiveacross.app`, because a wildcard fallback to `/` is precisely how a mistyped address would look like a working one. The existing `<Route path="*">` fallback in `src/App.tsx` stays correct *inside* a resolved basename and must not be the thing that swallows an unknown first segment—the future parse runs before the router exists, which is what keeps those two cases distinguishable.

### D4 — No app-promoted install, and refusal in every installed context

**Every path-addressed surface refuses to mount in an installed or standalone context.** Regimes (b) and (c) both. A web app can withhold its manifest link and its own install UI, but it cannot prevent a browser or OS from adding a site through native chrome (including iOS Add to Home Screen). So the enforceable contract is deliberately two-part: the product never promotes installation on a path-capable origin, and a path-addressed route refuses to mount whenever `display-mode` shows it is running as an installed app—regardless of when or how that installation was created. The following are future implementation requirements, not claims that today’s client has capability-aware navigation or path-regime install/refusal gates. Each clause must be separately checked before path addressing is enabled:

- **No manifest is served at, or linked from, a path-addressed document.** The `<link rel="manifest">` is absent. The per-host manifest #546's Worker serves is a property of a host, and a path is not a host. This withholds the product's install affordance; it does not claim to disable browser chrome.
- **`beforeinstallprompt` is never consumed on a path-addressed surface.** The future path-regime implementation must gate `src/hooks/useInstallPrompt.ts` on the address regime so `InstallPrompt` never mounts—including the iOS "Show me" branch, which fires no event and would otherwise slip through a listener-shaped guard. Native browser/OS install commands remain outside app control and are handled by the universal refusal below.
- **The service worker never returns its precached shell for a path-addressed route.** Registration scope is still the origin root, so a worker registered by the *doorway* controls every archive path unless its navigation handler declines the shell. A future `src/sw.ts` implementation must put a capability-aware navigation handler ahead of Workbox's generic `NavigationRoute`: it must consult the reviewed same-origin capability projection, share the reserved-path parser, and pass an eligible path navigation through to the network instead of `index.html`, keeping the existing `/__/*` denial intact. Today `src/sw.ts` registers only the generic `NavigationRoute` fallback to `index.html` with the `/^\/__\//` denylist; it does not fetch the capability endpoint or recognize path-addressed navigation. A pathname-only global denylist is prohibited: it would silently change offline app-route behavior on live subdomains, while a hard-coded host list would drift from `pathNamespace`. Reusing the navigation seam matters—#182 is the shipped proof that a fallback silently swallowing a route it should not own is a live failure mode here, not a theoretical one.
- **A path-addressed navigation is never served the precached shell.** It falls through to the network, which is the same statement as the bullet above from the Player's side, and the reason regime (b) has no offline cold boot to promise.

**What withholding app-promoted install does NOT buy, stated so it cannot be over-read.** It reduces the ordinary install collision, but it does not make the app's durable, origin-scoped storage stop being shared, and it cannot stop browser chrome from creating an installed wrapper. Once a path Event mounts in a browser tab, the ordinary app still uses Firestore's origin-scoped persistence, Event- and card-keyed `localStorage`, and—on a mirror, where the flagship's service worker deliberately stays registered—the worker's NetworkOnly proof-media route (#1410). The upgraded worker removes the legacy shared proof-media CacheStorage bucket on activation; new proof bytes are not retained there. Durable snapshots and shell storage for several path Events still share one origin and quota, and a site-data clear still crosses Event boundaries exactly as ADR 0009 warns.

**Repurposing a formerly installable root requires a one-time local-store retirement before its doorway or archive is live.** Turning `fiveacross.app` from Bodega's root into a doorway changes the server answer but does not erase the browser state Bodega left behind: Firestore's IndexedDB persistence, Event/card snapshots and other app-owned `localStorage`, and non-precache Cache Storage survive a worker precache cleanup. The replacement shell therefore runs a versioned migration after `initializeApp` has created the Auth and Firestore instances, but before any Firestore read, listener, persistence enablement, resolution, or React mount: it signs out the old root session, clears Firestore persistence, and deletes every app-owned localStorage key and named cache for that origin. It does not try to inspect, retain or reinterpret one Event's durable data on behalf of another; a clear migration failure renders an explicit recovery screen rather than mounting the new regime on residue. This is an intentional sign-in interruption on an origin being repurposed, not a background best-effort cleanup. It is separately verified on a client carrying each legacy store type, and a successful worker precache retirement is not accepted as evidence that these stores are gone.

That residue is **accepted, not refused**, and bounded the same way the camera exception is:

- **Namespacing is required where the app already does it.** Every durable key a path Event writes—`localStorage` entries, the card cache, the resolution cache (D3)—is keyed by the resolved Event, never by the serving host. This is the partitioning ADR 0009 calls buildable, and this repo already keys durable snapshots that way, so it is applied rather than invented.
- **What remains genuinely shared is the browser's to arbitrate:** the single quota and its cross-Event eviction, and the all-or-nothing site-data clear. Those do not become per-Event on a shared origin no matter how the app is written, which is exactly why regime (a) still exists and why a live Event's home is still its own subdomain.
- **An apex archive MUST opt out of durable caching entirely—this is a requirement, not an implementation choice.** No Firestore persistence, no card cache, no durable snapshots. The reason it cannot be left optional: both ADR 0009's scope note and `x-multi-event-schema.md`'s supersession note justify the apex-archive regime on the premise that a read-only archive *has no durable or offline cache for origin isolation to protect*. If an implementation were free to leave persistence on, it would invalidate the premise the whole regime was approved on while still passing every other criterion here. An archive reads once and keeps nothing, so it gives up nothing it was promised—regimes (b) and (c) have no offline cold boot by construction.
- **A mirror path may keep durable caching**, because its premise is different and stated differently: regime (c) accepts the storage coupling explicitly (above) rather than claiming it is absent, and a break-glass surface that re-fetches everything on a degraded network is a worse backup. What it owes is the namespacing requirement, not abstention.

The browser-enforced limit remains ADR 0009's point: a shared origin cannot promise installed-app isolation. The product response is therefore not a false claim that it can make an origin un-installable; it withholds every app-provided installation affordance and treats **every** installed wrapper as an unsupported context for a path route. #626 reached the same conclusion from the collision direction: a path-scoped app can collide with a root-scoped app, no matter whether the wrapper came from the manifest, browser chrome, or iOS Home Screen.

**The doorway and mirror root offer no app-provided installation surface.** An organiser does not install a create form, and a Player who wants an installed app uses the Event's live subdomain, where regime (a) gives real origin isolation. The mirror keeps serving its active flagship at `/` for #625's reachability requirement, but never advertises installation.

**A manifest scope can cover every `/<slug>` on a root, whether the wrapper is old or newly created.** Omitting a `<link rel="manifest">` on the path does not remove that URL from an existing root manifest's scope, and a browser can still independently add a site to its home screen. So a `/<slug>` can open inside another Event's app window unless the current shell rejects it. The requirement is therefore a **runtime refusal rather than a claim of prevention**, and it applies to every installed wrapper, not only a legacy install:

- **A path-addressed route must refuse to mount inside an installed app window.** When a path-addressed surface resolves and the display mode is standalone (or any installed-app display mode rather than a browser tab), the app does **not** mount the Event. It renders an explicit screen saying this address must be opened in a browser, with the reason and a one-tap way to do it. Refusing is correct rather than unhelpful: mounting would give the Player an Event wearing another Event's identity, offline shell and permissions, which is worse than a clear redirection.
- **Full remediation may require the Player to uninstall the wrapper, and the spec says so rather than implying it can do that for them.** The refusal screen is what bounds the damage in the meantime; it is not a browser-level isolation guarantee.
- **The refusal is keyed on display mode plus path addressing**, not on "is this a mirror," so it also covers a doorway origin whose Event was previously installed at `/`—the repoint case D1 describes, which has the identical stored-scope problem.

**Existing installed mirror clients receive the same best-effort retirement, not an impossible universal guarantee.** The forced-advancement path D1 states for a root being repointed to a doorway also applies to **a mirror gaining path addressing**: a client carrying the current root-scoped worker keeps its navigation fallback and env-pinned flagship shell under `registerType: 'prompt'`, so the release must arm the floor and retire its precache before the route is supported. A dormant pre-capability worker is outside the server's reach until it navigates; it can serve the old flagship shell once rather than the requested path Event. That is an explicit legacy compatibility outcome: the Player updates or clears site data from the mirror root and revisits the original path, and support material must describe it. It is not presented as an install, archive or path-resolution success, and no test may claim the deployment observed every installed client. Treat "a root-scoped worker already exists on this origin" as the trigger for the best-effort retirement and recovery obligation, rather than asserting that it can be eliminated globally.

**The guard must key on the resolved regime, never on the presence of a basename.** This is stated as a prohibition because the basename test is the obvious shortcut and it is wrong in both directions: a **doorway root resolves with an empty basename, exactly like a live Event subdomain** (and after the effective-basename rule in D3, so does every non-path-addressing host), so "suppress install when a basename is present" would leave the doorway's app-provided install UI enabled. The decision input is **the serving host's addressing capability**, which resolution already knows: an origin that does path addressing—doorway or mirror, at `/` or at any path—never promotes an install; only a host serving regime (a) does. That input is available precisely because D1 makes the root a resolution outcome rather than a hardcoded route.

### D5 — Share URLs keep the entry-point surface, path included

[#607](https://github.com/nathanjohnpayne/fiveacross/issues/607)'s rule—a share is composed from the origin the sharer is standing on, never rewritten to the Event's canonical host—applies to path-addressed surfaces **symmetrically**, and applies to the path as well as the origin. A share from `fiveacross.vercel.app/bodega-bay` is `https://fiveacross.vercel.app/bodega-bay/...`; a share from `fiveacross.app/bodega-bay` keeps that apex and that prefix. Neither is rewritten to `bodega-bay.fiveacross.app`.

The reason is #607's own: every serving host stays live and brands dynamically, so a link rewritten to another host unfurls and lands the recipient under a different Edition's brand—and, worse on a mirror, sends them back to the host that was blocked when the sharer reached for the backup.

**This is a real seam, not an inherited property.** `shareOrigin()` (`src/canonicalHost.ts`) returns `window.location.origin` and nothing else, so a share composed from it today would **drop the path prefix and land recipients on the doorway**. The three Web Share call sites (`Leaderboard.tsx`, `FarewellPodium.tsx`, `Celebration.tsx`) compose against it. Path addressing therefore needs share composition to go through the resolved basename—stated here so the implementation ticket is filed against a known defect rather than discovering it in production.

### D6 — Analytics canonicalise the host and record the surface

Both halves, because they are different dimensions answering different questions.

**The host dimension stays canonical, and the canonical analytics URL removes the entry prefix.** Per #599, analytics report the Event's one resolved canonical host regardless of entry point, so cross-host traffic aggregates instead of splitting three ways. `applyResolvedCanonicalHost` installs the value the *Event's* routing document names—reached by path or by host, it is the same document, so it is the same value. A path entry has two pathname components: the entry-only effective basename and the Event's app route. `canonicalizeOrigin` (`src/posthog.ts`) and `currentPageLocation()` (`src/analytics.ts`) therefore replace the origin **and strip exactly the resolved effective basename** before forming a canonical URL. For example, a mirror visit to `fiveacross.vercel.app/bodega-bay/feed` reports `https://bodega-bay.fiveacross.app/feed`, never the non-existent canonical route `/bodega-bay/feed`. Share composition deliberately keeps the prefix (D5); analytics does not, because the dedicated entry-surface dimension records it without inventing a canonical URL that cannot resolve.

**The entry surface is recorded separately, as its own dimension.** Which of the three regimes a visit arrived through is useful signal (#584/#601)—it is how "the canonical host is blocked again" becomes visible, and how archive traffic is told apart from live play. It must not be recovered by string-matching `$pathname`, which would silently conflate an archive path with an app route the moment either changes. A first-class regime dimension is the contract, and it needs **four** values rather than three: `live-subdomain`, `apex-path`, `mirror-path`, and **`mirror-root`**. That fourth one is the mirror flagship visit at `/`, which is neither a subdomain nor a path and which D1 and D4 deliberately treat as its own case—it serves the flagship, it is no longer installable, and it is the surface #625's whole backup story runs through. Leaving it out would force implementations either to mislabel it as `live-subdomain` (hiding exactly the "the canonical host is blocked again" signal this dimension exists to surface) or to invent an incompatible fourth value of their own.

The two together are the point: **the Event aggregates, the door is counted.**

### D7 — Auth reachability is a property of the host, and stays one

`isSignInReachableOnHost` (`src/auth-domain.ts`) gates on hostname and takes no path, and that is correct rather than a gap to close. The OAuth helper lives at `/__/auth/*`, an **origin-level** reserved namespace: Firebase Hosting serves it same-origin, `vercel.json`'s rewrites are host-conditional, and the Google OAuth client matches `redirect_uri` per origin. Nothing about a path can make sign-in more or less completable, so the predicate is asked the same question on `fiveacross.app/bodega-bay` as on `fiveacross.app`, and `parseAddress` discards the path before it is consulted—the shape `firebaseAuthOriginRedirectUrl` already uses, which takes a location and keeps only the hostname.

**#799's premise on the mirrors needs correcting, and the code is the evidence.** All three production brand mirrors are in `FIRST_PARTY_AUTH_HOSTS`, so `isAuthConfiguredForHost` is true for them. As `specs/event-resolution.md` specifies, the `auth-unconfigured` developer note also covers Vercel preview hosts, including the former stable preview alias removed from production trust by #1420. Preview builds are refused until a reviewed isolated test Firebase configuration exists; that note must not instruct production sign-in setup for previews. **A path-addressed Event on a production brand mirror needs no `auth-unconfigured` treatment**, and ADR 0010's central-auth handoff is not a blocker for regime (c).

**Regime (b) does not get the same free pass, and one of its two apexes is not ready.** The predicate is per-host, so each apex has to be checked individually rather than as a class. `fiveacross.app` **is** in `FIRST_PARTY_AUTH_HOSTS`. **`vacaybingo.com` is not**—the allowlist carries `vacaybingo.vercel.app` and `bodega-bay.fiveacross.app` but never the Vacay apex itself, and the shipped Bodega bundle bakes `bodega-bay.vacaybingo.com` as its `authDomain`. So `isSignInReachableOnHost('vacaybingo.com')` is **false** today, and archives parked at `vacaybingo.com/<slug>` would render `auth-unconfigured` rather than the sign-in gate this spec otherwise promises.

That is a precondition, not a defect in the design, and it is stated as one: **an apex may not serve regime (b) until it is registered as a first-party auth host**—an exact entry in `FIRST_PARTY_AUTH_HOSTS`, in Firebase Auth's authorized domains, and as `https://<host>/__/auth/handler` on that project's Google OAuth web client. The last of those is console-only and human-performed, so it is lead time rather than code. Until it is done for `vacaybingo.com`, Vacay archives belong at `fiveacross.app/<slug>`, which is registered and serves the same Event.

**An archive requires sign-in exactly as the live Event did.** It is not world-readable. Every read of Event data passes `signedIn()` today and the membership gate after it lands, and an archive is the same data at the same paths—`EventDoc.status` changes what serves it, not who may read it. What renders before sign-in is what already renders before sign-in: the gate, branded by the resolved Edition, with the `preview` postcard from `publicHostnames/{host}` when the document carries one (#647). That is display copy the page shows anyone regardless, so nothing widens. This is also what keeps the retained non-goal true—an archive at a path is not a public directory entry, because reaching it still gets you a sign-in screen.

### D8 — The archive interlock, proposed for #134

[#134](https://github.com/nathanjohnpayne/fiveacross/issues/134) is the ticket that will start setting `EventDoc.status: 'archived'`; nothing reads the field today. Rather than let #134 discover this requirement, the condition is proposed here.

**The interlock rides the `hostnames/{host}` document's own `status`, not `EventDoc.status`.** This is forced, not preferred: the Event document requires `signedIn()`, so its status cannot be consulted before first paint, which is when the addressing decision has to be made. The canonical status is projected atomically into `publicHostnames/{host}` for browser reads; only that strict public copy satisfies the #1419 anonymous field allowlist. Canonical root/path-capability fields remain authenticated-only and the signed edge registry still derives them from canonical state. The interlock is therefore a rule about which statuses serve **through which door**:

| `hostnames/{host}.status` | Served at its own host | Served by mirror path | Served by apex path |
|---|---|---|---|
| `active` | **yes**—regime (a) | **yes**—regime (c) | **no**—not-found |
| `archived` | **no**—not-found | **yes**—regime (c) | **yes, only with `apexPath`**—regime (b) |
| `disabled` | no | no | no |

**An apex path is archive-only, because a path cannot make an active Event safely read-only.** Firestore rules receive the Event and the authenticated caller, not the browser's pathname or display surface. An active Event therefore cannot be writable on its subdomain but reliably read-only on `fiveacross.app/<slug>`: hiding marks, claims, posts and capture controls in the client would be a presentation convention a direct client write can bypass. The early draft's migration-window exception had exactly that contradiction. It is removed. The archival transaction changes the Event document and every routing document together, so server-enforced `EventDoc.status: 'archived'` makes the path surface read-only for every client rather than merely for a polite browser.

**`pathNamespace` is host-wide, but `apexPath` is an archive-only per-Event opt-in.** A target routing document may serve at an apex path only when both `status: 'archived'` and `apexPath` are set; absent is the fail-closed default. The transaction that archives the Event writes both values together. An `active` document carrying `apexPath` is invalid configuration and resolves not-found at an apex rather than creating a shared-origin alias. This makes the eligibility matrix precise:

| | `apexPath` absent | `apexPath` present |
|---|---|---|
| `active` target reached at apex path | **not-found** | **not-found**—invalid configuration |
| `archived` target reached at apex path | **not-found** | serves—the archive |

**This condition is deliberately scoped to regime (b) and does not apply to mirrors.** The two regimes are asking for different things. An apex path is an archive surface, so it is both read-only and opted into per Event. A **mirror** path is the break-glass backup #626 exists to provide: it does not promote install and its current shell refuses path routes in standalone mode (D4), while the whole point is that *any* Event in the mirrored namespace is reachable when the canonical host is blocked. Requiring per-Event opt-in there would mean discovering, mid-outage, that the one Event needed had never been enrolled. So regime (c) stays namespace-wide and regime (b) is archive-only and opt-in.

Read off the three answers #799 asks for:

- **Does path-addressability require `status: 'archived'`? On an apex, yes.** An `active` Event is never reachable at an apex path, even if an invalid document carries `apexPath`; a **mirror** may reach active and archived Events with no per-Event condition, which is regime (c)'s entire purpose. This is what preserves a server-enforced read-only archive rather than a client-only path-mode convention.
- **Does path addressing replace the subdomain? It differs by regime.** At an **apex**, yes: no path serves while the Event is active; the archival transaction retires the subdomain and makes its `apexPath` address live together, with no window where both serve and none where neither does. At a **mirror**, no: the mirror path is an additional break-glass surface for both active and archived Events; archival still retires the Event's own canonical subdomain, and a retired mirror flagship root becomes the non-serving capability marker D1/D3 define. This needs **no rules change** (`specs/event-resolution.md` already refuses to serve a non-`active` status at an Event's own host) though it does need `pathNamespace`, `apexPath`, and the root discriminator this spec introduces.

**The cache does not carry that flip promptly, and the interlock must not pretend it does.** An earlier draft of this decision claimed the cache-drop makes an installed client stop on its next boot. That is wrong, and the correction matters because #134 would otherwise ship believing archival takes effect immediately:

- A **fresh**, active Version 2 entry with `adultContent !== false` and `previewValidated === true` resolves with **no network read at all** (`specs/event-resolution.md` step 2). A client taking that cache path never learns about the flip. The drop-not-expire behaviour applies to an entry that is *revalidated*: stale entries attempt it, and fresh entries with an unproven opt-out or missing preview validation also attempt it. None supplies a prompt archival guarantee for every fresh cached session.
- Worse on cold boot: the cached Event mounts first and the entry is dropped only on the subsequent revalidation, so a naive implementation needs **two** boots to reach the archived state.
- The live watcher drops the cache but does not itself re-resolve or unmount, so an open session keeps running the retired Event.

So the archive contract carries an explicit obligation rather than an inherited one. **#134's flip must produce a bounded, observable transition in every open session:** the future live resolved-target `publicHostnames/{host}` watcher drives a real re-resolution and unmount when it observes the status change. A path surface additionally observes serving-capability retirement through the separately reviewed D3 mechanism, never a canonical browser subscription: it must re-resolve and unmount if the current root stops supporting that path namespace, rather than continue on a target cache entry after a mirror-root retirement. Boot-time status revalidation on the Event's own host is additionally required before mounting a fresh cached entry; it protects a cold start but is never an alternative to either watcher, because an already-open client does not boot again.

**The network-failure policy, because the pre-mount check and ADR 0006 would otherwise contradict each other.** A revalidation that requires the server cannot complete on a device that is offline, and the two naive readings are both wrong: failing closed would destroy the offline cold boot regime (a) promises (ADR 0006, `specs/x-offline-cold-boot.md`), while mounting silently would let this decision claim a bound it does not have. This spec invents no new rule for that case—`specs/event-resolution.md` already settled it: **revalidation that cannot reach the server serves the stale-but-active entry and does not restamp it.** So an offline live-subdomain boot still mounts, offline cold boot survives intact, and the entry stays unrenewed so the next reachable boot revalidates again. A bound that renews itself would not be a bound.

What follows is a qualification this decision has to state rather than bury, because it is a physical limit and not a design choice: **the archival transition is bounded for REACHABLE clients only.** The fact a client must learn lives on the server, so a device with no path to it cannot be made to learn it—by a boot check, by a watcher, or by any other mechanism. The already-open offline session has exactly the same limitation, and for the same reason. The guarantee that does hold universally, and the one #134 should be held to, is: **no client mounts a retired Event past its next successful contact with the server.**

The exposure that leaves is deliberately small and worth naming so nobody over-corrects into breaking offline support: an offline client keeps reaching the Event *it already had cached*, at an address that should have retired, until it reconnects. That is a stale address, not a cross-Event leak—the isolation properties are unaffected.

**This is also why the future fail-closed serving-capability mechanism in D3 does not contradict any of the above.** The two rules govern different regimes, and each matches what its regime promises: a **path** surface (regimes (b) and (c)) fails closed when its reviewed serving-capability mechanism is unreachable, and can afford to because it promises no offline cold boot at all; a **live subdomain** (regime (a)) serves stale, because offline cold boot is precisely what it does promise. Read them as one policy keyed on the regime, not as two policies in tension.

**Be exact about the bootstrap check's host, because the obvious phrasing names the wrong one.** The client that must stop serving is the one installed on the retired **subdomain**—and by D3 a live Event subdomain carries no `pathNamespace` at all, so it is precisely *not* a path-capable host. Scoping the revalidation to "path-capable hosts" (doorway and mirror origins) would leave the subdomain's fresh cache mounting the retired Event for up to twelve hours while dutifully revalidating the origins that were never the problem. The implementation therefore requires both: universal watcher-driven transition for open sessions, and fresh status validation on the Event's own host before a cached boot mounts.

What is **not** acceptable is relying on TTL expiry. Until both mechanisms land, the honest statement is that archival is prompt at the origin and lagging on cached clients—and this spec says so rather than letting #134 discover it. **#134's flip is ONE transaction over every document involved—routing and Event alike.** An earlier draft asked only that the routing documents flip atomically with each other and left `EventDoc.status` as a separate obligation. That ordering is exploitable: if routing flips first, path resolution begins serving the Event as an archive while a still-`active` `EventDoc` renders **writable** gameplay behaviour—an "archive" a Player can still mark, claim and post into. The reverse order is merely useless rather than harmful, but neither is acceptable when one batch avoids both.

So the transaction includes, atomically: **every Event mapping** for that Event (Bodega has three), each moving `active → archived`; the `apexPath` field on whichever Event mapping is to become the archive address; and `EventDoc.status → 'archived'`. A mirror root that carries `pathNamespace` is converted in that same transaction from the archived Event's mapping into the `root: 'not-found'` capability marker—retaining `pathNamespace` but no `eventId`—so it can resolve other mirror paths without serving the archived flagship at `/`. The GCB mirror has no path namespace and becomes its non-serving marker or is removed. A canonical apex whose flagship the archive retires—`gaycruisebingo.com` for the live GCB Event (D1), and by the same class rule `fiveacross.app` and `vacaybingo.com`—is converted in that same transaction to its `root: 'doorway'` marker instead. That doorway has no staged state and no later activation: it serves as soon as its revision converges, at a root the retired Event's root-scoped service worker controlled, so D1's requirement applies unchanged and the transaction takes the same attested deployment-barrier record the doorway `convert-to-root` takes (the release that armed forced advancement and precache retirement). An archive that writes a doorway without an armed record is refused before anything commits, and one that writes no doorway refuses the record. The GCB apex carries no `pathNamespace`, but its Event's worker is retired the same way before the doorway may be treated as supported, so by the owner's decision on 2026-09-25 ([#1296](https://github.com/nathanjohnpayne/fiveacross/issues/1296)) it takes that same record with the same shape and validator; there is no GCB-specific attestation. Nothing observes a half-archived Event.

**Archived means server-enforced read-only, not hidden controls.** D8 leans on `EventDoc.status: 'archived'` to make the archive read-only, and that is worth nothing if it is only a rendering decision: an implementation could hide every control and satisfy each criterion here while direct Firestore writes still succeeded. That is precisely the client-only enforcement this spec refuses elsewhere, so it is refused here too. **Firestore rules must deny every mutation under an Event whose `EventDoc.status` is `archived`**—marks, claims, proofs, doubts, moments, tally writes, and Storage uploads under that Event's prefix alike—and the rules tests must cover that denial. This is a **precondition on an apex archive serving at all**, not a follow-up: until the denial exists, a path-addressed archive is simply a writable Event at a new address.

That obligation belongs to #134 alongside the rest of the archival work, and it is named here because #134's own framing—start *setting* `status`—does not by itself imply *enforcing* it.

**Status of this decision after #1149.** The enforcement half above has SHIPPED: `firestore.rules` and `storage.rules` deny every gameplay write—Marks, Boards, Prompts, Proofs, Claims, Doubts, Hearts, Moments, retractions, Tally markers and proof-media uploads—under an Event whose `EventDoc.status` is `'archived'` (and under the reversible closing state that precedes it), with paired rules coverage in `tests/rules/post-sailing-archive.test.ts` ([`post-sailing-archive`](post-sailing-archive.md)). What has NOT shipped, and is not a prerequisite of anything #134 serves, is the routing half in production. The atomic routing transaction now exists as the event-router registry's archive intent, which moves every routing document, writes `apexPath` and commits the application archive flip in one transaction ([`event-router-registry`](event-router-registry.md) § Disable/archive, #1256), but nothing calls it in production until the lifecycle operator command (#1488), the console's `archiveEvent` still flips the Event document alone, and neither the live-watcher transition nor the boot-time status revalidation is built—so the honest statement above stands unchanged, archival is prompt at the origin and lagging on cached clients. The apex precondition this section states is therefore half-met: an apex archive still needs that intent's production caller and the transition mechanisms before it may serve.

The two status fields stay deliberately separate even though they now move together, because they answer different questions for different audiences at different times: the **routing** status decides addressing and is read world-readably before first paint, while the **Event** status decides behaviour and is read after mount behind `signedIn()`. Collapsing them would put an authenticated read on the pre-paint path, which is the thing ADR 0009 exists to avoid. Moving together is a property of the write; being separate is a property of the read.

### D9 — What the root's create affordance does today

#787's `EventDraft` is device-local and holds no claimed slug until launch; the launch provisioner (#793) sits behind the Phase 3 membership gate. So the honest answer for today is not the fully-shipped one.

**The doorway always renders; the create affordance has two states, and the switch is configuration, not a probe.** When provisioning is available, the affordance links to the wizard's own reserved route, `/setup` (#788's shell)—it does not mount the wizard at `/` (D1). When provisioning is not available, the affordance renders an explicit not-yet-open state that names what it is waiting on. **Today it is the second.**

**The wizard route is a platform capability, not a universally valid app route.** Reserving `setup` keeps it out of slug parsing; it does *not* authorize the component on every resolved surface. Before the wizard mounts, its route guard requires all of: the resolved result is `root: 'doorway'`, the serving host is exactly `fiveacross.app`, the effective basename is empty, and provisioning is enabled. Every other direct navigation—including `vacaybingo.com/setup`, a mirror root or mirror path, a live Event, and an archive path—renders not-found without constructing an `EventDraft`. The check is at the route, not just the doorway link: a backup surface must not become a creation surface merely because a visitor typed the reserved URL.

Two things this deliberately refuses. It does not mount the wizard's draft steps behind a launch that cannot complete: #787's contract is explicit that a draft "neither reserves nor squats an address," and a draft is device-local, so an organiser who spent fifteen minutes filling one in would be holding something they cannot launch and can lose to a cache clear. A create form that cannot create is worse than a closed door, because it costs the organiser the work before it tells them. And the state is decided by configuration rather than by probing #793 at runtime, because a pre-paint network read to decide what the doorway looks like is exactly the blank-screen failure class `specs/event-resolution.md` bounds everywhere else.

**The doorway is a consumer of #787's contract, not a fork of it.** When the affordance opens, it hands off to the wizard's shipped `EventDraft` / `OccasionDef` surface (`src/data/eventDraft.ts`, `src/data/occasions.ts`, `src/data/draftValidation.ts`) and re-derives no draft semantics of its own.

## Reserved paths

A first path segment that is reserved is never a slug. The list is **one shared module**—`src/slug.ts`-shaped, per #790's note that #545 and #793 both need to consume it framework-clean—read by the client parse (D3), by the Worker's reserved-label check (#545), and by the wizard's availability check and the provisioner (#790/#793). Three independently maintained copies is the failure this consolidation exists to prevent: a slug accepted by the wizard and rejected by the router is an Event nobody can reach.

**The module holds a union of two floors, and neither may shrink the other.** #790 introduces the **hostname-label** floor the PRD names—`www`, `auth`, `api`, `admin`, `play`, `send`, `status`, `d`—which exists because those labels are or will be real subdomains. (`send` was added by [#1102](https://github.com/nathanjohnpayne/fiveacross/issues/1102), which made it a real subdomain: the Resend return path for `fiveacross.app`.) This spec adds the **path-segment** floor below, which exists because those segments are real routes. A slug must clear both, since a slug is simultaneously a subdomain label in regime (a) and a path segment in regimes (b) and (c). `admin` is in both floors and would be reserved twice over; nothing else overlaps, which is exactly why one list has to be the union rather than either list alone.

Sources, so the list can be re-derived rather than trusted:

- **The frozen tab table** (`src/components/tabs.ts`, the hot-file owner's mount-point table): `/` itself, `feed`, `leaderboard`, `more`. `more` mounts with a splat (`/more/*`), so everything under it is reserved with it.
- **`items` and `admin`**—reserved although neither is a top-level route any more: #203/#208 moved them inside More (`/more/admin[/section]`, `specs/admin-console-ia.md`). Reserved anyway, because links minted before that move still exist and because an Event slugged `admin` is a trap regardless of which route table is current.
- **`__`**—Firebase Hosting's reserved OAuth-helper namespace (`/__/auth/handler`, `/__/auth/iframe`), already denylisted in the service worker for exactly this class of reason (`specs/sw-auth-handler-denylist.md`) and rewritten host-conditionally in `vercel.json`.
- **`unsubscribe`**—a Hosting rewrite to the `emailUnsubscribe` Function (`firebase.json`), so it never reaches the SPA at all. An Event slugged `unsubscribe` would be unreachable and would look like a Function bug.
- **`assets`**—Vite's hashed-output directory.
- **`setup`**—the Event-setup wizard's own top-level route (`/setup/*` in `src/App.tsx`, `specs/event-setup-wizard.md` § Mount point). It sits outside the tab table because the wizard is not a tab, which is exactly why the tab table alone could not be this list's source. Reserved by the owner's decision on #1223 (2026-10-02); `hostnames/setup.fiveacross.app` and `hostnames/setup.vacaybingo.com` both read `NOT_FOUND` before the reservation landed.
- **A structural rule, not an entry: a segment containing a `.` is never a slug.** This covers `sw.js`, `manifest.webmanifest`, `registerSW.js`, `workbox-*.js`, `build-floor.json`, `favicon.svg`, `apple-touch-icon.png`, `pwa-192.png`, `pwa-512.png` and every `og-*.png` without enumerating a build output that churns. Enumerating them instead would guarantee the list goes stale silently, which is the same defect as maintaining three copies.

**Where it lives (#1387).** `src/slug.ts` holds `RESERVED_LABELS` (the hostname-label floor), `RESERVED_PATH_SEGMENTS` (the path-segment floor) and `RESERVED_SLUGS`, their sorted union, which is the one set every consumer reads: `validateSlug` and `isReservedLabel` refuse every word of the union (reason `reserved-label`, so the wizard's availability check, its launch gate and the Worker's namespace guard refuse a path word exactly as they refuse an infrastructure label); `isReservedPathSegment` adds the dot rule and compares case-insensitively and percent-decoded, because the router decodes each segment and matches routes case-insensitively, so `/Feed` and `/f%65ed` both reach the Feed tab; and `parseAddress`, the pure parse D3 keeps as a product decision, reads it: it answers `{ slug, basename }` with no I/O, a reserved or dotted first segment yields `slug: null` and an empty basename, and its basename is only ever the speculative one. The three programs that cannot import the module (`router-publisher/src/runtime.ts`, `scripts/event-router-registry/hostname-projection.mjs`, `scripts/event-router-registry/recovery-controller.mjs`) carry literal copies of the union, pinned by parity tests in `src/slug.test.ts`.

The list is a floor. #545 and #790 may reserve more (platform words, profanity, single characters); nothing here may be removed without a route table changing under it.

## Contracts this spec extends, and what each amendment must say

This spec proposes authenticated canonical `hostnames/{host}` variants with **no `eventId`** and `root`/path-capability fields, and separately requires a future **third** browser resolution outcome. Today’s browser has only `event` and `not-found` and accepts strict public Event mappings; it cannot consume those authenticated canonical variants. The browser outcome and transport remain deferred under D3. Naming the required amendments here—rather than leaving an implementer to infer them—is part of this spec's job, but the amendments themselves land with the implementation ticket, since changing an accepted contract ahead of the code that honours it would leave both specs describing something that does not exist.

**`specs/hostnames-lookup.md` must gain:**

- The **root-shaped document** as a documented variant: `eventId` becomes optional and a required `root` discriminator is either `doorway` (mount the Edition doorway) or `not-found` (keep host capability but do not serve `/`). This is a canonical registry shape, not a browser public projection. Root-serving behavior is a planned edge contract over the signed registry shape, not a shipped browser doorway outcome; browser `coerceHostnameDoc` reads only the approved public Event mapping and must not gain a canonical fallback.
- **`pathNamespace`** as an optional field on an authenticated canonical/registry **serving** host, with the fail-closed default (absent ⇒ no path addressing) and the validity rule (it may only name an apex that issues Event subdomains).
- **`apexPath`** as an optional field on an authenticated canonical **target** Event's routing document, fail-closed absent, gating apex-path eligibility per Event (D8). It is deliberately a different field on a different document from `pathNamespace`: one says "this host can address by path," the other says "this Event may be addressed that way on an apex," and conflating them is what would alias every live Event onto the shared origin.
- Canonical root/path fields stay authenticated-only under #1419 and keep the signed edge registry/recovery contract. The browser public projection does not contain those fields; its point lookup admits only the eleven approved semantic fields, with no listing/client writes. Any future widening of that public payload requires another owner decision.

**`specs/event-resolution.md` amendments remain deferred:**

- The **third root outcome** and `src/main.tsx` handling, only after a reviewed architecture defines how the browser learns it without canonical reads or unapproved public fields. The old `{ kind: 'root', edition, pathNamespace }` proposal does not describe today's browser API.
- The **derived-target cache key** for path resolution, kept separate from the root marker's own entry.
- The **single `timeoutMs` budget spanning all resolution operations**, and failure behaviour when exhausted mid-chain; the withdrawn pair of canonical reads does not define that future implementation.
- The **resolved public routing key** in the future resolution result, so target posture subscriptions use strict `publicHostnames/{host}` rather than `window.location.hostname`; serving-capability retirement needs its own reviewed mechanism.
- The **route-aware status rule**: `archived` is not-found at its own host and servable by path, so status can no longer be evaluated without knowing which door was used.

The last point is the one most likely to be missed, because today's contract states a status rule that is unconditionally true and would stay compiling while becoming wrong.

## Deliberately not in this spec

- **The rules workstream for tenant isolation.** `specs/x-multi-event-schema.md` § "Rules / indexes / hosting implications" already carries the honest inventory: today's rules are path-scoped, not membership-scoped. Path addressing changes no rule and widens no read—it changes which URL reaches a document, not who may read it.
- **Slug format, length, reservation, expiry and rename.** #790's contract; this spec names only the reserved *floor* the router forces.
- **Whether an archive renders differently once mounted.** #134's subject. This spec decides addressing; the read-only surface is behaviour.
- **Per-host manifest and OG injection.** #546's Worker. D4 constrains it (never serve a manifest at a path) and adds nothing else.
- **The Worker's own routing.** #545. D3's browser derivation remains deferred; the Worker consuming the same reserved list and the same `pathNamespace` field is a coordination point, not a decision made here. One warning for whoever lands it: #545's acceptance has the Worker fail closed on "unknown, reserved, disabled, **archived** and domain-ineligible slugs." That is right for **subdomain** routing and is the same rule as D8's first column—but it must not be applied to a path route on a host carrying `pathNamespace`, where an `archived` slug is precisely what is supposed to serve. The two routes read the same field and want opposite answers from it, which is the kind of thing that is obvious here and invisible in a Worker diff.
- **Creation on a namespace apex.** D1 refuses it for now; whether `vacaybingo.com` ever creates Vacay Events is a product decision, not a routing one.

## Acceptance criteria

**D1 — root shape per host class**

- **Given** the canonical apex `fiveacross.app` with a root-marker routing document, **when** a visitor loads `/`, **then** the platform doorway renders with the `fiveacross` brand and a create affordance, and no Event is mounted.
- **Given** `vacaybingo.com`, **when** a visitor loads `/`, **then** its Edition doorway renders and **no** create affordance appears.
- **Given** a live Gay Cruise Bingo Event, **when** a visitor loads `gaycruisebingo.com/`, **then** that Event remains the canonical production surface and its Vercel mirror remains only a backup; **when** that Event is archived, **then** its routing document is retired from the GCB apex only after `fiveacross.app/<gcb-slug>` is live, and a GCB root marker may then render the Edition doorway with no create affordance.
- **Given** any of the three brand mirrors with an **active flagship** routing document, **when** a visitor loads `/`, **then** that mirror's flagship Event renders exactly as it does today (#625)—no doorway, no create affordance, and the backup path is unchanged.
- **Given** a Five Across or Vacay brand mirror whose flagship has archived and no active replacement was explicitly provisioned, **when** a visitor loads `/`, **then** its non-serving capability marker renders not-found rather than a doorway or the archived Event, while retaining `pathNamespace` so the archive remains reachable at its applicable `/<slug>` path; **given** the GCB mirror, **then** it has no path namespace and is simply not-found.
- **Given** a strict `publicHostnames/{host}` Event mapping with the approved fields and an eligible status, **when** today’s anonymous browser lookup runs, **then** it resolves the mapped Event without reading canonical metadata. A future doorway outcome needs the separately reviewed D3 mechanism; an authenticated canonical root marker is not today’s browser input.
- **Given** `hostnames/fiveacross.app` still pointing at the Bodega Event, **when** the doorway work is scheduled, **then** it is sequenced behind #601's repoint and the apex is not converted while it is Bodega's serving address.
- **Given** a build with a non-empty `VITE_EVENT_ID`, **when** it is served on a host carrying a root marker or a `pathNamespace`, **then** it still short-circuits to its baked Event and no doorway or path addressing takes effect—so **given** any host intended to serve regime (b) or (c), **then** it must first be served by a hostname-resolved build (empty `VITE_EVENT_ID`).

**D2 — path is not an equivalent origin**

- **Given** a Player signed in at `bodega-bay.vacaybingo.com`, **when** they open `fiveacross.app/bodega-bay`, **then** they are not signed in there—the surfaces share an `eventId`, not a session.
- **Given** a path-addressed surface, **when** it renders, **then** it never navigates the visitor to the Event's subdomain automatically; **and given** the Event is still live, **then** it may offer a user-initiated link to the installable address.
- **Given** an archived Event, **when** its path surface renders, **then** no link to a subdomain is offered, because none serves.
- **Given** a visitor signed in at one path surface, **when** they open another path or the doorway on that same origin, **then** they are still signed in—an accepted, documented consequence of origin-scoped auth persistence that grants no authority a fresh sign-in would not, but makes sign-out origin-wide and widens shared-device exposure.
- **Given** an Event reached on a mirror path, **when** the Player captures proof, **then** capture works, and **then** the camera grant is understood to be shared with every other Event on that mirror origin—an accepted, documented consequence, not an oversight.
- **Given** an Event reached on an apex archive path, **when** the surface renders, **then** it offers no capture at all, so the shared-grant question never arises there.

**D3 — parsing, resolution and basename (browser architecture deferred)**

The former acceptance criteria requiring anonymous canonical document reads or subscriptions are withdrawn. The following constrain a future reviewed architecture; none claims that the current client implements path addressing:

- **Given** `/bodega-bay/feed`, **when** the pure address parser `parseAddress` runs (shipped with #1387; nothing calls it yet), **then** it identifies the candidate slug and speculative basename without I/O (`slug: 'bodega-bay'`, `basename: '/bodega-bay'`); reserved or dotted segments answer `slug: null` and an empty basename, so they remain ordinary routes.
- **Given** a path candidate, **when** a future capability mechanism selects a path regime, **then** target resolution uses only the strict public Event mapping, without listing or canonical fallback; root outcomes and apex eligibility require the separately reviewed mechanism, not fields added to the public projection by this spec.
- **Given** a missing, malformed, disabled or ineligible path target, **then** it renders not-found rather than the doorway or flagship.
- **Given** a cached target, **then** it cannot establish serving capability; entries remain isolated by derived address and capability binding, and pre-capability root cache cannot enable install UI.
- **Given** a resolved path target, **then** future posture watchers read that target's strict public projection; capability retirement must invalidate the path through its separately reviewed mechanism, not a canonical browser subscription.
- **Given** resolution requiring more than one operation, **then** one `timeoutMs` bounds the whole pre-paint operation.
- **Given** a live Event subdomain or a host not selected for path addressing, **then** the effective basename stays empty; a speculative parsed prefix never rebases ordinary app routes.
- **Given** GCB canonical/registry provisioning, **then** no `pathNamespace` names its Edition apex, because it issues no Event subdomains.

**D4 — installed-context refusal**

- **Given** a path-addressed surface in either regime, **when** the document renders, **then** it links no manifest.
- **Given** a path-addressed surface, **when** the browser fires `beforeinstallprompt`, **then** the app does not consume it and no install affordance renders—including the iOS branch, which fires no event.
- **Given** a future capability-aware service worker registered at the origin root of a doorway or mirror host, **when** a navigation to a path-addressed route occurs, **then** the capability-aware navigation handler passes it to the network and never returns the precached shell.
- **Given** the future capability-aware worker source, **when** it decides whether a route is path-addressed, **then** it reads the same-origin `/.well-known/fiveacross-path-capability` projection of that host's `pathNamespace`, uses the shared reserved-path parser, and retains the existing `/^\/__\//` denial; no hard-coded host list or pathname-only global denylist is permitted.
- **Given** that capability endpoint is unavailable before the worker has a fresh result, **when** a non-reserved candidate slug is navigated to, **then** the worker passes it to the network rather than serving a possibly wrong precached shell; known app routes remain available through the shared reserved-path parser.
- **Given** a host is about to gain `pathNamespace`, **when** rollout is performed, **then** the endpoint and capability-aware worker deploy and the release arms forced advancement for every reachable root-scoped worker before the field and eligible targets are published, so a prompt-waiting worker that reaches the update path cannot serve its env-pinned flagship at the first supported path URL; a dormant pre-capability worker remains an explicit legacy-recovery case, not a claim this deployment can eliminate.
- **Given** a doorway host, **when** `/` renders, **then** it offers no manifest link or app-provided install affordance.
- **Given** a brand mirror that has gained path addressing, **when** its active flagship renders at `/`, **then** it still serves exactly as today (#625 preserved) but offers no manifest link or app-provided install affordance; **and given** any origin that does path addressing, **then** no surface on it promotes an install. Browser/OS chrome may still create an installed wrapper.
- **Given** a device running the capability-aware shell in any installed-app display mode—whether installed before or after this change, from the manifest or from browser/OS chrome—**when** a `/<slug>` on that origin is opened, **then** it must not mount the path Event inside that window and instead renders the explicit open-in-a-browser screen. A dormant pre-capability installed shell follows the explicit legacy recovery case below instead of receiving an unachievable prevention guarantee.
- **Given** an origin that already carries a root-scoped service worker, **when** path addressing is enabled on it—whether by repointing a root to a doorway **or** by a mirror gaining paths—**then** the release arms forced advancement and retires the precache on every client that reaches that path before the route is supported; it does not claim to update dormant installed clients that the browser has not contacted.
- **Given** a dormant client controlled by a pre-capability root worker, **when** it opens a new `/<slug>` path for the first time, **then** that old worker may render its former flagship shell once; the Player must update or clear site data from the root and revisit the original URL. The rollout records this as a legacy compatibility outcome, never as a successful path render or a proof that the current shell protected that client.
- **Given** a doorway root, **which resolves with an empty basename exactly like a live Event subdomain**, **when** the install guard evaluates it, **then** it is still suppressed—so **given** any implementation, **then** the guard keys on the resolved regime and never on the presence of a basename.
- **Given** a device that installed the Event previously served at a root being repointed to a doorway, **when** it reaches the release's forced-advancement path, **then** the old root-scoped service worker is retired and its precache cleaned up before the doorway is supported on that device—omitting the manifest neither unregisters it nor stops it answering `/`, and `registerType: 'prompt'` means a replacement worker may otherwise sit in `waiting` indefinitely. A device that has not returned cannot be pre-updated and follows the explicit legacy recovery above.
- **Given** a path-addressed surface, **when** it writes any durable state, **then** every key it controls is keyed by the resolved Event rather than the serving host; **and given** the quota, cross-Event eviction and site-data clear, **then** those remain shared and are accepted as such, not claimed to be removed by withholding install UI.
- **Given** an origin previously serving an installed Event root is repurposed as a doorway or apex-archive origin, **when** its replacement shell first runs, **then** it initializes the SDK and creates Auth/Firestore, then retires every app-owned legacy durable store **before any Firestore use, listener, persistence enablement, resolution, or mount**—Firestore persistence, Event/card localStorage and named Cache Storage—and signs out the old root session; **when** that migration fails, **then** it renders recovery rather than mounting the new regime on stale data. Worker precache cleanup alone is not sufficient evidence.
- **Given** an apex archive path, **when** it renders, **then** durable caching is **disabled**—no Firestore persistence, no card cache—because ADR 0009 and `x-multi-event-schema.md` both justify this regime on the premise that an archive keeps nothing durable; leaving it optional would let an implementation invalidate that premise while passing every other criterion.
- **Given** a mirror path, **when** it renders, **then** durable caching is permitted and every key it writes is namespaced per Event.
- **Given** a device with the Event installed at that origin's root by any mechanism, **when** a path-addressed route is opened **in an installed-app display mode**, **then** the app refuses to mount the Event and renders an explicit open-in-a-browser screen—because a stored or browser-created wrapper cannot be revoked from the server and a web app cannot uninstall itself.

**D5 — share composition**

- **Given** a share initiated from `fiveacross.vercel.app/bodega-bay`, **when** the URL is composed, **then** it carries that origin **and** the `/bodega-bay` prefix, and is not rewritten to the Event's canonical subdomain.
- **Given** a share initiated from `fiveacross.app/bodega-bay`, **when** the URL is composed, **then** the same holds—the rule is symmetric across regimes (b) and (c).
- **Given** a share initiated from a live Event subdomain, **when** the URL is composed, **then** it carries no path prefix, exactly as today.

**D6 — analytics**

- **Given** a visit through any of the three regimes, **when** analytics report the host dimension, **then** it is the Event's one resolved canonical host.
- **Given** a path-addressed visit, **when** the URL is canonicalised for analytics, **then** the origin is rewritten and the resolved effective basename is removed while the Event app route remains—for example `fiveacross.vercel.app/bodega-bay/feed` becomes `bodega-bay.fiveacross.app/feed`; the entry prefix remains only in the dedicated surface dimension and in share URLs.
- **Given** a visit, **when** it is recorded, **then** the entry surface is reported as a first-class regime dimension, not inferred by string-matching a pathname.
- **Given** a mirror flagship visit at `/`, **when** it is recorded, **then** it reports **`mirror-root`**—a distinct fourth value alongside `live-subdomain`, `apex-path` and `mirror-path`—so it is neither mislabelled as a subdomain visit (which would hide the "canonical host blocked again" signal) nor left for an implementation to invent a value for.

**D7 — auth reachability**

- **Given** any path-addressed surface, **when** `isSignInReachableOnHost` is consulted, **then** it is passed the hostname only and its answer is identical to the answer for that host's `/`.
- **Given** a path-addressed Event on `fiveacross.vercel.app` or `vacaybingo.vercel.app`, **when** the app boots, **then** it mounts and offers sign-in—no `auth-unconfigured` state and no developer note, because every registered Vercel host is first-party.
- **Given** `vacaybingo.com`, **when** `isSignInReachableOnHost` is consulted today, **then** it is **false**—so **given** an apex not registered as a first-party auth host, **then** it may not serve regime (b), and Vacay archives are parked at `fiveacross.app/<slug>` until the registration lands.
- **Given** an apex being made regime-(b) capable, **when** the enabling work is done, **then** it has an exact `FIRST_PARTY_AUTH_HOSTS` entry, a Firebase Auth authorized-domain entry, and a `https://<host>/__/auth/handler` registration on that project's OAuth web client—the last being console-only and human-performed.
- **Given** an archived Event reached at a path, **when** a signed-out visitor loads it, **then** the sign-in gate renders—branded by the resolved Edition, with the `preview` postcard when the routing document carries one—and no Event data is readable without signing in.

**D8 — archive interlock**

- **Given** a routing document with `status: 'active'`, **when** it is reached at its own host, **then** it serves; **when** it is reached by path on a **mirror**, **then** it serves; **when** it is reached at an **apex** path, **then** it always renders not-found—even if an invalid document carries `apexPath`—so no active Event has a client-only read-only alias.
- **Given** a namespace apex that has gained `pathNamespace`, **when** an active Event in that namespace is reached at an apex path, **then** it is **not** reachable there—host-wide capability never confers path eligibility on a live Event, so enabling the apex does not alias any live Event onto the shared origin.
- **Given** a mirror, **when** any Event in the mirrored namespace is reached by path, **then** it serves without per-Event opt-in—so an outage cannot reveal that the one Event needed was never enrolled.
- **Given** a routing document flipped to `status: 'archived'`, **when** it is reached at its own host by a client with no fresh cache, **then** it renders not-found; **when** it is reached by a mirror path, **then** it serves; **when** it is reached at an apex path, **then** it serves only when that document carries `apexPath`, and renders not-found otherwise.
- **Given** a client holding a **fresh** (`active`, within TTL) cached entry, **when** the document is flipped to `archived`, **then** that client does **not** learn of the flip from the cache alone—so **given** #134's implementation, **then** it must drive a bounded, observable transition rather than relying on TTL expiry.
- **Given** a cached boot at the Event's own host, **when** the routing status is no longer active, **then** it revalidates before mounting; this applies to the retired subdomain and not merely to "path-capable hosts," because the subdomain carries no `pathNamespace`.
- **Given** a live Event subdomain on an OFFLINE device with a fresh cached entry, **when** the app boots, **then** the pre-mount status revalidation cannot reach the server and the entry **still mounts**, unrestamped—offline cold boot (ADR 0006) is preserved and the bound does not renew itself.
- **Given** a PATH surface on an offline device, **when** its reviewed serving-capability mechanism is unreachable, **then** it fails closed—the opposite of the subdomain rule above, and correct because regimes (b) and (c) promise no offline cold boot.
- **Given** an archived Event and a client with no path to the server, **then** no mechanism bounds that client—the archival transition is bounded for **reachable** clients only, and the universal guarantee is that no client mounts a retired Event past its next successful server contact.
- **Given** an open session, **when** the resolved-target watcher observes archival, **then** it drives re-resolution and unmount before the session can continue running the retired Event; **and given** a path surface, **when** the separately reviewed serving-capability mechanism reports removal or change (including a mirror-root retirement), **then** it also re-resolves and unmounts. Boot revalidation is additional cold-start protection, not an alternative.
- **Given** `status: 'disabled'`, **when** it is reached either way, **then** it serves in neither.
- **Given** an Event whose `EventDoc.status` is `archived`, **when** any client attempts a mutation under it—mark, claim, proof, doubt, moment, tally write, or a Storage upload under that Event's prefix—**then** Firestore/Storage **rules** deny it, not merely a hidden control; **and given** that denial does not yet exist, **then** an apex archive must not serve, because a path-addressed archive without it is just a writable Event at a new address.
- **Given** an Event with more than one routing document, **when** #134 archives it, **then** every Event mapping, the `apexPath` field, **and** `EventDoc.status` change in **one** transaction—no observer ever sees routing archived while the Event document is still `active`, which would serve an "archive" that still accepts marks, claims and posts; and no observer sees an active Event become reachable at an apex path. A mirror-root mapping with `pathNamespace` is converted in the same transaction into `root: 'not-found'` with that capability retained, so `/` does not serve the archive while `/<slug>` can still resolve other mirrored Events.
- **Given** an archived Event, **when** the app has mounted, **then** the read-only surface is driven by `EventDoc.status`, while addressing was driven by the routing document's `status`—two fields, two audiences, two times.

**D9 — the root's create affordance today**

- **Given** provisioning is not available, **when** the doorway renders, **then** the create affordance shows an explicit not-yet-open state naming what it waits on, and the wizard is not mounted. **This is the state today.**
- **Given** provisioning is available, **when** the doorway renders, **then** the create affordance links to the wizard's own reserved `/setup` route and does not mount the wizard at `/` or an unreserved top-level segment.
- **Given** a visitor directly navigates to `/setup`, **when** the resolved surface is not the `fiveacross.app` doorway with provisioning enabled and an empty effective basename, **then** the route renders not-found and constructs no draft; this includes Vacay doorways, mirror roots and paths, live Events, and archive paths.
- **Given** either state, **when** the doorway renders, **then** it performs no pre-paint network read to decide which state it is in.
- **Given** the affordance opens, **when** the wizard is entered, **then** it consumes #787's shipped `EventDraft` / `OccasionDef` contract and re-derives no draft semantics.
