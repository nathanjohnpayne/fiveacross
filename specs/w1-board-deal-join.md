# Board render + deal/freeze-at-join (w1-board-deal-join)

Feature: a Player's Board is dealt once, at join, from the active non-free Prompt pool and then frozen—24 sampled Prompts plus the always-marked "Complain about Circuit Music" Free Space centre, rendered as a 5×5 card. There is NO re-deal and NO Square-swap (ADR 0003). When the active pool is too thin to fill a card (< 24 Prompts, ADR 0004) the deal guard is surfaced to the Player instead of a blank, forever-spinning card.

## Contract

- `src/game/logic.ts`—`dealBoard(pool, freeText, seed)` deals a frozen 5×5 Board deterministically from `seed`: 24 Prompts sampled from `pool` plus the free centre at index `CENTER` (12), which is `free: true` and `marked: true`. It throws when `pool.length < MIN_POOL` (24) rather than persisting a card with blank cells. `MIN_POOL` is the single source of truth for the 24-Prompt floor, shared by the deal and the Board render.
- `src/data/api.ts`—`joinAndDeal(u)` freezes the Board at join: it early-returns when a Board already exists for the uid (re-joining never re-deals), otherwise reads the active, non-free Prompt pool (`items` where `status == 'active'` and `!isFreeSpace`), deals via `dealBoard` seeded per-uid (`seedFromUid`), and batch-writes the `boards/{uid}` doc plus the Player row. The Player row denormalizes the Player's SAVED identity, not the raw Google one: it prefers the `users/{uid}` profile's `displayName`, and that profile's `photoURL` when it carries `customPhoto: true` (without the flag the profile photo is just a stale copy of the Google one, so the live auth photo wins). Because `users/{uid}` is self-writable (firestore.rules shape-checks only its `attestedAdultAt`), the saved fields are VALIDATED before denormalizing: a saved name counts only as a real, trimmed-non-empty string of ≤ 100 chars—`players/{uid}` writes themselves are deliberately unvalidated (self-writable by design, ADR 0001), so the guard adopts the 100-char `displayName` bound firestore.rules enforces on every other public displayName denormalization (markers, moments, proofs)—a saved photo counts only as a well-formed `https://` URL string (no other scheme, nothing unparseable), and the `customPhoto` opt-in counts only as EXACTLY boolean `true` (truthy junk like `'false'` or `1` never publishes the saved photo). Anything malformed falls back per-field to the auth values, exactly like a missing profile. The profile read is best-effort and join-path only—one extra read, fetched alongside the pool; a missing or unreadable profile falls back to the Firebase Auth values rather than blocking the deal. The `dealBoard` throw propagates (it is not caught here), so a thin pool never persists a broken Board.
- `src/components/Board.tsx`—renders the dealt Board's 25 Squares under the fixed `B I N G O` header: each regular cell shows its `text` verbatim; the free centre pairs a visually prominent `FREE` label with the seeded `FREE_TEXT` prompt, while its accessible name remains the prompt itself. It reflects `marked` / `pending` / winning state. There is no re-deal, shuffle, or Square-swap control anywhere on the card. Before a Board exists, the component surfaces the ADR 0004 guard: once the active non-free pool has loaded and is `< MIN_POOL`, it shows the "not enough prompts" message (`role="alert"`) rather than the neutral "Dealing your card…" state, so a thin pool is never rendered as a blank card. The guard fires only on SERVER-CONFIRMED data: under the ADR 0006 persistent cache a cold or stale IndexedDB can resolve both listeners from cache with `board=null` and an empty pool, so `useDocSub`/`useColSub` expose a `hasServerData` latch (subscribed with `includeMetadataChanges`, latched by the first `!metadata.fromCache` snapshot, reset per subscription key) and the alert additionally requires it for both the board and the pool—cache-only data keeps the neutral state. Board subscribes to `useItems` only while there is no Board yet (that is what sizes the guard); once a Board exists, `useItems` is disabled (no live pool listener)—the pool is irrelevant to a Player whose card is already frozen.
- `src/components/SignIn.tsx` (`DealError`)—the retry surface App mounts while `dealError` is set. It owns the MANUAL Retry: the button re-invokes the deal, and the `/items` Prompts tab stays reachable (the shell keeps rendering, per the w1-auth-google wiring) so a Player or Admin can add Prompts and come back. The AUTOMATIC pool-recovery retry is NOT on this panel—a watcher here would unmount the moment the Player navigates to `/items` (the exact recovery path, the PR #66 finding)—so it lives at the app shell (`src/components/PoolRecoveryWatcher.tsx`, mounted in `AuthProvider`); see `specs/w1-deal-auto-retry.md`. This panel remains the manual fallback.

## Acceptance criteria

- Given an active pool of ≥ 24 Prompts, when a User joins, then a frozen 5×5 Board is dealt once (24 Prompts + Free Space) and re-joining does not re-deal or swap any Square.
- Given an active pool of < 24 Prompts, when a User joins, then `dealBoard`/`joinAndDeal` throw rather than persisting a blank Board, and the Board render surfaces the guard to the Player (ADR 0004) instead of a blank card.
- Given a cold persistent cache (new device / cleared IndexedDB), when the listeners first resolve from cache with no board and an empty pool, then the thin-pool alert does NOT flash—the neutral "Dealing your card…" state holds until a server-confirmed snapshot arrives, and only a server-confirmed thin pool (or the server-delivered Board) replaces it.
- The Free Space centre is visually distinguished with a `FREE` label and the seeded `FREE_TEXT` prompt ("Complain about Circuit Music"), is always marked, and counts toward completed lines. It is a keyboard-focusable feedback control: click, Enter, or Space replays a short pulse confirming it is already free without changing Board data. Assistive technology receives the prompt as the control's name without the decorative label.
- No re-deal / Square-swap affordance exists on the Board (ADR 0003).
- Given a deal error is up (App shows the `DealError` retry surface with the shell and `/items` still reachable), recovery has two paths: the panel's MANUAL Retry, and the shell-level AUTOMATIC pool-recovery retry that fires when the pool crosses `MIN_POOL` upward (owned by `specs/w1-deal-auto-retry.md`, not this spec).
- Given a Player already has a Board, the pool subscription (`useItems`) is disabled—no live listener stays open on prompts that can no longer affect an already-frozen card.
- At join, the public Player row prefers the saved `users/{uid}` profile identity (custom `displayName`; `photoURL` when `customPhoto`) over the raw Google identity, and falls back to the auth values when no profile doc exists, the read fails, or a saved field is malformed (non-string / empty / over-100-char name; non-string or non-`https://` photo; `customPhoto` anything but boolean `true`).

## Test coverage

`src/components/w1-board-deal-join.test.tsx` (Vitest, RTL-jsdom + firestore-mocked unit):

- Board render—a real `dealBoard` result (from the seed pool) rendered through `Board`: exactly 25 Squares, one marked Free Space at the centre with a distinct `FREE` label plus the seeded `FREE_TEXT` prompt ("Complain about Circuit Music"), click feedback that removes its one-shot pulse class at animation end without unmarking it, and no re-deal / shuffle / swap / "new card" control present.
- Board deal guard—with no Board yet and the active non-free pool `< MIN_POOL`, `Board` shows the guard alert; with the pool `≥ MIN_POOL` (or still loading) it shows the neutral "Dealing…" state, proving the guard fires only on a genuinely thin pool, not on an in-flight deal.
- Board cold-cache suppression—with both subscriptions resolved but cache-only (`hasServerData: false`), an empty pool and missing board keep the neutral state (no alert); the alert appears only after the server confirms a thin pool, and a server-delivered Board renders the card with no alert flash.
- Board pool-listener gate—`useItems` is called with `enabled: true` while there is no Board, and `enabled: false` once a Board exists.
- `joinAndDeal` freeze-at-join—with an existing Board doc it early-returns without reading the pool, the profile, or writing (no re-deal, no extra read for returning Players); with no Board and a healthy pool it deals once and batch-writes a 25-cell Board whose centre is the marked `FREE_TEXT` ("Complain about Circuit Music"), excluding the Free Space item from the sampled Prompts.
- `joinAndDeal` guard propagation—with no Board and a pool of `< MIN_POOL` active Prompts, the deal throws and no Board doc is committed (the api-layer half of the "not a blank Board" criterion).
- `joinAndDeal` Player-row attribution—a saved profile with a custom name is written to the Player row instead of the Google name, its `photoURL` wins only under `customPhoto: true` (a stale non-custom profile photo loses to the live auth photo), a missing profile doc or a failed profile read falls back to the auth identity without blocking the deal, and malformed saved fields are ignored per-field in favour of the auth values: non-string, whitespace-only, and over-100-char names; non-string photos, non-`https` schemes (`http://` downgrade), and unparseable photo strings; truthy-junk `customPhoto` values (`'false'`, `1`) never publish the saved photo.

`src/hooks/useData.test.ts` (Vitest, firestore-mocked unit)—proves, against the real hooks: the `useItems` `enabled` gate (subscribes once by default and when re-enabled, zero `onSnapshot` calls while disabled) and the `hasServerData` latch (subscriptions pass `includeMetadataChanges: true`; the flag is false over a cache-only snapshot even though `loading` clears, latches on the first server-confirmed snapshot for both the collection and the doc sub, and stays latched through a later cache-served snapshot).

The pure `dealBoard` contract—deterministic sampling, 24 unique Prompts + null centre, and the `< 24` throw—is unit-tested in `src/game/logic.test.ts` (owned by the test-harness ticket) and not duplicated here.

## Amended by #409: the join write is TRANSACTIONAL (idempotent under overlap)

`runDeal`'s `withTimeout` (#403) rejects the race but cannot cancel the underlying `joinAndDeal`, so a timed-out deal keeps running while a Retry starts a second one—two joins for the same uid in flight at once (the Codex finding on #408). Every read-and-write in `joinAndDeal` therefore now runs inside a `runTransaction` (the same primitive `dealDayCard` and `reshuffleBoard` already use), superseding this spec's original "batch-writes" description; everything else above—freeze-at-join, the early return, the pool guard, identity validation and fallback—is unchanged:

- **Legacy (this spec's original shape):** the plain board-exists probe stays as a FAST PATH (a returning Player still early-returns without the pool or profile read—the acceptance criterion above), but the transaction RE-CHECKS board existence before creating the board + Player row. Two overlapping joins serialize server-side: the loser's transaction retries against the winner's committed board, sees it exists, and resolves `false`—never a double-commit or a `joinedAt` re-stamp. Pool and profile reads stay outside the transaction (a query cannot run inside one; the deal is deterministic from the uid, so a contention retry recomputes identical cells).
- **Daily mode (#246's identity-row-only join):** the Player-row read + conditional identity/aggregate seed run in one transaction, so the per-field guards act on the row state the write actually lands on. The stale-read hazard this closes is concrete: an overlapping join could re-seed `reshufflesUsed: 0` over a spend committed in between, a write firestore.rules' monotonic counter DENIES—failing the entire join.
- **`join_event` attribution moves to the ORIGINAL deal promise** in `runDeal`: exactly ONE `joinAndDeal` call resolves `true` per actual join, and it is not necessarily the current attempt (a superseded, timed-out attempt's transaction can win while the Retry resolves `false`). The analytic is tracked wherever the `true` lands, guarded on the still-signed-in uid so a join that commits after a sign-out/account switch never attributes to the wrong session.
- Offline, `runTransaction` REJECTS promptly where the old plain write hung until the #403 timeout; the deal path is online-gated in `AuthContext`, and both rejection codes (`aborted`/`unavailable`) are already classified as transient by the deal-error classifier, so the recovery UX is unchanged.

Coverage: the transactional re-check and guard degradation are unit-pinned in `src/components/w1-board-deal-join.test.tsx` ("the transaction RE-CHECKS board existence…", "alreadyJoined derives from the row read INSIDE the transaction…") and `src/data/reshuffle.test.ts` (the allowance-seed guards, now through `tx.set`); the real-concurrency proof is the emulator suite `tests/offline/join-idempotent.test.ts` (two overlapping joins → exactly one actual-join verdict, one coherent committed row).

## Amended by #519: the first deal after an update reload gets one silent re-deal

`updateServiceWorker(true)`—the update banner's Reload and the #342 build-floor force (`specs/app-update-reload-prompt.md`)—reloads the page the instant the new service worker takes control, so the reloaded document runs its first `joinAndDeal` against a Firebase auth token and a Firestore connection that may still be coming up. Observed twice during post-deploy verification on 2026-08-01: the deal failed transiently and the player was handed the full-screen "check your connection" `DealError` seconds after being told the reload takes two seconds, and tapping Retry succeeded on the spot. The timing is self-inflicted—the reload is ours—so the recovery is too.

- `src/postUpdateDeal.ts`—the grace. `watchPostUpdateReload()` arms it on a `controllerchange`, which IS the update taking effect, and mirrors the arming into `sessionStorage` (`gcb:post-update-reload`) because that event fires in the OUTGOING document while the failing deal runs in the incoming one; the marker is read AND cleared by the next document, so it arms exactly one load. `consumePostUpdateDealGrace()` claims it, and the first taker spends it. Storage and service-worker touches are guarded the way `src/shellRecovery.ts` guards its own—a grace path that can throw is worse than no grace.
- `src/main.tsx`—`watchPostUpdateReload()` is called at module scope, beside the #342 build-floor force and OUTSIDE the tree `ErrorBoundary` wraps (Codex P2 on #719). The boundary deliberately covers only `AuthProvider`, leaving `UpdatePrompt`—the sole in-app caller of `updateServiceWorker(true)`, and therefore the only way a client moves off a broken build—running after a crash, so a player can take an update with the auth tree unmounted. A watcher living inside that tree would already be gone when they did: no marker written, no grace in the incoming document, and the recovery reload—the load most likely to need it—left uncovered. Out here nothing ever unsubscribes it, which is what makes "installed for the document's life" true rather than aspirational.
- `src/auth/AuthContext.tsx`—the two places the grace is claimed, through the single `claimPostUpdateGrace` predicate. `runDeal`'s catch consumes it instead of calling `failDeal`, re-entering `runDeal` for one more attempt: `dealError` is never SET, so `DealError` never renders—not even for a frame, which no post-hoc retry watcher could achieve—and `dealing` stays up because the re-entrant attempt bumps `dealAttemptRef` before the outer `finally` reads it. The re-deal is exactly the manual Retry the player would have tapped: the two joins serialize inside the transaction above, and the attempt guard keeps the superseded one from reporting.
- `src/auth/AuthContext.tsx`, `bootstrapUser`'s online branch—the OTHER half of the same race (Codex P2 on #719). The reload can drop `ensureUserProfile` or the server-only attestation read just as easily as it drops the deal, and that failure reaches `failDeal` without `runDeal` ever being entered. The player cannot tell the two apart: identical connection-worded `DealError`, identical Retry that succeeds on the spot (`retryBootstrap` re-runs the same pair). So the bootstrap claims the same grace on the same terms and repeats the authority read once. Nothing has settled at that point—`loading` is still held and `profileReady` still false—so the repeat is silent: the player stays on the "Loading…" they were already on. Only the no-sticky arm needs it; the optimistic-sticky arm keys off `attestedUidsRef`, a per-document ref a reload always resets to empty.

The grace is bounded four ways so it can never mask a real failure. Only TRANSIENT failures reach it—a pool-shortfall keeps its own copy and its own #70 recovery, and a permanent Firestore error still surfaces at once. It is consumed by its first taker, so it is one silent repeat per document and cannot loop. That taker is whichever half of the race fails first, so a graced bootstrap leaves none for the deal and vice versa—two failures on one load always surface the second. And a definitely-offline player is excluded (`isOnline()`), so genuine no-connectivity reaches the retry surface on the first failure rather than after a second doomed attempt. On the deal path it is also only ever load-bearing for a player with NO cached card: a returning player's transient failure is already swallowed behind the #403 cached-card fallback before the grace is reached.

Coverage: `src/auth/post-update-deal.test.tsx` (Vitest, RTL-jsdom integration against the REAL `AuthProvider`, with `navigator.serviceWorker` stood in by an `EventTarget` and `main.tsx`'s module-scope arming stood in by an explicit `watchPostUpdateReload()` per simulated document). Deal half: a controller change followed by a transient first deal renders no `DealError` in ANY committed frame (latched during render, not sampled at the end) and deals on the re-attempt; the same failure with no controller change surfaces immediately; the arming crosses a simulated reload via the marker and does not survive to a third document; a second failure in the same document surfaces rather than looping; an offline failure and a pool-shortfall failure both surface on the first attempt with the grace unspent. Bootstrap half: a controller change followed by a transient `ensureUserProfile` failure renders no `DealError` and goes on to deal; the same failure unarmed surfaces at once with no deal attempted; a bootstrap that spends the grace leaves the deal's own failure to surface; and an offline or permanent bootstrap failure surfaces on the first attempt. Where the watcher is mounted is pinned by a static scan of `src/main.tsx` and `src/auth/AuthContext.tsx`, because a listener that was never registered is not something any render can exhibit.

The Player-facing sign-in-time surfacing of a failed deal—`dealError`/`dealing`/`retryDeal` state and App mounting `DealError` as the Card route—is wired in the auth/App join effect and owned by the auth ticket (`specs/w1-auth-google.md`). This spec owns the Board-side render guard that keeps a thin pool from showing as a blank card. Deal-failure recovery has a manual path (the `DealError` Retry button + the reachable `/items` tab) and an automatic path (the shell-level pool-recovery watcher that retries when the pool crosses `MIN_POOL` upward), the latter owned by `specs/w1-deal-auto-retry.md`.
