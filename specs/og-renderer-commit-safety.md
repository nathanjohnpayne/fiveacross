# OG renderers: fail-closed output guards and atomic multi-destination commit

`render-og-editions.mjs` (#699, #713) generates the per-Edition link-unfurl artwork (`public/og-{gcb,vacay,fiveacross}.png` and their byte-identical `plans/og-images/` mirrors) from `scripts/og/og-edition.html`. Two behavioral guarantees govern how a render is allowed to reach those committed destinations, documented for operators in `docs/app/og-artwork.md`: a render that would ship a broken link preview must never replace a committed one, and `--all` must update every targeted Edition or none of them, never a partial set.

The mechanism lives across four small modules the render script composes, each independently testable without booting Playwright: `og-size-guard.mjs` (the hard cap), `og-scratch-path.mjs` (per-invocation-unique staging paths), `og-stage-commit.mjs` (atomic staged commit with rollback), and `og-commit-lock.mjs` (cross-process serialization over the destination set). Nothing else in the repo writes to `public/og-*.png` or `plans/og-images/*-og.png`, so those destinations' contract binds this one caller — but it binds any future one too, per the note in `docs/agents/code-modification-rules.md`.

#887 added a second publisher, over a different destination set, composing the same three commit-safety modules: the share-card publisher described in its own section below. The sections up to that point are about `render-og-editions.mjs` and the unfurl destinations; the share-card section states where the two contracts are identical and where the share cards need more.

## Every render must clear the hard cap before it can replace a committed copy

WhatsApp caps `og:image` at 600 KB. A render lands in a per-destination scratch file first; only a render whose final bytes (after an optional pngquant pass) clear the cap is allowed to become the committed `public/og-*.png` / mirror pair.

- **Given** a render whose final bytes exceed the 600 KB hard cap even after quantisation **when** `assertWithinHardCap` runs **then** it throws and the caller deletes the scratch file before any committed destination or mirror is touched. (Test: "throws — without writing anything — when the final render is still over budget".)
- **Given** a render at or exactly on the cap **when** the same check runs **then** it passes through and staging proceeds. (Tests: "passes through a render within the hard cap", "passes through a render exactly at the hard cap".)
- **Given** a failure **when** the error is read by an operator or CI **then** it names the Edition and both the measured and cap byte counts. (Test: "names the Edition and both sizes in the failure so it is actionable from CI logs".)

## `--all` commits every targeted Edition or none of them

`render-og-editions.mjs` stages every targeted Edition to its own scratch path and calls `commitStaged` only once every targeted Edition has individually cleared the hard cap. A failure at any point before that — a later Edition's hard cap, a degraded font load — must leave every already-staged Edition uncommitted.

- **Given** `--all` targets multiple Editions and a later one fails its hard-cap or font-integrity check **when** the run ends **then** no earlier Edition's `public/` destination or mirror has been replaced, and every staged scratch file is removed. (Test: `discardStaged` "deletes every staged scratch file without touching any destination".)
- **Given** the commit phase itself fails partway through the staged list (a mirror directory going unwritable, a rename failing) **when** `commitStaged` unwinds **then** every destination/mirror it had already touched in this call is restored to its pre-commit bytes — an entry that existed before the commit gets its original bytes back, one that did not exist is removed rather than left behind. (Tests: "restores every already-committed destination and mirror to their pre-commit bytes when a later entry fails", "removes a newly-created destination and mirror that had no prior version, rather than leaving them behind".)
- **Given** two invocations both target the same destination and stage independently **when** their scratch writes happen **then** neither invocation's staged bytes are visible to or overwritten by the other — scratch paths are unique per invocation (pid + random token), not a pure function of the destination. (Test: "keeps two invocations' staged bytes independent even though both target the same dest".)

## Concurrent invocations never interleave one destination's commit

Two `render-og-editions.mjs` processes can legitimately target the same destination at once (a manual preview racing a scheduled `--all`, or two overlapping `--edition` runs). `render-og-editions.mjs` acquires a lock on every destination it is about to commit, in a fixed (sorted) order, and holds every one of those locks for the whole commit-or-rollback phase — not just a single file touch — before `commitStaged` is ever called.

- **Given** two invocations race to commit the SAME destination **when** either reaches its commit phase **then** the second is blocked until the first releases, so their rename+copy pairs (and their rollback backups) never interleave. (Tests: "a second acquire on an already-locked destination times out instead of proceeding", "WITH the lock, no two workers are ever inside the critical section at the same time".)
- **Given** no lock is held at all **when** the same two invocations race **then** they CAN observe each other mid-critical-section — proving the race the lock closes is real, not hypothetical. (Test: "WITHOUT the lock, workers CAN be inside the shared critical section at the same time — proving the race is real".)
- **Given** a lock's owning process is confirmed dead **when** a waiter polls **then** the lock is stolen so a crashed renderer never bricks a future commit to that destination — but elapsed time alone never revokes a lock held by a live or unprobeable process. (Test: "steals a lock file left by a process that is no longer running".)
- **Given** a lock is judged stale and about to be stolen **when** the steal proceeds **then** ownership of the takeover is established via an exclusive takeover record (`${lockPath}.takeover`) created before the staleness read and held through the unlink — not via a `dev`/`ino` filesystem-identity re-check immediately before the unlink, since POSIX has no conditional-unlink syscall and inode reuse means a pathname+inode comparison still cannot be an atomic CAS — and `tryAcquireOne` checks that takeover record both before and after publishing its own lock, so no compliant waiter can publish, or retain, a healthy lock at the same path while a steal is in flight. (Tests: "blocks an ordinary acquirer for as long as another process holds a live takeover gate, and never publishes a lock in that window" in `og-commit-lock.test.mjs` covers the takeover gate appearing before an acquirer's first check; "never leaves its own lock visible when the takeover gate is created between the first check and publication" in `og-commit-lock-atomicity.test.mjs` covers the gate appearing strictly between the two checks, forcing withdrawal of an already-published lock.)
- **Given** a lock is published **when** any process reads it **then** it never observes a lock file that exists but has incomplete content — publication is via `linkSync` from an already-fully-written scratch file, never an in-place `openSync` + separate write. (Tests: "never creates the lock path itself via a direct openSync — only a private scratch path", "publishes the lock only via linkSync, whose target is the lock path", "the source linkSync publishes from already contains the full pid line — never empty or partial".)
- **Given** two invocations' commits interleave under the lock (one fully commits and cleans up its own recovery backup while the other is still mid-rollback) **when** the still-rolling-back invocation restores its own pre-commit bytes **then** it restores from its OWN backup, never the other invocation's — backup paths are unique per `commitStaged` call, not a pure function of the target path. (Test: "restores the pre-commit bytes even when another invocation fully commits (and cleans up its own backup) in the middle of this invocation's failure".)
- **Given** `commitStaged` is called directly, bypassing `withDestinationLocks` **when** two such calls race **then** the race reopens — `commitStaged` performs no locking of its own; the guarantee above holds only for callers that acquire the lock for the whole commit-or-rollback phase first. (Test: "deletes invocation A's committed file when B's own destExisted/mirrorExisted check ran before A ever created it — proving the caller's lock is still required even with unique backup names, and that this is real, not hypothetical".)

## A process killed mid-commit is diagnosed, not silently masked — and not silently "recovered" either

For every destination or mirror that existed before the commit, `commitStaged` writes a per-entry rollback backup before the destructive rename/copy and removes it only through its success-path unlink or catch-block rollback — both synchronous in the calling process. A process killed between those points (SIGKILL, a crash, a machine shutdown) leaves that pre-existing artifact's backup on disk and can leave `dest` and its mirror out of sync. A first render has no prior artifact to back up, so it intentionally leaves no equivalent diagnostic file; the renderer's next full run overwrites both paths and the byte-parity test still catches a torn pair before a PR.

This is diagnosed, not repaired: a leftover backup's mere presence cannot distinguish "commit interrupted mid-flight" from "commit fully succeeded and was killed only during its own final cleanup," and treating the two the same by restoring from the backup would silently undo a successful commit in the second case. Given that ambiguity, and that `render-og-editions.mjs` is a manual, human-supervised, git-reviewed tool whose next run is a full fresh overwrite (not an incremental patch), automatic recovery is out of scope — see the round-8 rebuttal on `commitStaged` in `og-stage-commit.mjs` and on `stealIfStale` in `og-commit-lock.mjs`.

- **Given** a lock is stolen because its holder is confirmed dead **when** a rollback backup for that destination is still on disk **then** the steal logs a warning naming the destination and the possibility of a killed mid-commit process, in addition to the ordinary steal warning — surfacing the evidence without acting on it. (Test: "warns about a leftover rollback backup when stealing a lock left by a killed commit".)
- **Given** a lock is stolen and no rollback backup exists for that destination **when** the steal warning is logged **then** it does not mention a rollback backup — this includes an ordinary abandoned lock and a first-render interruption with no pre-existing artifact to diagnose. (Test: "does not mention a rollback backup when stealing a lock with no leftover backup".)

## The share-card publisher: `plans/og-images/share-final-photo-*.png`

Two tools write the wireframes' reference pictures of the final-standings share card, and both publish through one function, `renderCardSet` in `scripts/og/render-share-rasters.mjs`: that script itself re-renders a whole card by screenshotting its `.shc` artboard, and `scripts/og/render-share-footer.mjs` repaints only the 32-row brand-footer band on the card already committed. They compose the same `og-scratch-path.mjs`, `og-stage-commit.mjs` and `og-commit-lock.mjs` as the unfurl renderer, so everything the three sections above say about scratch-path uniqueness, `commitStaged`'s rollback and the lock's own semantics holds here unchanged and is not restated. What differs is the output guard (a format and content contract rather than a byte budget), the fact that one of the two publishers READS the destination it replaces, and the absence of mirrors — a share card has a single committed path, so `commitStaged` entries carry no `mirror`.

The committed cards are 600x750, 8-bit, non-interlaced, truecolor (PNG colour type 2). `src/recon-share-og.test.ts` requires exactly that of the files in the tree, so a publisher that writes anything else does not fail at the moment it is wrong — it fails on the next `npm test`, with the good picture already overwritten.

### Every capture must prove its format and content before it can replace a committed card

- **Given** a capture that is not 600x750, or not 8-bit, or interlaced, or not colour type 2 **when** `assertCapturedCardFormat` runs **then** it throws naming the Edition and every faulty field at once, while the capture is still a scratch file and no committed card has been touched. (Tests: `share-raster-format.test.mjs`, "refuses a correctly sized capture with an alpha channel", "refuses an interlaced capture", "refuses a 16-bit capture", "names the Edition and every fault at once, so one re-run clears them all".)
- **Given** a capture that is not a structurally complete PNG (a chunk that runs past the end of the file, a chunk whose stored CRC does not match, no IEND chunk, an IEND chunk that carries a payload or is followed by any bytes, or image data that does not inflate to exactly the scanlines IHDR declares) **when** `inspectCapture` decodes it with `readPngPixels` **then** it throws while the capture is still a scratch file, for every Edition including Vacay, whose overlay check is exempted but whose decode is not. A capture cut off after its last IDAT chunk used to decode as complete whenever its compressed payload still inflated, and no CRC was checked at all. (Tests: `png-pixels.test.mjs`, "readPngPixels refuses a PNG that is not structurally complete"; `render-share-rasters.test.mjs`, "refuses the committed %s card truncated after its last IDAT chunk", "refuses the committed GCB card with a corrupted chunk CRC", "keeps the truncated capture out of the committed tree".)
- **Given** a capture of a dark-ground card whose upper-right quadrant is mostly near-white **when** the overlay check runs **then** it throws, because that is the #887 defect — a foreign card composited over this one — expressed as a number. Vacay's own card is cream end to end and is exempted rather than measured against a threshold that means nothing for it. (Test: `render-share-rasters.test.mjs`, "commits every target once all of them validate" asserts the measured share on the passing path; `src/recon-share-og.test.ts` holds the committed files to the same cap.)
- **Given** a capture whose near-white share lands EXACTLY on the cap **when** the overlay check runs **then** it is refused, because the committed-file guard accepts only a share strictly below the cap — the two ends share one constant and one predicate (`scripts/og/share-card-overlay.mjs`), so a capture the renderer publishes can never be a file the suite rejects. (Tests: `render-share-rasters.test.mjs`, "refuses a capture sitting exactly on the cap, and commits nothing", "accepts a capture one pixel under the cap", "measures the fixture at exactly the cap, so the boundary case is the one being tested".)
- **Given** the artboards' display stack resolves to any face other than the one the committed pictures were captured with **when** the run starts **then** it refuses before the first capture, because `document.fonts.ready` resolves on a host with no such face installed and the resulting capture passes every size, format and content check while carrying different typography. (Tests: `render-share-rasters.test.mjs`, "aborts before the first capture when the display face is missing", "refuses a host where neither display face resolves, and names the one to install", "refuses a face that document.fonts.check claims but the cascade did not use", "refuses a host that resolves the stack to a different face".)
- **Given** a canvas-encoded repaint, which is colour type 6 because a 2D context carries an alpha channel **when** it is staged **then** it is converted to colour type 2 by dropping an alpha plane proved to be entirely 255, and refused by pixel coordinate if any alpha is not. (Tests: `png-truecolor.test.mjs`, "converts an opaque RGBA image to colour type 2, pixel for pixel", "refuses to drop an alpha channel that carries something, and says which pixel"; `render-share-footer.test.mjs`, "converts an opaque RGBA canvas result and commits it as truecolor", "refuses a canvas result with a transparent pixel and commits nothing".)

### `--all` commits every targeted Edition or none of them

Every target is captured to its own scratch path and validated there; `commitStaged` is called only once the LAST target has passed. Publishing per Edition as each one validated — which is what the first implementation did — turns a single failed batch into a mixed render set, with nothing in the tree to say which cards came from which run.

- **Given** an `--all` run whose later target fails its format, content or conversion check **when** the run ends **then** no earlier target's committed card has been replaced, every scratch file in the run is removed, and the error names the Edition that failed. (Tests: `render-share-rasters.test.mjs`, "leaves an earlier card untouched when a later one fails its checks", "names the Edition that failed, and carries the underlying refusal"; `render-share-footer.test.mjs`, "leaves every card alone when one Edition in an --all run fails".)
- **Given** a capture that dies partway through writing its scratch file, or a commit phase that throws **when** the run unwinds **then** the same sweep runs: no committed card changes and no scratch file is left behind. (Tests: `render-share-rasters.test.mjs`, "discards the scratch file when the very first capture fails", "sweeps the scratch files and keeps the tree when the commit phase fails".)
- **Given** every target passes **when** the commit phase runs **then** all of them are published in one pass. (Test: `render-share-rasters.test.mjs`, "commits every target once all of them validate".)

### The lock spans the read when the publisher reads what it replaces

`renderCardSet` holds `withDestinationLocks` over the whole commit-or-rollback phase for every run, exactly as the unfurl renderer does. A publisher whose capture READS the card it is about to replace needs more than that, and says so with `readsDestination: true`: the locks are then acquired before the run does anything at all and held until it is finished. `render-share-footer.mjs` is that publisher, and it reads the committed card from inside its capture seam rather than before the call, so the lock cannot be bypassed by a read that happens earlier.

- **Given** a footer refresh and a full re-render targeting the same Edition **when** the full re-render commits a new card after the footer run has started but before it acquires its locks **then** the footer run reads and repaints the NEW card, not the one that was there when it started. (Test: `render-share-footer.test.mjs`, "sees the raster that landed before it took the lock, not one read earlier".)
- **Given** the same race with the lock covering only the commit phase **when** the full re-render commits mid-paint **then** the footer run publishes a repaint of the stale snapshot over it, discarding the new render with no error — proving the widened lock scope closes a real race, not a hypothetical one. (Test: `render-share-footer.test.mjs`, "would repaint the stale snapshot if the lock only covered the commit — the race is real".)
- **Given** another process already holds a destination's lock **when** a footer refresh targets it **then** the refresh is refused by the lock's ordinary timeout before it reads, paints or stages anything, and the holder's lock is undisturbed. (Test: `render-share-footer.test.mjs`, "is refused rather than proceeding while another process holds the destination".)
- **Given** a run that already holds its locks for the whole run **when** it reaches the commit phase **then** it does not acquire them a second time — the locks are exclusive rather than reentrant, so a re-acquire would block against this process's own lock file until it timed out. (Covered by every `readsDestination: true` test above completing: each one would time out instead.)

### A share card has one committed path, not a destination/mirror pair

- **Given** a staged entry with no `mirror` **when** `commitStaged` publishes it **then** it renames the scratch file over the destination, backs that destination up beforehand, rolls it back if a later entry in the same call fails, and reports the entry's mirror as `null` — the mirror half of every step is skipped rather than special-cased by the caller. (Tests: `og-stage-commit.test.mjs`, "publishes an entry with no mirror, and reports its mirror as null", "rolls a mirror-less entry back when a later entry in the same call fails".)

## Acceptance criteria

- **Given** the merged behavior **when** `npm test` runs the `scripts/og/*.test.mjs` suite **then** it is green.
- **Given** a new caller that wants to write to `public/og-*.png`, `plans/og-images/*-og.png` or `plans/og-images/share-final-photo-*.png` **when** it is added **then** it acquires `withDestinationLocks` for its whole commit-or-rollback phase before calling `commitStaged`, per `docs/agents/code-modification-rules.md`'s pointer to this spec — `commitStaged` and `stealIfStale` provide no protection on their own for a caller that skips it — and if its capture reads the file it replaces, for the read as well.
- **Given** a change to either publisher's output contract **when** it lands **then** `src/recon-share-og.test.ts`'s guards on the committed files move with it: they are the other end of the format contract, checking the bytes in the tree rather than the bytes a run is about to write.
