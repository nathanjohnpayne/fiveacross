# Offline cold boot: render the cached app without awaiting network-bound auth bootstrap

[ADR 0006](../docs/adr/0006-offline-resilience.md) makes the DATA layer offline-durable—the persistent IndexedDB cache renders the last-seen Board/Feed/Tally and Marks queue durably—but the BOOT path was online-only, inverting that promise. After an offline reload the app stuck on "Loading…" indefinitely: `AuthContext`'s `onAuthStateChanged` callback `await`ed `ensureUserProfile` (a Firestore **transaction**, which needs the network and never resolves offline—transactions do not queue) and then `readAdultAttestation` (a server point read) BEFORE it ever published `loading: false`. The service worker served the shell and the durable Mark queue survived, but the UI never rendered the cached Board. Worse, once the bootstrap had failed offline, post-reconnect recovery was nondeterministic (~1-in-3 flake in the #47 e2e diagnostics).

This ticket makes auth bootstrap a **connectivity/attestation state machine** whose organizing principle is: the persistent cache lifts the 18+ gate **provisionally while offline**, and the server read is **authoritative when it arrives**. It renders the cached app offline without ever awaiting a network-bound bootstrap, WITHOUT weakening the 18+ attestation gate (#23/#112).

## The state machine

- **Auth change (the render decision).** The callback publishes the User, re-arms the gate (`attested` UNKNOWN, `profileReady` false, `attestedAuthoritative` false), and—for a signed-in User—GATES on `loading: true` for BOTH connectivities. It never renders the Board before proof-of-18+; `bootstrapUser` releases the hold. (A signed-out User publishes `loading: false` → the signed-out SignIn.)
- **Bootstrap (off the render path).**
  - **Offline** → settle the gate CACHE-FIRST via `readAdultAttestationFromCache` (`getDocFromCache`). A cached stamp, or a same-session optimistic attest (`attestedUidsRef`), is PROOF of 18+: it lifts `attested` true AND releases `loading: false` so the cached Board paints (the #115 cold-boot). A cache MISS or a definite-unstamped row is UNKNOWN: it never lifts `true` (cache-first can't fail the age gate open) and it does NOT render—it HOLDS on "Loading…" (finding B) until reconnect, because offline can't re-prompt (the attest transaction needs the network). It only ever lifts, never downgrades (that is the online read's job). `ensureUserProfile` (a transaction that never resolves offline) and the server read are deferred to reconnect.
  - **Online** → run the AUTHORITATIVE bootstrap (`ensureUserProfile` + the **SERVER-ONLY** `readAdultAttestationFromServer`), staying gated on "Loading…" until it settles—an un-attested returning User with a cached board must NOT view the Event during the read (finding B). The combined bootstrap is bounded by `AUTH_BOOTSTRAP_TIMEOUT_MS` (10 seconds): Safari/captive Wi-Fi can report `navigator.onLine === true` while a Firestore transaction or server read never settles, so timeout is treated as the same genuine connection failure as a rejection and releases the gate to the retryable error surface rather than loading forever. The authority read is `getDocFromServer`, NOT the cache-capable `getDoc` (`readAdultAttestation`), whose Web API may silently serve cached data when the server is unreachable—so deal authority can never come from a stale cached stamp (round 6). The server value is definitive: a present stamp settles `true`, a MISSING stamp settles `false`—DOWNGRADING even a provisional cache lift (e.g. a deleted/recreated `users/{uid}` row) to a re-prompt. It sets `attestedAuthoritative` true and releases `loading`. The only sticky override is `attestedUidsRef` (this session's own optimistic attest, #112 Finding 3), never a stale cache value. A genuine network FAILURE (`getDocFromServer` REJECTS when the server is unreachable, the transaction throws, or the combined operation times out despite `navigator.onLine`) is not authoritative: it does NOT set `attestedAuthoritative`, does NOT deal, and surfaces the retryable `dealError`—but for a CONNECTION-class failure it does lift RENDER from the cache (#521, below). The provisional offline RENDER still uses the cache-first `readAdultAttestationFromCache`; only the deal-authority read is server-only.
- **Connectivity transitions (both directions supersede).** A React `online` state mirrors the browser `online`/`offline` events. BOTH handlers bump `profileAttemptRef` (superseding any in-flight bootstrap so its late resolution cannot clobber) and re-run `bootstrapUser` for the current connectivity. **Reconnect** (`online`) finishes the deferred authoritative work and, via the `online` dep, lets the deferred deal fire once the read confirms. **Connectivity LOSS mid-bootstrap** (`offline`, finding C) supersedes the pending online attempt—whose transaction may never settle offline and would otherwise strand "Loading…"—and switches to the cache-first path: render if proof-of-18+ is cached, else hold. So `loading` is never stranded on a bootstrap owned by the wrong connectivity.
- **Deal gate—online AND authoritative.** The deal (auto effect AND the manual `retryDeal`, finding A) fires only when `attested === true`, `attestedAuthoritative` (server-settled or a same-session attest whose transaction succeeded), AND the reactive `online` state is true. Distinct from the provisional offline cache lift: on reconnect `online` flips true BEFORE the authoritative round trip finishes, so gating on `online` alone would let a fresh-Event User `joinAndDeal` on the stale cache value—creating durable board/player rows for a User the server may then downgrade (defeating the age gate for WRITES). A `retryDeal` that is offline or on a provisional attestation re-runs the bootstrap instead of dealing. Holding the deal for authority means a server-null downgrades to the re-prompt WITHOUT ever dealing; a confirmed-attested (or same-session-attested) User deals exactly once. Never offline; a returning boarded User re-runs `joinAndDeal` on reconnect but its board-exists early-return makes that a no-op.

### Connection-failure recovery preserves a cached card (#403)

A deal is a create/identity path, not what renders the card: the Board renders from the persistent Firestore cache (ADR 0006) via its own `onSnapshot`, independently of `joinAndDeal`. So a `dealError` set on a connection-class deal failure is what tears the card down—App renders the DealError panel over the Board whenever `dealError` is non-null. Because the deal effect re-fires on every reconnect, and daily-mode `joinAndDeal` re-reads the Event and re-writes the player row even for an already-joined Player (it is not a pure no-op in the day-scoped model), a transient blip on an unreliable network would otherwise kick a Player with a perfectly good cached card onto the error panel. `runDeal` therefore SWALLOWS a TRANSIENT connection failure when the Player already has an ACTUAL cached card to fall back on—`hasCachedCard`, which scans the `boards` collection group from cache, scopes to the active `events/${EVENT_ID}/` ancestor, and matches this uid (mode-agnostic: both the legacy `boards/{uid}` and the day card `days/{d}/boards/{uid}` carry a `uid`): it clears any stale error and leaves the cached Board up, letting Board's own per-day retry handle a missing Day Card. Three failure classes are DELIBERATELY excluded so they still surface the retryable `dealError`: (1) a genuine no-card case—a first-timer whose very first deal failed; (2) a pool-shortfall—not a connection issue, and PoolRecoveryWatcher owns its recovery keyed on the reason; and (3) a permanent or unknown Firestore/Firebase failure—a rules/schema/data-integrity problem must not be hidden behind the cached Board forever. The fallback signal is deliberately a cached CARD, not a cached `players/{uid}` row (Codex #408): the row can be cached from the Leaderboard query or another tab while no board was ever loaded here, and swallowing on the row alone would strand the Player on Board's indefinite "Dealing…" state with the retry gone. It is a per-account, per-event cache probe rather than an AuthProvider-lifetime latch—so it cannot mistake a daily identity-row merge for a real card, cannot leak across an account switch, and reflects a card dealt this session too (a local write lands in cache before its server ack).

The deal is also BOUNDED by `DEAL_TIMEOUT_MS` (20 seconds), reusing the same `withTimeout` the bootstrap uses: previously only the bootstrap was time-bounded, so a hung `joinAndDeal` on captive Wi-Fi (where `navigator.onLine` reports the link, not reachability) left `dealing` true with no fallback. A timed-out deal rejects as a connection failure and flows through the same swallow-or-surface path—swallowed for a Player who already has a card, retryable for a first-timer. Because `withTimeout` rejects the RACE but cannot cancel `joinAndDeal`, a first-timer's deal that times out and THEN succeeds would otherwise leave its freshly-written card hidden behind the stale `dealError` (the deal effect does not re-run on the late write); a late-success handler on the original promise clears that error (attempt-guarded) so the card surfaces without a manual retry. A fully idempotent/transactional join—so a timed-out deal and its Retry cannot both write—is tracked as a follow-up.

### Durable card snapshot renders when the Firestore cache is empty (#434)

The #403 swallow above keeps a cached card ONLY when the card is present in THIS device's Firestore cache (`hasCachedCard`). A returning Player whose local Firestore cache was evicted—or who never loaded a board into it on this device—has no such card to fall back on, so a deal failure still drops them onto the full-screen reload screen (the "switching to the Card tab shows the reload screen, not my card" report, #434). To make the card durable across Firestore-cache eviction, Board writes a compact snapshot of the card it paints—exactly 25 uniquely-indexed cells, the presentational Day header (number, port, theme, label), and the bingo count—to `localStorage` (`src/data/cardCache.ts`), keyed per `(EVENT_ID, uid, dayIndex)` so it never leaks across Events/accounts and a daily-card offline Day switch cannot render the last snapshot from a different Day. Loads validate the full persisted shape and treat malformed/corrupt blobs as misses, never as partial cards. On a CONNECTION-class `dealError`, App then prefers the latest snapshot over the reload screen only when AuthContext exposes explicit render authorization (`canRenderEventContent`, backed by cached/server/same-session 18+ proof); a saved card is never itself proof-of-18+. Board also reads the matching day-scoped snapshot when the live attributable board is unavailable—including Firestore cache eviction, retained foreign-board data during account switches, and captive or otherwise unreliable Wi-Fi where `navigator.onLine` can remain true while Firestore is unreachable. The fallback is read-only on purpose—marking, Tally, and Doubts all need the live board and its writers, which the interactive Board takes back over the instant the deal recovers and `dealError` clears. This LAYERS UNDER #403 rather than replacing it: a live Firestore-cached Board is still preferred when present (and #403 clears the error to show it); the durable snapshot is the last-resort render for when even the Firestore cache has nothing. The write is attribution-gated (`cellsAttributable`), so a mid-account-switch board never overwrites the new account's snapshot, and best-effort—a full or unavailable store is swallowed, never a crash. Covered by `src/data/cardCache.test.ts`, `src/components/CachedCardFallback.test.tsx`, `src/App.test.tsx`, and the durable cached-card fallback cases in `src/components/Board.test.tsx`.

### The ONLINE authority read can fail while the device is effectively offline (#521)

`navigator.onLine` reports the link, not reachability. After an offline reload on captive/ship Wi-Fi it can report `true` while every Firestore request fails, so `bootstrapUser` takes the ONLINE branch, `ensureUserProfile` and `readAdultAttestationFromServer` both fail, and the failure arm surfaced `dealError` without ever settling `attested`. `canRenderEventContent` therefore stayed false and App withheld the WHOLE Event—including the #434 durable card snapshot sitting on the device—which inverts the ADR 0006 promise at exactly the moment the saved card exists for. The failure arm now falls back to the SAME cache-first proof the OFFLINE branch accepts: a cached `attestedAdultAt` lifts RENDER, never `attestedAuthoritative`, so no deal fires and no durable rows are created for a User the server has not confirmed, and a cache MISS changes nothing (the gate stays up—cache-first still cannot fail the age gate open).

Two boundaries keep that lift from widening into a hole. **It is CONNECTION-class only.** The lift and App's #434 cached-card fallback both read the single `dealErrorReasonFor` classifier, so a PERMANENT rules/schema/permission or unknown-coded failure never lifts the gate—the same refusal the #403 swallow already makes, and the reason the two decisions cannot disagree about whether cached state may stand in for a given failure. **The authoritative read still wins, even late.** `withTimeout` rejects the race but cannot cancel the in-flight read, so a result arriving after `AUTH_BOOTSTRAP_TIMEOUT_MS` used to be discarded; with a provisional lift standing and no connectivity event to trigger a re-read while `navigator.onLine` stays true, a discarded server-NULL would leave the stale lift up indefinitely. Every authority read—the initial bootstrap's, the #519 grace repeat's, and the Player's Retry (`retryBootstrap`)—now starts through the shared `startAuthorityRead`, which routes a result landing after the bound back to that caller's settle. A late stamp clears the error, grants authority, and fires the deferred deal (the same recovery `runDeal`'s late-success net gives a timed-out deal); a late null downgrades to the re-prompt. Each settle latches for its attempt, so nothing that resolves afterwards—a fire-and-forget cache lift, a slower `hasCachedBoard` probe, or a second read started by the grace repeat—may re-open a gate the downgrade closed or re-post an error the settle cleared. Routing Retry through the same helper is what closes the last hole: without it a provisional lift survived Retry indefinitely, because `navigator.onLine` never flips on captive Wi-Fi and nothing else re-reads authority.

**The #519 grace repeat runs BEFORE the lift.** Both live in this failure path and both fire on the same transient authority failure, so their order is a behavioural choice. The lift sits downstream of `failDeal`, so lifting first would set a connection-worded `dealError` and paint the cached card for the instant it takes the repeat to land—the exact error frame the #519 grace exists to skip—then clear both. Repeating first also makes the lift strictly rarer and better-informed: it is reached only once TWO reads have failed, and a repeat that succeeds settles real `attestedAuthoritative` authority, which the cache lift by construction can never grant. If the first read's orphaned answer lands while the repeat is in flight, that answer is authority for the attempt and the repeat's own failure is discarded rather than painted over it.

### State-machine contract (completeness matrix)

Every cell of `{boot-offline, boot-online} × {cache-attested, cache-unknown, same-session-attested} × {stays, connectivity flips mid-bootstrap}` resolves to: render only with proof-of-18+; deal only `online && attestedAuthoritative`; `loading` always eventually released (a hung online operation times out to Retry; an offline transition supersedes to the cache path); the authoritative server read always wins over the provisional cache when it lands; and `dealError` is CLEARED on any recovery that renders the Board or re-prompts (App renders the DealError panel over the Board whenever `dealError` is set, so a stale error must never linger over a state that should render/re-prompt), and set only on a genuine online failure with no cached card to fall back on (#403—a connection-class deal failure is swallowed only when an actual cached card exists, or a hung deal times out via `DEAL_TIMEOUT_MS`, so the cached Board stays up).

### Flag lifecycle (set / clear / supersede-reset)

There are TWO supersede tokens. `profileAttemptRef` guards the bootstrap path (`bootstrapUser` / `retryBootstrap`); `dealAttemptRef` guards the deal path (`runDeal`). The auth callback, the `online` handler, and the `offline` handler each bump `profileAttemptRef`; the auth callback and the `offline` handler (round 6) also bump `dealAttemptRef`; `runDeal` and `retryBootstrap` bump their own. Every attempt's resolution early-returns on a mismatch. The rule a superseder MUST uphold: it OWNS resetting every flag the superseded attempt would otherwise have settled, so no stale late resolution and no cross-transition permission survives. The reads split by purpose: the RENDER read is cache-first (`readAdultAttestationFromCache` / `getDocFromCache`, provisional); the deal-AUTHORITY read is SERVER-ONLY (`readAdultAttestationFromServer` / `getDocFromServer`, which rejects when unreachable and never serves cache)—a cache-capable `getDoc` never gates a deal (round 6).

Two-tier attestation (r7): the same-session attest is split into an OPTIMISTIC-UI tier (`attestedUidsRef`, set immediately so the UI never flickers the re-prompt) and a DURABLE-AUTHORITY tier (`attestCommittedUidsRef`, set only after `attestAdult` commits). Optimistic-for-UI is NOT authoritative-for-writes: a deal fires only on server-confirmed authority or a COMMITTED attest, so an attest that rejects/never resolves leaves the UI attested but creates no board/player rows.

Attest-failure recovery (r8 finding A + r9): because the optimistic lift dismisses the re-prompt while withholding authority, an `attestAdult` write that REJECTS would otherwise STRAND a first-time User with no board—re-prompt gone, no deal, stuck on "Dealing…". So on a rejected write, `attest()` ROLLS the optimistic lift BACK (removes the uid from `attestedUidsRef`, sets `attested` false) so the re-prompt returns and the User can re-attest in session. But the rollback is GUARDED (r9 finding B): it fires ONLY when the uid is NOT authoritatively attested—if the bootstrap already SERVER-CONFIRMED the stamp (`attestedAuthoritativeRef`, a ref mirror of `attestedAuthoritative` so the async catch reads the latest value) or a COMMITTED attest holds, the rollback is SKIPPED, so a returning User with a valid server stamp whose redundant sign-in attest merely dropped the network is never re-prompted despite authoritative proof. The SUCCESS path and the #112 no-flicker behavior are untouched, and a never-resolving OFFLINE attest never reaches the catch. (Redundant-attest decision: `signIn()` still calls `attest()` for every sign-in—eliminating the redundant write for an already-confirmed User would require a server read the sign-in path does not have before the bootstrap runs, and `attestAdult` is already an idempotent stamp-if-absent no-op write for a confirmed User, so the conditional-rollback guard is the clean fix rather than removing the call.)

Optimistic-only bootstrap-failure recovery (r9 finding A): a first-time User clicks 18+ (optimistic, `attestedUidsRef` set) BEFORE `attestAdult` commits, then the ONLINE bootstrap's SERVER read FAILS (`getDocFromServer` rejects on captive wifi). This branch keeps the UI attested but grants no authority, so the deal is gated off—and a BOARDLESS User would sit on "Dealing…" with no control. So when the online bootstrap fails on an optimistic-only attestation, `bootstrapUser` checks `hasCachedBoard`: a returning User WITH a cached board renders it (no deal needed), while a BOARDLESS User gets a retryable `dealError` whose Retry re-runs the bootstrap. The check is fire-and-forget (never delays the loading release) and attempt-guarded.

Join analytics fire on ACTUAL joins only (r8 finding B): `runDeal` re-fires the deal on every online/authority flip, and `joinAndDeal` early-returns a no-op for an already-boarded Player, so `joinAndDeal` now RETURNS whether it dealt a NEW board and `runDeal` records `track('join_event')` ONLY when it did. An unreliable-network reconnect that re-runs the deal for an existing board records nothing; only a genuine first join counts.

The round-5..9 behaviors this encodes: **(r5-A)** `attestedAuthoritative` is re-armed false on going offline (unless a COMMITTED same-session attest holds), so a reconnect deal requires authority proven by EITHER the fresh reconnect read OR a committed attest—never a possibly-stale pre-offline read; **(r5-B)** the offline/reconnect superseders clear `dealing`, so a retry invalidated by the `profileAttemptRef` bump never strands the Retry button; **(r6-A)** the authority read is SERVER-only (`getDocFromServer`), so a cache-served stamp never authorizes a deal; **(r6-B)** the offline handler bumps `dealAttemptRef`, so a deal in flight when connectivity drops is retired and its late rejection cannot set `dealError` over the rendered cached board; **(r7)** deal authority is granted only by a server-returned stamp or a COMMITTED attest, never by the optimistic pre-commit UI lift; **(r8-A)** a rejected attest write rolls the optimistic lift back so the re-prompt returns (no stranding); **(r8-B)** `join_event` fires only when `joinAndDeal` dealt a new board, so reconnects do not inflate join analytics; **(r9-A)** an optimistic-only attest whose online server read fails gives a BOARDLESS User a retryable error (a boarded User renders), so neither is stranded on "Dealing…"; **(r9-B)** the attest-failure rollback is GUARDED so it never downgrades a server-confirmed User to a re-prompt.

## Design invariants preserved

- The `attested` tri-state (#112): `undefined` = UNKNOWN, `true` = attested, `false` = SETTLED-without-stamp → re-prompt. Cache-first only ever settles `true` (on a genuine stamp) offline; the authoritative `false` comes only from the server read.
- The `profileReady` bootstrap-settled signal (#77) re-arms per auth change and stays `false` until the bootstrap actually settles; offline it stays `false` (deferred, not settled).
- The `attestedUidsRef` sticky optimistic attestation (#112 Finding 3) still wins over any later settle for the UI (no re-prompt on a not-yet-visible write)—but as an OPTIMISTIC-UI signal only; deal authority now comes from the separate durable-authority tier (`attestCommittedUidsRef`, set only after the write commits) or a server-confirmed stamp (r7).
- The deal side-effect gate (#112 Finding 1): the deal fires only for an AUTHORITATIVELY-attested User (never on the provisional cache lift), never for a returning boarded User (board-exists early-return), never offline.
