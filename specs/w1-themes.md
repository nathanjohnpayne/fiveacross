# Themes: switcher + persistence + Edition scoping + WCAG contrast (w1-themes)

Feature: cosmetic Themes a Player can switch between, applied instantly to the whole app via a `[data-theme]` attribute on `<html>`, with the explicit pick persisted locally and Neon Playground as the default. Themes are a look, never a mechanic—switching never alters play. The Gay Cruise Bingo Theme names and emoji are the entire homage to Atlantis Events; no marks, branding, or affiliation appear anywhere.

The Theme set started as the eight Atlantis party Themes; it has since grown to include Gay Cruise Bingo's two tutorial-Day Themes (#206), five more party Themes, and—from #555 and #617—Themes belonging to other **Editions**. The registry is therefore no longer the pick list: see "Registry vs. picker" below.

## Contract

- `src/theme/themes.ts` exports `THEMES: ThemeMeta[]`, one entry per `ThemeId` (`src/types.ts`), in a fixed order with `neon-playground` first. Each entry is `{ id, label, emoji, description }`, plus an optional `chrome: true` (#882, see "Registry vs. picker")—no Atlantis trademark or affiliation text in any `label`.
- `src/theme/themes.css` defines one `[data-theme='<id>']` block per `ThemeId`, each setting eleven custom properties (`--bg`, `--panel`, `--ink`, `--dim`, `--primary`, `--secondary`, `--accent`, `--cell`, `--border`, `--shadow`, `--on-gradient`) that `src/index.css` reads for the audited foreground/background pairs the WCAG AA contrast contract below covers, so every Theme reskins those surfaces. This contract does not claim `src/index.css` reads theme tokens exclusively or that no component hardcodes a color: `.proofbtn`'s `#fff` badge fill over a fixed photo-scrim is a deliberate, documented exemption (theme-independent by design, not a theme-token surface). `.cell.marked` (plus its `::after` checkmark and its border), `.celebrate .big`, and `.signin h1` used to fill text/border with a hardcoded `#fff` regardless of the active Theme—a real, pre-existing defect that predated this ticket (`index.css` was unchanged by the original w1-themes PR; issue #29 didn't list `index.css` as a file to modify). That follow-up (issue #72) is now fixed: see `specs/theme-on-color-contrast.md`. The two composited-`#fff` overlay badges on a marked Square (`.tally-badge` and `.doubt-badge`) are a related but distinct case, not in this token contract's inventory; they have their own contrast contract in [specs/a11y-badge-contrast.md](a11y-badge-contrast.md).
- `src/theme/ThemeContext.tsx` (`ThemeProvider`/`useTheme`) owns the active Theme: it applies the id to `document.documentElement.dataset.theme` synchronously on every change (`< 5s` PRD switch-latency metric), defaults to `neon-playground` absent any signal, and persists only an explicit `setTheme` call to `localStorage['gcb.theme']`. The async event/player default that arrives later from Firestore is adopted only when the user has not made an explicit pick—it must never overwrite a saved choice.
- `src/components/ThemeSwitcher.tsx` renders one chip per **pickable** Theme for the active Edition (`themesForEditionIncluding(preference)`, see "Registry vs. picker") and calls `setTheme` on tap, which drives `ThemeContext`'s `localStorage['gcb.theme']` persistence and DOM application (above). For a signed-in Player it additionally calls `savePlayerTheme` (`src/data/api.ts`) directly, a second and independent persistence path the switcher owns itself: it writes the pick to that Player's Firestore row so the choice follows them across devices. `src/main.tsx`'s `ThemedApp` reads that saved value back out and passes it to `ThemeProvider` as its OWN `playerTheme` prop—deliberately **not** folded into `defaultTheme` (#232), so `ThemeProvider` can tell a Player's cross-device pick apart from the Event's Auto fallback. `defaultTheme` is separately `event?.defaultTheme ?? defaultThemeForEdition()`; both are async event/player defaults `ThemeContext` (above) adopts only when the user has no local pick.

## Registry vs. picker (#555)

`THEMES` is the complete **registry** and stays complete on every Edition. `Leaderboard`, `dayIdentity`, `DaySwitcher` and `Board` look a Theme up *by id* there to render its emoji and label, and the contrast suites iterate it; narrowing the registry would turn those lookups into silent fallbacks and drop Themes out of the WCAG audit. Only the **pick list** is scoped.

- `themesForEdition(edition?)` returns the Themes pickable on an Edition. `THEME_EDITIONS` maps **every** `ThemeId` to the Editions it belongs to. That map is total (`Record<ThemeId, readonly string[]>`), not partial: there is no "unscoped means shared" default, so a Theme added without an Edition is a type error rather than a Theme that quietly appears everywhere. A Theme genuinely belonging to two Editions lists both.
- The Editions **pick-partition** the non-chrome registry: the fifteen Gay Cruise Bingo Themes are `gcb`, the three Bodega Bay Themes are `vacay`, the three Five Across Themes (#617) are `fiveacross`, and nothing is in more than one. A platform-chrome Theme (below) is `THEME_EDITIONS`-bound to an Edition the same way but sits outside this pick-partition entirely — registered and contrast-audited, never returned by any picker.
- A Theme may instead be flagged **platform chrome** (`ThemeMeta.chrome: true`, #882) rather than an ordinary occasion Theme: chrome dresses surfaces that have no Day — utility states, the admin console, email, gallery/share surfaces outside a Day context — never a Day a player or organizer can wear. `fiveacross-slate` is the first: registered in `THEMES`, WCAG-audited like any other Theme, and `THEME_EDITIONS`-bound to `fiveacross`, but `themesForEdition` filters it out of every picker's output regardless of Edition — including `fiveacross`'s own. The registry drew no selectable-vs-chrome distinction before this flag; it is the one mechanism, not a parallel concept invented alongside it.
- The active Edition comes from `activeEdition()`, seeded from `VITE_EDITION` (absent = `gcb`, so existing builds are unchanged) and settable via `setActiveEdition()` once hostname resolution (#543, ADR 0009) knows the Edition. An Edition string no Theme claims falls back to `gcb`—degrading to the legacy experience, never to an empty picker.
- **Every** picker uses the scoped list, admin ones included: `ThemeSwitcher` (Player), `GameSettings` Appearance (`defaultTheme`), and `SchedulePanel`'s per-Day `<select>`. An Admin must not be able to set a Theme the Player picker will not offer.
- **All three** controls use `themesForEditionIncluding(current)`, which adds an already-set off-Edition Theme to the front of the list. Narrowing what may be picked must not misreport what is set—a `<select>` whose `value` matches no `<option>` renders the first one instead, which would show a Day as a Theme it is not. The player switcher needs this most, not least: `ThemeContext` validates a saved pick against the whole registry, so an off-Edition preference is still *applied*, and a plain scoped list would leave the player wearing that skin with Auto inactive and no chip marked. The preference is kept, never cleared—clearing is a destructive fix for a display bug, and a player who moves between Editions on one device would silently lose their pick.
- `defaultThemeForEdition(edition?)` is the last resort in the chain player pick → Event `defaultTheme` → Edition default. `gcb` resolves to `neon-playground`; `vacay` to `the-birds`, its Day 1 Theme; `fiveacross` to `marquee`, its doors-open Theme (#617). It matters most where the chain is shortest: the signed-out shell reads no Event doc (`useEventDoc(false)`), so this line alone decides what a Vacay build wears on the pre-auth surface [ADR 0009](../docs/adr/0009-event-resolved-from-hostname.md) requires to be Edition-correct. Every Edition's default must be pickable on its own Edition, or a fresh device opens the switcher with no chip active.

## WCAG AA contrast contract

Every `[data-theme]` block meets WCAG 2.1 AA across the foreground/background token pairs `src/index.css` assigns as literal `color` values (the flat custom-property value, not whatever else may be layered underneath at paint time—see `specs/theme-on-color-contrast.md` for the composited-surface checks). Every one of `--ink`/`--dim`/`--accent` is used as a real text fill somewhere in `src/index.css`—not only as a border or glow—so every pair meets the 4.5:1 normal-text minimum (1.4.3 Contrast (Minimum)); a looser 3:1 non-text/UI-component floor (1.4.11) does not apply to any of them because none is text-free:

- `--ink`/`--dim` against the surfaces they render on: `--ink` on `--bg`, `--panel`, `--cell`; `--dim` on `--bg`, `--panel`.
- `--primary` on `--panel` (`.row .rank`, leaderboard rank numbers).
- `--accent` on `--cell` (`.cell.free` text) and on `--panel` (`.badge`).

Border- and glow-only call sites that reuse these same custom-property values (`.btn.primary` / `.chip.active` / `.seg-btn.on` borders, `.btn` border, `.cell.free` / `.row.leader` borders) are covered for free since they share the checked fg/bg pair—no separate weaker check is needed.

**Retired: "gradient-tinted backdrops are not checked."** This contract used to check `--primary`/`--secondary` against the flat `--bg` token only and explicitly did not check the real composited backdrop `body`'s two radial-gradient tints produce behind `.brand b` / `.bingo-head span` (the B-I-N-G-O header) / `.count b`—a documented bound, since those three used `--primary`/`--secondary` as literal text fills directly on that tinted surface. Issue #72 (`specs/theme-on-color-contrast.md`) retired this bound: all three now fill with `--ink` instead (decoupled from the tint they used to sit on and self-referentially fail against), checked against the composited backdrop at its actual maximum tint strength in every Theme. `--primary`/`--secondary` are no longer used as literal text fills directly on `--bg` anywhere in `src/index.css`, so those pairs are dropped from the table above; `--primary` still backs `.row .rank`'s text on `--panel` (unaffected by the tint, kept above) and various border/box-shadow-only call sites at their own looser floor.

## Acceptance criteria

- **Given** any Theme in the registry, **when** it is applied, **then** every pair above meets the WCAG AA 4.5:1 threshold. Editions do not narrow this: a Theme is audited because it is in `THEMES`, not because it is pickable here. **Light Themes are audited identically**—`summer-white` and `fog-froth-farewells` are light-ground and earn their place on the same numbers, which is why the wireframe's sketch palette for the latter had to be darkened on three tokens before it could ship.
- **Given** a build with no Event doc resolved yet, **when** the signed-out shell renders, **then** it wears its Edition's default Theme rather than another Edition's.
- **Given** a Player picks a Theme, **when** they reload, **then** the pick persists (`localStorage['gcb.theme']`) and is not overridden by the event/player default.
- **Given** a Player switches Themes, **when** they tap a chip, **then** `document.documentElement.dataset.theme` reflects the new Theme well under the 5s PRD budget.
- **Given** no saved pick and no resolved event/player default yet, **when** the app first mounts, **then** Neon Playground (`neon-playground`) is the active Theme.
- **Given** any Theme's metadata, **when** its label is read, **then** it names no Atlantis mark, trademark, or affiliation.
- **Given** a Player or Admin on one Edition, **when** any Theme picker renders, **then** it offers only that Edition's Themes—plus the currently-set Theme if that one is off-Edition—and never another Edition's.
- **Given** a Theme set on a Day or as `defaultTheme`, **when** it belongs to another Edition, **then** the admin control still displays it as the current value rather than silently showing a different Theme.
- **Given** a platform-chrome Theme (`ThemeMeta.chrome`, #882), **when** any Day/`defaultTheme` picker renders on any Edition, **then** it is never offered—even on the Edition it is `THEME_EDITIONS`-bound to—while `THEMES` lookups by id (`Leaderboard`, `dayIdentity`, `DaySwitcher`, `Board`) and the WCAG contrast audit still cover it exactly like an ordinary Theme.

## Test coverage

`src/theme/w1-themes.test.tsx` (Vitest, jsdom project):

- Parses `themes.css` at test time (no hand-transcribed color table) and asserts every `ThemeId` has a `[data-theme]` block, then computes the WCAG relative-luminance contrast ratio for each pair above per Theme. The luminance/contrast math and the `themes.css` parser live in `src/theme/contrast.ts` (extracted by issue #72) and are shared with `src/theme/theme-on-color-contrast.test.tsx` below.
- Exercises `ThemeProvider`/`useTheme` through a minimal probe component: an explicit pick persists to `gcb.theme` and applies to `<html data-theme>` within the 5s budget; the initial default is never auto-saved; an async-arriving `defaultTheme` prop change (simulating the Firestore event/player default resolving after mount) is adopted when no pick was saved, and is ignored once a pick exists.
- Asserts `THEMES[0].id === 'neon-playground'` and that no `label` matches an Atlantis mark or a trademark glyph.
- Pins the Edition scoping: the `vacay` pick list is exactly the three Bodega Themes and the `fiveacross` pick list is exactly the three Five Across Themes (`marquee` / `confetti-hour` / `afterglow`—`fiveacross-slate` is chrome and stays out); each of the thirteen legacy party Themes is named and asserted absent from both; the three Editions **partition the pickable (non-chrome) registry** pairwise with no overlap and nothing left out (the guard that makes an undeclared Theme fail rather than leak); an unrecognised Edition falls back to `gcb`; and `setActiveEdition` changes what the no-argument call returns.
- Pins the platform-chrome exclusion (#882): `fiveacross-slate` is in the registry (`THEMES`, flagged `chrome: true`) and WCAG-audited by the suite above, but absent from every Edition's `themesForEdition` output—including `fiveacross`, the Edition it is `THEME_EDITIONS`-bound to—and from the unrecognised-Edition fallback; `themesForEditionIncluding` still surfaces it, prepended, if a stored value ever names it (the same defense an ordinary off-Edition Theme gets).
- Pins `themesForEditionIncluding`: an off-Edition current Theme is prepended, an in-scope one is not duplicated, and no current Theme yields the plain scoped list.
- Pins `defaultThemeForEdition`: the legacy default is unchanged, Vacay and Five Across each get their own, an unknown Edition falls back, the no-argument call follows the active Edition, and every Edition's default is pickable on that Edition.

`src/theme/theme-on-color-contrast.test.tsx` derives "is this Theme light?" from its own tokens (`--bg` lighter than `--ink`) rather than naming `summer-white`. That assumption was hardcoded until `fog-froth-farewells` became the second light Theme and broke it; deriving it means the next light Theme is covered rather than silently exempted, and the mirror case—a dark Theme's `--ink` over a light page—is now documented alongside the original.

`src/theme/theme-on-color-contrast.test.tsx` covers the composited-surface checks this contract's "Retired" note above references (`--on-gradient` vs both `.cell.marked` gradient endpoints, `--ink` vs the composited `body`/`.celebrate`/`.share-card` backdrops, the no-hardcoded-`#fff` source pin)—see `specs/theme-on-color-contrast.md`.
