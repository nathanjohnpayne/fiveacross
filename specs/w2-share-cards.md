# w2-share-cards—on-device BINGO + Leaderboard Share Cards, native share sheet, ADR 0005

A Share Card is a retina image a Player generates on their own device—for a BINGO/Blackout win or the Leaderboard—to drop into the group chat (ADR 0005). Before this ticket (issue #36), the only share affordance was `Celebration.tsx`'s "Share" button, which shared *text and a URL* (`navigator.share({ title, text, url })`, falling back to the clipboard), and the Leaderboard had no share affordance at all. This ticket replaces that with an on-device image—canvas-free DOM rasterization via `html-to-image`—handed to `navigator.share({ files })` so the native share sheet carries the picture itself into the chat, plus a matching secondary affordance on the Leaderboard. Per ADR 0005 this ships **BINGO + Leaderboard Share Cards only** (no per-square proof cards—a Proof already carries its own shareable media) and stays entirely **behind the auth wall**: no server render, no public URL.

## Text-message-first redesign (issue #423)

The card composition below was reworked for readability at iMessage-bubble size: an image dropped into a group chat displays ~300px wide, where 25 cells of prompt text turn to gray noise. The rule is **the word and the name are the picture; the board is shape, not data**. The pipeline is untouched—same `html-to-image` render, same off-screen host, same `[data-theme]` inheritance, same `shareCardBlob` fallback chain, same eager pre-render, same `share_click` analytics, same 25-cell validity gate. Only the DOM the two builders emit (and its CSS) changed. The parity reference is `plans/daily-cards-wireframes.html` § "Share Cards—text-message-first redesign"—frames `#frame-share-bingo`, `#frame-share-blackout`, `#frame-share-leaderboard`. In shorthand:

- **BINGO/Blackout**: a context line (`<event> · Day N · <place>`), a giant `BINGO!`/`BLACKOUT` title, the Player name in the theme accent, then the 5×5 board—marked squares fill with the theme gradient, the **newest** completed line is lit brighter (`.line`: `--ink` outline + `--primary` glow), the free centre stays accent, a `pending` square reads faded/dashed—then a single stat line (`Bingo #N · M squares · <night>` / `All 24 squares · <night>`) and hairline footer branding. A 2px `--primary` border rings the card.
- **Leaderboard**: title `LEADERBOARD`, the top three as a **podium** (rank baked into the bar, the ★ First-BINGO pin above its holder, name + bingo count), ranks 4–10 as compact rows, a `Through Day N of <total>` snapshot-dating line, footer branding.

Two new optional fields—`contextLine?` and `statLine?` on both card data types—carry the composed copy; the renderer stays dumb and derives none of it. `Board.tsx` composes the BINGO lines (it holds the win's Day and the Player's stats) and `Leaderboard.tsx` composes the Leaderboard lines. Absent, `contextLine` falls back to the bare `eventName` and `statLine` renders nothing. The winning-line highlight needs no new caller data: it is derived inside the builder from the cells' own `markedAt` (the newest completed line = the one whose latest-marked cell has the greatest `markedAt`; ties glow together). Resolved decisions: **newest line only** (not every completed line), **cap the Leaderboard card at ten ranked rows** (`MAX_SHARE_ROWS = 10`; issue #444 raised it from #423's five)—with the First-BINGO pin still appended when its holder falls outside the top ten, so the honored Player never silently drops off the card (§ Design decisions: "The pin can't silently fall off the card"), i.e. at most eleven rows and only in that edge case—and **match the frame copy exactly**.

## Final standings: the farewell podium as a card (issue #449)

A third card kind—still no per-square proof cards, still entirely on-device behind the auth wall (the ADR 0005 boundary this spec's "only BINGO + Leaderboard" scoping was actually protecting). `renderFarewellShareCard({ eventName, champion, firstBingo, honors, contextLine?, statLine? })` renders the FROZEN farewell podium (`specs/d15-finale.md`): a `FINAL STANDINGS` title, the 🏆 champion and 👑 First to BINGO as labeled honoree blocks (names one-line-clamped—two blocks plus ten rows leave no wrap budget in the fixed frame), the ten daily honors as day-label-vs-name rows (honor names ellipsize; day labels stay whole), the caller-composed context/stat lines, and footer branding. The renderer stays dumb: `FarewellPodium.tsx` shapes the `Podium` payload (labels resolved via its own `dayLabel` mapper, statLine `Final standings · N days`)—same caller-shapes rule as the Leaderboard card. The share affordance is a full-width "Share final standings" button at the BOTTOM of the on-page podium section (`.farewell-podium-actions`), rendered eagerly once sharing is ready and warmed on intent thereafter (§ Eager pre-render (1a); hover/focus/press warms; the warmed promise is keyed on the serialized card payload, not the roster array's identity, because Board re-filters `players` every snapshot while the frozen podium rarely changes), degrading through the same `shareCardBlob` chain, firing `track('share_click', { surface: 'farewell' })` from a `finally`. The presentational `FarewellPodiumView` takes the affordance as an optional `share` prop, so fixture-driven tests without the wrapper render no button. Two Codex P2s on PR #450 shaped the data flow: the event reaches the wrapper as **Board's own prop**, never a second `useEventDoc()` subscription (Board's `frozenAt` gate guarantees it is loaded; a second listener would start `null` and let an early tap bake the bare-app-name card—the PR #111 props-not-listeners lineage), and the share affordance is **withheld until `dayMetasLoaded`** (buildPodium deliberately omits derived honors while day-meta listeners are answering, so sharing earlier would bake a permanently incomplete honors list; the podium itself still renders).

**Photo-hero composition (#534/#561, `specs/most-loved-photo.md`).** One surface, two compositions (wireframes `fx-share-final-photo-*`): when the Event's frozen Most-Loved Photo award has a winner that survives the live display gate, the same `renderFarewellShareCard` call renders the photo-hero variant—`data.mostLoved` (`photoUrl` = an already-fetched blob object URL, the FROZEN `heartCount`, a fully composed `creditLine` with the `shared with` tie suffix) plus `data.runnersUp` (standings rows 2-3 from `buildPodium().runnersUp`) drive a 500x276 letterboxed hero box (badge `📷 Most-loved photo`, frozen ❤ chip), the credit line, and the compressed ranked rows; the daily honors yield their space and stay on the photo-less card, which remains the documented fallback for no award, `winners: []`, a hidden winner, or any media failure — a failed or timed-out fetch, a failed `img.decode()` (the renderer awaits it where available and rebuilds photo-less on failure), **or a throwing `URL.createObjectURL` (#660)**. That last one is minting, not fetching, and it used to sit outside the render `try`, so the throw escaped to the warmed promise's `.catch(() => null)` and resolved the whole card to `null` — no PNG for the share sheet at all, strictly worse than the photo-less card. Every media step now degrades to the same composition: the contract is that a hero which cannot be produced costs the hero, never the card. The slug, share title, and share button do not fork. `FarewellPodium.tsx` owns the mechanics: `useProofFeed(500)` supplies the display join (opened only when the persisted award exists), the hero's bytes go fetch → blob → object URL (a plain proof-media `<img>` is opaque/no-cors, unreadable to html-to-image) with an 8s timeout and the object URL revoked after rasterization, the warm cache keys on the winner `proofId` rather than the per-fetch object URL, and the share gate additionally waits for the proofs when the award names winners. Full award semantics, eligibility, and the never-recomputes rule live in `specs/most-loved-photo.md`.

**The hero's decode is bounded, and the tie suffix counts the true tie (#661, #659).** Two corrections to the composition above. First, the `img.decode()` the renderer awaits is now wrapped in the same `Promise.race` bound the fetch already had (`HERO_IMAGE_DECODE_TIMEOUT_MS`, `src/components/ShareCard.tsx`): a decode that STALLS—not just one that rejects—lands on the photo-less composition, because an unbounded await there wedged the warmed promise and any tap behind it forever, defeating the fetch bound sitting right in front of it. Second, the `creditLine`'s `shared with` suffix counts from the award's `winnerCount` (the true tied cardinality) rather than the length of its deliberately bounded 100-entry `winners` prefix, and stops naming individual co-winners once that prefix is known to be truncated. `specs/most-loved-photo.md` § The share credit line reports the TRUE tie is canonical for the exact wording in each case.

## Emoji are isolated from shared text runs before rasterization (issue #603)

html-to-image rasterizes through an SVG `<foreignObject>`, and that pass can shape an emoji differently from the live document — observed in desktop Chrome as the shipped "Day 4 🌊alletta" defect: the emoji paints displaced over neighbouring characters, or an emoji-bearing letter-spaced line re-wraps in the raster and overpaints its sibling. The fix is structural, not font-based: every text the card renders goes through `el()` → `appendEmojiIsolatedText`, which splits the string into emoji/non-emoji runs (`segmentEmojiRuns`, `src/format.ts` — grapheme-segmented so flags and ZWJ sequences stay whole) and wraps each emoji run in its own `display: inline-block` `.emoji-run` span. The raster clone inlines that box's computed width, freezing the emoji's advance at its live value, so however the raster pass shapes the glyph it cannot displace the surrounding text. The same treatment is available to on-page surfaces subject to the bug-report screenshot capture (the other `html-to-image` consumer) via `components/EmojiText.tsx`, applied to the farewell podium's honor-day labels and the Leaderboard's day chips. Pinned by a structural jsdom test (`w2-share-cards.test.tsx`) and a real render measurement (`tests/e2e/emoji-raster.spec.ts`, headed real Chrome — the only environment where the defect manifests; it skips elsewhere).

## BINGO-card polish: glow, hyphenation, dead band (issue #449)

Three Day-10 oddities from a real column win, fixed in CSS: **(1)** `.share-card-cell.line`'s glow drops 18px → 8px—five ADJACENT 18px glows on a column/row win merged into one solid hot bar down the grid; 8px keeps a per-tile halo. **(2)** The cell wrapping pair becomes hyphenate-first: `overflow-wrap: break-word; hyphens: auto;` instead of the on-page `.cell`'s `word-break: break-word`—Chrome treats `word-break: break-word` as break-anywhere and skips hyphenation, which printed raw mid-word breaks ("sunglasse s") on real cards; `overflow-wrap` lets `hyphens: auto` place a real hyphen first and hard-breaks only tokens with no hyphenation point, with `fitCellText` still the measured backstop. **(3)** `.share-card-player` loses its two-line `min-height` reserve—it left a dead 52px band between a one-line name and the grid; the frame's slack now pools above the footer (its `margin-top: auto`), and a two-line name still fits because the height budget was always computed with both lines.

## Turned-over squares carry their text; the leaderboard runs to ten (issue #444)

Two refinements to the #423 composition, keeping the pipeline and the text-message-first rule intact. First, the all-textless board rule is narrowed: **marked squares (free centre included) render their prompt text again**—small (`9px` at card scale, legible on pinch-to-zoom), `--on-gradient` over the gradient fill and `--ink` on the free centre's accent wash, with a wrapping pair so a long unbroken token wraps instead of vanishing (originally the on-page `word-break`/`hyphens` pair; issue #449 revised it to hyphenate-first `overflow-wrap`/`hyphens`—§ BINGO-card polish)—while **unmarked squares stay textless**, so the board still reads as shape at iMessage-bubble size and never regresses to the pre-#423 25-cells-of-gray-noise look. The renderer writes text only into turned-over cells (`c.free || c.marked`). Second, the Leaderboard card cap rises to `MAX_SHARE_ROWS = 10` (five left the fixed frame looking bare): the renderer's podium/rows split is unchanged, but the compact rows are compressed—smaller type, tighter gaps, single-line name clamp (podium names keep their two-line clamp)—and the podium bars shed a step (104/76/52) so the worst-case frame (a 2-line context line, a 2-line podium name, eight compact rows incl. an appended pin, stat + footer) stays inside the fixed 750px height.

## The change

- **`src/components/ShareCard.tsx` (new)**—the on-device renderer. Two data-in/blob-out entry points:
  - `renderBingoShareCard({ kind, playerName, eventName, cells, contextLine?, statLine? }): Promise<Blob>`—a BINGO/Blackout card: the context line (or bare event name when absent), a big BINGO!/BLACKOUT title, the Player name, the Player's own 25-cell grid (free/marked cells styled distinctly, the newest completed line lit brighter via `.line`, a `pending`-marked cell styled distinctly again—see § Pending squares below), and the optional stat line. Prompt text renders on the **turned-over** squares only—unmarked squares stay textless (issue #444, narrowing #423's all-textless rule—§ Turned-over squares above). Refuses to render anything but a real 25-cell board—see § Empty-card race below.
  - `renderLeaderboardShareCard({ eventName, rows, contextLine?, statLine? }): Promise<Blob>`—a Leaderboard card: the context line (or bare event name), a "LEADERBOARD" title, the given rows laid out as a **podium** for the first three (rank baked into the bar, ★ First-BINGO pin above whichever is flagged `firstToBingo`) and compact rows for the rest, and the optional stat line. `rows` is already the exact list to render—shaping (which Players, how many, whether the pin needs to be force-included) is the caller's job, not the renderer's; the renderer only decides layout (podium vs. rows).
  - Both build a real, off-screen `<div class="share-card ...">` node with plain `document.createElement` calls (no second React root), mount it via a `.share-card-host` wrapper (real layout so html-to-image can measure it, but `position: fixed; left: -10000px` so it's never visible or part of normal flow), rasterize with `html-to-image`'s `toBlob(node, { pixelRatio: 3 })`, then tear the host down. Because the card is just another node under `document.body`, it automatically inherits whichever `[data-theme='…']` CSS variables `ThemeContext` currently has set on `<html>`—"themed via the CSS variables in play" comes for free from the cascade, not a second copy of the palette.
  - `shareCardBlob({ blob, filename, title, text, url })`—the shared native-share-sheet + fallback chain BOTH `Celebration.tsx` and `Leaderboard.tsx` call, so the degrade path lives once, not twice: hands the blob to `navigator.share({ files })` when `navigator.canShare({ files })` says yes; otherwise falls back, in order, through a text/URL `navigator.share`, the clipboard (`navigator.clipboard.writeText(url)`), then a direct file download (`<a download>` on an object URL). Never throws—every branch self-catches—so callers can await it without their own try/catch. `blob: null` (an on-device render failure, including the validity gate above) simply skips the file-share and download legs. A cancelled share is terminal on BOTH legs, but detected differently—see § Cancellation vs. failure below.
- **`src/components/Board.tsx`**—hands its own already-loaded `cells` AND its already-resolved display identity to `<Celebration>` as props, plus (issue #423) the composed `contextLine`/`statLine` it builds from the win's Day (port, night) and the Player's stats (`bingoCount`, `countMarked(cells)`)—data it already holds. See § Empty-card race and § Stale-name race below for why the `cells`/`playerName` props exist, and § Text-message-first redesign for the copy props.
- **`src/components/Celebration.tsx`**—eagerly pre-renders the BINGO/Blackout card at mount (§ Eager pre-render below) via `renderBingoShareCard` with the rejection caught into a cached `Promise<Blob | null>` (a render failure—including the validity gate rejecting a non-25-cell board—degrades gracefully to the text/URL share leg rather than throwing or sharing a bad image); the `share` handler awaits that cached promise and hands the blob to `shareCardBlob`. `track('share_click', { surface: 'celebration' })` fires from a `finally`, exactly once, on every path (image share, cancelled share, every fallback leg, or a render failure). Card content: the board `cells` and the resolved Player name come from Board.tsx's own props, not Celebration-local listeners (§ Empty-card race, § Stale-name race); only the Event name still resolves via `useEventDoc`—it is not identity (no per-user staleness to leak) and has the benign app-name fallback the "falls back to the app name" test pins. The Share button is disabled while `playerName` is null (identity not yet known).
- **`src/components/Leaderboard.tsx`**—a new "Share leaderboard" button (`.lb-actions`, a full-width action below the ranked list—#174 moved it there from its original spot above the filter row, where it read as wedged between the theme carousel and the filters) calls `shareLeaderboard`, which shapes the current roster into `LeaderboardShareRow[]` via the new `buildShareStandings` helper (top `MAX_SHARE_ROWS = 10` by rank plus the pin), composes the `contextLine`/`statLine` from the event schedule (issue #423—the current Day's port + a `Through Day N of <total>` stamp), renders the card—reusing the warm-on-intent pre-render started by hover/focus/press when its inputs still match (§ Eager pre-render)—and hands it to `shareCardBlob`. `track('share_click', { surface: 'leaderboard' })` fires from a `finally`, mirroring Celebration's shape.
- **`src/index.css`**—new blocks: `.lb-actions`/`.lb-actions .btn` (the Share button's own layout—a full-width action below the ranked list per #174, distinct from `.lb-filters`), `.lb-empty` (the compact empty-filter message, kept off the 70vh `.center` so the below-list CTA stays reachable—#174), and `.share-card*`/`.share-card-host` (the off-screen card's own visual language—deliberately its own class family, not a reuse of `.grid`/`.cell`/`.row`, so this ticket's `index.css` ownership this wave can't collide with any other in-flight ticket's styling of the on-screen Board/Leaderboard). `.share-card-cell.pending` and `.share-card-title`'s ink-token fill are later additions—see § Pending squares and § Title contrast below.
- **`package.json`/`package-lock.json`**—adds `html-to-image` as a regular dependency (it ships in the app bundle, not a build-time-only tool).

## Design decisions

- **Plain DOM construction, not a second React root.** `html-to-image` needs one real, already-laid-out element to walk and inline computed styles from. Standing up a second `react-dom/client` root (or `react-dom/server`'s `renderToStaticMarkup`) just to produce one throwaway node would add React lifecycle/`act()` complexity (and, for the server-render path, a Node-oriented dependency this Vite SPA doesn't otherwise need) for no benefit over `document.createElement`. This also mirrors the rest of the app's own image work—`data/storage.ts`'s `downscaleImage` reaches for raw `<canvas>`/DOM APIs, not React, for its one-shot image transform.
- **The card inherits the live theme for free.** Because the off-screen host is mounted under `document.body` (not a detached, never-attached node), it sits inside the same `[data-theme='…']` cascade `ThemeContext.tsx` already applies to `<html>` (`src/theme/ThemeContext.tsx:62`). No explicit `ThemeId` needs to be threaded into `ShareCard.tsx`—the card simply uses `var(--primary)`/`var(--bg)`/etc. like every other themed surface, and it renders in whatever theme the Player is currently using.
- **The renderer takes shaped data; the caller does the shaping.** `ShareCard.tsx` knows nothing about `sortPlayers`, the presentational leaderboard filter, or how "top standings" is defined—it only knows how to lay out whatever `LeaderboardShareRow[]` it's given (as a podium for the first three, compact rows for the rest). `Leaderboard.tsx` owns `buildShareStandings` (top `MAX_SHARE_ROWS` by rank—10 since issue #444; 5 under #423's redesign before that—plus the First to BINGO Player appended if their rank falls outside that slice) because that's presentation policy specific to the Leaderboard, exactly like `matchesFilter` already is (`specs/w2-leaderboard.md`). This keeps the renderer reusable and keeps ranking/pin logic in one place (never duplicated into the renderer as a second, potentially-divergent calculation).
- **The pin can't silently fall off the card.** `buildShareStandings` appends the First to BINGO Player as an extra row when their rank is outside the top `MAX_SHARE_ROWS`—mirroring the live Leaderboard's own principle (`specs/w2-leaderboard.md`: bingo-count rank and earliest-`firstBingoAt` are independent signals, so the pin holder is not guaranteed to be a top-ranked Player). Without this, a fixed-size card could cut the honoured Player off entirely just because they stopped playing after their early win while others racked up more bingos later.
- **The Share Card always reflects the FULL roster, never the active filter.** `shareLeaderboard` reads `players` (the full, already-ranked list) and the same `firstBingoUid` the pin badge uses—not the filtered `visible` subset. Sharing while "Blackout" is selected still shares the real top standings, not just the Blackout achievers; this mirrors the pin's own full-roster scope (`specs/w2-leaderboard.md`) and avoids a confusing card whose contents silently shift with whatever filter a Player happened to have open.
- **A cancelled native file share does not cascade into more fallbacks.** `shareCardBlob` treats a caught error from `navigator.share({ files })` as `'cancelled'` and stops—it does not then also try a text share, the clipboard, or a download. A Player who explicitly dismissed the OS share sheet should not be handed a second, different share prompt (or a surprise clipboard write / file download) immediately after declining the first. The fallback chain (text → clipboard → download) is reserved for when file sharing wasn't *available* in the first place, not for when it was available and refused.
- **No per-square proof cards (ADR 0005).** The card kinds are aggregate surfaces only—`renderBingoShareCard`, `renderLeaderboardShareCard`, and (since issue #449) `renderFarewellShareCard`—never a per-square proof card; `ProofSheet.tsx`/`ProofFeed.tsx` are untouched (off-limits this wave in any case).

## Empty-card race: `cells` is now a prop, not a second listener (Codex P2, PR #111 finding 1)

Post-review, Codex flagged that `Celebration.tsx` opened its OWN `useBoard(uid)` listener and read `board?.cells ?? []` for the card—a subscription that starts with `data: undefined` until its first snapshot arrives. `Board.tsx` already has the loaded Board by the time it ever renders `<Celebration>` (the `!board` early-return guarantees it), but Celebration's second listener does not inherit that guarantee—it starts fresh on mount. A Player who tapped Share fast enough to beat Celebration's own first snapshot rendered and shared a card with the free center only, or nothing at all: a ZERO-CELL card, not the honor-system win it claimed to depict.

**Fix.** `Board.tsx` hands its own `cells`—the exact array it just rendered the Board from—to `<Celebration>` as a `cells: Cell[]` prop; `Celebration.tsx` no longer calls `useBoard` at all. This removes the race structurally rather than papering over the timing: there is no second subscription left to lose. (Round 2 widened the same render call with the `playerName` identity prop—§ Stale-name race below—so `Board.tsx`'s footprint is now that one `<Celebration kind cells playerName onClose />` call, still with no change to Board's own gating, hooks, or render logic.)

**Backstop.** `renderBingoShareCard` refuses to rasterize a board that is not exactly 25 cells (`dealBoard`'s own invariant in `game/logic.ts`—free center + 24 prompts), throwing instead. `Celebration.tsx` catches that rejection into the cached pre-render promise as `blob: null` and falls through to `shareCardBlob`'s text/URL fallback leg—so even a future bug that hands Celebration a malformed board degrades to a text share rather than ever producing or sharing an empty/partial image.

## Stale-name race: `playerName` is now a prop, not a second listener (Codex P2, PR #111 round 2 finding 1)

The identity twin of the empty-card race above, flagged by Codex in round 2. `Celebration.tsx` still ran its own `useMyPlayer(uid)` listener and resolved the card's name as `resolveDisplayName(player, user?.displayName)`—a subscription that starts `data: null` on mount, making the resolver fall back to the live AUTH name until the first snapshot arrives. An immediate Share tap therefore rendered and shared the STALE Google name for a returning Player with a saved custom name—the exact window in which `Board.tsx`'s `doMark` deliberately withholds the name from Tally markers (`displayName: identityKnown ? displayName : undefined`, Codex P2, PR #87) and the Moment broadcasts HOLD (PR #99 finding 1).

**Fix.** `Board.tsx` passes its own already-resolved identity down: `playerName={identityKnown ? displayName : null}`—the SAME single `resolveDisplayName(player, user?.displayName)` output the Tally marker, Proof attribution, and Moment broadcasts carry, gated by the SAME `identityKnown` tri-state. `Celebration.tsx` drops `useAuth`, `useMyPlayer`, and its own `resolveDisplayName` call entirely; there is no second identity resolution left to race. The card renders no avatar (`BingoShareCardData` has no photo field), so only the name is threaded.

**The `null` gate, and why it is reachable.** `playerName: null` means the saved identity is not yet KNOWN, and Celebration disables the Share button (and skips the pre-render) until it resolves—holding, like the Moment broadcasts, rather than ever stamping the auth fallback onto a card. In every online flow this gate is belt-and-braces: the player-row subscription resolves at app start, long before a Board can render and a win can be marked, so `identityKnown` is true by the time Celebration can open. The reachable-null window is the one Board.tsx already documents for `knownFirstBingoAt` (Codex P2, PR #75/#87/#99): an offline reload whose ADR 0006 persistent cache holds the board but not the player row—the celebration still opens (the win animation is local UI, never held), the Player can keep playing, and Share enables when the row resolves (on reconnect). Accepted residual: in that offline window the Share affordance stays disabled rather than degrading to an 'Anonymous' card or the stale auth name.

## Eager pre-render: rasterization starts before the tap (Codex P2, PR #111 round 2 finding 2)

`navigator.share` may only run under transient user activation, and the activation a tap grants EXPIRES after a browser-defined window (~seconds). Round 1's share handlers started rasterizing at tap time and `await`ed the result before calling `navigator.share`—on a slow device a long rasterization could outlive the activation window, making the share call reject `NotAllowedError`, which the round-1 cancellation classifier treats as terminal: the tap did NOTHING—no sheet, no fallback, no feedback.

**Fix (Celebration—mount-eager).** The card's data is fixed the moment the modal opens (the `kind`/`cells`/`playerName` props plus the resolved event name), so `Celebration.tsx` starts `renderBingoShareCard` in a mount effect and caches the promise in a ref; the tap awaits the usually-already-settled cache and `navigator.share` runs within the activation window. The effect re-keys on the card's inputs, so a late-arriving Event name re-renders the card once rather than baking the fallback in. The `.catch(() => null)` lives INSIDE the cached promise—a render failure resolves null (degrading to the text/URL leg at tap time) and can never surface as an unhandled rejection when the Player closes with "Keep playing" and the blob is never consumed. Deliberate consequence: the card is now rasterized even when never shared—it stays on-device and unobserved (ADR 0005), and the "Keep playing" test pins that closing shares nothing and fires no analytics.

**Fix (Leaderboard—warm-on-intent, deliberately NOT mount-eager).** `Leaderboard.tsx` re-renders on every roster snapshot (any Player's Mark updates a player row), so a mount-eager render re-keyed on live data would re-rasterize per snapshot—real CPU/battery burn on phones for a card that is rarely shared. Instead the Share button warms the render when the Player signals intent—`onPointerEnter` (mouse hover, a real head start), `onFocus` (keyboard), `onPointerDown` (touch press, a small head start)—caching the promise keyed by its inputs (the roster array's identity + the resolved event name). The tap reuses the warmed promise only while those inputs still match; a roster that moved between warm-up and tap renders fresh at tap time, so the card never shows stale standings. Stated residual: that cold/stale-tap path keeps round-1 timing, so a very slow device can still expire the activation window there—rare, and strictly no worse than before this fix.

**The `NotAllowedError` decision, revisited honestly.** `NotAllowedError` is ambiguous by platform: some browsers report a user dismissal / declined permission that way, while an expired activation window rejects with the same name. The round-1 classifier (`isUserCancelledShare`) treats it as a cancellation that STOPS the chain, and round 2 KEEPS that behavior, with this rationale: the eager pre-render removed the main non-dismissal cause (a full tap-time rasterization inside the activation window), so a `NotAllowedError` reaching the classifier is now predominantly a real dismissal—and the residual failure mode (a rare do-nothing tap on a slow device whose warmed render was cold or stale) is strictly better than the alternative (clobbering the Player's clipboard or downloading a file right after they declined to share). `AbortError` remains the unambiguous, spec-mandated cancellation and always stops. Both stops are pinned by test.

**The blob-ready gate completes the design (Codex P2, PR #111 round 3 finding 1).** Pre-starting the render narrowed the race but did not close it: a tap landing while the mount render was still UNSETTLED on a slow phone would await it inside the click handler and burn the activation window all the same—`NotAllowedError`, classified terminal, do-nothing tap. `Celebration.tsx` now tracks the cached render's settled state (`cardReady`, set when the mount promise resolves—with a promise-identity check so a STALE effect's settle cannot open the gate for a newer in-flight render) and keeps the Share button DISABLED until it settles, visually identical to the existing identity-gated disable. "Settled", deliberately not "blob exists": a failed or gate-refused render settles to `null` and still enables the button, so the text/URL fallback stays reachable—the gate must never dead-end the affordance. A tap can therefore only ever await an already-settled promise, keeping `navigator.share` inside its own activation window structurally. The Leaderboard deliberately gets NO equivalent gate (decided, stated): no render exists there until intent (warm-on-intent is the round-2 design), so disabled-until-settled would present a permanently disabled button that nothing warms—and a disable between `pointerdown` and `click` would swallow the very tap that warmed it. Its round-2 cold/stale-tap residual therefore stands, made rare by the warm-on-intent triggers.

**The farewell card's cold tap never waits, and the chain can no longer dead-end (Codex P1, PR #712).** The warm-on-intent residual stated above turned acute on the photo-hero farewell card (§ Final standings): its hero pipeline carries TWO generous per-stage bounds—an 8s fetch and, since #661, an 8s `img.decode()`—so a cold tap on a stalled hero could await up to sixteen seconds before reaching `navigator.share`, by which point the activation window had certainly closed. This took three rounds, and the two failed attempts are worth stating because they share one mistake. Round 1 bounded the decode: the HANG stopped, but the file leg reads any rejection as a dismissal, so the tap returned `'cancelled'` with nothing behind it. Round 2 bounded the TAP at four seconds and skipped the share legs on a dead activation, routing to the clipboard—but a four-second wait can still outlive the activation, and `clipboard.writeText` is activation-gated on Safari and Firefox, so with `blob: null` there was no download either and the chain returned `'none'`. **Each fallback depended on the very resource that had expired.** Round 3 fixes that in both directions: remove the wait, and end the chain in something that needs no activation at all.

**The acceptance property.** A tap NEVER results in a silent no-op. The Player ends up with a share sheet, a copied link, a downloaded image, or a visible affordance telling them what to do next—and the last of those is now a real leg, not a hope. It is pinned end to end, in the exact case that defeated rounds 1 and 2: stalled cold render, activation already spent, clipboard gated.

**(1) The tap does not wait at all.** `FarewellPodium.tsx` no longer races the render against a clock; it takes the warmed card only when that render has ALREADY SETTLED (tracked on the cached entry, `blob` valid only with `settled: true`), and otherwise passes `blob: null`—exactly what a failed render already produces. Nothing is awaited before `shareCardBlob`, so `navigator.share` is invoked in the SAME TURN as the gesture and the activation is unambiguously alive. This is the structural version of what round 2's budget only approximated, and it is the same rule Celebration's blob-ready gate enforces with a disabled button (the farewell button deliberately stays enabled instead: a link share is a fine outcome, and disabling the affordance is worse than degrading the payload). The cached promise keeps rasterizing, so a second tap gets the image.

**(1a) …which is why the farewell card is now rendered eagerly.** With no wait, a cold mobile tap would otherwise always lose the image—`onPointerDown` gives the render only the length of the press. So `FarewellPodium.tsx` starts ONE render as soon as `shareReady` is true, the Celebration treatment for the Celebration reason: the payload is FROZEN (`buildPodium` excludes the farewell Day's own marks; the award is a persisted record), so pre-rendering cannot bake in something a later snapshot would change. Deliberately ONE, guarded by a ref rather than a dep list, which caps the cost at a single fetch+rasterize even if the payload key later churns—so this does not become the per-snapshot re-rasterization the Leaderboard refused to take on. A post-eager key change falls back to warm-on-intent exactly as before.

**(2) An activation-aware chain.** `shareCardBlob` reads `navigator.userActivation` ONCE, before either share leg—`navigator.share` CONSUMES the activation, so a post-hoc read cannot tell an expiry apart from a call that ran normally—and when `isActive` is definitively `false` it SKIPS both share legs for the clipboard and download legs. This does not re-litigate the ambiguous rejection: it removes the ambiguity where the platform exposes the answer, since there is no dismissal to respect when no sheet can open. Browsers without the User Activation API report nothing and keep the previous behaviour exactly, so the guard costs the normal path nothing. Pinned by test: activation gone with a URL → clipboard; activation gone without one → download; activation alive → the file leg, unchanged.

**(3) A terminal leg that needs no activation—outcome `'prompt'`.** The clipboard is not activation-free (Safari and Firefox gate it), so (2) alone still dead-ended whenever there was no blob to download. `shareCardBlob` therefore ends in `showShareFallbackSheet`: a small sheet on `document.body` (`.share-fallback-backdrop`, reusing the app's `.sheet` vocabulary and theme tokens) carrying the link as selectable text plus the buttons the Player can press—"Copy link" where a Clipboard API exists, "Save image" where a blob does, "Close" always. It calls no gated API to appear; pressing a button is a FRESH gesture that mints FRESH activation, which is precisely what the silent write was missing. Only a call with genuinely nothing to offer (no URL and no image) still reports `'none'`. It is deliberately NOT shown after a real dismissal—`'cancelled'` stays terminal, so a Player who declined the OS sheet is not handed a second one.

## Pending squares render distinctly from confirmed marks (Codex P2, PR #111 finding 2)

In `admin_confirmed` claim mode a cell can be `marked: true` with `status: 'pending'`—the Player tapped it, but an Admin has not yet confirmed the Claim. `game/logic.ts`'s `markedMask` (and therefore `hasBingo`/`isBlackout`/`countMarked`) explicitly excludes `status: 'pending'` cells from counting as "on": `c.free || (c.marked && c.status !== 'pending')`. Before this fix, `buildBingoCardNode` rendered every `marked` cell identically (`.share-card-cell.marked`), so a Share Card could show more solid, confirmed-looking wins than the Player's stats actually credit—overstating unconfirmed squares exactly where the game logic itself withholds credit.

**Fix.** `buildBingoCardNode` now also applies a `.share-card-cell.pending` class when `c.status === 'pending'`, mirroring `Board.tsx`'s own on-screen treatment (`'cell' + ... + (c.status === 'pending' ? ' pending' : '')`)—a pending mark carries BOTH `.marked` and `.pending` together, never one instead of the other. The rule originally mirrored `.cell.pending`'s tile-level opacity; since issue #444 put prompt text on the tile, `.share-card-cell.pending` instead fades only the FILL (both gradient endpoints mixed toward `--bg`) with the text opaque on `--ink`—a whole-tile opacity would composite the text toward the card background and wash it out, worst on summer-white (Codex P2, PR #445)—so a pending square still reads as faded/dashed rather than a solid win, with its prompt legible.

**Long prompts fit the tile (Codex P2, PR #445).** The pool's prompt ceiling is 80 characters (`firestore.rules`), and a ~58px tile at the base 9px fits only ~50—`overflow: hidden` would clip the rest out of the rasterized image where pinch-to-zoom can't recover it. `buildBingoCardNode` applies length-tiered fit classes on turned-over cells—`.long` (>40 chars → 7px) and `.xlong` (>70 chars → 6px, sized against the tightest `.line`-bordered tile)—deterministic character thresholds rather than a measure-and-fit pass, since the card is a fixed frame.

## Cancellation vs. failure on the text/URL fallback leg (Codex P2, PR #111 finding 3)

`shareCardBlob`'s file-share leg (`navigator.share({ files })`) already treated ANY caught rejection as a Player cancellation and stopped the chain—deliberately: a Player who dismissed the native sheet should not be surprised with a second share prompt right after declining the first (the comment on that branch is unchanged and still applies). The text/URL leg (reached when file sharing is unsupported) did not make the same distinction: it caught every rejection—including a genuine `AbortError` cancellation—and unconditionally fell through to the clipboard/download legs. A Player who opened the OS share sheet on the text/URL leg and dismissed it would have their clipboard silently overwritten (or a file silently downloaded) immediately after declining to share.

**Fix.** A new `isUserCancelledShare` helper inspects the rejection's `name` for `AbortError` (the spec-mandated name for a user-cancelled Web Share API call) or `NotAllowedError` (some browsers report a declined permission/dismissal this way—an ambiguity round 2 revisits and resolves in § Eager pre-render above). On the text/URL leg specifically: a cancellation now returns `'cancelled'` and stops, matching the file leg's Player-respecting behavior; any OTHER rejection (a genuine failure—the API existed but something actually went wrong) still falls through to the clipboard, then the download, as before.

**Neither leg runs at all when the activation is already gone (Codex P1, PR #712).** The classifier only ever sees a rejection; when `navigator.userActivation.isActive` reports `false` before the call, that rejection is a foregone conclusion and the respect-the-dismissal rule has nothing to respect—the chain skips both share legs for the clipboard/download legs instead, and ends in the activation-free `'prompt'` sheet when even those cannot fire. See § Eager pre-render for the full rationale, the no-wait farewell tap, and the terminal affordance.

**`share_click` still fires on every path, cancelled or not.** Both call sites (`Celebration.tsx`, `Leaderboard.tsx`) fire `track('share_click', { surface })` from a `finally` around the whole `shareCardBlob` call—unconditionally, once per tap, regardless of `shareCardBlob`'s return value. That contract is unchanged by this fix and is the intended, documented behavior: `share_click` measures the Player's intent to share (they tapped Share), not the outcome, so a cancelled share still counts as a click. `shareCardBlob`'s return value (`'files' | 'text' | 'clipboard' | 'download' | 'cancelled' | 'prompt' | 'none'`) is what distinguishes outcomes for any caller that cares; the analytics event deliberately does not fork on it.

## Title contrast: `.share-card-title` follows the theme ink, not hardcoded white (Codex P2, PR #111 finding 4)

`.share-card-title` filled its text with a hardcoded `color: #fff`—invisible against `summer-white`'s light `--bg` (`#f6f1e7`), the one Theme (of 8) with a light background. This is the same failure mode issue #71 already found and fixed for the (since-removed, #39/ADR 0005) Cloud Run OG renderer's own `.title` rule (hardcoded `#fff` measured ~1.13:1 against `summer-white`, far under WCAG AA's 4.5:1), which was fixed to fill with the theme's `ink` token instead.

**Fix.** `.share-card-title` now sets `color: var(--ink)`, mirroring that precedent. The `text-shadow: 0 0 14px #fff, ...` glow is left as `#fff` deliberately—it is a bloom/halo effect layered around the fill, not the fill itself (the same choice the OG renderer's own fixed `.title` rule made, keeping its glow white while switching only the `color`), and does not reintroduce a contrast failure the way the flat fill did. This fix—consuming an existing `themes.css` token from `index.css`—leaves `themes.css` itself untouched.

**Audited at the time, since fixed: `.share-card-cell.marked`'s hardcoded white.** The same share-card CSS block had one other hardcoded-`#fff` pair—`.share-card-cell.marked { color: #fff; border-color: #fff; ... }`—mirroring the app's own on-page `.cell.marked`. At the time this ticket shipped, that was a real, pre-existing, out-of-scope defect (alongside `.celebrate .big` and `.signin h1`) tracked as a follow-up by issue #72, deliberately left alone here rather than folded into this ticket's own scope; `.share-card-bhead span` had the analogous body-gradient-tint self-fill defect `specs/w1-themes.md`'s "Known bound" carve-out covered. Issue #72 (`specs/theme-on-color-contrast.md`) has since fixed both, the same way it fixed `.cell.marked`/`.celebrate .big`/`.signin h1`/`.brand b`/`.bingo-head span`/`.count b`: `--on-gradient` (new per-theme token) for `.share-card-cell.marked`'s text, `--ink` for its border, and `--ink` for `.share-card-bhead span`.

## Long unbroken prompts: wrapping parity is live again (Codex P3, PR #111 round 3 finding 2 → superseded by issue #423 → reinstated by issue #444)

Originally `.share-card-cell` hid overflow WITHOUT the on-screen `.cell`'s `word-break: break-word; hyphens: auto;`, so a long unbroken token lost most of its text on the shared image; the fix copied that wrapping pair onto `.share-card-cell`. The text-message-first redesign (issue #423) removed the cause entirely by making the board textless. Issue #444 put prompt text back on the **turned-over** squares, so the wrapping pair is load-bearing again—and issue #449 revised it to hyphenate-first: `.share-card-cell` carries `overflow-wrap: break-word; hyphens: auto; overflow: hidden;` (pinned by the CSS source-parity test; see § BINGO-card polish for why `word-break: break-word` was wrong here), and the textless assertion narrows to the UNMARKED squares only.
