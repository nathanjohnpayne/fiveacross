# post-sailing-archive—freeze the Event, keep the Leaderboard and the First-to-BINGO hall of fame

Delivers the PRD's *"remember the winners"* end state (issue #134): after the occasion, an Admin freezes the Event, and the final Leaderboard standings plus the First-to-BINGO hall of fame persist unchanged from then on. `EventDoc.status` has been typed `'active' | 'archived'` since the schema contract landed, but nothing set it and nothing read it; this ticket makes it a real state with a real consequence on both sides—a durable record on the read side, and a server-enforced write denial on the other.

Honor-system-consistent throughout ([ADR 0001](../docs/adr/0001-honor-system-trust-model.md)). The archive **snapshots** the client-authoritative standings; it never recomputes, re-derives or "verifies" them. Archiving is a per-Event state transition, not a migration: the data model is already event-scoped ([ADR 0003](../docs/adr/0003-pool-is-pre-cruise.md)), a future occasion is a NEW Event document, and an archived Event is never reset or reused.

## Contract

### The frozen record—`EventDoc.archivedAt` + `EventDoc.archive`

`src/domainTypes.d.ts` gains `archivedAt?: number` (the freeze stamp), `archive?: EventArchive` (the record), `archiving?: boolean` (the quiescing phase—see § "The quiesce protocol") and `archiveToken?: string` (WHICH quiescing phase), alongside `ArchivedStandingRow`, `ArchivedFirstBingo`, `ArchivedDayHonor` and `EventArchive` itself. All four Event fields are ABSENT until the Event is archived (or mid-archive) and pass through `eventConverter` untouched, exactly as `frozenAt` and `mostLovedPhoto` do—inventing a default could only ever manufacture an archive that was never taken, or shut an Event nobody shut.

`EventArchive` carries the final `standings` (already ranked, ban-filtered, in Leaderboard order), `playerCount` (the complete ban-filtered roster size), `firstBingo` (the Event-wide headline honour, or `null`), `firstBingoRow` (that holder's own standings row and true rank, or `null`), `dailyHonors` (each Day's own First to BINGO, each carrying the chip label it renders under), `eventName` (the Event's own name at the freeze, or `null`), `freezeAt` (the resolved Standings Freeze the snapshot cut on) and `archivedAt`.

`standings` retains a bounded prefix of `MAX_ARCHIVED_STANDING_ROWS` (200) rows while `playerCount` records the true cardinality—the `MostLovedPhotoAward.winners` / `winnerCount` pattern, for the same reason: the Event document has one 1 MiB budget that `days`, `bannedUids` and `mostLovedPhoto` already draw on, and an unbounded roster copy is the one field that could make it unwritable. Both live Events have two-figure rosters, so nothing is dropped in practice.

**`firstBingoRow` exists because the two bounds are independent.** The prefix is cut by RANK; the headline honour is decided by who bingoed EARLIEST. On a roster past the cap those can disagree completely—the holder can sit at rank 553 of 640, outside every retained row—and the Share Card's pinned eleventh row was built by searching `standings` alone, so it silently vanished from exactly the Event large enough to have truncated (Codex P2, PR #1139). The field carries the holder's whole row plus the rank they held in the COMPLETE standings, which the retained prefix has no way to recompute. It is `null` exactly when `firstBingo` is: the two are selected together, so a record with one and not the other is a half-built map the archived Share Card would read a hole from, and `completeArchiveRecord` refuses it on those terms.

**`eventName` is stored for the reason `ArchivedDayHonor.dayLabel` is** (Codex P2, PR #1139). The archived Share Card built its title and its context line from the LIVE `EventDoc.name`, and that field sits outside the write-once clause—which protects `status`, `archivedAt` and `archive` and deliberately nothing else—so an Admin renaming the Event afterwards silently re-titled a frozen card, and two people sharing the same standings a week apart got two different images of them. It is the only Event copy the archived surface consumes, which is why `name` came off that component's Event prop entirely, exactly as `days` did. `null` rather than a stand-in when the Event has no usable name: the card already falls back to the app's own name, and inventing one here would freeze a name nobody chose. Trimmed and bounded at `MAX_ARCHIVED_EVENT_NAME`—the same 100 the rows take, for the same reason, since `EventDoc.name` is admin-written and equally unvalidated at the rules boundary.

It is taken from the freeze's own TRANSACTIONAL read, and is deliberately outside `archiveSnapshotFingerprint`: the name decides nothing about which rows were read, so a rename mid-snapshot must not cost an archive attempt—and reading it from the document the write lands on is what keeps the record self-consistent regardless.

**`archivedAt` is named at arm's length from `frozenAt` on purpose,** the same discipline ADR 0011 applied to `standingsFreezeAt` versus `frozenAt`. `frozenAt` stamps the FINALE—competitive scoring stops, the podium computes, the closing Day opens, and the Event keeps running. `archivedAt` stamps the END—gameplay writes are denied at the rules boundary and the frozen record is what the Leaderboard renders. Two different events, hours or weeks apart.

**`EventDoc.status` is not `HostnameDoc.status`.** They are different fields with different value sets answering different questions for different audiences: the routing status (`'active' | 'disabled' | 'archived'`) decides ADDRESSING, world-readably, before first paint (`src/eventResolution.ts`, [ADR 0009](../docs/adr/0009-event-resolved-from-hostname.md)); the Event status decides BEHAVIOUR, after mount, behind `signedIn()`. An Event can be archived while its hostname is still perfectly servable—that is how a Player reaches the archive at all.

### The snapshot—`src/data/eventArchive.ts`

`buildEventArchive(...)` is pure, Firestore-free and React-free (the `src/data/finale.ts` precedent), so the freeze rules are unit-testable without an emulator or a mounted component. `isEventArchived(event)` is the ONE place the client asks whether an Event is frozen, so no surface invents its own spelling of the comparison; `isEventArchiving(event)` is the same discipline for the quiescing phase. Neither implies the other, on purpose—a closing Event has no record to render, so its Leaderboard stays live, while the archive write clears the flag as it lands.

The builder mirrors `src/components/Leaderboard.tsx` clause for clause, because the archive's promise is "the Leaderboard, kept":

- **Standings** are the ban-filtered roster in `sortPlayers` order—exactly the rows the live Leaderboard lists and the Share Card prints. Every number is COPIED off the Player-written `PlayerDoc`; a row whose root totals disagree with its own `dayStats` keeps its root totals, because the Player wrote both and the archive records what the Leaderboard showed rather than adjudicating between them (ADR 0001). The only derivation is the ORDER, and `sortPlayers` is a stable sort, so passing `useLeaderboard`'s already-ranked roster reorders nothing—running it anyway means the record cannot depend on a caller remembering to sort.
- **The headline First to BINGO** comes from `eventFirstBingoWinner`, the ONE selector the live pin, the frozen podium and the ceremonial `first_bingo` Moment gate already share, cut on the same resolved Standings Freeze (`resolvedStandingsFreezeAt`). The archive must not become a fourth answer to a question three surfaces already agree on.
- **Daily honours** come from `pinnedOrDerivedDailyHonors`, exported from `src/data/finale.ts` by this ticket rather than restated—the write-once day-meta pin when a Day has one, the roster-derived fallback when it does not. Each one carries the CHIP LABEL it renders under (`ArchivedDayHonor.dayLabel`), resolved here and stored, because `EventDoc.days` is not frozen: the write-once clause protects `status`, `archivedAt` and `archive` and deliberately nothing else, so an Admin re-theming a Day after the archive silently re-labelled a frozen honour—the one thing "nothing here changes again" promises it cannot (Codex P2, PR #1139). `dayHonorChipLabel` is the LIVE strip's own derivation, moved beside the honours it labels and shared by both callers, so the frozen label is by construction the label the last live strip rendered.

### The inputs are validated BEFORE the Event is shut

`players/{uid}` is self-written under the honour system and its rules arm validates NOTHING about the fields the archive copies—not `uid`, not `displayName`, not `bingoCount` or `squaresMarked`. A Player can therefore delete a field from their own row, or store a very large string in it, and the snapshot copies it straight onto the Event document. Firestore refuses to serialize an `undefined`, and 200 rows share one 1 MiB budget, so either shape makes the archive write fail—**after** the closing write has already shut the Event. Every attempt would close play and then fail, permanently (Codex P2, PR #1139).

So `draftEventArchive` decides four things about the inputs, and the Admin console reads that decision before the first write rather than around the second:

1. **A row with no usable `uid` is SKIPPED and counted.** There is nothing to default an identity to: the row cannot be ban-filtered, cannot be matched against the headline honour, and cannot be pinned on the Share Card. The count is stated on the confirm row, so the Admin is told what the record will not contain instead of comparing rosters afterwards. The filter runs BEFORE the honour selections, so an unidentifiable row cannot take the headline either.
2. **A daily honour whose `dayIndex` is not an integer is dropped**, for the same want-of-anything-to-default-to reason. A derived honour reads that index off a `dayStats` KEY, and `dayStats` is a Player-written map with no rules validation, so a junk key becomes a chip nothing could label. The live honours strip already drops it by matching against the schedule; the record has to drop it itself, because an Event with no schedule renders the derived list straight through and the record is permanent.
3. **Every other malformation is COERCED to a safe default**—a missing name reads `'Anonymous'` (the estate's existing stand-in), a missing or non-finite count reads `0`, a bad instant reads `null`—and every name is bounded at `MAX_ARCHIVED_DISPLAY_NAME` (100), the cap `firestore.rules` already enforces on every OTHER Player-authored display name (the per-Day honour pin, Tally markers, Moments, Proofs). The profile editor's own limit is 40, so no name a Player can enter through the app is ever shortened. None of this adjudicates a stat (ADR 0001): it decides nothing about who won, it only makes the row expressible in the shape the record declares.
4. **The finished record is measured TWICE, and the second measurement is the one the write actually meets.** `MAX_ARCHIVE_BYTES` (256 KiB, a quarter of the Event document's budget) bounds the RECORD's own share; `MAX_ARCHIVED_EVENT_BYTES` (900 KiB, leaving ~148 KiB of margin under Firestore's 1 MiB limit) bounds the PROJECTED DOCUMENT—every stored field the update retains, plus the four it writes. Either ceiling REFUSES.

   The second exists because the archive never lands on an empty document (Codex P2, PR #1139). `days` carries a per-Day `snapshotItemIds` list, `bannedUids` holds up to 1000 entries and `mostLovedPhoto` up to 100 winners, and all of them are already there when the freeze commits—so an Event that grew large on its own could pass the record's quarter-budget and still overflow the document, inside the transaction, AFTER the closing write had shut the Event. That is the one failure this whole section exists to make impossible, so the guard measures what the write produces rather than what it carries. A prior `archive` is dropped from the retained side, because the update replaces it.

   With rows and names both bounded a real record is tens of kilobytes, so the record's own ceiling stays the backstop for whatever those clamps did not anticipate—`dailyHonors`, for one, is derived one-per-`dayStats`-key from a Player-written map with no rules validation. Both refusals are reported, not thrown, and both are taken twice: `ArchiveEvent` disables the control and states the cause against the Event it has subscribed to, and `archiveEvent` re-checks the record built from the SERVER re-read against the STORED document it is about to update, reporting `too-large` without writing. The copy names the document rather than a Player row, because the check is on the finished size and cannot prove which row caused it—the remedy it points at (ban the Player carrying far more text than a name) is still the one an Admin can take from the console.

### The quiesce protocol—`EventDoc.archiving`, then the freeze

**The archive is TWO writes, in order, and the order is the guarantee.** A Firestore transaction serializes only against the documents it READS, and the freeze reads one document and writes one document—so a Player's Board write, a stat write or a Claim create, each landing in a different collection, is not ordered against it at all. A record built beside the flip can therefore be missing a Mark that committed alongside it (permanently, since the rules then lock the record), and a Claim can go pending in the instant before the freeze that makes it unresolvable. No client-side latch closes that: `hasServerData` and `serverLoaded` say the server has SPOKEN, never that it has STOPPED speaking.

1. **`beginArchive` shuts the Event, and identifies the shut.** One admin-only update setting `archiving: true` and `archiveToken`—a fresh opaque id per quiesce. `eventClosedToPlay` in `firestore.rules`—and its mirror in `storage.rules`—treats that state exactly as it treats `status: 'archived'` for every gameplay write, so from the moment it commits the roster, the Day honours and the Claim queue cannot move again. Admins are bound by it too: a quiescing phase its own organiser can mark through quiesces nothing.
2. **`archiveEvent` re-reads the inputs and freezes them.** It pre-reads the Event FROM THE SERVER (a cache-sourced copy could still report the pre-quiesce state), refuses with `not-closing` if the quiesce was never taken, CAPTURES the quiesce's `archiveToken`, re-takes the **pending-claim drain gate** from the server (see below), then reads the roster and every Day's honour pin with `getDocsFromServer` / `getDocFromServer` before taking the snapshot in ONE `runTransaction` update that writes `status: 'archived'`, `archivedAt`, `archive` and `archiving: false` together—having first confirmed that the transaction's own read still carries the SAME token.

**The snapshot is bound to the quiesce it was read against, because being shut is not the same as being THAT shut** (Codex P1, PR #1139). `archiving: true` says the Event is closed; it cannot say WHICH closing. Between `archiveEvent`'s reads and its commit, an Admin can reopen play (`abandonArchive`), gameplay can resume—Marks, Claims, honours—and a second archive can begin, and the document the transaction then reads carries an `archiving: true` indistinguishable from the first. A check on the flag alone commits standings that predate play the Event had already accepted, permanently, because the record is what the rules lock. So `beginArchive` mints a fresh `archiveToken` per quiesce, `archiveEvent` captures it before its first read and requires the transaction's fresh read to carry the same one, and the rules require the flip write to restate it (`boundToStoredQuiesce`)—so a direct SDK write carrying a superseded generation is denied at the boundary too, not only by the client that happens to check.

The token is PRESERVED when `beginArchive` is called on an Event already closing, because that call is idempotent and takes no new snapshot: re-minting there would abort an in-flight freeze that is still perfectly valid. A closing state carrying no usable token is refused rather than bound to by guesswork—an unidentified quiesce is exactly the state the binding exists to tell apart from another—and `beginArchive` mints one, so reopening and archiving again is the way through. That state can only come from a hand edit or an Event shut by a build older than this field.

**The snapshot-defining CONFIGURATION is held across the same window** (Codex P2, PR #1139). The quiesce shuts gameplay, not administration—deliberately, so an Admin can still moderate and still reopen—which leaves the Event's own settings movable between the pre-read the drain gate is evaluated against and the transaction the record is built against. Two concrete ways that goes wrong: flipping `claimMode` from `honor` to `admin_confirmed` turns a drain gate that passed VACUOUSLY (the gate is scoped to `claimsQueueOpen`) into a queue full of Claims the freeze has just made unresolvable; and editing `days` leaves the record built from honour pins fetched for a schedule that no longer exists, against a Tutorial-Day set and a derived freeze boundary that have both moved. So `archiveEvent` fingerprints `claimMode`, `days`, `standingsFreezeAt` and `frozenAt` (`archiveSnapshotFingerprint`, with object keys sorted so two decodes of an unchanged document cannot report a spurious change) at the pre-read, re-fingerprints the transaction's own read, and refuses with `config-changed` rather than combining the two.

**And the two documents the record is BUILT FROM hold still for the same window** (Codex P2, PR #1139). The fingerprint above covers the Event's own configuration; it cannot cover the roster and the Day honour pins, because those are not fields on the Event document and the freeze's transaction reads only that one document. A transaction serializes against the documents it READS, so an Admin deleting a `players/{uid}` row or a `days/{i}/meta/{i}` honour between `archiveEvent`'s server re-read and its commit neither conflicts with the freeze nor retries it—the write-once record simply keeps a row moderation had already removed, permanently. Those are the only two admin writes that decide what the snapshot CONTAINS, so `firestore.rules` denies both for the length of the quiesce (`eventQuiescing`), exactly as it denies the gameplay writes.

They REOPEN the moment the record exists, and that asymmetry is the whole point: the archived Leaderboard renders the frozen record rather than those documents, the write-once clause protects `status`/`archivedAt`/`archive` and nothing else, and a permanent record whose Players could never be erased is #808's support incident in a new place. The remedy while closing is the one already on screen beside the button—**Reopen play**, moderate, archive again—which is also why blocking was chosen over binding each document to a generation the final transaction validates: a generation would have to be stamped onto every row and pin by the writes the quiesce has just denied, and the transaction would then have to read the whole roster to check them, which is the read set the bounded one-document commit exists to avoid.

`bannedUids` is deliberately OUTSIDE that fingerprint. Moderation is not a gameplay write and stays available through the quiesce on purpose (§ Design decisions), and a ban is applied to the rows the record keeps rather than deciding which rows were read—so a ban landing mid-snapshot changes what the record CONTAINS in exactly the way it should. Aborting on it would make the freeze race the one administrative action this spec keeps open across it.

**Four things are refused after the close rather than written through**, and each reports instead of throwing so the console can say what happened: `claims-pending` (a Claim was still awaiting an Admin when the Event shut), `too-large` (the record built from the server re-read would not fit the Event document), `config-changed` (the Event configuration the snapshot is defined by moved underneath it) and `quiesce-changed` (the closing state in force is not the one the record was read against). None writes anything.

The two-tap path REOPENS PLAY on the first three, because that handler is what shut the Event; the closing-state surface deliberately does not, because that Event was already shut when the Admin arrived and **Reopen play** sits beside the button they pressed. `quiesce-changed` is the exception on both paths: the Event standing there is not the one this call shut, so clearing its closing flag would reopen an Event underneath somebody else's in-flight freeze. It is reported and left exactly as found.

**And that reopen is BOUND to the same generation** (Codex P2, PR #1139). `archiveEvent` compares the token inside its own transaction, but the console's cleanup runs after it RETURNS—and everything the ABA case describes can happen in that gap too, so an unconditional `abandonArchive` there clears a later Admin's quiesce out from under their in-flight freeze, which is precisely what `quiesce-changed` refuses to do one step earlier in the same handler. `beginArchive` therefore reports the generation it left in force (`BeginArchiveOutcome`), `abandonArchive` takes it as an optional `expectedToken`, and a mismatch reports `quiesce-changed` and writes nothing. A stale token cannot be laundered into a match: `abandonArchive` leaves `archiveToken` in place, and `beginArchive` preserves a token only while the Event is STILL closing, so a reopened-and-re-shut Event carries a fresh one. The console states both halves—why nothing was frozen, and why play is nonetheless still closed.

The console's own **Reopen play** button passes NO token and stays unconditional, because it is a deliberate act on the Event standing in front of the Admin rather than an automatic cleanup by a call that has already failed. The binding exists to stop a stale handler, and there is no stale handler at that button.

**Why an explicit server read rather than waiting on the subscriptions.** The obvious criterion—"wait until the roster and day-meta subscriptions are server-confirmed again, after the closing write"—deadlocks in exactly the case the quiesce creates: a passive listener re-delivers only when its documents CHANGE, and nothing changes once gameplay is shut, so the confirmation would never arrive. A read issued after the closing write is acknowledged is the stronger criterion anyway: its result is the state of a collection that can no longer change, which is what "confirmed after the close" is trying to approximate.

That is a READ, not a recompute (ADR 0001). Every number still comes verbatim off the Player-written `PlayerDoc`, through the same converter-attached references (`playersCol()`, `dayMetaRef()`) the live Leaderboard subscribes with; only the freshness differs. `dayMetasLoaded` is `true` by construction, because every pin was answered by the server rather than possibly by an unfilled cache.

**The closing state is REVERSIBLE until the archive commits, and inert afterwards.** `abandonArchive` clears the flag, and `archiving` is deliberately outside the write-once clause: the first write shuts gameplay for everyone, so a failed second write, a tab closed mid-flight, or an Admin who changed their mind must not leave a live Event permanently unplayable. That is safe precisely because `status` is NOT clearable—once the record lands, the freeze is carried by the half that cannot be moved, and clearing `archiving` reopens nothing.

**The flip is refused from anywhere else.** `status` may only become `'archived'` from a stored document already carrying `archiving: true`, so a direct SDK write cannot skip the quiesce either—the ordering is a rules invariant, not a convention one client happens to follow.

The transaction re-reads the Event inside itself and returns `already-archived` rather than re-freezing, so a double tap—or a second Admin's tap—can never overwrite the record with a later roster, and `not-closing` if the quiesce was lifted underneath it. It re-reads the Event RAW (the `setDayTheme` / `confirmClaim` discipline) so the ban roster and schedule the record freezes against are the stored ones.

### The pending-claim drain gate

`ArchiveEvent` refuses to arm while the Review queue holds a pending Claim, and says so: *"Resolve the N pending claims in the Review queue first."*

The freeze and admin-confirmed claim resolution are otherwise in direct contradiction. The claims arm keeps `allow update: if isAdmin(eventId)` open on an archived Event, and `ReviewQueue` keeps offering Confirm and Reject—but `resolve()` (`src/data/admin.ts`) writes the claimant's Board and their Player row in the same transaction, and both are gameplay writes the freeze denies. A claim still pending at the moment of archival is therefore pending FOREVER, behind a control pair that can only fail. `tests/rules/post-sailing-archive.test.ts` pins exactly that shape.

**The remedy is client-side because it cannot be anything else.** Rules cannot query a collection, so "no pending claims" is not a condition the archive write can carry; the resolution paths themselves cannot be exempted from the freeze without reopening the Board and Player arms that make the record frozen at all. Draining first is the only remedy that keeps both properties.

`claimsAwaitingAdmin` (`src/data/moderation.ts`, beside `isBanned`—Firestore-free and React-free, so the gate is unit-testable and lives in a module no admin test stubs) is the one predicate, built on the `claimsQueueOpen` that `ReviewQueue` itself now renders from, so the gate and the queue it points at cannot disagree. The claims come from `Admin.tsx`'s EXISTING `usePendingClaims` subscription, threaded through `GameSettings`, so the gate opens no second listener—and `usePendingClaims` now exposes `hasServerData`, because a queue that has not arrived reads as zero pending claims and a gate that passes vacuously is no gate at all. The gate is re-checked at the second tap, not only the first: a claim can land while the confirm row is armed.

**And it is taken a third time, from the server, AFTER the closing write** (Codex P2, PR #1139). A subscription reports what has already been DELIVERED, never what is about to commit, so a Claim landing between the last render and the quiesce clears both taps—and nothing downstream notices, because the freeze reads no Claim collection at all. `archiveEvent` therefore re-reads the queue with `getDocsFromServer` once the pre-read has confirmed `archiving: true`, applying the SAME `claimsAwaitingAdmin` so the two halves of the gate can never disagree about what counts, and returns `claims-pending` without writing. It is the identical argument the roster re-read rests on: a read issued after the closing write is acknowledged sees a collection that can no longer change. The order matters—the queue is read only after the quiesce is confirmed, because a queue read before it proves nothing.

The remedy at that point cannot be to resolve the claim (that is the gameplay write the freeze just denied), so the call refuses and the console reopens play, putting the Event back in the one state from which the queue CAN be drained.

### The surfaces

- `src/components/admin/ArchiveEvent.tsx`—the archive door, rendered last inside **Game settings** (`specs/admin-console-ia.md` § "Game settings"), because it is the one control there that ends the Event rather than tuning it. Two taps, never one: the button arms an inline confirm row stating what is about to be frozen (derived from the same builder the write uses, so the preview cannot drift from the record), and the result is reported in place. The second tap runs BOTH writes of the quiesce protocol in order. Once the Event is archived the control retires and the row states the frozen record instead.

  **The closing state has a surface of its own**, because an Event shut with no record is the worst outcome this feature can produce and nothing else in the console would ever show it. When `archiving` is set and `status` is not yet `'archived'`, the control says so and offers both ways out: **Freeze the record** (re-runs the second write alone—the first is already done) and **Reopen play** (`abandonArchive`). That is how a failed second write, or a tab closed between the two, is recovered.

  **Three preconditions sit ahead of the first tap**, and the control is DISABLED with the reason stated in place until they hold. The write is permanent behind write-once rules, so there is no second attempt to correct what it froze.

  1. **Every preview input server-confirmed.** `useLeaderboard`'s `hasServerData` and `useDayMetasStatus`'s `serverLoaded` are latches on "the server has spoken for this key", and until they hold, an empty roster and an unpinned Day are indistinguishable from an ADR 0006 persistent cache that has not filled in yet—so the confirm row would understate what is about to be frozen. The Event document is part of the same precondition, because `useDayMetasStatus(0)` reports `serverLoaded` vacuously while it is absent. `serverLoaded` is added by this ticket beside the existing `loaded`: `loaded` means every Day has DELIVERED something (a cache snapshot counts, which is what the live honours strip wants), `serverLoaded` means every Day has been answered by the SERVER. The fan subscribes `{ includeMetadataChanges: true }` for the reason `useDocSub`/`useColSub` already do—without metadata events Firestore never re-notifies when the server confirms byte-identical cached data, so the latch would deadlock on exactly the documents that were cached. An ERRORED subscription resolves the Day for both flags: it can never deliver a server snapshot, and treating it as unresolved would disable the archive forever. The RECORD no longer depends on these subscriptions—`archiveEvent` re-reads its inputs after the quiesce—but a console that has not loaded is still not a console to end an Event from.
  2. **The claim queue drained.** See § "The pending-claim drain gate" below. It gates the freeze in the closing state too, where the only way to drain is to reopen play first. The client half is a listener, so it is only the first of three takes—the last one is `archiveEvent`'s own server read after the close.
  3. **The record fits the DOCUMENT.** `draftEventArchive`'s refusal, read here rather than around the write, for the reason § "The inputs are validated BEFORE the Event is shut" gives: a record that cannot be stored must stop the FIRST write, or every attempt shuts the Event and then fails on the second. The console passes the Event document it is already subscribed to, so the measurement is of the projected document rather than of the record alone—an Event whose own fields fill the budget refuses here with a perfectly ordinary roster.

- `src/components/ArchivedLeaderboard.tsx`—the read-only archive surface: the frozen standings, the hall of fame (Event-wide First to BINGO plus the daily honours strip), and the Share Card. It subscribes to NOTHING. There is no `useLeaderboard`, no `sortPlayers`, no `cruiseFirstBingoUid` and no day-meta read in it; every number, name and honour was decided once, at the archive—down to the LABEL on each honour chip, which is why `days` came off this component's Event prop entirely. That is what makes "opened later, the standings persist unchanged" true rather than merely likely.

  **Moderation is the one live input, and it is not a re-derivation.** The surface takes the CURRENT `bannedUids` off the Event document its parent already subscribes to, and hides a banned Player's stored row, their daily honour chip, and their appearance on the Share Card—vacating the headline First to BINGO to "No one got there." rather than naming the next-earliest Player. The repository's ban contract is that every public Leaderboard view hides a banned Player (`specs/w2-ban-console.md` § Leaderboard), the freeze deliberately leaves `bannedUids` editable so a permanent record still has a takedown path, and a record whose only Leaderboard view could not be moderated would be the #808 support incident in a new place. Nothing is promoted into the vacancy and nothing is recalculated: the stored `standings`, `playerCount`, every remaining row's numbers and the honours all keep the values the archive stamped, and an unban restores the hidden row exactly as it was. The displayed rank ordinals close the gap over the visible rows, which is what the LIVE Leaderboard already does with a banned row—leaving a hole at #1 would advertise that a row was removed, which is the opposite of what hiding is for. The truncation footnote keys on the STORED pair, so moderating one Player never makes an un-truncated archive claim it was cut short.

  **The Event's own name comes out of the record too.** The card's title and context line read `EventArchive.eventName`, not the live `EventDoc.name`—the freeze leaves that field editable, so a card rebuilt from it drifted the moment an Admin renamed the Event. The app's own name stays the fallback for a record that carries none, which is a hand-written one; the fallback is frozen-safe rather than reaching back into the live document.

  **The Share Card's pinned eleventh row falls back to `firstBingoRow`.** It prints the ten visible rows plus the headline holder when they rank outside them, and it searched `archive.standings` for that row—which on a truncated record does not contain the holder at all, so the row this card names in its own headline silently disappeared. The stored row is used instead, at the rank it held in the complete standings; a ban still vacates the headline first, so a hidden Player is never printed from it.

- `src/components/Leaderboard.tsx`—splits into a routing component that owns only `useEventDoc`, and a `LiveLeaderboard` child that owns the live view's three subscriptions: the whole `players` roster (`useLeaderboard`), every Day's meta document (`useDayMetasStatus`) and up to 60 live Proofs (`useProofKindsByUid`). An archived Event renders `ArchivedLeaderboard` from the routing component and NEVER MOUNTS the child, so none of those listeners open. The split is what makes "it subscribes to NOTHING" true: a branch taken after the hooks had already run would render the frozen page with a live listener fan open behind it. It is also the only way to do this without breaking the #280 hook-order rule—conditioning hooks in place is illegal in React, whereas returning a different component unmounts the live one and its listeners with it, and each component's own hook sequence stays fixed.

  **And the branch WAITS FOR THE SERVER** (Codex P2, PR #1139). The split decides nothing on a cold visit: `useEventDoc` starts at `data: null`, and the ADR 0006 persistent cache can then replay the Event as it stood when the tab last saw it—`active`, because it was. Falling through to the live child on either mounts the whole fan on an archived Event and tears it down a snapshot later, so "it subscribes to NOTHING" was false for exactly as long as the roster, every Day's meta and 60 Proofs took to answer. An UNRESOLVED status therefore renders the live view's own loading state, under the same label, so there is no visible seam between this wait and the roster's.

  `useDocSub` gains `serverResolved` beside `hasServerData` for it, the same pair `useDayMetasStatus` already draws between `loaded` and `serverLoaded`: `hasServerData` is "the server has spoken", `serverResolved` is that OR the subscription ERRORED, which is terminal for an `onSnapshot` listener and can therefore never become a server answer. Two things end the wait short of a server snapshot, because a spinner nobody can get past is worse than the listeners it avoids: a cached `archived` record, which needs no confirmation at all (the flip is write-once at the rules boundary, so an archived Event can never be un-archived—the archive renders immediately, as it always did); and a client the browser reports as OFFLINE, since no server answer can arrive for it and this app is offline-durable by design. `useOnline`'s `false` is the trustworthy half of that hook, and it is read here to stop waiting, never to authorize anything. The latch is monotone, so a reconnect cannot bounce an already-rendered live view back through the spinner—which would unmount the child, drop its listeners and reset the Player's filter. It is held in STATE, adjusted during render the way `Board`'s dangling-sheet close already is, rather than in a ref: React discards a state update from an abandoned render, while a ref written during one would keep a conclusion that never committed (the #452 finding).
- `src/data/api.ts` and `src/App.tsx`—**the archived VISIT**, which is the one path every returning Player takes and the one the freeze would otherwise close in their face (Codex P1, PR #1139).

  `joinAndDeal` merges the Player's identity into `players/{uid}` on EVERY visit to a daily Event, a returning Player included, and `eventOpenForPlay` denies that write on both halves of the freeze. Attempting it anyway is not a harmless failure: `AuthContext.runDeal` classifies a permission-denied as PERMANENT (deliberately—a rules or schema misconfiguration must not hide behind a cached Board), `App` replaces the Card tab with the full-screen `DealError`, and its **Retry** repeats precisely the same forbidden write. The archive was unreachable from the Card tab behind a retry that could never succeed.

  So the client asks the question the rules already answer, through the same `isEventArchived` / `isEventArchiving` pair every other surface uses, and declines: `joinAndDeal` returns on the Event read its MODE decision already takes—no second read—and reports `false`, the same "no new Board was dealt" a returning Player has always produced, so no `join_event` is recorded, nothing throws, and `runDeal` clears any stale error. Nothing is lost by skipping it: the record froze every standings row's `displayName`, and the archived Leaderboard renders that record rather than these rows. The rules are deliberately NOT loosened to admit an identity-only update—an exemption would have to be carried by the one arm the standings are frozen at, to refresh a name no archived surface reads.

  **And the visit is ROUTED, not merely un-erroring.** A closed Event has no card to play: the join is declined, and `Board`'s own lazy Day-Card deal is a write the rules deny too. The Card tab therefore redirects to the standings tab, which is where the record lives—one mount point for the archive rather than a second copy of it, and a tab bar that names where the Player actually is. Decided in the route table for the reason the Leaderboard's own split states: a branch taken after the hooks have run still mounts the component and opens its listeners, and `Board`'s mount is what deals.

  **A CLOSING Event routes exactly the same way**, and it is worth stating what that shows: the quiesce denies every gameplay write while carrying no record at all, so the standings surface renders them LIVE—and they simply cannot move. The Player sees the current standings, frozen in fact if not yet in bytes, which is the truthful answer for an Event that has been shut but not yet archived. A separate surface for the gap would have to describe a state that lasts as long as one Admin's two taps.

  This routing does NOT wait for the server, and that asymmetry with the Leaderboard's own gate is deliberate. `useEventDoc` starts at `null`, which reads as OPEN by the predicate's own default, so a cold visit renders the Board exactly as it does today and re-routes when the snapshot lands. Making the Card tab of every LIVE Event wait on a round trip would cost far more than one late redirect—and the write half needs no such wait, because `joinAndDeal` asks the server itself.
- `src/index.css`—the `.lb-archived-banner` block. Quiet on purpose: an archive is a keepsake, not an error state, so it borrows the panel chrome the honours strip already uses.

The archived view stays shareable through the existing on-device Share Cards (#36, [ADR 0005](../docs/adr/0005-client-side-share-images.md))—a frozen leaderboard is the most shareable thing an Event ever produces—and there is still no crawler-facing page.

**The card is pre-rendered on mount, and the tap never waits on it**—the `FarewellPodium` treatment (#712 round 3), which the archive earns more plainly than anything else in the app because its payload is IMMUTABLE at the rules boundary: pre-rendering cannot bake in something a later snapshot would change, and unlike the live Leaderboard (which re-renders on every roster snapshot and refused mount-eager rasterization for exactly that reason) there is no per-snapshot churn to pay for. `navigator.share` needs transient user activation, and so does `clipboard.writeText` on Safari and Firefox, so a tap that AWAITS a rasterization can outlive the activation and skip every share leg on precisely the slow phone that needed it (Codex P2, PR #1139). The handler therefore takes the warmed render only if it has ALREADY settled and calls `shareCardBlob` in the same turn as the gesture; an unsettled render costs the image, never the share. Hover, focus and pointer-down warm it too, covering the one input that can invalidate the card—a ban or an unban.

### The enforcement—`firestore.rules` and `storage.rules`

`eventOpenForPlay(eventId)` is the single predicate, and it is ANDed into every gameplay write arm: Boards, Player rows, the write-once per-Day honour, reshuffle spends, Prompt creates and reports, Proof creates and reports, Claims, Tally markers (create, update and delete), Doubts (raise, satisfy, withdraw), Hearts (create and delete), Moments, and retraction tombstones. It is the negation of `eventClosedToPlay(eventId)`, which reads the Event document ONCE and closes on either half of the freeze—`status == 'archived'` or `archiving == true`. `storage.rules` mirrors it on proof-media upload, because a Proof document and its media must refuse together or the archive still grows blobs—the #806 lesson, restated by `specs/path-addressing-and-root.md` § D8 as "Storage uploads under that Event's prefix alike". The Storage copy binds the document read to a helper argument rather than re-reading it, because Storage Rules allow at most two Firestore accesses per evaluation and make no promise of deduplicating a repeated `firestore.get()` on one path.

`eventQuiescing(eventId)` is the ONE predicate that tells the two halves apart—shut but not yet frozen—and it guards exactly two arms: the admin deletes on `players/{uid}` and on the per-Day honour. Those are the two documents the record is built from, and they are the only writes in the file that must be denied while the archive is being taken and allowed once it has been (§ "The quiesce protocol"). Every other arm reads `eventOpenForPlay`, which does not care which half is in force.

Rendering is not enforcement, and this spec refuses to pretend otherwise: hiding the controls client-side would leave a direct Firestore write succeeding, which is exactly the client-only convention D8 rejects. Every rules case in the test map below is a direct SDK write, not a UI path.

The Event document's own writes split across TWO admin-gated arms—which is where "admin-only toggle" comes from, inherited rather than invented, since no Player may write that document at all. The split is legible and mechanical at once: `allow` statements short-circuit, so the archive flip is decided by a small dedicated arm and never pays for the schedule and freeze-boundary validation the general arm performs. That arm already sits one clause from Firestore's 1000-expression cap (#850/#934), and folding the archive checks into it exceeded the cap on the very write they exist to validate.

**The archive-flip arm** accepts exactly one shape of write, and states everything the freeze needs to be trustworthy in one place:

1. It may only be taken from the QUIESCED state—a stored document carrying `archiving: true` and not yet archived—so no writer, client or direct SDK, can skip the window in which gameplay was already shut. And only from the SAME quiesce the record was read against: the stored document must carry a non-empty `archiveToken` and the write must restate that exact value (`boundToStoredQuiesce`), so a write bound to a superseded generation is refused at the boundary. Restating an unchanged value keeps the field out of `affectedKeys()`, which is why the `hasOnly` guard in clause 5 still names four keys.
2. It must carry a numeric, bounded `archivedAt`.
3. It must carry the COMPLETE record: `standings` (list), `playerCount` (number), `dailyHonors` (list), the First-BINGO PAIR, `eventName` (string or `null`), `freezeAt` (number or `null`), and an `archivedAt` equal to the document's own stamp. Type-checking `archive` only when present accepted `{status: 'archived', archivedAt}` on its own, and that state is both irreversible and useless—the freeze denies every gameplay write while the Leaderboard falls back to the LIVE view the archive exists to replace, and a half-built map throws in `ArchivedLeaderboard`.

   **`firstBingo` and `firstBingoRow` are validated TOGETHER, not one at a time** (Codex P2, PR #1139). They are SELECTED together—the row exists only to carry the honour's holder outside the bounded `standings` prefix—so the record has exactly two legitimate shapes: both `null` (nobody got there), or both maps naming the SAME holder. Typing them independently accepted the two shapes the pairing exists to refuse: a map beside a `null`, which is the half-built record the archived Share Card reads a hole from, and two maps naming DIFFERENT Players, which puts one name in the hall of fame's headline and another on the pinned eleventh row of the same card. The pairing lives in its own `firstBingoPairComplete` helper for the reason `completeArchiveRecord` does—the arm calling it sits against Firestore's expression cap.
4. It must clear `archiving`, so the freeze is carried only by the half that cannot be moved.
5. It must touch NOTHING ELSE (`affectedKeys().hasOnly`), which is what lets the arm skip the configuration validation without opening a hole through it: a write that also moved `days`, `bannedUids` or `standingsFreezeAt` is not an archive flip and falls through to the arm that checks those fields, where a not-yet-archived document is refused.

**The general admin arm** keeps every other Event write and gains three clauses:

1. `status`, now that something finally reads it, must be `'active'` or `'archived'`. A typo'd status reads as OPEN through `eventOpenForPlay`'s default, so an Event an organiser believed was frozen would silently keep taking Marks.
2. `archiving` must be a BOOLEAN. A truthy string would read as closed through one reader and open through another, on the flag that decides whether every gameplay write is denied. It is deliberately NOT write-once: an abandoned archive must be reversible. `archiveToken` deliberately gets NO clause here—this arm sits against Firestore's 1000-expression cap, and every property the token needs is decided on the flip arm above, where a malformed one can only fail the flip closed rather than open a hole.
3. This arm may only produce `status: 'archived'` on a document that was ALREADY archived, which is what keeps moderation and configuration working after the freeze while leaving the flip to the arm above.
4. The freeze is WRITE-ONCE: once `status` is `'archived'`, `status`, `archivedAt` and `archive` are locked to their stored values. Every OTHER field stays editable, so moderation (`bannedUids`) and configuration survive the freeze.

### The server-side half—the Admin SDK writers

`firestore.rules` stops a Player from marking a square on a frozen Event. It stops none of the Cloud Functions, which run on the Admin SDK and bypass the rules entirely. `eventClosedToPlay(event)` in `functions/src/unlockDay.ts` is the same predicate restated at that boundary, with the same defaults, and it guards every core that writes gameplay state: `stampDaySnapshot`, `manualUnlockNow`, `resnapshotDayIfNoBoards`, `runScheduledUnlock`, `runFinaleBeats`, the finale freeze transactions, and `postFinaleMoment`.

Each guard is checked against the core's FIRST read and re-checked **inside the transaction that writes**. The window is real in three ways: the quarter-hourly sweep selects its Events once per run and then processes them one at a time, so a run selected moments before the archive still arrives on a frozen Event (and a Cloud Functions retry can arrive minutes later); the selection query is `status == 'active'`, which does not exclude the CLOSING state at all; and `unlockDayNow` is an ADMIN callable, which the rules bind to the freeze for gameplay for the stated reason—an archive whose own organiser can still open a Day is not a frozen record. `SnapshotResult` and `ResnapshotResult` each gain an `'archived'` member, reported rather than thrown: a sweep that finds a frozen Event has done its job correctly.

**`postFinaleMoment` writes inside a transaction for that reason too** (Codex P2, PR #1139). It used to re-read the Event and then `set` the system Moment, and a fresh read only SHORTENS that gap—the archive can commit between the read and the write, and the beat then appends to a Feed the record has already preserved, which is the one thing an archived Feed promises it will not do. Reading the Event inside the transaction that writes the Moment closes it, because a transaction serializes against the documents it READS and the archive's own write touches that document: a commit landing in the window aborts the attempt, and the retry re-reads the closed state. That is the guarantee the snapshot, re-snapshot and finale-freeze transactions already had; this beat was the last one taking it on trust. The injected `Transaction` surface gains the `set` the real Admin-SDK transaction already has.

**The daily engagement email is stopped by the same predicate.** `runDailyEmailSweep` selects `status == 'active'`, and `sendDailyEmailForEvent` checked neither half of the freeze—so an Event held in the closing state kept inviting people to play while every gameplay write the mail asks for was denied at the rules boundary, and a sweep selected just before the final flip could continue after it. Two distinct holes: the closing state is deliberately still `'active'`, so the selection query never excluded it; and the selection runs ONCE per sweep, before any Event is processed. `sendDailyEmailForEvent` now reads `eventClosedToPlay` off the Event document itself—the same predicate, imported rather than restated—and reports `reason: 'archived'` for both halves. It reads it TWICE: once off the Event the call opens with, and again from a fresh read taken immediately before delivery begins, after the hostname resolution, the roster page and the standings snapshot, which is exactly the elapsed time a sweep selected just before the freeze spends getting there.

## Design decisions

- **Archiving is one-way from the client.** `status: 'archived'` is terminal: the rules refuse to move it back, refuse a second stamp, and refuse a rewritten record. The alternative—a reversible toggle—means the "frozen" standings can silently drift out of sync with a roster that resumed playing, and hands an Admin a switch that reopens writes on a record other people have already shared. Write-once is the same posture the day-meta honour doc and Moment immutability already take in this rules file. See § Recovery for the escape hatch.
- **The QUIESCE, by contrast, is reversible—and that asymmetry is the design.** `archiving` shuts gameplay without producing a record, so leaving it un-clearable would mean a failed second write could strand a live Event permanently unplayable with nothing to show for it. Making it clearable costs nothing, because the moment a record exists the freeze is carried by `status`, which is not.
- **Reversible therefore means IDENTIFIED.** The moment a quiesce can be lifted, two of them can exist in sequence inside one archive attempt, and a flag cannot tell an in-flight freeze that its window has been and gone. `archiveToken` is the cost of the reversibility: one opaque field, minted per quiesce, compared once in the transaction and once in the rules. The alternative—an irreversible quiesce—buys the same guarantee by stranding Events.
- **A separate boolean, not a third `status` value.** `'closing'` as a status would have dropped the Event out of three server-side `status == 'active'` sweeps as a side effect, widened `EventDoc.status` (which `eventResolution.ts` deliberately does not share with `HostnameDoc.status`), and made the two states one field where the write-once rule must apply to only one of them. A field of its own is absent by default, needs no migration, and reads as exactly what it is.
- **Moderation is not a gameplay write.** Every `isAdmin(eventId)` arm keeps working on an archived Event: hide, restore, delete, ban, resolve a dangling claim, edit configuration, and delete proof media from Storage. A permanent record needs a takedown path—a reported photo that can never be hidden again is the support incident (#808's "an archive that locks out its own Admin"), and the write-once clause deliberately protects only the three archive fields.
- **The one exception is the WINDOW, not the archived state.** The `players/{uid}` and day-meta honour deletes are the two admin writes that decide what the snapshot contains, and the freeze cannot serialize against either (its transaction reads one document). They are therefore denied for the length of the QUIESCE and open again once the record exists—the only moment at which a delete could silently edit a record nobody can rewrite. Everything above still holds on an archived Event, which is the state a takedown actually has to reach.
- **Admins are bound by the freeze for GAMEPLAY, though.** The Board and Player arms deny the admin branch too. An "archive" whose own organiser can still mark a square is not a frozen record.
- **A ban hides; it never reassigns**, at the freeze AND after it. `buildEventArchive` selects the headline honour over the FULL, RAW roster and then drops it to `null` if its holder is banned, so a later Player is never promoted into an honour that already happened; a pinned daily honour whose holder is banned yields no chip for that Day rather than the derived runner-up. `ArchivedLeaderboard` applies the SAME rule to the stored record against the CURRENT ban roster, because a ban that lands after the archive is exactly the case the frozen copy cannot have anticipated—and a permanent record whose only Leaderboard view could not be moderated would be the #808 support incident in a new place. Both halves are needed: the freeze-time filter keeps a banned Player out of the stored bytes, the render-time filter keeps a later-banned Player off the screen. This is the live Leaderboard's own rule (`specs/w2-ban-console.md` § Leaderboard), made permanent.
- **The record stores no photo URLs.** Standings rows carry no `photoURL`, for the reason `MostLovedPhotoWinner` persists no media URL: a frozen record must never render a Player's identity from a stale copy they have since changed or removed. The archived rows show initials.
- **The archive freezes the LEADERBOARD, not the podium.** The frozen podium (`specs/d15-finale.md`) answers a different question—champion as of the Standings Freeze, with ceremonial Days re-excluded from the totals—and it already has its own immutable Moment. The archive keeps what the Leaderboard showed, which is what a returning Player is looking for.
- **The archive control lives inside Game settings**, not behind a seventh hub door. It is a once-per-Event switch, not a surface anyone visits; giving it its own card would put the most destructive control in the console at the same level as the prompt pool.

## Out of scope—and stated, so nothing is assumed

- **Read gating is untouched, deliberately.** An archived Event stays exactly as readable as it was live, to exactly the audience it was readable to. Who may read an archived Event, and for how long—member, ex-member, stranger, and the mirrored Storage posture—is [#808](https://github.com/nathanjohnpayne/fiveacross/issues/808)'s question, and that ticket is explicit that #134 must not independently invent what `status: 'archived'` means for reads. A rules case in the test map asserts reads still succeed after the freeze, so a future read gate is a deliberate change rather than an accident of this one.
- **The `apexPath` / routing half of `specs/path-addressing-and-root.md` § D8 does not ship here.** D8 requires the archival write to move every routing document, the `apexPath` field and `EventDoc.status` in ONE transaction. Path addressing ships nothing today (that spec says so itself), so there are no routing fields to move: `archiveEvent` is one update on one document, which satisfies the ordering hazard D8 actually names (routing flipping first, serving an "archive" a Player can still mark) by construction. When path addressing lands, that transaction has to grow to include the routing documents; this spec is the record that it has not yet.
- **The bounded client transition does not ship here either.** D8 requires a live `hostnames/{host}` watcher to re-resolve and unmount an open session, and boot-time status revalidation before a cached entry mounts, so archival is not left waiting on TTL expiry. This ticket ships neither, and the honest statement is D8's own: **archival is prompt at the origin and lagging on cached clients.** The bound that does hold is the server one—an archived Event's gameplay writes are denied for every client from the moment the flip lands, whatever a stale client still renders.
- **The Functions change is the status guard and nothing else.** `runScheduledUnlockForActiveEvents`, the daily-email sweep and the admin-alert sweep all filter `status == 'active'`, which was originally taken as sufficient. It is not, in two ways: the sweep SELECTS once and then processes Events one at a time (so a run selected just before the archive—or a retry of one—still reaches a frozen Event), and the filter does not exclude the CLOSING state at all, because that state is deliberately still `status: 'active'`. The guard described in § "The server-side half" is what closes both, on the scheduler AND on the daily email; no scheduling, content or sweep behaviour changes—a frozen Event mails nothing, and every other Event mails exactly what it did before. The **admin-alert** sweep is deliberately NOT guarded here: it reports moderation state to the organiser rather than inviting a Player to play, and an archived Event's report queue is still one an Admin acts on. `defaultListEventThresholds` (`functions/src/autohide.ts`) reads every Event with no status filter and continues to touch archived ones, for the same reason; that asymmetry predates this ticket and is left alone rather than changed under it (#808 § Contract facts records it).

## Recovery

Un-archiving is not a client operation, on purpose. If an Event is archived by mistake, the fix is an Admin-SDK or console edit—the same escape hatch the write-once day-meta honour and the immutable Moment already rely on, and the same trust boundary the Cloud Functions Admin SDK already sits on (it bypasses these rules). That is a deliberate trade: a mis-click costs an operator intervention, and the alternative costs the guarantee the whole feature exists to make.

**Abandoning an archive that has not committed IS a client operation**, and that is a different thing. Until the record lands there is nothing to un-do—no frozen standings anyone has seen, no shared page—only a shut Event, and shutting one is not the guarantee the write-once rule protects. `abandonArchive` is the Admin console's own way back, so the operator intervention above is reserved for the case that actually needs it.

## Residuals

- **A Player can still delete their own proof MEDIA from an archived Event.** The Firestore Proof document's owner-delete is denied, and the Admin takedown path is preserved, but the Storage delete arm is left ungated: it already spends its one `firestore.get()` on `isEventAdmin()`, and Storage Rules allow at most two Firestore accesses per evaluation—which the create/update arm now uses in full. The exposure is bounded and one-directional: it can remove media, never add it, and it cannot touch `EventDoc.archive`, which is what the archived Leaderboard and hall of fame actually render.
- **The `archive` payload's ROWS are shape-unchecked AT THE RULES BOUNDARY.** Every top-level key is typed, but Rules cannot iterate a list, so per-row validation of `standings` and `dailyHonors` is not expressible there—the same stated residual `bannedUids` carries. Two things bound it: the write-once clause, so exactly one payload is ever accepted, from an Admin, from a quiesced Event; and `draftEventArchive`, which is where the per-row coercion, the name bound and the size ceiling actually live (§ "The inputs are validated BEFORE the Event is shut"). That is client-side by necessity, not by preference—the same honest bound the drain gate carries.
- **An Event marked `archived` with no record renders the live Leaderboard.** No longer a state a write can even reach—the flip is refused without the complete record—so this is now only the shape of a hand-edited or pre-existing document, which falls back rather than dead-ends. It is still read-only where it counts: the rules key on `status` alone.
- **A closing state shut by a build older than `archiveToken` cannot be frozen directly.** The flip requires the stored quiesce to carry a generation, and `archiveEvent` refuses to bind a snapshot to one that does not, so an Event left mid-archive across this change reports `quiesce-changed` on **Freeze the record**. The way through is the one already on screen beside it: **Reopen play**, then archive again, which mints a generation. One extra tap, on a state that only exists if an Admin shut an Event on the previous build and never came back.
- **An Event can be left CLOSING indefinitely.** Nothing expires the quiesce: if an Admin shuts an Event and never returns, gameplay stays denied until someone reopens or archives it. A timeout would be worse—it would silently reopen an Event mid-archive, which is precisely the state the protocol exists to make impossible. The bound is the console: the closing state is stated wherever an Admin would look for it, with both exits one tap away.
- **A configuration change mid-snapshot costs an archive attempt, not a record.** The freeze aborts and reopens play rather than reconciling the two configurations, because there is no honest reconciliation available: the Day pins it fetched were chosen by the old schedule, and the drain gate it passed was scoped by the old Claim Mode. Re-running the whole protocol under the new configuration is one tap, and the alternative is a permanent record assembled from two different Events.
- **The quiesce protects the record's CONTENTS, not the Admin's own timing.** A Mark that lands one millisecond before the closing write is in the record; one that lands after is not, and its Player sees a denial. That boundary is the point rather than a defect—the alternative is a boundary that exists nowhere, which is what this replaces.
- **The drain gate is scoped to the Claim Mode that can actually drain.** `claimsAwaitingAdmin` counts pending Claims only while `claimsQueueOpen`, because #269's mode gate means the Review queue offers no Confirm/Reject outside admin-confirmed mode—so a stale pending Claim left behind by a mid-Event mode change would block archival with no affordance to clear it, which is a dead end rather than a gate. That claim was already unresolvable through the console before this ticket; the freeze does not make it more so. Flipping the Event back to admin-confirmed surfaces the queue and drains it.
- **The gate is client-side, so a direct SDK write can still archive over a pending Claim.** Rules cannot query a collection, so the precondition is not expressible where it would be enforced; the honest bound is the one the whole feature already states—rendering is not enforcement, and what the rules DO hold is that the freeze denies the gameplay writes either way. The post-close server re-read narrows the window to nothing for the app's own path, but it is still a check the archiving CLIENT performs, not one the write carries.
- **`firstBingoRow.rank` is the rank at the freeze, and a later ban cannot shift it.** A Player ranked above the holder who is banned afterwards vacates a place the visible rows close over—but the retained prefix does not contain the rows between it and the holder, so the pinned row's own ordinal cannot be recomputed from what the record carries. The alternative was storing the whole roster, which is the one thing the bound exists to prevent. It affects one appended row on a Share Card, on an Event with more than 200 Players, after a moderation action.
- **A record with no `eventName` renders the app's own name on its card.** The flip now requires the key, and the record is write-once, so this is only the shape of a hand-edited document—the same class as the archived-with-no-record and no-`dayLabel` cases above it. The fallback is deliberately the app name rather than the live `EventDoc.name`: reaching back into the editable field to repair a frozen record would reintroduce exactly the drift the field was stored to stop.
- **Erasing a Player mid-quiesce costs a reopen, and a reopen is a real reopen.** The two snapshot-defining deletes are denied while the Event is closing, so an Admin who has to remove a row right then reopens play, deletes, and archives again—and gameplay is genuinely open in that gap, so a Mark can land in it. That is the same trade **Reopen play** already makes for a failed freeze, and it is bounded by the Admin's own two taps. The alternative—allowing the delete—edits a record nobody can rewrite. A ban needs none of this: `bannedUids` stays editable throughout and hides the row from every Leaderboard view, live and archived alike.
- **A captive portal still spends the routing wait.** The Leaderboard's cold-visit gate ends early on an OFFLINE client, and `navigator.onLine` reports the LINK rather than reachability—so ship wifi that has not been paid for reads as online and the wait runs until the Event subscription errors or the portal is cleared. That is `useOnline`'s own stated caveat rather than a new one, and it is bounded on the side that matters: the surface behind the wait is a spinner, not a denial, and nothing else in the app is gated on it.
- **An Event that closes mid-join still denies the write.** `joinAndDeal` decides on the Event read it already takes, and the freeze can land between that read and the transaction—so the identity merge is denied at the boundary and `runDeal` reports it, exactly as it does for every other gameplay write that straddles the quiesce. The window is one round trip on the visit's first startup, the remedy is the reload the retry surface already offers, and the SECOND startup routes to the archive. Closing it would mean re-reading the Event inside the join transaction, which buys a bounded window on a path whose denial is already correct.
- **A skipped row is counted, not identified.** `draftEventArchive` reports HOW MANY roster rows carried no usable `uid`, and the confirm row states the count, but there is nothing to name them by—that is what makes them skippable. They were already unrenderable on the live Leaderboard for the same reason.
- **The size refusal names a remedy it cannot prove is the cause.** The copy states the true condition—the record and the Event data it would sit beside do not fit in one document—and then points at the overwhelmingly likely cause once rows and names are both bounded, a Player row carrying far more text than a name. The check is on the projected DOCUMENT's size, not on any one row, so it cannot point at the Player, and an Event whose own `days` / `bannedUids` / `mostLovedPhoto` fields fill the budget reaches the same refusal with a perfectly ordinary roster. Banning is the drain that is available from the console either way; the rest is an operator edit.
- **A freeze landing MID-LOOP still finishes the roster it started.** The daily email re-reads the Event immediately before delivery, which closes the selection-to-delivery window; it does not re-read per recipient. A large roster paced through Resend can still straddle a freeze taken while it is sending. Bounded by one Event's send rather than by the sweep interval, and the writes those late emails invite are denied regardless.
