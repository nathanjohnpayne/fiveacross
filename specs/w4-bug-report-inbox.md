# W4—Private bug-report inbox

## Behavior

A signed-in Player can open a persistent, unobtrusive lower-right bug-report control above the fixed tab bar from every authenticated route. The control uses the [Lucide Bug](https://lucide.dev/icons/bug) outline (ISC license) as an inline, theme-token-colored SVG, remains a 44×44 px target on phones, expands to a labeled pill on wider screens, shifts above the install prompt, and disappears while a sheet or celebration is open. It is app-shell utility chrome, not a primary tab.

`BugReport` supports this as its default `variant="floating"` presentation, still exercised in full by this spec's own tests. As of Phase 1.5 (#208, daily-cards-spec § "More menu") the LIVE app mounts only `variant="row"` instead—a plain menu row inside the More tab, replacing the fixed floating control (`App.tsx` no longer mounts the default variant). The trigger+sheet flow itself (capture, submission, retry) is identical in both variants; see specs/d15-more-menu.md § Contract for the relocation.

Because that relocation left the only launcher on `/more`, capture-at-open could only ever photograph the More menu (#324). The flow is therefore split: `BugReport` (either variant) is just the launcher, and `BugReportProvider`—mounted once at the app shell inside `.app` (`App.tsx`)—owns the sheet, the capture state, and a pick-a-screen step. From the sheet's capture-ready or capture-failed state, "Capture a different screen" parks the sheet behind a fixed bar above the tab bar; the reporter navigates to any tab (or opens another sheet—the bar sits above the generic sheet layer so that surface is itself capturable), then captures it or steps back (button or Escape). The description draft and any prior capture survive throughout—including across the launcher's own unmount when leaving `/more`—and re-tapping a launcher mid-pick recalls the parked sheet rather than discarding the draft. Submission reports the route the attached screenshot was captured on, not the submit-time pathname.

Opening the control captures only the rendered `.app` surface while excluding the reporting UI. If full-surface capture fails, the client retries with a compatibility pass that lowers pixel ratio and excludes embedded media surfaces that desktop Safari and stale canvases commonly cannot serialize, then falls back to a viewport-sized canvas renderer that avoids the SVG/foreignObject path used by the first two attempts. Every capture path solves its render scale against the server contract's PNG dimension caps (at most 8192 px per side and 40,000,000 total pixels, `functions/src/bugReportContract.cjs`) before rendering, so a long scrolled route downscales just enough to stay submittable instead of failing at the server, and the preview shows exactly the image that will be sent (#361). The fixed bottom tab bar is excluded from every capture path: html-to-image paints the whole scrollable surface into a `<foreignObject>` sized to the full box, where `position: fixed` no longer tracks the visible viewport, so an included bar would float mid-capture over the below-the-fold content and read as "not pinned to the bottom" even though it is correctly pinned in the live app (report `GwT3bmAqwu2eKeQF1uOf`). It is app-shell chrome rather than the report's subject, so it is dropped from the screenshot rather than the live bar being moved during a render—which would displace it on-screen mid-capture, notably in the pick-a-screen flow where the tab bar stays usable. The sheet explains which diagnostics are sent and previews the screenshot; the capture actions (retake/retry and capture a different screen) share a row when the sheet is wide enough and wrap back to stacked when narrow (#362). A capture failure never discards the description: the Player can retry capture or submit text only. A submission the server rejects surfaces the server's stated reason rather than generic connection copy (#361). Submission includes bounded description, current app-relative route, event id, deployed commit, user agent, viewport, online state, optional capture error, and optional PNG. It includes no email, token, console log, local-storage value, proof URL, browser chrome, or other application.

### One report flow has one submission identity

Opening a NEW report mints one `submissionId` with the browser's native `crypto.randomUUID()`. That id belongs to the whole draft lifecycle: parking the sheet to pick a screen, reopening it, and retrying after an error all reuse it. The first press of Send freezes the entire built `SubmitBugReportInput`, including the diagnostics and screenshot bytes, and every ambiguous/retryable failure resends that same value—the fields stay disabled rather than letting one id name two semantic reports. A server `invalid-argument` response is definitively pre-claim because validation runs first, so that one response may unfreeze the draft for correction; the next Send rebuilds the payload under the same still-unused id. Cancel discards the id and frozen payload, success clears both with the rest of the draft, and the next fresh open mints another. A retry may therefore recover a response that was lost after commit without filing a second inbox row or producing a second abuse-alert trigger. The id is opaque plumbing, never shown to the Player, and it is not durable across a page reload; `data-unsaved-work` continues to prevent the app's own update flow from destroying the in-memory draft. It is the coordination field the intake needs, not an authentication token.

`submissionId` is an OPTIONAL shared-contract field matching `^[A-Za-z0-9_-]{8,64}$`. Absent means a legacy client and preserves the current behavior exactly: an auto-ID report document, an auto-ID-derived screenshot path, and one rate-limit charge per invocation. An unknown or malformed PRESENT value is rejected rather than normalized or treated as absent. That asymmetry with `kind` is deliberate: dropping an unknown kind loses only an escalation, while dropping a supplied retry identity silently restores duplicate creation. The client includes the id in `SubmitBugReportInput`, and the callable persists it on idempotent reports; the exporter does not copy it into `report.json`, because it is intake coordination rather than operator evidence.

For a present id, the callable derives `reportId = SHA-256("bug-report-v1\\0" + uid + "\\0" + submissionId)` as 64 lowercase hexadecimal characters. The authenticated uid is part of the preimage, so one account cannot collide with or squat another account's chosen id; the raw uid is never stored. It separately derives a canonical `requestHash` over the server-normalized fields in fixed contract order plus the screenshot bytes' SHA-256 (or the literal no-screenshot sentinel). Reusing an id with any different description, classification, diagnostic, or screenshot fails with `failed-precondition`; the hash is compared before an existing or in-progress submission can be treated as success. A genuine new report always has a newly minted submission id, so two intentional reports still produce two ids and two inbox rows.

Validation happens before any dedupe, claim, or rate-limit decision, so an existing id cannot turn a malformed second payload into success. The callable then runs one Firestore transaction over `bugReports/{reportId}` and the reporter's rate-limit document. If the report is absent and capacity remains, the transaction charges one slot and `create`s a private PENDING report carrying only `submissionId`, `reporterHash`, `requestHash`, `intakeState: 'pending'`, `intakeStartedAt`, a native `crypto.randomUUID()` lease id, and `leaseExpiresAt = now + 60 seconds`. The transaction returns OWNER. If a matching COMPLETE report exists, it returns COMPLETE without changing the limit. If a matching PENDING report has a live lease, it returns FOLLOWER without changing the limit. If its lease expired, the transaction replaces only the lease fields and returns OWNER, so a retry can recover a crashed invocation. A mismatched or malformed coordination document fails closed. Firestore normally retries a create race through this transaction; if an SDK/emulator instead surfaces `ALREADY_EXISTS`, the shared classifier routes to the same verified readback rather than to cleanup or a second charge.

Only an OWNER performs the abuse-membership lookup or touches Storage. A FOLLOWER polls the report document every 100 ms for at most 5 seconds. COMPLETE returns the STORED receipt—its report id and stored escalation outcome, never an outcome recomputed from the retry payload. A still-PENDING report returns callable `unavailable`, so the client resends later; after the 60-second lease it can take ownership. On a known owner failure before finalization, intake best-effort expires the lease only when a transaction proves its lease id still owns the pending report, making the next retry immediate without disturbing a takeover. On an ambiguous Firestore result it reads back first and never releases ownership that may have committed.

The OWNER writes screenshot evidence create-only at `bug-reports/{uidHash}/{reportId}/screenshot.png`, with `requestHash` in object metadata. A takeover finding the object already present verifies that metadata and reuses the identical bytes instead of overwriting them. It then runs one final transaction that requires the same pending `submissionId`, reporter, request hash, and lease id; that transaction replaces the coordination-only shape with the normal immutable report fields, retains `submissionId` and `requestHash`, sets `intakeState: 'complete'`, and removes the lease. Claim, takeover, and finalize transactions may never rewrite `requestHash`; a mismatch aborts before any ownership or state change.

`notifyAbuseBugReport` remains `onDocumentWritten`, and its pure transition predicate becomes explicit about the staging write: PENDING and DELETING states never enqueue; exactly the transition from a matching PENDING document to `intakeState: 'complete'` with `kind: 'abuse'` may enqueue for an idempotent submission. A later update of a COMPLETE report cannot enqueue again. A legacy create with no `intakeState` retains today's absent-before/abuse-after behavior, so already-shipped clients still alert once. The finalization write's CloudEvent id remains the admin-alert queue's deterministic transition id. Tests cover pending create as a no-op, pending-to-complete as one alert, redelivery as the same queue id, later complete updates as no-ops, and the legacy create.

The exporter likewise skips only a structurally valid PENDING or DELETING coordination document; unknown states or malformed coordination fields remain pull failures rather than being hidden. A COMPLETE document validates and exports as a normal immutable report while omitting `submissionId`, `requestHash`, and `intakeState`. The transition to COMPLETE is therefore the one report creation visible to both downstream consumers for semantic purposes. Once complete, only retention may mutate/delete it.

This pending-document protocol makes every deterministic screenshot discoverable even if the owner crashes after upload: there is no Storage object without its `bugReports/{reportId}` coordination document. The operator owns cleanup through `npm run bugs:prune-pending`, added to `docs/app/bug-reports.md`'s monthly retention procedure. It uses the same existing deploy-mode `applicationDefault()` credential, explicit Firebase project, and private bucket as `bugs:pull`; it introduces no runtime function, schedule, credential, or deployment. Dry-run is the default and `--apply` is required to write. The command pages PENDING reports in 100-document, document-id-ordered batches, selects only a server-written `intakeStartedAt` at least 90 days old with an expired lease, and transactionally changes that exact `intakeStartedAt`/`requestHash`/lease tuple to `intakeState: 'deleting'`. A live takeover or completion therefore wins the compare-and-set and is reported as `skippedRace`. The cleaner reconstructs the deterministic screenshot path, deletes it with `ignoreNotFound`, then deletes only its own DELETING document; an interrupted cleanup is idempotently resumable. Its JSON summary reports `scanned`, `eligible`, `claimed`, `deleted`, `skippedRace`, and per-report `failed`, and any failure exits nonzero. Tests drive multiple pages, the 90-day edge, a takeover/finalization race, absent objects, resumed DELETING work, dry-run, and partial failure. Legacy auto-ID submissions retain their existing best-effort immediate screenshot cleanup because no other invocation can refer to their private id.

Firestore's `ALREADY_EXISTS` classifier is shared by bug-report intake, admin-alert enqueue, and direct-mark analytics rather than copied a third time. It recognizes the Admin SDK's numeric code `6`, canonical string forms, and emulator/message fallbacks; each caller still decides what an existing document MEANS at its own seam.

- **Given** a valid first submission and a sequential retry with the same id and payload **then** one COMPLETE report and at most one screenshot exist, the retry returns the first report's stored receipt, and only one rolling-limit slot was charged; **given** a different payload under that id **then** it fails before success/readback.
- **Given** two concurrent matching calls **then** one becomes OWNER, the other waits as FOLLOWER without repeating escalation or upload, and both return the same stored receipt when the owner completes; **given** interleaved calls with different payloads **then** the request-hash mismatch fails and cannot combine one call's metadata with another's evidence.
- **Given** an `ALREADY_EXISTS` result whose readback is missing, malformed, PENDING past the follower bound, or belongs to a different stored submission/reporter/request hash **then** the callable fails closed and never deletes deterministic evidence.
- **Given** an owner crash before completion **then** the pending document keeps the screenshot discoverable, a retry takes over after the lease (or immediately after a proven release), and the authenticated retention workflow removes a still-pending document and matching object at 90 days without racing a live takeover.
- **Given** no `submissionId` **then** validation, auto-ID allocation, per-invocation rate limiting, and best-effort screenshot cleanup remain the already-shipped behavior.

The authenticated `submitBugReport` callable is the only write path. It validates the schema and real PNG signature, rate-limits a uid to three reports per rolling 15-minute window, hashes the uid before storing report metadata, and writes screenshot evidence privately with no browser read path. When `BUG_REPORT_APP_CHECK` is enabled after #44, a missing App Check token fails closed.

An operator manually runs `npm run bugs:pull` to atomically materialize new immutable reports under the gitignored `.github/bug-reports/inbox/`. The exporter is idempotent across inbox and imported reports and removes partial output after a malformed report or failed download. Import dedupe is durable across fresh clones and deleted worktrees: `bugs:archive` appends each successful immutable issue receipt to the committed `.github/bug-reports/imported-ledger.jsonl` ledger before moving the report to `imported/`, and `bugs:pull` skips any report ID already recorded there even when the local gitignored `imported/` tree is absent. Ledgered report IDs are skipped before validating the current Firestore source fields, so a historical imported report cannot start failing pulls just because its immutable source document no longer matches the current exporter schema. The ledger stores only opaque report IDs, issue numbers/URLs, and import timestamps, never report descriptions, screenshots, reporter hashes, or other private evidence. Malformed, incomplete, or conflicting ledger rows fail closed instead of being ignored, so a corrupt durable record cannot silently re-open duplicate imports or suppress a report without a valid receipt. If a stale local `inbox/<id>/` directory exists for a ledgered report, `bugs:archive` may clean it up only when the requested issue matches the committed ledger receipt; a different issue target fails before moving anything. The LLM workflow requires confirmation before GitHub writes, distinguishes evidence from inference, deduplicates related reports, and archives each imported source with an issue receipt through `npm run bugs:archive`.

### Bug or abuse

The sheet asks what kind of report this is before it asks what happened: a radio pair, "Something is broken" (pre-selected) or "Abuse or harmful content" ([#670](https://github.com/nathanjohnpayne/gaycruisebingo/issues/670)). Choosing abuse reveals one line—"We'll try to raise this with the event's admins; either way your report is filed."—because that is the whole behavioral difference and it should not be a surprise. Deliberately an ATTEMPT rather than a promise: nothing has been checked at this point, and the server may decline (a stranger naming somebody else's Event, a member reporting against an archived one). The clause that is always true carries the reassurance instead. A radio pair rather than a checkbox because the two are alternatives rather than a flag on a bug, and because radios state the default visibly. Each label is a full 44 px target, like every other phone-first control here. Opening a NEW report resets the choice to bug; the draft-preserving park/reopen of the pick-a-screen flow does not.

**The sheet opens ON the choice**, rather than autofocusing the description field below it as it used to. Forward navigation never reaches a control that sits above the focused one, so a keyboard or screen-reader user could otherwise describe harmful content and submit it under the default `bug` classification without ever meeting the control that escalates it. It costs every reporter one Tab before typing—a real cost, paid by the common case—and it is worth it because the failure it removes is a report of harm being silently misclassified.

The focus trap treats the pair as ONE sequential tab stop, matching what a browser does: only the checked member is tabbable. Comparing the backward wrap against the first radio in DOM order stops matching the moment a later member is selected, and focus then leaves the modal entirely.

**The sheet states ELIGIBILITY, never delivery and never even that an alert exists.** The pre-submit line says the app will *try* to raise the report with this event's admins, and the callable returns `escalationEligible`—membership AND a live Event, both read at intake, since the trigger refuses to enqueue against an Event that is not `active` (`specs/admin-notification-emails.md`). So a member reporting against an archived Event is not told their report reached anyone.

The wording is load-bearing rather than cautious, and it took three attempts to get right. This callable RETURNS BEFORE the trigger that queues the alert has run, so it cannot honestly report that one exists—let alone that anyone saw it. Downstream there are three further gates: the trigger re-reads Event status for itself, a transient Firestore failure means a retry rather than an alert (yet), and the digest may resolve no admin recipient at all (an Event with no verified admin email and no `ADMIN_NOTIFY_EMAIL` override leaves the alert queued and unsent). Eligibility is the only thing knowable at the moment the reporter is looking at the screen, so it is the only thing claimed: the trigger owns whether an alert exists, and the digest owns whether anyone was told.

The confirmation therefore states only what was RECORDED—"Your report is marked for this event's admins", or that it was filed but is not marked—followed by an **unconditional** line: we cannot confirm when an admin will see it, and if someone may be in danger they should tell an event organizer directly. Unconditional is the point. Even the positive branch reflects only checks made before the alert is queued: the trigger can still decline or fail, and the digest may resolve no recipient. A receipt that sounds like escalation is already underway can steer somebody reporting harm away from a faster route, and that is the failure that actually matters here. Earlier drafts said an admin "has been alerted", then that the report "will be raised", then that we were "escalating" it—each asserting an outcome the trigger, the Event's status and the digest's recipient resolution had not determined. A response with no `escalationEligible` field at all—an older deployed callable—degrades to the second message, because "no claim made" must not read as a success.

The classification is frozen while a submit is in flight, and the receipt reports the kind that was SENT rather than the one currently selected. The sheet stays mounted across a slow submission, so a control that can still move would let the reporter switch to bug after pressing Send and watch the abuse outcome silently disappear.

The choice rides the payload as `kind` and is persisted on the report document. It is what the `notifyAbuseBugReport` trigger reads to decide whether an admin hears about it (`specs/admin-notification-emails.md` § "The fourth kind: `abuse-reported`"); a plain bug notifies nobody and waits in the inbox. `bugReports` is denied to clients in both directions, so the stored value cannot be forged or downgraded—the callable is the only writer.

**An abuse report only escalates for somebody who belongs to the Event it names.** `eventId` is client-supplied. That was harmless while it was a label on an inbox row, but an abuse report mails the named Event's admins, so the field became a delivery address—and nothing else in the flow would stop a signed-in player naming somebody else's Event and routing arbitrary text into its digest. The rate limit caps how much of that a single account can send and says nothing about where it goes. So intake resolves the question server-side (`reporterBelongsToEvent`): a player document under the Event, or the Event's own `admins` roster for an organizer who never dealt a board. The roster answers first and saves the player read when it does. An unreadable answer is RETRIED (`ESCALATION_LOOKUP_ATTEMPTS`) and then recorded as UNKNOWN, never as "no". Those are different facts and only one of them is an authorization decision: a backend failure that lands as `reporterInEvent: false` is indistinguishable from a confirmed non-member and unrecoverable, because nothing downstream can tell the question was never answered. So an unanswered lookup writes NO `reporterInEvent` at all and sets `escalationLookupFailed: true` instead. The trigger still fails closed (it requires a literal `true`), which is the right direction—failing open would make a Firestore outage a window for routing text into another Event's digest—but nothing false is recorded, and the export shows an operator which of the two happened.

The answer is persisted as `reporterInEvent` and written only on abuse reports, so its presence means "this was checked" rather than "this defaulted", and the trigger compares it strictly to `true`. It is resolved at intake rather than at the trigger because the trigger only ever sees `reporterHash`, a truncated SHA-256 that deliberately cannot be resolved back to a uid; the callable is the one point in the flow holding both facts at once. **It never rejects the submission**: a report filed from the sign-in or join screen, by somebody who has not joined yet, still lands in the inbox exactly as before. Only the escalation is declined.

**An absent or unknown `kind` validates as a plain bug rather than failing.** This is the one field the contract NORMALIZES instead of validating, and the asymmetry is deliberate. Every client already in the wild sends no `kind` at all, and an installed PWA can hold a stale precached bundle for weeks after a deploy (`specs/app-update-reload-prompt.md`), so rejecting the field's absence would break bug reporting for exactly the players most likely to have something to report. An unknown value degrades for the mirror-image reason: the value arrives from a client the server cannot force to upgrade, so a future Edition adding a third kind would otherwise start failing every submission against a server that has not been redeployed yet. The failure mode of rejecting is a lost report; the failure mode of normalizing is a report that lands in the inbox instead of the digest. The direction is safe because `abuse` is the only value that DOES anything—normalization can decline an escalation, never invent one.

The client restates the kind list in `src/data/bugReports.ts` rather than importing the server's, because `functions/` is a separately-rooted project whose modules pull `firebase-admin` and `resend` and importing across that boundary would drag the Functions tree into the browser bundle. Contract-parity tests on both sides are what keep the restatement honest: the client suite asserts that a payload this app builds validates on the server field-for-field and that the two kind lists match, and the functions suite asserts that the persisted `ValidBugReport` stays a superset of the shared `ValidClientReportFields`.

The exporter (`npm run bugs:pull`) carries `kind` into each report's `report.json`, so a report stored before this existed exports as `bug` rather than as a hole an importer has to interpret. It carries TWO more fields alongside it, because `kind` alone does not say whether the report escalated and escalation has two conditions. `reporterInEvent` answers "did the reporter belong to the Event they named?"—the trigger's gate input, necessary but NOT sufficient. `escalationEligible` answers "did this submission meet the conditions to be escalated?"—membership *and* a live Event, the same answer the reporter's receipt gave. `escalationLookupFailed` answers "could the question even be asked?", which is what keeps an infrastructure failure from reading as a decision about the reporter; when it is true, `reporterInEvent` is absent by construction and exports as `null`. Conflating the two is how an operator reads a suppressed report as delivered: an Event member reporting against an archived Event has `reporterInEvent: true` and was never eligible. Neither is a delivery claim, nor a claim that an alert exists, for the reasons above. A bug report exports `null` for both rather than `false`—nothing was checked, because there was nothing to escalate.

Both fail closed in BOTH directions on an abuse report: a wrong type is malformed, and so is an ABSENT one, because intake writes both booleans on every abuse submission. A missing value therefore means a half-migrated or hand-repaired record, and exporting it as `false` would make an unknown decision indistinguishable from an explicit negative. `null` cannot stand in for "unknown" here—it already means "not applicable". It also inverts intake's normalization for a value that is PRESENT but unrecognized, and fails closed on it like every other stored field it checks: normalizing down is right at intake, where the alternative is losing a report from a client that cannot be forced to upgrade, but a document reaching the exporter has already been through that normalizer—so an unrecognized value means a hand-repaired, half-migrated, or newer-producer record, and exporting it as `bug` would silently discard triage information. An ABSENT field stays the legacy default.
