# Cloud Vision moderation: auto-hide extreme/illegal Vision flags (#133)

The **consumer** half of Cloud Vision. `moderateProof` (the producer, [`w4-gate-vision-moderation.md`](w4-gate-vision-moderation.md) and #132) scans an uploaded Proof photo with SafeSearch and, for extreme/illegal media only, writes `{ status: 'flagged', visionFlag }` onto the Proof doc — or, when the scan beats the document into existence, parks the verdict where the trigger below picks it up (§ [The scanner never creates the Proof](#the-scanner-never-creates-the-proof)). Nothing acted on that flag: the shipped report-count auto-hide ([`w4-server-authoritative-hide.md`](w4-server-authoritative-hide.md), #43) is deliberately **active-only** and leaves a `'flagged'` doc alone, so an extreme Vision verdict surfaced to admins and was hidden by nobody. This spec records the path that closes it — a second server-authoritative writer that takes a Vision-flagged Proof to `status: 'hidden'` — plus the moderation-queue treatment that makes a Vision hide legible as one, the Restore semantics that keep it reversible, and the one other client write that had to stop undoing it (confirming a pending claim).

It completes reactive moderation's automated leg per [ADR 0004](../docs/adr/0004-reactive-moderation.md): automated flagging and hiding for illegal/extreme content only, never a posting gate and never a pre-moderation review queue. It is not authorization ([ADR 0001](../docs/adr/0001-honor-system-trust-model.md)) — hiding media touches no Mark, no stat, and no Board, and the honor system is unchanged.

## Why the report-count path could not simply be widened

`shouldHideAtThreshold`'s active-only gate exists so a stale report bump can never downgrade the stronger `'flagged'` state to a **plain** `'hidden'` — one that carries no reason, that the console renders identically to a community hide, and that an admin could Restore without ever learning the media had been Vision-flagged. Relaxing that gate to cover `'flagged'` docs would have produced exactly the outcome it was written to prevent.

So the fix is a second writer rather than a wider first one, and the split is the doc's own state:

| | `functions/src/autohide.ts` (#43) | `functions/src/visionHide.ts` (#133) |
|---|---|---|
| Owns | `'active'` docs | `'flagged'` docs, plus its own marker on the `'hidden'` ones |
| Reads | the Event's `settings.reportHideThreshold` | the Proof's own `visionFlag` |
| Applies to | Prompts and Proofs | Proofs |
| Lifted by | `Clear reports` (zero the counter) | `Restore` (there is no counter) |

Neither predicate can fire on a doc the other owns, so the two paths cannot contend for one write, and #43's decision path is untouched by this change: `autohide.ts` gains one additive `export` on its existing Firestore-handle factory (`adminFirestore`, shared so the second writer reaches Firestore exactly the way the first does) and no behavioural diff at all.

## The Vision hide

`hideProofOnVisionFlag`, an `onDocumentWritten` trigger over `events/{eventId}/proofs/{proofId}` in `functions/src/index.ts`, delegates to `applyVisionFlagHide` (`functions/src/visionHide.ts`). As with the threshold pair, the decision is a pure predicate and the Firestore surface is injected, so the whole flow is unit-testable without a Functions runtime. It inherits the module's global `us-central1` region and pins `ADMIN_SDK_SERVICE_ACCOUNT`, because the transactional re-read and the hide write are Firestore data-plane calls the project's default Gen2 compute identity cannot make.

### Extreme/illegal only, by allowlist

`AUTO_HIDE_VISION_FLAGS` is `['violence', 'extreme']` — exactly the two verdicts `moderateProof` emits for extreme/illegal media — and `isAutoHideVisionFlag` is a strict membership test. An **allowlist rather than a denylist** is the ADR 0004 guarantee rather than a style preference: the app is intentionally racy, and auto-hiding for raciness is the one outcome this feature must never produce. A denylist ("hide unless the verdict is `racy`") would auto-hide every flag a future producer learned to write the moment it appeared, with no change here. The allowlist fails the other way — an unrecognized verdict reaches admins as a `'flagged'` doc and is hidden by nobody.

### One state predicate, at both gates

`qualifiesForVisionHide(doc)` is true iff the doc is currently `'flagged'` **and** carries an allowlisted `visionFlag`. It is deliberately a **state** predicate where the report path's snapshot gate is a **transition** one (`shouldHideAtThreshold` needs "`reportCount` rose" to tell a fresh crossing from an admin restore that left the count over the bar). Here the status carries that distinction alone, so the same predicate serves the snapshot gate and the live write-time re-confirm, and three properties follow:

- **Loop guard.** The hide write makes the doc `'hidden'` and carries the `safetyHide` marker below, and no arm of `visionHideAction` claims that pair, so the re-fired `onDocumentWritten` no-ops. No infinite loop, and the same holds for the two marker-only arms: each writes the state its own predicate then rejects.
- **Admin Restore is preserved.** `restoreProof` (`src/data/admin.ts`) writes `status: 'active'` (or `'pending'`, when a claim on the Proof is still undecided), clears the `safetyHide` marker below, and leaves `visionFlag` in place. That doc is no longer `'flagged'`, so the hide arm never re-hides it; and its marker is an explicit `false` rather than an absence, so neither marker arm touches it either. The restore sticks. It is the same shape as the report path's restore, which survives because it leaves `reportCount` un-raised. A restored Proof is re-hidden only by a fresh scan (a re-upload re-flags it) or by an admin.
- **Retry-safe.** Because it reads state rather than a transition, any later write that leaves the doc `'flagged'` with an extreme verdict — a report bump, an admin `Clear reports` — re-attempts a hide an earlier swallowed best-effort failure never landed. A transition gate would have to see the verdict appear a second time, which nothing would ever do.

### The write is conditional on LIVE state, in a transaction

`applyVisionFlagHide` decides on the event snapshot and hands off to `hideVisionFlaggedIfQualifies`, which inside a Firestore transaction re-reads the Proof and applies whichever arm of `visionHideAction` its LIVE state still asks for (via `tx.update`, never a re-creating `set`) — the same guard `hideIfQualifies` gives the report path. So an admin who Restored or hand-Hid the Proof since the trigger fired is not silently reverted, a Proof deleted since the snapshot is never re-created, a verdict no longer in the allowlist writes nothing, and a marker that landed in the gap is not written twice.

It writes `status`, the `safetyHide` marker below, and **nothing else**. Leaving `visionFlag` on the doc is the point of the whole ticket: the result is `hidden` *with its reason attached*, which is what lets the console tell a Vision hide from a report-count one, and what `notify.ts` `deriveReason` already labels with the verdict rather than `(reports >= threshold)`.

### The `safetyHide` marker: the server's own record of the hide

The hide's transactional update carries a second field — `safetyHide: true` (`SAFETY_HIDE_MARKER`, `functions/src/visionHide.ts`) — beside the status, and that boolean, not the verdict, is what the one client write that could undo the hide reads.

The reason is deployment skew. `visionFlag` is a string whose meaning lives in `AUTO_HIDE_VISION_FLAGS`, and Functions and the PWA deploy separately: widen the allowlist here and, until every cached bundle catches up, a client holding the older list reads a newly hide-worthy verdict as safe and publishes a Proof this trigger deliberately hid. A mirrored allowlist plus a parity test cannot close that — a parity test compares two files in one revision, and the hazard is two revisions running at once. A boolean the server writes carries no such interpretation: a client that has never heard of the verdict still sees the hide.

The marker is tri-state, and the third state is the point. `true` means a safety hide stands. `false` means an admin lifted it through the warned console Restore, the one place an AI verdict may be overridden — written rather than deleted, for the same reason `visionFlag` survives the lift: the override is a fact worth keeping, and the row keeps its reason pill and its place in the queue. Absent means no safety hide has ever stood on this Proof, which is every Proof the trigger never touched — including one an admin hand-Hid, and one the #43 report threshold hid, each of which has its own console lift and neither of which the confirm path has ever withheld.

Both fields ride the same rules bound, so this needed no `firestore.rules` change: `safetyHide` is not in the create `hasOnly` list (so a create carrying it is denied outright), and a non-admin's update is bounded to `reportCount` alone (so it can be neither forged nor scrubbed). The rules comment records the marker; the pins are in `tests/rules/cloud-vision-moderation.test.ts`.

- **Given** the hide fires **then** `status: 'hidden'` and `safetyHide: true` are written in ONE `tx.update`, so there is no window in which the Proof is hidden without the server's record of why. (Tests: the "STAMPING the safety marker" and "NOTHING else" cases.)
- **Given** a non-admin **then** forging, flipping, or scrubbing `safetyHide` is DENIED on update — alone or smuggled onto a report bump — and a create carrying it in either direction is DENIED. (Tests: the `safetyHide` rules cases.)

`applyVisionFlagHide` is best-effort and never throws: a write failure is swallowed (`console.error`, return `false`) so the trigger never crashes the proof pipeline, mirroring `applyThresholdHide`, `moderateProof`, and the #101 notifier. The snapshot predicate runs before any Firestore access, so every write no arm claims — every report bump, every admin action on an unscreened Proof, and the trigger's own writes re-firing — costs one predicate and no read. Nothing here reads the Event doc at all. The Proof's own **create** is the single exception, and only since #1143: it consults the scanner hand-off for a verdict reached before the document existed (§ [The scanner never creates the Proof](#the-scanner-never-creates-the-proof)), which is one read on the write that already costs a document write.

### An admin Hide on a flagged row must not demote the hold

The console offers **Hide** on a `'flagged'` row, and correctly so: the row renders the moment `moderateProof` writes the verdict, and the trigger is neither instantaneous nor guaranteed — its write is best-effort, and a swallowed failure is retried only on the Proof's next write. An admin who clicks Hide there is agreeing with the AI screen, not overriding it.

A bare `status: 'hidden'` nonetheless loses the hold. It moves the doc out of the `'flagged'` state the hide arm looks for, so the trigger stands down and never stamps the marker, and `safetyHideStands` reads the result as a **plain** hide — so a later Confirm on the same Proof publishes the media the admin had just taken down, from the one control that is emphatically not the warned Restore. Both ends are closed, in the safe direction on each:

- **The client carries the hold forward.** `hideProof` (`src/data/admin.ts`) reads the live Proof inside a transaction — the row may have moved since it rendered — and writes `safetyHide: true` beside the status when `safetyHideStands` is already true of it. That is the **same predicate** `confirmClaim` gates on, so the console can never hide a Proof into a state its own confirm would then publish. It reads no verdict, for the deployment-skew reason above: a stale bundle can only ever under-stamp, never over-stamp. Where no hold stands, the write is byte-for-byte the one it always was, so an ordinary moderation hide stays liftable by `Restore` and publishable by a confirm.
- **The trigger backfills what the client missed.** `visionHideAction` gains a second arm: a `'hidden'` Proof carrying an allowlisted verdict and **no boolean** marker is stamped `safetyHide: true` in the same transactional re-read, writing the marker alone because it did not decide the status. Absent-or-non-boolean, never `false`, is the precision that matters — `false` is the warned Restore's explicit override, and re-stamping over it would let the server silently overrule the one decision ADR 0004 reserves for a human. So a Proof an admin Restored and then hand-Hid keeps its `false` and stays a plain hide.

The arms compose without looping: the hide arm's own output carries `true`, the backfill arm's output carries `true`, and neither state matches any arm on the re-fire.

- **Given** an admin Hides a Proof on which a safety hold stands — `'flagged'`, or already carrying the marker — **then** `hideProof` writes `status: 'hidden'` and `safetyHide: true` in one update, having read the Proof LIVE inside its transaction; **given** an ordinary hide with no hold **then** it writes `status: 'hidden'` alone. (Tests: the "hideProof — an admin Hide preserves a standing safety hold" cases in `src/data/cloud-vision-moderation.test.ts`.)
- **Given** a `'hidden'` Proof with an allowlisted verdict and no boolean marker **then** the trigger stamps `safetyHide: true` and nothing else, and the stamped doc is one the confirm-time gate holds; **given** the marker already `true` or `false`, a non-allowlisted verdict, or no verdict **then** it writes nothing. (Tests: the "backfill arm" cases in `tests/functions/cloud-vision-moderation.test.ts`.)

### A standing marker outranks an active status

Both client-side gates — `confirmClaim`'s refusal to publish, and Restore's marker-clearing lift — ship in the same PWA bundle, and a bundle is cached. An admin tab opened before this work landed still runs the old unconditional publish and the old marker-less restore, either of which writes `status: 'active'` and leaves `safetyHide: true` standing. The read rule exposes active Proofs to every Player, and the hide arm sees `'active'` rather than `'flagged'`, so it would stand down forever: extreme/illegal media back in the Feed, with no server-side path left to take it down.

So the enforcement is server-side as well. `visionHideAction`'s third arm covers `status === 'active' && safetyHide === true` and re-hides the Proof transactionally, writing `status: 'hidden'` and **keeping** the marker — the hold was never lifted, only ignored by a client too old to read it, so the record of it must survive.

The arm fires on the marker alone, with no verdict test, and that is safe precisely because a legitimate lift records itself: the warned Restore writes `safetyHide: false` in the **same update** as the status, so an override is never contested, and an active Proof still carrying `true` cannot have come from any current client. `'pending'` is deliberately excluded — it is admin-only readable, so a standing marker there exposes nothing, and it is where the claim-aware Restore parks an undecided Proof.

**Rollout.** For as long as a pre-change console bundle is cached, a Restore performed from it will be **reverted** within seconds by this arm, because that build clears no marker and the write is indistinguishable from a stale-client publish. The admin's recovery is to reload the console and Restore again: the current build writes the `false`, and the lift then sticks. That is the intended direction of failure — an override that has to be repeated once is a smaller harm than extreme/illegal media sitting in the Feed with no way back down — but it is a real transitional behaviour, and it is worth reloading admin tabs after the deploy rather than discovering it on a live moderation call. Proofs predating the deploy are unaffected: nothing but this trigger and the console ever writes the marker, so a Proof that has never carried one is never re-hidden.

- **Given** an `'active'` Proof whose `safetyHide` is still `true` **then** the trigger re-hides it transactionally, keeping the marker, whatever verdict it carries or lacks; **given** `safetyHide: false`, no marker at all, or a non-boolean value **then** it writes nothing; **given** a `'pending'` Proof carrying the marker **then** it writes nothing. (Tests: the "re-hide arm" cases in `tests/functions/cloud-vision-moderation.test.ts`.)

### It deploys independently of the producer

The trigger is exported **unconditionally**, unlike the `ENABLE_VISION_MODERATION`-gated `moderateProof`. With the producer off nothing ever writes a `visionFlag`, so the trigger short-circuits on every write; with it on, the consumer is already deployed and needs no second cutover. Gating it on the same flag would additionally mean a Proof flagged while Vision was enabled silently stops being auto-hidden the moment an operator turns the producer back off — the wrong direction to fail. The remaining #132 work (enable the Cloud Vision API, set `ENABLE_VISION_MODERATION=true`, deploy) is human provisioning that this half neither performs nor assumes.

- **Given** `moderateProof` wrote `{ status: 'flagged', visionFlag: 'violence' }` (or `'extreme'`) **when** the trigger runs **then** the Proof is flipped to `status: 'hidden'` with `visionFlag` intact and nothing else written. (Tests: `tests/functions/cloud-vision-moderation.test.ts`.)
- **Given** a verdict outside the allowlist — `racy`, `adult`, an unknown or mis-cased string, a non-string, or no verdict at all — **then** nothing is hidden, with no Firestore read. (Tests: the `isAutoHideVisionFlag` and short-circuit cases.)
- **Given** a `'pending'` or deleted Proof, a restored one (`'active'` with the marker cleared, or with no marker at all), or one this trigger already hid and marked **then** the path no-ops — so the loop guard holds, an admin Restore sticks, and a deleted Proof is never re-created. (Tests: the `qualifiesForVisionHide` and `hideVisionFlaggedIfQualifies` cases.)
- **Given** the live doc no longer qualifies at write time (an admin acted between the trigger and the write) **then** the transaction writes nothing and returns `false`. (Test: "re-confirms LIVE state".)
- **Given** the injected write throws **then** `applyVisionFlagHide` swallows it and resolves `false` — never rejects. (Test: "never throws".)
- **Given** #43's report path **then** it still refuses to hide a `'flagged'` doc, still hides a restored-then-re-reported `'active'` Proof, and the Vision path stands down for it — the two never contend. (Tests: the "composition with the #43 report-count auto-hide" cases.)

## The scanner never creates the Proof

`moderateProof` is a **Storage** trigger, and `attachProof` (`src/data/proofs.ts`) uploads the media *before* the transaction that writes the Proof document — it has to, because `firestore.rules` pins `storagePath`/`mediaURL` to the exact uploaded object, so a media Proof is unwritable until its media exists. The scan therefore runs on an object whose Proof may not have been created yet: the upload-before-document race the #101 notifier already accounts for on its own side (`onDocumentWritten`, so a Proof that arrives already `'flagged'` still alerts).

The producer used to close that gap by **merge-setting** the verdict, which creates the Proof when it is absent. That created document then broke the submission still on its way, differently for each kind of uploader and badly in both directions:

- **An ordinary Player's submission failed outright.** `attachProof` writes the Proof with an unconditional whole-document `tx.set` and never reads it first — correctly, because it is a create. The rules judge a write by whether the document exists, so against a scanner-created doc that same write is an **update**, where a non-admin is bounded to `hasOnly(['reportCount'])`. The write is denied, the whole transaction fails, and the Player is told their proof did not post — for a reason they cannot see or act on, and only when the media was extreme enough to flag.
- **An admin uploader's submission silently un-hid the media.** The `isAdmin(eventId)` arm allows that update, and the full `set` then overwrites `status`, `visionFlag` and `safetyHide` with `'active'`, `null` and absence. The result matches **no** arm of `visionHideAction`: not `'hide'` (not `'flagged'`), not `'rehide'` (no marker), not `'backfill'` (no verdict, not `'hidden'`). Extreme/illegal media sits in the Feed with every server-side path to take it down closed.

So the Proof document has exactly **one** creator, `attachProof`, and the producer records its verdict without ever writing a document that does not exist. `writeVisionVerdict` (`functions/src/visionHide.ts`) is one transaction with two arms, chosen on whether the Proof is there yet:

- **the Proof exists** — `tx.update` writes `{ status: 'flagged', visionFlag }`, exactly what the merge-set wrote. `update` rather than `set` is itself a small tightening: a Proof deleted between the upload and the scan is no longer resurrected as a two-field ghost, the same promise `hideVisionFlaggedIfQualifies` already makes.
- **the Proof is absent** — `tx.set` parks the verdict at `events/{eventId}/proofScans/{proofId}`, a **server-only** collection no client may touch in any verb, and the trigger applies it when the Proof appears.

**The transaction is what makes the hand-off airtight**, and it is the load-bearing claim of this section. A Firestore read-write transaction commits only if every document it read is unchanged, and that includes a document it read as **absent**. So if `attachProof` creates the Proof between this read and this commit, the scanner's transaction aborts, retries, re-reads, and takes the first arm instead. "A verdict is parked" therefore *implies* "the Proof did not exist at commit time", which implies its create is still to come — and that create is the write the trigger consults the record on. There is no interleaving in which a verdict is parked and nothing ever picks it up, and no second trigger is needed to cover one.

`hideProofOnVisionFlag` consults the hand-off on the Proof's own **create** and nowhere else (`awaitsPendingVisionScan`), which is why the cost model above survives: a create already costs a document write, and every other Proof write — every report bump, every admin action, every write this trigger makes itself — still costs one predicate and no read. The create is also the only write that *can* be the moment the Proof appeared. `applyPendingVisionScan` then writes the producer's own `{ status: 'flagged', visionFlag }` and **deletes the record in the same transaction**, so the hand-off is exactly-once and a redelivered trigger cannot re-flag a Proof an admin has since acted on. The hide itself happens on the re-fire, through the ordinary `visionHideAction` arms: flag, then hide, then mark. Nothing here hides in one write, so `visionHideAction` stays the single place a Proof's status moves.

It applies **whatever the producer flagged**, with no allowlist test of its own. The producer decides what is worth *flagging* and this module decides what is worth *hiding*; a race that quietly applied a second, laxer policy would be worse than the race. A verdict outside `AUTO_HIDE_VISION_FLAGS` reaches admins as a `'flagged'` doc and is hidden by nobody, exactly as a scan that had won the race would leave it.

Three residuals. A record whose Proof is never created — an upload that succeeded while `attachProof`'s transaction failed — is left where it is: it is invisible to every client, costs one small document, and can never be misapplied, because proof ids are auto-ids and the id will not recur. The Proof is briefly in the Feed between its create and the flag write, which is inherent to reactive moderation rather than new here (ADR 0004: the scan runs on the uploaded object, so every Vision hide is after the fact).

The third is a **weaker retry story than the hide arm's**, and it is the one to weigh. `applyVisionFlagHide` swallows a failing hand-off exactly as it swallows a failing hide, but the hide arm recovers on its own — its state predicate re-attempts on ANY later write that leaves the doc `'flagged'` — and the hand-off, gated on the create, has no second chance: a transaction that fails there leaves the verdict parked and the media public. The exposure is small (the Admin SDK already retries a contended transaction internally, and the Proof was written moments earlier by the same request), and closing it costs a read on every Proof write rather than only on creates, which is why it is not closed here. If the trade is ever worth reversing, `awaitsPendingVisionScan` is the single place to widen: drop the `before === undefined` test and the lookup runs on every verdict-less write, retry-safe and one read dearer.

- **Given** an existing Proof **when** the scan flags it **then** `writeVisionVerdict` updates it in place with `{ status: 'flagged', visionFlag }` and writes no hand-off record; **given** no Proof document **then** it creates NOTHING at the Proof path and parks `{ visionFlag, scannedAt }` instead. (Tests: the `writeVisionVerdict` cases in `tests/functions/cloud-vision-moderation.test.ts`.)
- **Given** a parked verdict **when** the Proof is created **then** the trigger writes `{ status: 'flagged', visionFlag }` onto it and deletes the record in the SAME transaction, and the re-fire hides and marks it through the ordinary arms; **given** no parked verdict **then** the create costs one read and writes nothing; **given** a parked verdict whose Proof is still missing **then** the record is kept for the create to come, and a malformed one is dropped rather than written. (Tests: the `applyPendingVisionScan` and end-to-end race cases.)
- **Given** any write that is not the Proof's create **then** no hand-off lookup is made at all; **given** a create that already carries a verdict **then** none either. (Tests: the `awaitsPendingVisionScan` cases.)
- **Given** a verdict outside the allowlist **then** the hand-off still applies it, and the Proof is flagged for admins and hidden by nobody — the producer/consumer split survives the race. (Test: the "applies whatever the PRODUCER flagged" case.)
- **Given** `attachProof` **then** its Proof write is still a whole-document `set` with no merge option, carrying exactly the create rule's allowlisted keys, `visionFlag: null`, no `safetyHide`, and no read of the Proof at all. (Tests: the "attachProof — the Proof write stays a plain CREATE" cases in `src/data/cloud-vision-moderation.test.ts`.)

## `firestore.rules`: a second server writer, no new client surface

Adding the writer required no change to the **Proofs** rules, and the rules half of this spec is the pin that says so. `status` and `visionFlag` were already server/admin-only on Proofs: a non-admin's sole `update` is `hasOnly(['reportCount']) && reportCount == resource.data.reportCount + 1`, and `create` requires `visionFlag == null` with `status in ['active','pending']`. So a client can neither self-hide, un-hide, forge an AI verdict, nor **scrub** the one an admin's Restore deliberately leaves behind. The `proofs` update rule gains a comment recording the second admin-SDK writer; the read rule (`isAdmin(eventId) || resource.data.status == 'active'`) already makes both `'flagged'` and `'hidden'` admin-only, so the Vision hide is authoritative for the player Feed rather than presentational — `useProofFeed`'s `where('status','==','active')` query is what a non-admin is permitted to run.

The one rules change is the **new collection** the section above introduces, and it grants nothing: `match /proofScans/{proofId} { allow read, write: if false; }` under the Event. The Admin SDK bypasses rules, so the two functions that use it are unaffected, and every client verb is denied — **including an admin's**. That is deliberate rather than an oversight. A readable record would leak a moderation verdict for a Proof the read rule above keeps admin-only, through a path with no `isAdmin` arm to bound it, and the console has no use for it: it reads the verdict off the Proof, where it lands moments later. A writable one would let a Player pre-empt their own scan with a harmless verdict, or delete the one their create is about to pick up. Nothing in `src/` knows the path exists.

- **Given** a non-admin (including the Proof's own uploader) **then** setting `status: 'hidden'` on a flagged Proof — alone or smuggled onto a report bump — is DENIED, un-hiding or demoting a Vision-hidden Proof is DENIED, and forging, changing, or clearing `visionFlag` is DENIED; **given** a create carrying `visionFlag`, `status: 'flagged'`, or `status: 'hidden'` **then** it is DENIED while the ordinary active create SUCCEEDS. (Tests: `tests/rules/cloud-vision-moderation.test.ts`.)
- **Given** any client — Player, uploader, or admin — **then** reading a `proofScans` record, listing the collection, creating, updating, or deleting one is DENIED; **given** the admin SDK **then** the park → flag → consume round trip SUCCEEDS; **given** a Player whose verdict is already parked **then** the ordinary Proof create still SUCCEEDS, because the record is on its own path. (Tests: the "scanner hand-off is server-to-server ONLY" cases.)
- **Given** a non-admin **then** the flagged and Vision-hidden Proofs are unreadable (single-doc gets), the Feed's `status == 'active'` query is ALLOWED and an unconstrained one DENIED; **given** an admin **then** every state reads, single-doc and unconstrained. (Tests: the read-gate cases.)
- **Given** an admin **then** Restore (`status: 'active'`) and a manual hide still SUCCEED, and a bare `reportCount + 1` from a non-admin still SUCCEEDS on a flagged or Vision-hidden Proof — #133 narrowed nothing. (Tests: the Restore and report-path cases.)

## The moderation queue: reason, distinct treatment, and a safe Restore

`useReportedProofs` (`src/hooks/useData.ts`) is the **only** admin surface for Proofs — there is no all-proofs list the way `useAllItems` lists every Prompt — so queue membership gains a `visionFlag` arm alongside reported / `'flagged'` / `'hidden'`. The Vision-hidden Proof already queued on the hidden arm; the arm this ticket adds matters one step later, when the admin's Restore writes `status: 'active'` with `reportCount` 0 and every older arm would drop the row out of the console, taking the AI verdict with it and leaving no way to re-hide it short of a community report. Membership on the verdict itself keeps every AI-screened Proof reachable for as long as that verdict stands, so the override is visible and reversible. It is a pure client-side filter over the queue's existing broad subscription — no second listener, no composite index.

`ProofQueueRow` (`src/components/admin/ReviewQueue.tsx`) renders the verdict as a **reason**, replacing the bare `visionFlag` enum echo: `AI screen: violence`, and `hidden · AI screen: violence` on the hidden-state pill when the Proof is currently hidden. That is deliberately **two facts the row already carries** — `hidden` from `status`, the verdict from `visionFlag` — and never an inference about cause, so a Proof an admin restored and the community later re-reported over the threshold reads truthfully instead of being labelled with whichever hide came first. The report-count treatment is untouched and stays visually distinct: its own `auto-hidden` pill, and its own lift (`Clear reports`, which zeroes the counter). A doubly-hidden Proof shows both pills and both affordances.

Restore keeps its exact label in every state — it is the same `restoreProof` write, and renaming it would change nothing but break the console's muscle memory — and gains a `title` saying what it is about to undo when an AI verdict stands: `Put this proof back in the Feed. The AI screen flagged it: violence.` That is the safe-restore contract in full: the admin is told what they are lifting, the write clears the `safetyHide` marker so the lift actually lifts, it leaves `visionFlag` as the audit record of the override, the row keeps its reason pill and its place in the queue afterwards, and the Vision path will not fight the decision because the Proof is no longer `'flagged'`.

- **Given** a Vision-hidden Proof **then** the queue row reads `hidden · AI screen: <verdict>` and offers Restore, whose title names the verdict; **given** a Proof still awaiting its hide, or one an admin restored **then** the row reads `AI screen: <verdict>` and offers Hide. (Tests: `src/components/admin/cloud-vision-moderation.test.tsx`.)
- **Given** a report-count auto-hidden Proof with no verdict **then** the row shows `auto-hidden` and `Clear reports` and NO AI pill; **given** one that is both **then** it shows both pills and both affordances. (Tests: the "keeps the report-count hide DISTINCT" and "shows BOTH mechanisms" cases.)
- **Given** a Proof carrying a non-auto-hide verdict such as `racy` **then** it is queued for review and shown with its reason, and is never marked hidden — nothing auto-hides for raciness. (Tests: the raciness cases in the component and hook suites.)
- **Given** a Vision-flagged Proof at any lifecycle stage — flagged, hidden, or restored — **then** `useReportedProofs` queues it, while an active, unreported, never-screened Proof is not queued and the three pre-existing arms are unchanged. (Tests: `src/hooks/cloud-vision-moderation.test.tsx`.)

### Restore returns the Proof to the state it came from

Restore is not always a publish. In admin_confirmed claim mode a Proof is created `'pending'` — admin-only readable — and stays there until confirming its claim publishes it, and Cloud Vision scans the uploaded object, so a photo whose claim nobody has judged can be flagged, hidden, and then Restored. An unconditional `status: 'active'` there would put it in every Player's Feed **before** the decision, and rejecting the claim afterwards would leave it public: `rejectClaim` deliberately writes nothing to the Proof (a rejected Proof is left `'pending'` rather than exposed), so nothing would ever take it back down.

So `restoreProof` restores to `'pending'` when a claim on the Proof is still undecided, and to `'active'` otherwise — including when the claim was confirmed or rejected, and when there is no claim at all. The photo goes back to the queue that was already going to decide it, where Confirm publishes it and Reject leaves it unpublished. Either way the same write clears the `safetyHide` marker, because the marker is what `confirmClaim` gates on: leaving it set would hold the Proof after the admin had explicitly overridden the verdict, and no second control could clear it.

Which claims reference the Proof is discovered **outside** the transaction, because claims carry auto-ids and the web SDK's `Transaction.get` takes a `DocumentReference`, never a query. The decision is still transactional: each candidate is re-read live inside the transaction, so a claim resolved between the lookup and the write reads as resolved. Nothing can appear in the gap — a Proof's claim is created in `attachProof`'s own transaction alongside the Proof itself, so an existing Proof never gains a new one. The admin arm of the `claims` read rule already permits the lookup; a non-admin is denied it, and denied the Proof either way.

That lookup asks for the **owner's** claims, not the Proof's. Only the owner's claim may steer a restore, and the read bound is applied to the query — so a `proofId`-only lookup would let any signed-in user decide what the query returns: enough forged pending claims naming someone else's Proof fill the bounded page, the owner's real claim falls off the end, and Restore publishes a photo whose claim nobody has judged. `restoreProof` therefore reads the Proof's `uid` first (a plain `getDoc`; `uid` is written once at create and immutable, and this read only *scopes* the query) and looks the claims up by `proofId` **and** `uid`, still bounded — now against the one case the query cannot exclude, a Player minting many claims against their own Proof. Two equality filters need no composite index: Firestore serves an equality-only conjunction by merging the single-field indexes it maintains by default, so `firestore.indexes.json` is untouched. The in-transaction re-read and owner check are unchanged, because the query reads a snapshot and only the live re-read can be trusted with the decision.

The row says so before the click rather than after. A hidden Proof with an undecided claim carries the line `A claim on this proof is still pending. Restore returns it for review, not to the Feed.`, and Restore's `title` names the destination alongside the verdict: `Put this proof back for claim review; it stays out of the Feed until the claim is confirmed. The AI screen flagged it: violence.` The destination is a fact about the claim, not about the AI screen, so a plain report-count hide over a pending claim gets both too. An ordinary Restore — no claim, no verdict — still carries no tooltip at all.

- **Given** a hidden Proof whose claim is still pending **then** `restoreProof` writes `status: 'pending'`; **given** no claim, or a confirmed or rejected one **then** it writes `status: 'active'`; **given** either **then** it clears `safetyHide` in the SAME write, reads every claim before writing, and never touches the claim itself. (Tests: the "restoreProof — claim-aware" cases in `src/data/cloud-vision-moderation.test.ts`.)
- **Given** a claim resolved between the lookup and the transaction **then** the live re-read sees it resolved and the Proof publishes. (Test: "decides on the LIVE claim".)
- **Given** an admin **then** the owner-scoped claims lookup and the restore-to-`'pending'` write both SUCCEED, a non-admin is DENIED the lookup, and the restored Proof is unreadable to them. (Tests: the "restores a claim-backed Proof to PENDING" case in `tests/rules/cloud-vision-moderation.test.ts`.)
- **Given** forged pending claims naming another Player's Proof — the claim-create rule binds `uid` to the caller, not `proofId` to the caller's Proof — **then** none of them steers the Restore, and 25 of them do not displace the owner's own claim from the bounded lookup, which carries both equality filters and the cap and is not run at all when the Proof is missing; **given** the owner's pending claim **then** it still steers the Restore, decided by the live in-transaction re-read. (Tests: the `restoreProof` cases in `src/data/cloud-vision-moderation.test.ts`; the admin/non-admin lookup pin in `tests/rules/cloud-vision-moderation.test.ts`.)
- **Given** a hidden Proof with an undecided claim **then** the row states the destination and Restore's title names it, with or without a verdict; **given** no such claim, or a Proof that is not hidden **then** neither appears. (Tests: the "claim review" cases in `src/components/admin/cloud-vision-moderation.test.tsx`.)

## Confirming a claim is not a Restore

Restore is the *only* lift, and one other client write had to be taught that. `confirmClaim` (`src/data/admin.ts`) publishes an admin_confirmed claim's Proof — created `'pending'`, admin-only readable — by writing `status: 'active'` when the admin confirms the Mark. Cloud Vision scans the uploaded object, so a photo is routinely flagged and hidden **before** its claim is ever reviewed, and an active Proof sits outside `qualifiesForVisionHide`: an unconditional publish would put extreme/illegal media back in front of every Player and the trigger would never hide it again. The lift would come from a control whose row states only the submitter and the Prompt — not the warned, explicit Restore above, which is the one place an admin may override an AI verdict having been told what they are lifting.

So the publish is conditional. Inside the same transaction that resolves the claim (the read placed before every write, per Firestore's reads-before-writes contract), `confirmClaim` re-reads the **live** Proof and skips the `status` write entirely when a safety hide stands on it. The claim still resolves, the Square still credits, the Mark is still confirmed; only the media stays hidden. There is no new write — the safety hide simply survives, and the admin lifts it where lifting belongs.

And the client is not the only thing enforcing it. A `'pending'`→`'active'` publish from a bundle cached before this gate shipped leaves the marker standing on an active Proof, which the trigger re-hides (§ [A standing marker outranks an active status](#a-standing-marker-outranks-an-active-status)). The gate below is what keeps the console honest; the arm above is what makes the hold hold.

`safetyHideStands` (`src/data/moderation.ts`) is that gate, and it reads only what the server writes: the `safetyHide` marker is `true`, **or** the Proof is still `'flagged'`. Two facts, no allowlist. The marker is the trigger's own record of the hide it made, so a client that has never heard of the verdict behind it still holds — the staggered-deploy hole a mirrored allowlist could not close, because a parity test compares two files in one revision and the hazard is two revisions running at once. The `'flagged'` arm covers the one state the marker has not landed on yet: the Proof the trigger is about to hide, or failed to hide and will retry on the next write, where publishing would move the doc out of the state the retry looks for. `'flagged'` is server-set too — `moderateProof` alone writes it, and the rules admit only `'active'`/`'pending'` at create and bound a non-admin's update to `reportCount`.

A `'hidden'` Proof carrying no marker is deliberately publishable, and that is the same rule as before stated on a firmer field: it was hidden by an admin's own Hide or by the report-count threshold, each of which has its own console lift (`Restore`, `Clear reports`) and neither of which confirm's behaviour has ever withheld. What changed is that the distinction is now the server's record rather than the client's reading of a verdict string.

`ReviewQueue`'s claims group says so on the row, so the admin is not surprised by a Confirm that does less than it used to: the pending-claim row gains the same `hidden · AI screen: <verdict>` pill the Proof row carries, plus `Confirming credits the mark; the photo stays hidden for moderation.` Row membership is the **same** `safetyHideStands` predicate the write gates on, so the row can never promise one thing and the write do another; the verdict rides along only as copy for the pill (a hold with no verdict reads `hidden · safety hold`). It reads both off the Reports group the console already renders — `useReportedProofs` queues every Vision-flagged Proof — so there is no second subscription and no per-claim read. No rules change: `status` is admin-writable on the `isAdmin(eventId)` arm either way, and this narrows a client write rather than widening one.

- **Given** an admin_confirmed claim whose Proof carries the `safetyHide` marker, or is still `'flagged'` **then** `confirmClaim` writes NOTHING to the Proof — the safety hide stands — while the claim resolves `confirmed`, the cell flips to `confirmed`, and the Square credits. (Tests: `src/data/cloud-vision-moderation.test.ts`.)
- **Given** a marked Proof whose verdict is one this build has never heard of **then** the hold survives anyway, because the gate reads no verdict; **given** an extreme verdict with NO marker **then** the confirm publishes, because an unmarked hide is not this path's to keep. (Tests: the unknown-verdict and no-marker cases.)
- **Given** a genuinely `'pending'` Proof with no verdict, one carrying a non-allowlisted verdict such as `racy`, or one an admin already Restored **then** the confirm publishes it `'active'` exactly as it always did. (Tests: the publish cases.)
- **Given** the Proof is read for the gate **then** the read is LIVE (inside the transaction) and precedes every write, and a reject or a legacy claim with no `proofId` reads no Proof at all. (Tests: the "reads the Proof LIVE and BEFORE any write" and no-read cases.)
- **Given** the trigger's write and the client's gate **then** they name the same marker field and agree on the doc the trigger produced, with no verdict list on the client to drift. (Tests: the "the confirm-time gate reads the SERVER marker" block in `tests/functions/cloud-vision-moderation.test.ts`.)
- **Given** a pending-claim row whose Proof carries a standing safety hide **then** it shows the pill and says the photo stays hidden; **given** any other claim — including one whose Proof is plainly hidden with no marker — **then** it is unannotated and Confirm behaves as before. (Tests: the "Pending claims" cases in `src/components/admin/cloud-vision-moderation.test.tsx`.)

## What this does not do

- **No posting gate, no pre-moderation queue** (PRD non-goals). The scan runs on the uploaded object, so the hide is always reactive: the Proof exists, the Mark stands, and only the media stops being readable.
- **No stat or Mark effect** (ADR 0001). Hiding is not authorization; `recomputeStats` is neither re-added nor repurposed.
- **No raciness hiding** (ADR 0004), and no Prompt-side Vision path — SafeSearch scans proof media, and Prompts carry no media.
- **No producer change.** `moderateProof`, its `ENABLE_VISION_MODERATION` gate, and its region pin are untouched; enabling the Cloud Vision API and flipping that flag remain #132's human provisioning.
