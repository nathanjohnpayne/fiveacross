# Community Prompt approval is server-authoritative: the `approvePrompts` callable

## Context

Approving a pending Community Prompt decides two things at once: which Day the Prompt is routed to, and the `approvedAt` instant the Day snapshot's cutoff filter later judges it against. Until #1275 both were computed in a client transaction on the approving Admin's device clock (`approveItems`, `src/data/admin.ts`), which was the #210 approval contract under ADR 0001's client-authoritative posture. A skewed Admin clock could therefore shift both the Day and the value the cutoff is judged against, and `serverTimestamp()` could not repair that client-side because its value is unreadable before the commit that routing has to decide (#813).

A second ordering shared the same root. `stampDaySnapshot` reads its `status == 'active'` item query inside its own transaction, but a row flipping `pending → active` was not a document that query matched, so a document-level conflict mechanism would let the scheduler commit a list computed before an approval that had just reported "scheduled for Day N". The failure was bounded (a misreported Day, never a mutated frozen Day) and documented as a residual in `specs/community-prompt-targeting.md`; the decision of 2026-09-23 was to remove it rather than keep accepting it.

## Decision

Approval of a pending player submission moves behind the `approvePrompts` callable (`functions/src/approvePrompts.ts`, onCall v2, us-central1, Admin SDK service account). In one Admin-SDK transaction it reads the Event and every requested row, verifies the caller is on the Event's `admins` roster, refuses a closed Event (#134), takes the server clock once per attempt after the reads, routes every row from that instant with the client's routing helpers materialized byte-for-byte into the Functions package (`communityPromptRouting.generated.ts`, from the one implementation in `src/data/communityPrompts.ts`, pinned current and held to the client's answers by the parity suite), keeps the #558 classification guards and the #1070 per-row `malformed` isolation as the one copy, and stamps `approvedBy` from the verified auth uid and `approvedAt`/`retainedAt` from the server instant, as epoch-ms so no reader changes. It returns the existing `ApprovalPlacement[]`. `src/data/admin.ts`'s `approveItems` becomes a thin `httpsCallable` wrapper with the same signature; the Approvals queue and `bulkApproveItems` are unchanged.

When any row is written, the same transaction bumps `approvalSeq` on the Event document. Firestore documents serializable isolation for transactions, which already rules the phantom ordering out; the fence is defense-in-depth, added because every mechanism the documentation describes is document-level and the emulator cannot confirm predicate protection. `stampDaySnapshot` reads and updates the same document, so the two transactions conflict at the document level in both concurrency modes and the loser re-runs against the state that won.

`firestore.rules` bound an Admin client's item status moves to `pending → rejected` and `active ↔ hidden`. `pending → active` is denied to every client, an Admin's stale bundle included, as are the two-step launderings through `hidden` or `rejected`. Rejection stays a client write. App Check on the callable follows the other callables' posture: an off-by-default `APPROVE_PROMPTS_APP_CHECK` param.

## Consequences

- Marks, Boards and Player stats remain client-authoritative under ADR 0001; this ADR moves only Community Prompt approval (routing, `approvedAt`/`retainedAt`, `approvedBy`) to the `approvePrompts` callable. It is the third server-authoritative exception, after the server-side hide (ADR 0004) and the adult-content posture (ADR 0012).
- Rules, functions and hosting are coupled: a client on the old bundle loses approval after the rules release until it reloads (`specs/app-update-reload-prompt.md`); rejection keeps working. `public/build-floor.json` is not bumped for an Admin-only change.
- The first deploy that creates the callable is two passes per project, functions-only first. On create, firebase-tools grants `allUsers` the Cloud Run invoker role, which the org's Domain Restricted Sharing policy rejects, so the functions step fails and the release chain stops before hosting; on update the invoker is left alone. Rollback is a full redeploy of the previous main, never rules or hosting alone.
- The callable is unreachable until the deploy's invoker reconciliation covers it. `unlockDayNow` answers an unauthenticated POST with an HTML 403 in both projects today for exactly this reason, so an admin-callables invoker family (`unlockdaynow`, `approveprompts`) is a prerequisite PR that merges first; the probe after every pass is a `401 UNAUTHENTICATED` JSON answer.
- The fence costs one Event write per approving call, the `deriveAdultContentOnEvent`, `settleAdminAlertsOnArchive` and `backfillHideOnThresholdDecrease` invocations it wakes, one `useEventDoc` listener read per connected client, and contention with every other Event-doc transaction, absorbed by the callable's 60-second timeout and the Admin SDK's retries and surfaced as `aborted` when persistent. A call in which every row is stale, missing or malformed writes nothing.
- The guarantee is scoped to approving pending player submissions. Named residuals for trusted Admins: `adminAddItem` creates organiser Prompts `active` with the device's `createdAt`, which the cutoff filter uses when `approvedAt` is absent; the admin create and update arms still admit `approvedAt`, `retainedAt` and `targetDayIndex` directly on status-neutral writes (pinned by a rules test); and a legacy row hidden while pending could be restored straight to `active`. No new row can reach that state once the rules ship, so it is closed by a one-time pre-deploy step: `npm run audit:pending-hidden -- <project>` (`scripts/audit-pending-hidden-items.mjs`) lists every `hidden` row with no `approvedAt` whose `createdBy` is neither the seed nor an Admin, exits nonzero while any remain, and `--requeue` moves them back to `pending`, where only the callable can activate them. A row an Admin rejected and then hid under the old rules carries `rejectItem`'s `approvedAt` and is invisible to that audit; restoring it takes a deliberate Admin action, and it stays a named residual.
- Declaring `invoker: 'private'` on the onCall would skip the invoker grant on create, but on update firebase-tools rewrites the binding from the explicit value, and that interaction with the reconciled invoker-IAM-disabled service is untested. It is a possible follow-up, only on proof; the two-pass deploy uses only paths this repo already exercises.
- `resnapshotDayIfNoBoards` computes its list outside its transaction; it is a pre-existing, documented recovery path and is unchanged.
- Bulk approvals are capped at 400 rows per call and are not chunked; a larger queue is refused whole rather than approved in part.

## Considered alternatives

- **A client `serverTimestamp()` stamp**—rejected: the value is unreadable before the commit routing has to decide, and changing only the stamp would change `approvedAt` from epoch-ms to a Timestamp under every numeric reader while routing stayed on the device clock.
- **A rules guard comparing `request.time` to the targeted Day**—rejected: it turns skew into a failed approval rather than a correct reroute, and leaves the phantom ordering open.
- **Citing serializability and writing no fence**—rejected in favour of writing both: the documentation covers the case, but its described mechanisms are document-level and no local layer can confirm predicate protection, so the correctness argument should not rest on an undescribed mechanism when a document-level conflict is cheap to add.
- **Moving rejection server-side too**—rejected: rejection carries no routing and no cutoff-relevant stamp, and moderation must keep working on a closed Event where the callable refuses.
